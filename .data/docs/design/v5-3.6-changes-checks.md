## Decisions made by this unit

- **D1 Checks run in step 6, with the validator,** after the claim test; report-only checks of milestone 5 stay in
  step 5. Reason: checks and validators are both declared refusals, so report-only checks see the same messages
  under both; checks still run after `limit` and before the validator (§1.4).
- **D2 One `xpcall` per game function** (`reference`, `fn`, validator), not one around everything: Lync's own code
  stays outside game-function protection, so a Lync fault is never reported as `validatorError`; cost +18–38 ns per
  function (§1.7). Throws and yields keep `validatorError`/`validatorYielded`, with the function named in the
  message (same trigger class, action and spacing).
- **D3 Every delivered message commits,** a failing `"deliver"` check included, so check state describes what game
  code received and `observed` under `"deliver"` reads real delivered traffic (§1.4).
- **D4 `policy` evidence** 1 drop, 2 deliver.
- **D5 Caller codes:** `fieldKind`, `checkPool`, `viewPlacement`, `telemetryTwice`, `seriesMissing`, `sealSettled`
  (§10); declaration `sealedInstance`; option-table codes are `v5.md` §7.1's set. Names provisional.
- **D6 Telemetry fields widened** (u32 `ms` and `key`, u16 `n`; 19 B atom header; memory recomputed to 14.8 KB per
  player, 1.48 MB per 100 players) (§8.2, §8.4, §8.10).
- **D7 Aim from a record** goes through the direction vector, so every aim codec shares one extraction (§8.2).
- **D8 One atom declaration per definition;** batches per (player, definition); one buffer copy per connection;
  streams anchored by `serverTime` and `ms` at the `read` call (§8.4, §8.5).
- **D9 Sealed details:** `blocks:EG0` of 8-byte blocks; `sealedInstance`; K_i over (d u32, i u64); S drawn at the
  first sealed send from an unseeded `Random` (documented entropy source); `fire` returns `Seal`; `sealSettled`;
  reveal before the seal's flush leaves after it in the same flush (§9).
- **D10 `hideLength` default true** (§9.7, design-first).
- **D11 `:input()` reinstated** against M4, for the lint's on-line record (§7.1).
- **D15 `maxRate`'s `burst` and `window` required** (§6.2, design-first), by the brief's "exactly" rule.
- **D12 Milestones:** markers and their hash in milestone 1, the claim requirement with validators in milestone 2,
  the lint in milestone 3 (as `v5-tooling.md` has it), the rest of `v5-checks.md` in milestone 7.
- **D13 `within` on `t.direction`** normalises r; the per-message maximum m is used as returned (NaN or negative
  fails) (§2.1, §2.2). `monotonic`'s `order` default is derived as the weaker rule (§3.5).
- **D14 `v5-extensions.md`** keeps `acked` and `inputs` with what is fixed and, per open value, what decides it; no
  draft 3.6 research covers them, and this unit invents no mechanism for them.

## Scope rule ("Lync does only what it can do exactly")

Applied now: every check bound is a required developer option (`maxDistance`, `tolerance`, `cap`, `seconds`,
`rate`, `burst`, `window`); `policy` has no default; no default comes from a network model. Defaults that remain,
each exact or a capacity setting rather than a judgement about a player: `order` "nondecreasing", `oneIn` 1,
`plane` "xyz", `resetChecks` `seconds` 0, the telemetry capacities (`ring`, `pending`, `telemetry.batch`,
`telemetry.seconds`), `sealed.outstanding` 1. For the audit to rule on when it lands: telemetry's `before` 0.5 s and
`after` 0.25 s (a capture window taken from VACnet, not a judgement of a player, but chosen by Lync), and the
`freeFormField` threshold of 65,536 codes (a build lint's boundary of "free-form"; its severity is the developer's
`[check]` setting).

replaced (§1.7). Checked with luau 0.740: the pipeline coroutine reaches its end when the game function yields in
its own thread, and doesn't under `xpcall`. Cost checked in the CLI: 101.5 ns per call through a reused runner
against 28.3 ns under `xpcall` (245.3 ns with a new thread per call). The validator's rule is the runtime unit's

## Open

1. **Counter for a check function's throw or yield.** Naming S-6 splits the codes by subject (`checkFunctionRaised`
   apart from `validatorRaised`, "so a filter on `validatorRaised` doesn't catch check functions"), but §8 splits the
   counter `validatorErrors` only by condition. `v5-checks.md` §1.7 and §10 count a check function's fault in
   `validatorsRaised` / `validatorsYielded` (the table read literally); S-6's reasoning would give
   `checkFunctionsRaised` / `checkFunctionsYielded` in `v5.md` §7.4. For the naming critic.
2. **`Stream` (telemetry) against `Lync.stream`.** The table keeps the type `Stream` (a copy of a telemetry ring,
   `v5-checks.md` §8.5, §8.6) and §8.5's "(c) for streams", written before `v5-collections.md` §15 made `stream` a
   definition kind. The two now share a word in one API. For the naming critic.
3. **Telemetry buffer and decode fields** not in the table: `ms` (a millisecond `os.clock()` reading; C5 allows
   seconds only, but the u32 entry needs ms resolution), `key`, `n`, `flags`, and `decode`'s `dt` (seconds, may be
   negative). Kept as written; C5 has no rule for a sub-second clock reading in a binary layout.
4. **Role markers in stream data.** `v5-checks.md` §7.1 and `v5.md` §3.3 allow `:claim()`/`:input()` only in `data`
   of client-sent events and requests and in server requests' `reply` (so a marker in `Lync.stream` data is
   `roleMarkerMisplaced`), while `v5-collections.md` §15.4 lists "the claim requirement" among what runs per index.
   Either markers are allowed in stream data (and §7.1's placement and the lint change) or §15.4's mention goes.
5. **Commit wording in `v5.md` §6.1 step 6.** It says "the checks' commit, for messages that will be delivered",
   while `v5.md` §3.5 and `v5-checks.md` §1.4 commit on every accepted message, handler or not. `v5.md` §6.1 is the
   runtime consistency unit's text.
6. **The server join hold's drop code.** `v5-checks.md` §9.5 names `joinHoldBytesExceeded` for a seal row the
   server's hold refuses; naming §5.1 maps cause 1 (the client's hold) to that code, and `v5.md` §5.3's server
   paragraph says only "reports `sendDropped`". Which code the server hold raises is the runtime unit's to state.

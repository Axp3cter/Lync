# Lync v5: design

Draft 1, 2026-10-15. Built on the research in `.data/docs/research/` (cited as `[brief §n]`) and the
experiments in `.data/docs/probes/`. Each decision states the problem, the options that were actually
viable, and the choice. Nothing here is implemented yet.

## 0. What v5 is

Typed buffer networking for Roblox, in Luau and roblox-ts:
- **One schema, two sides.** A schema written once in Luau declares every event, request and replicated
  collection.
- **A compiler** turns the schema into straight-line codecs and a typed API for each side, in Luau and `.d.ts`.
- **A runtime** batches everything into one frame per player per lane per tick.
- **The server owns the truth.** Every inbound byte is budgeted, decoded strictly, rate-limited and checked.
  Every anomaly becomes a typed signal the game decides what to do with.

The same schema also runs with no build step. That path has the same wire and the same API, is about 4x slower,
and gets exact types only under the new type solver.

## 1. Principles

When two of these conflict, the earlier one wins.

1. **Server authority.** Nothing a client sends is trusted. Security comes from what the server checks, never
   from what the client is assumed not to know.
2. **Correct before fast before small.** Byte savings that cost correctness or robustness are refused. Fast
   paths are measured.
3. **Exact types for everyone.** No payload, handler, reply or patch is ever `any`, on either type solver.
4. **One way to do each thing.** One naming convention, one error model, one shape for analogous features.
5. **Declarations in declarative formats, behaviour in Luau.** Build configuration is TOML, generated artefacts
   are JSON, and handlers and validators are Luau. The schema is Luau because the no-build path needs it as a
   live value.
6. **The library comes first.** Tooling and extensions are built on stable seams of a working runtime and
   compiler, never before them. The first v5 attempt shipped 19k lines of harness and no library
   `[v5-attempt §10]`.
7. **Every claim is measured.** Performance and size claims cite a probe; Roblox behaviour cites docs or a
   Studio measurement.

## 2. Architecture

```
schema module (Luau)
      │  evaluated by
      ▼
planner (pure Luau, one implementation) ──► IR: definitions, layouts, ids, limits, hash
      │                                         │
      ├─► runtime interpreter (no build)        ├─► codegen ──► client shard, server shard (Luau)
      │                                         │              .d.ts, manifest.json, report.json
      ▼                                         ▼
runtime: transport · scheduler · lanes · sessions · integrity · observers
```

- **One planner.** The planner is shared by the runtime, the CLI and the Studio plugin, so the generated path
  and the runtime path cannot disagree on a single bit `[client-security-build §1.1]`.
- **Packages:**
  - `lync`: runtime and planner. Wally, pesde and the Creator Store.
  - `lync` CLI: a Rust binary embedding Luau through `mlua`, installed with rokit. Lune is the prototype host.
    Lute 1.0 is not ready `[client-security-build §1.2]`.
  - Lync Studio plugin: embeds the planner and regenerates as you edit.
  - `@lync/core` on npm: roblox-ts declarations, plus an optional transformer.
- **Layers inside the runtime**, each depending only on the ones above it: `wire` (bit reader and writer,
  integer codes, quantizers) → `plan` (planner, IR) → `codec` (interpreter for the IR) → `transport`
  (remotes, lanes, frames) → `session` (handshake, acks, integrity) → `sched` (dirty tracking, budget,
  priority) → `api` (views).

## 3. Schema and API

### 3.1 Decision: how a schema is written

- **Problem.** The schema must be readable, give exact types, be evaluable at runtime with no build, and be
  readable by a compiler.
- **Options:**
  1. A separate IDL file, as Blink and Zap do. Concrete types and an easy compiler, but a second language,
     mandatory codegen, and the regenerate step is the top complaint about both `[landscape §1]`.
  2. Luau builder chains, as v4 does. Familiar, but modifiers mutated in some places and copied in others, and
     the types collapsed at records `[v4 §6, §8]`.
  3. **Luau declarative tables: definitions are option tables, records are plain tables, codecs are
     constructor calls.**
- **Choice: option 3.**
  - Records need no wrapper.
  - Every definition option has a name the type checker and autocomplete know.
  - The compiler reads the evaluated value rather than parsing source, so helper functions and loops in the
    schema just work.

### 3.2 Decision: where exact types come from

- **Problem.** Type functions infer exact types from schema values, but only under the new type solver. Roblox
  still checks `--!strict` scripts with the old solver unless `Workspace.UseNewLuauTypeSolver` is enabled, and
  luau-lsp defaults to the old solver too. On the old solver, type functions degrade silently to error types
  `[landscape §3.3]` `[probes/typing-and-codegen T7]`.
- **Options:**
  1. Type functions only: no build step, but silent `any` for most users.
  2. Generated code only: concrete types everywhere, but no runtime path.
  3. **Both, with generated code primary.**
- **Choice: option 3.**
  - Game code requires the generated shards, whose types are concrete and need no solver features.
  - The runtime path, `Lync.server(schema)` and `Lync.client(schema)`, is typed through type functions in a
    separate types module marked `--!nocheck`. New-solver users get exact types; old-solver users get no
    spurious errors.
  - The docs and the plugin state which path a project is on.
- **Consequence for syntax.** Schema syntax is designed for people, not bent around inference limits. Example:
  `t.enum({ "red", "blue" })` is exact in generated code, even though the runtime path widens it to `string`
  `[probes T3]`.

### 3.3 Codecs

Every codec is a constructor call returning a plain table, so `{ read _value: T }` inference holds
`[probes T1]`. Constructors take what they need and nothing optional changes the meaning. Accuracy is
`(min, max, step)` in the value's own unit. Values are exact unless declared otherwise.

| Codec | Luau type | Wire (bit section) |
|---|---|---|
| `t.bool()` | `boolean` | 1 bit |
| `t.int(min, max)` | `number` | ⌈log2(span)⌉ bits; refuses fractions and out-of-range |
| `t.int()` | `number` | zigzag + adaptive Exp-Golomb/Rice, any integer up to 2^53 |
| `t.number(min, max, step)` | `number` | fixed point, ⌈log2(span/step)⌉ bits; refuses out-of-range (no silent clamp) |
| `t.f32()`, `t.f64()` | `number` | 32 or 64 bits; NaN and ±inf refused unless `t.f64({ nonFinite = true })` |
| `t.angle(step)` | `number` (radians) | wrapped fixed point |
| `t.string(maxBytes)` | `string` | length code + bytes in the byte tail, or an intern id (§4.4) |
| `t.buffer(maxBytes)` | `buffer` | length code + bytes in the byte tail |
| `t.vector3(min, max, step)` | `Vector3` | 3 fixed-point components, column-coded with prediction (§4.3) |
| `t.vector3()` | `Vector3` | 3 × f32 |
| `t.direction(bits)` | `Vector3` (unit) | octahedral, `bits` per axis, 10–12 recommended `[compression §4.5]` |
| `t.rotation(bits)` | `CFrame` (rotation only) | smallest-three, 9 bits = 0.45° max error; axis-aligned shortcut |
| `t.cframe(position, rotation)` | `CFrame` | the two parts, bit-packed together |
| `t.color3()` | `Color3` | 3 × u8 |
| `t.enum({ "a", "b" })` | `"a" \| "b"` | ⌈log2(n)⌉ bits; wire index = declaration order |
| `t.enum(Enum.Material)` | `Enum.Material` | index into the pinned API dump's item list |
| `t.instance(className?)` | `Instance?` | index into the frame's instance array; `IsA` checked on both ends |
| `t.optional(codec)` | `T?` | presence bit |
| `t.array(codec, maxCount)` | `{ T }` | count code + elements, columnar |
| `t.map(key, value, maxCount)` | `{ [K]: V }` | count + sorted pairs; strictly ascending on read |
| `t.union({ name = record, ... })` | discriminated on `kind` | variant index bits + variant |
| `{ field = codec, ... }` | record | fields in declaration order, column-coded |
| `t.custom(spec)` | user `T` | extension point (§7.1) |

Rules:
- Every count and length has a declared maximum. The decoder checks it against the remaining bits before it
  allocates anything.
- Field order is declaration order, not sorted name order. Renaming a field changes the schema hash but not
  the layout.
- Codec methods are non-generic, which keeps type-function inference working `[probes T1]`. The only codec
  methods are the state-field markers in §3.6.
- There's no flags or bitfield codec. Boolean fields in a record already pack to 1 bit each, so
  `{ jump = t.bool(), crouch = t.bool() }` is the bitfield.

### 3.4 Definitions

```luau
-- ReplicatedStorage/Net/schema.luau
local Lync = require(ReplicatedStorage.Packages.Lync)
local t = Lync.types

return Lync.schema("arena", {
	chat = Lync.event({
		from = "client",
		data = t.string(200),
		rate = 5, -- per player per second, enforced on the server before decode
	}),
	strike = Lync.event({
		from = "client",
		lane = "unreliable",
		data = {
			target = t.int(1, 64),
			aim = t.direction(11),
		},
	}),
	announce = Lync.event({
		from = "server",
		data = t.union({
			round = { number = t.int(1, 99) },
			winner = { team = t.enum({ "red", "blue" }) },
		}),
	}),
	buy = Lync.request({
		from = "client",
		data = { item = t.enum({ "sword", "shield" }) },
		reply = t.int(0, 100_000),
		timeout = 10,
	}),
	fighters = Lync.collection({
		key = t.int(),
		data = {
			name = t.string(20),
			team = t.enum({ "red", "blue" }),
			health = t.int(0, 100),
			position = t.vector3(-2048, 2048, 1 / 32):newest(),
			look = t.rotation(9):newest(),
			title = t.optional(t.string(16)),
		},
	}),
})
```

**Shared options.** Every definition takes:
- `from`: `"client" | "server"`, required. It goes into the schema hash, so a message sent in the wrong
  direction or on the wrong lane is rejected with certainty at no cost `[client-security §3.6]`.
- `data`: the payload codec. Omit it for no payload.

**Per primitive:**

| Option | event | request | collection | Meaning |
|---|---|---|---|---|
| `lane` | `"reliable"` (default) \| `"unreliable"` | reliable only | managed (§5) | which remote carries it |
| `newest` | `boolean` | — | per field (§3.6) | only the latest value per recipient is kept and sent |
| `timestamped` | `boolean` | `boolean` | — | handlers receive the sender's tick and sub-tick offset (§5.6) |
| `rate` | number per second | number per second | — | server-enforced token bucket per player; burst = 2 × rate |
| `reply` | — | codec | — | the reply payload |
| `timeout` | — | seconds (default 10) | — | |
| `key` | — | — | codec | record key, sent once per record on add |
| `priority`, `rateHz` | — | — | numbers | scheduling (§5.3) |

### 3.5 Using it

Generated shards:
- `ReplicatedStorage/Net/client` (a client shard per namespace);
- `ServerScriptService/Net` (a server shard).

Game code requires the shard for its side. The runtime-path equivalents are `Lync.client(schema)` and
`Lync.server(schema)`. There's no `start()` and no `flush()`: the runtime starts on first use and sends at
the end of each frame (§5.1).

**Server:**

```luau
local Net = require(ServerScriptService.Net)

Net.chat:validate(function(player, text)
	return if string.find(text, "%S") then nil else "blank"
end)

Net.chat:connect(function(player, text)
	Net.announce:fire(Lync.all, { kind = "round", number = 3 })
end)

Net.buy:handle(function(player, request)
	return PRICES[request.item]
end)

Net.fighters:set(player.UserId, {
	name = player.Name,
	team = "red",
	health = 100,
	position = Vector3.zero,
	look = CFrame.identity,
})
Net.fighters:patch(player.UserId, { health = 90 })
Net.fighters:audience(player.UserId, redTeam) -- a Lync.group(); default audience is everyone
Net.fighters:remove(player.UserId)
```

**Client:**

```luau
local Net = require(ReplicatedStorage.Net.client)

Net.chat:fire("gg")

local result = Net.buy:invoke({ item = "sword" })
if result.ok then
	print(result.value)
end

Net.fighters.added:connect(function(id, fighter) end)
Net.fighters.changed:connect(function(id, fighter, previous) end)
Net.fighters.removed:connect(function(id) end)
local fighter = Net.fighters:get(id) -- a frozen snapshot, never the live table
```

**Verbs.** One per action, and the same everywhere:
- `fire` sends.
- `connect` listens.
- `invoke` asks.
- `handle` answers.
- `validate` is a server-only check.
- `set`, `patch`, `remove` and `audience` write a collection (server only).
- `get` and the `added`, `changed` and `removed` signals read a collection.

**Recipients.** Server-to-client `fire` takes one target: a `Player`, an array of players, a `Lync.group()`,
`Lync.all`, or `Lync.except(target)`. A target resolves when the frame is flushed, not when it's queued.

**Results.** Requests never throw. They return
`{ ok: true, value: R } | { ok: false, error: "timeout" | "rejected" | "unanswered" | "left" | "shutdown" }`.
A request the server rejects in validation is answered `rejected` straight away, rather than timing out
`[v4 §8]`.

**Handler arguments.** A server handler receives the player first, matching Roblox's `OnServerEvent`. A client
handler receives the payload. `timestamped` definitions add one trailing typed argument.

**Patches.** `patch` is generic over the literal, so a misspelled key or a wrong type is a compile error
`[probes T4]`.

**Type errors** name the side. Generated shards simply don't have the other side's methods, so calling a
client method on the server is "key `invoke` not found in `ServerRequest<...>`".

### 3.6 Collection field markers

These are methods on codecs that return the same codec type, so inference is unaffected:
- `:newest()`: the field is sent on the unreliable lane, newest value wins, and losses are repaired by the
  notify protocol (§5.2).
- `:priority(weight)` and `:rate(hz)`: scheduling (§5.3).
- `:owner()`: the record's owner gets this field at a higher priority.

Anything a marker does is declared in the schema, so the compiler sees it, the report lists it, and the hash
covers it.

### 3.7 roblox-ts

- The same schema written in TypeScript compiles through the transformer to the same IR, or a `.luau` schema
  compiles to `.d.ts`.
- Declarations follow the side split, use dot calls (`this: void`), `size()` and `entries()` adapters, and
  `LuaTuple` only where Roblox requires it `[v4 §2.3, §6]`.
- `.d.ts` and Luau shards come from the same IR, so they can't drift. v4 hand-wrote its `.d.ts` and nothing
  checked it against the Luau.
- Type tests run on both sides in CI.

### 3.8 Errors

- **Declaration mistakes** throw when the schema is evaluated, naming the definition path
  (`arena.fighters.data.position`). Under the compiler, the same message is a build error.
- **Caller mistakes** throw at the caller's line, found by walking `debug.info` to the first frame outside Lync
  `[v5-attempt §7]`. The message says what and where:
  `[Lync] arena.buy:invoke data.item must be one of "sword" | "shield", got "axe"`.
- **User callbacks** each run in a pooled thread, so their errors surface with native tracebacks and never
  break Lync's loop.
- **Bad input from other players** is never thrown or printed per message. It becomes a counted, typed
  observer event (§6.4).

## 4. Wire

### 4.1 Lanes and frames

- **Remotes.** Each namespace group uses one reliable `RemoteEvent` and one `UnreliableRemoteEvent`,
  created by the server. Each remote call carries exactly one buffer argument, plus an instance array when the
  frame references instances. Multiple top-level arguments cost a tag each `[landscape §2.1]`.
- **Sending.** Per player, per lane, per tick: one frame. The server sends `FireAllClients` when every
  recipient's frame is identical; otherwise it sends per player.
- **Frame layout:**

```
frame   := header section*
header  := tick:u16  [ack:u16 ackBits:u32 — upstream frames only]  [tag:u16 — upstream reliable, §6.2]
section := kind:u3 length:prefixVarint body   -- length-prefixed: a bad or unknown section is skipped,
                                                 not fatal to the frame
```

- **Section order on the reliable lane:** state adds and updates → events, requests and replies → state
  removes. Every event therefore sees the state it refers to `[state-sync §5]`.
- **Unreliable frames** are packed to at most 1000 B, a limit the docs say is checked after encoding
  `[compression §1]`. A single item that can't fit is demoted to the reliable lane with its sequence intact.
  Items whose worst-case size can exceed the limit are refused at build time.

### 4.2 Decision: how values become bits

- **Problem.** Roblox appears to zstd-compress buffers of roughly 100 B and up (undocumented). Bit-packing
  defeats zstd, but byte alignment wastes bits.
- **Options:**
  1. Byte-aligned layouts that lean on zstd. That was the landscape study's tentative pick.
  2. Plain dense bit-packing, as v4 and the attempt did.
  3. **A column coder: bit-packed, column by column, with residuals against a prediction, and an integer code
     and parameter chosen per column per frame.**
- **Choice: option 3.**
  - It came out 1.3–2.4x smaller than byte-aligned plus zstd in three of four traffic models, and tied in the
    fourth `[compression §2]`.
  - Its output doesn't compress further, so the unknown engine zstd level barely affects it.
  - One layout serves every frame size, with no switching at the threshold.
- **Hedge.** The layout is one module behind the IR, and the handshake carries a format version. The only result
  that could overturn this choice is the engine keeping compression context across frames. The Studio probe
  settles that (`probes/compression/studio/`), and current evidence says it doesn't.

### 4.3 Column coder

- **When it applies.** A section holding many rows of one definition gets column coding: a collection
  section, an array, or a run of the same event to one recipient. A single row (one event, one reply) uses
  plain fixed-width bits with no column headers. Column headers cost about 6–7 bits per column per frame,
  which only pays off over several rows. The planner sets the row-count crossover per definition from its
  field widths. A `bool` is always 1 bit in a single row, and a column of bools can use the zero mode.
- **Structure.** A frame's bit section holds columns: one per record field per section. Literal strings and
  user buffers go in a byte-aligned tail, which the engine can still compress.
- **Per column:**
  - a 2-bit mode: zero, Exp-Golomb with parameter k, sparse, or raw/frame-of-reference;
  - k in 4–5 bits, chosen per frame;
  - values coded as zigzagged residuals.
- **Prediction:**
  - motion fields use guarded linear prediction, which halves position bits compared with plain delta;
  - other fields are coded against the baseline (§5.2).
- **Decoding** uses a 12-bit lookup table for Exp-Golomb, at 35–58 ns per value interpreted
  `[compression §3, §8]`.
- **Not yet measured:** the encoder's search over k could double or triple the measured 0.45 ms per tick for 100
  players. The first benchmark measures it, and the fallback is a running-mean estimate of k.

### 4.4 Strings

- **Static vocabularies** in the schema (enums) become ids.
- **Dynamic strings** go through a per-connection, append-only intern table on the reliable lane. It holds at
  most 4096 entries and needs no eviction messages.
- **Formatted messages** can be declared as templates.
- Together these cut string bytes 6.5x on the tycoon model; zstd does nothing for per-frame strings
  `[compression §5]`.

### 4.5 Handshake

- **The client sends `HELLO`:**
  - the protocol version;
  - the layout format;
  - the schema hash (with each definition's direction and lane folded in);
  - a hash for each definition;
  - the build seed.
- **The server replies `WELCOME`:**
  - the session parameters: the per-server id permutation and the integrity key (§6.2);
  - on a mismatch, the names of the definitions that differ. Only hashes travel on the wire; the server looks
    the names up in its own schema `[v5-attempt §3]`.
- **Generated code that's out of date** makes both sides fall back to the runtime path together, rather than
  refusing the client `[client-security-build §2.4]`.
- **Joining.** Until `WELCOME` arrives, the client holds its reliable sends (up to a cap) and drops unreliable
  ones. A late joiner gets catch-up keyframes for every collection it can see.

## 5. Delivery and state

### 5.1 Ticks and flushing

- **Event and reply flushing.** Events and replies flush every frame at `RunService.PostSimulation`.
- **State ticks.** Replicated state runs on a separate state tick: `stateRate` 20 Hz by default, a divisor of 60.
- **Frame numbering.** Every frame carries a u16 tick.
- **Manual control.** There's no manual flush by default; a `Lync.scheduler` seam allows it (§7.4).

### 5.2 Replication models

Each case uses the model that won on the measured trade-off `[state-sync §1, Implications]`:

| What | Lane | Model |
|---|---|---|
| events, requests, replies | reliable (or declared unreliable) | in call order inside the events section; never budget-limited, but charged first |
| collection structure (add, remove, audience change) and exact fields | reliable | changes since the last send, encoded once per audience partition, no acks needed (reliable order guarantees the client's state matches) |
| `:newest()` fields | unreliable | absolute quantized values encoded once per tick; per-viewer dirty bits; losses repaired by an ack bitfield that re-dirties only what has not been superseded since ("notify", Tribes) |
| client inputs (`lane = "unreliable"` events from the client) | unreliable | every input since the last ack, delta-coded, capped at 32; a server jitter buffer of 2–5 ticks |

- **Acks.** Upstream frames carry the newest server tick the client applied, as a u16 tick plus a u32 bitfield
  (6 bytes). An idle client sends a 10 Hz heartbeat.
- **What the acks also give.** The same ack lets the server work out exactly what the client saw, which
  lag-compensated checks need (§7.3).
- **Deltas against acked baselines** are the cheapest on bytes but cost CPU and a history buffer per player.
  They're an opt-in extension for a single collection, not core.

### 5.3 Scheduling and budget

- **Budget.** `stateBudget`: 16,000 B/s per player by default, with a range of 4,000–64,000. It may burst to
  4x for up to 1 s on join or when a player gains sight of new records. Events and replies are charged first;
  state keeps a floor of 25%.
- **Priority.** Each record with unsent changes accumulates `priority × boosts` per tick and resets to zero when
  sent. Scheduling is a 40-bucket log2 pass, never a comparison sort: 3.5–7x cheaper, and it doesn't starve
  far-away records `[state-sync §3]`.
- **Over budget.** Lync defers. It never lowers precision at runtime. `maxPendingAge` (2 s) is a starvation
  floor.
- **Per-field rate caps.** `:rate(hz)` caps a field, rounded to a divisor of `stateRate`.

### 5.4 Audiences and relevance

- **Core.** Each record has an audience: everyone by default, or a `Lync.group()`. Groups are live sets of
  players; changes take effect at the next state tick, and newly visible records get catch-up keyframes.
- **Extension: `interest`** (§7.3).
  - Per-viewer relevance through cell subscriptions, with exact distance used only for priority.
  - Cells cost about 0.01 ms per pass, against 4–7 ms for exact membership at 200 players × 10k entities
    `[state-sync §7]`.
  - This is also the anti-ESP measure, following VALORANT's fog of war `[anticheat-design §1]`.

### 5.5 Requests

- **Ids.** u16 request ids in a ring.
- **Server side.** The server times requests out, cancels them when the player leaves, and caps in-flight
  requests per player (default 16).
- **Unsolicited replies** (to ids that were never issued) are dropped and become a suspicion signal.
- **Not used:** `RemoteFunction` and `InvokeClient`.

### 5.6 Time

- **Ticks, not timestamps.** Ticks replace wall-clock stamps. `timestamped` adds a 1-byte sub-tick offset.
- **Never trusted for rewind.** Client stamps aren't used to choose a rewind time; the server derives what the
  client saw from acks.
- **Client interpolation helper** (an extension):
  - delay is `max(2/rate, 0.1 s) + 2 × jitter`;
  - extrapolation is capped at 0.25 s.

## 6. Security

### 6.1 Inbound pipeline (server)

In this order, and nothing is decoded before it is paid for:

1. **Lane and size checks.** Each frame must arrive as exactly one buffer on a known lane.
2. **Per-player budgets.** Token buckets per player for frames per second and bytes per second, using
   `buffer.len` before any decode.
3. **Integrity.** Check the frame tag and, on the unreliable lane, the replay window (§6.2).
4. **Strict, canonical decode.** Section lengths, counts and ranges are checked before anything is allocated.
   Non-canonical encodings, NaN and infinities (unless declared) and unknown ids are refused.
5. **Definition checks:** direction, lane, then `rate` per definition, then schema constraints (§6.3).
6. **Validators.** Server `validate` functions run in protected calls. A validator that throws drops that
   message and is reported once per window.
7. **Delivery.** Handlers run in their own threads.

**Refusals.**
- A refused section is skipped by its length prefix; the rest of the frame still delivers.
- Every refusal is a typed observer event and, where appropriate, a suspicion signal.

### 6.2 Wire integrity (core)

These are ranked by value; all are on by default unless marked opt-in `[client-security §8]`.

| Measure | Cost | Catches | Limit |
|---|---|---|---|
| Direction and lane in the schema hash | 0 B | any message an honest client never sends | only senders of the impossible |
| 16-bit keyed tag (HalfSipHash) over the implicit reliable-frame counter + length + first 1024 B; per-session key in `WELCOME`; rekey on desync | 2 B per upstream reliable frame | raw senders, replays, injection below Lync's encoder, blocked calls (counter gaps) | defeated by calling Lync's own API, or by reading the key from memory |
| 12-bit sequence + tag + 64-frame replay window on the upstream unreliable lane | ~3.5 B per frame | replays of input frames | as above |
| Consistency checks (unknown request ids, impossible acks) | 0 B | fuzzers and hand-built frames | only those |
| Per-server permutation of definition ids | 0 B | public scripts that hard-code bytes | one shared memory scan, or any use of Lync's encoder |
| Trap definitions: server-only `:trap()`, plus generated client→server ids hidden from the typed API | 0 B | attackers who browse the schema and call Lync's API | does nothing until fired; careful attackers send only what honest code sends |
| Per-build field-order rotation (generated path, nonzero seed) | 0 B, 0 CPU (constants) | static byte tooling across releases | lasts one release |
| Clock-rate beacon (opt-in) | 2 B/s | clock-speed tools, forged stamps | narrow coverage |

Refused:
- client environment, hook and caller checks (they belong to a game's own anti-cheat);
- tags on server-to-client frames;
- XOR masking or whitening (+62% to +272% bytes after zstd, and it stops nothing);
- any automatic kick, ban or visible penalty `[client-security §8]`.

### 6.3 Constraints and claims in the schema

Definitions and fields can declare bounds that compile into per-player server checks, costing 27–49 ns each
natively `[anticheat-design §4.2]`:
- `maxRate`
- `within(radius, of)`
- `cooldown`
- `monotonic`
- `maxTotal`

Each declares its failure policy: `drop`, `clamp` or `signal`.

**Input, claim, outcome.** Client→server fields are typed by kind: `:input()` or `:claim(verifier)`. A claim
with no server verifier is a server-view error. Outcomes ("I hit X") can be declared only as claims. This is
deliberate friction toward intent-based protocols, not a semantic proof.

### 6.4 Signals

- **`Suspicion`.** A typed observer event with 14 reasons in three confidence tiers (certain, strong, weak).
  It carries evidence but no client bytes.
- **Aggregation.** Signals aggregate per player within limits, and each player gets a decaying score.
- **What Lync never does:** kick, ban, throttle or tell the client. It follows Roblox's September 2025
  guidance: never act on client-side detection alone `[client-security §6]`.
- **The game's response.** The game reads the score or the events and calls a quiet-mitigation hook if it wants
  one (`rejectClaims`, `inboundDelay`).

### 6.5 Where policy lives

Integrity and suspicion policy are set with one server-only call:

```luau
-- ServerScriptService, server only; never in shared code or lync.toml
Lync.integrity({
	tag = { bits = 16, cover = 1024 },
	replayWindow = 64,
	traps = 2,
	clockBeacon = false,
	suspicion = { decay = 300, tiers = { certain = 10, strong = 3, weak = 1 } },
})
```

Build-time options (seed, rotation, checks) live in `lync.toml` (§8.2). Validators and handlers are Luau on the
server.

## 7. Extensions

Extensions plug into fixed seams. A seam with nothing registered compiles out, so no branch is paid per message.

### 7.1 Codecs

`t.custom({ ... })` declares a leaf codec through the bit writer and reader. Its fields:
- `encode(w, value)` and `decode(r)`;
- `maxBits` (or `maxBytes` for tail data);
- a Luau type and a TypeScript type name, for codegen;
- an optional `predict` for the column coder.

Custom codecs are hashed by their declared name and version.

Transforms over existing codecs: `t.map(base, decode, encode)`, typed both ways. Example: `UDim` built from two
numbers.

### 7.2 Middleware

Per-definition and per-namespace hooks:
- `onSend(data, target) -> data?` (nil drops the message);
- `onReceive(player, data) -> data?`;
- observers at frame level.

Middleware runs on the server view by default. Client middleware exists for game logic, not security.

### 7.3 First-party extensions

These are opt-in and documented separately `[anticheat-design]` `[state-sync]` `[compression]`:

- **`interest`:** per-viewer relevance with cells, distance priority, look-ahead reveal, hold ticks, and field
  visibility classes (`owner`, `team`, `relevant`, `all`).
- **`rewind`:** lag-compensated hit verification over rewind rings, keyed by the client's perceived time
  derived from acks.
- **`decoys` and `canaries`:** per-viewer decoy records and canary fields that honest code never sees through
  the typed API.
- **`telemetry`:** schema-marked feature streams (`:aim()`, `:atom()`) exported in batches to the developer's
  own backend over HttpService.
- **`interpolation`:** a client-side interpolation buffer for `:newest()` fields.
- **`acked`:** deltas against acknowledged baselines for one collection.
- **`rans`:** trained rANS for a single field that dominates a game's traffic. It's worth at most about 10%,
  only where that is measured.

### 7.4 Runtime seams

- **`transport`:** remotes by default; an in-process transport for tests; anything Roblox ships later.
- **`scheduler`:** frame-driven by default, or manual.
- **`clock`.**
- **`roster`:** players.
- **`observer`:** a typed event stream of sends, receives, drops, suspicion and budget. The Studio inspector,
  the PacketProfiler adapter and metrics all read it.

### 7.5 Compiler plugins

Passes over the IR, declared in `lync.toml`. A plugin can add codecs, add sections, or emit extra files. The
`rans` extension and the `interest` codegen are compiler plugins.

## 8. Tooling

### 8.1 Compiler outputs

For a given schema, seed and planner version, the compiler always produces the same files:

| Output | Format | Consumer |
|---|---|---|
| client shard, server shard per namespace | Luau, readable, MIT header, source-mapped to schema lines | the game |
| type declarations | `.d.ts` | roblox-ts |
| `manifest.json` | JSON: definitions, hashes, ids, worst-case sizes, reachability | CI, server shard (facts compiled in) |
| `report.json` + rendered `report.md` | JSON + Markdown | developers, CI gates |
| `debugmap.json` | JSON, never shipped | Studio inspector, CLI (decode rotated traffic) |

### 8.2 `lync.toml`

TOML with a published JSON Schema, read the same way by the CLI, the plugin and the transformer
`[client-security-build §5]`:

```toml
#:schema https://lync.dev/schema/lync.toml.json
format = 1

[build]
seed = 0                # 0 = canonical build; "release" = a fresh seed per CI release

[[namespace]]
schema = "src/shared/Net/schema.luau"
client = "src/shared/Net/client"
server = "src/server/Net"

[rotate]
fields = true           # applies only when seed != 0

[check]
rawRemotes = "warn"     # client code touching RemoteEvents directly
unreliableSize = "error"
reachability = "report"

[output]
dts = "types/net.d.ts"
report = "build/lync-report.json"
```

Studio-only projects keep the same TOML text in a plugin-managed `StringValue` in ServerStorage.

### 8.3 Hosts

- **CLI:** `lync build`, `lync watch`, `lync check`, `lync diff <old> <new>` (flags breaking wire changes),
  `lync replay <capture>`.
- **Studio plugin:**
  - regenerates on schema edit, with a "Prepare release" action. No plugin can hook publish or save, since those
    APIs are RobloxScriptSecurity `[client-security-build §1.4]`;
  - schema diagnostics in the script editor;
  - the network inspector.
- **CI:** Open Cloud place publishing with `seed = "release"`.

### 8.4 Inspector and profiler

- **Studio inspector.** It reads the observer stream to show bytes per definition and per player per second,
  live frames decoded through `debugmap.json`, and budget, suspicion and drops. It can also capture and replay.
- **PacketProfiler adapter.** It registers Lync as a traffic layer, so frames show decoded in the community's
  inspector from day one `[landscape §5]`.
- **MicroProfiler labels** are opt-in.

### 8.5 Repo tooling

These are never shipped:
- StyLua and selene, with a Lync `std` YAML file that also lets games lint their own use of Lync;
- Moonwave for API reference;
- Markdown guides;
- GitHub Actions;
- Python for compression simulations and capture analysis.

## 9. Testing and benchmarks

- **Headless CI** runs on the CLI host:
  - unit and property tests (seeded, shrinking);
  - golden frames stored as `.bin` files plus a JSON index;
  - an in-process two-sided world over a simulated network with loss, delay, duplication and reorder;
  - type tests that check consumer code under both solvers, for Luau and TypeScript.
- **In-engine tests** run in Studio or through Open Cloud Luau execution (to verify). They're for what only
  Roblox can show: remotes, budgets and compression.
- **Benchmarks:**
  - random-per-frame traffic from the four game models;
  - CPU interpreted (client) and native (server);
  - bytes before and after an engine-compression estimate;
  - results stored per commit as JSON;
  - a public comparison against Blink, Zap and ByteNet on the community's benchmark, which v5 has to win
    `[landscape §1.7]`.

## 10. Milestones

Each milestone ships something usable:

1. **Wire and codecs.**
   - Covers the bit writer and reader, integer codes, quantizers, the column coder, the planner and IR, and the
     runtime interpreter.
   - Proven by golden frames, property round-trips and the column coder benchmark (including the k search).
2. **Events and requests, runtime path.**
   - Covers transport, frames, handshake, the inbound pipeline (budgets, strict decode, rate, validate), results
     and errors.
   - Proven by the two-sided simulated world.
3. **Compiler.** Codegen of the shards and `.d.ts`, the CLI (`build`, `watch`, `check`), and type tests on both
   solvers.
4. **Collections.** Reliable structure, notify for `:newest()`, the scheduler and budget, audiences and catch-up.
5. **Integrity core.** Tags, replay window, traps, permutation, `Suspicion`, constraints and claims.
6. **Tooling.** The Studio plugin and inspector, the PacketProfiler adapter, report, manifest and debug map.
7. **Extensions:** interest, rewind, interpolation, telemetry, decoys, then acked and rans.

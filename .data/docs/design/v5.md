## 0. What v5 is

Typed buffer networking for Roblox, in Luau and roblox-ts:
- **One schema, two sides.** A schema written once in Luau declares every event, request and replicated
  collection.
- **A compiler** turns it into straight-line codecs and a typed API per side, in Luau and `.d.ts`.
- **A runtime** batches everything into at most one frame per player per lane per flush, over one remote pair.
- **The server owns the truth.** Every inbound byte is budgeted, decoded strictly, rate-limited and checked.
- **The client is defended too.** Client-side integrity measures make tampering cost work that has to be redone per
  build, per server or per session, and report what they observe to the server.
- **Lync reports facts, never verdicts.** What it observed reaches game code as typed facts with exact triggers
  and numeric evidence; what to do about them is the game's code.

The same schema also runs with no build step: the same API and wire format, with layouts varied per server (§3.2),
and exact types only under the new type solver. Its interpreter, as milestone 1 built it, encodes a row 1.7–1.9x
slower than a generated encoder on the same bit writer and 3.2–3.9x slower than the generated inline form
interpreted (4.5x to decode a 3-field row), and 2.4–2.9x slower native `[generation-methods M14]`
(`probes/generation-methods/runtime_path.out`).

## 1. Principles

When two conflict, the earlier one wins.

1. **Server authority.** Nothing a client sends is trusted. Client-side measures raise the cost of tampering and
   report what they observe; they never replace a server check.
2. **Correct before fast before small.** Byte savings that cost correctness are refused. Fast paths are measured.
   For a security measure, runtime, wire and size cost is a trade-off, never a veto: each measure states what it
   protects and what it costs, and is adopted when the protection is worth the cost. Where the cost matters, an
   option with a stated range and cost controls it, rather than the measure being left out.
3. **Exact types on both Luau solvers and roblox-ts.** No payload, handler, reply or patch is `any`. Generated
   shards meet this on both solvers; the no-build path under the new solver only (§3.2).
4. **One way to do each thing.** One naming convention, one error model, one shape for analogous features.
5. **Precise, never simplified.** No presets, tiers or labels in place of definitions. Every option has a name,
   type, unit, range, default and cost; every fact has an exact trigger and its known causes on an unmodified
   client.
6. **Declarative formats for declarations, Luau for behaviour.** Build configuration is TOML, generated artefacts
   are JSON, and handlers, validators and runtime settings are Luau. The schema is Luau because the no-build path
   needs it as a live value.
7. **The library comes first.** Tooling and extensions build on stable seams of a working runtime and compiler.
8. **Every claim is measured or marked unverified.** Roblox-only claims are listed in §10 until measured.

**Unmodified client:** a client running this build's Lync runtime and shard as published, whose game code reaches
Lync only through its API. The design uses this term wherever it describes what a client can produce; it never
classifies players. A client that is not unmodified is a *modified client*; the term names the code it runs, not
the person.

## 2. Architecture

```
schema module (Luau) ──evaluated by──► planner (pure Luau) ──► IR: definitions, layouts, ids, limits, hash
                                          │                       │
                                          ├─► runtime interpreter ├─► codegen ──► shards (Luau), .d.ts, manifest.json
                                          ▼
runtime: wire · plan · codec · transport · session · sched · api
```

- **One planner**, shared by the runtime, the CLI and the Studio plugin, so the two paths cannot disagree on a bit
  `[client-security-build §1.1]`. The planner takes per-record layout seeds as input: the build draws them from
  its `rotationSeed`, the runtime path from its per-server layout seed (§3.2). A differential test encodes random
  values through both paths and compares bytes, at seed 0 and at fixed nonzero seeds with field order, code
  offsets (first rows coded against 0, §4.3) and `layout` 1 (§4.5) on, passed through that same input; it also
  checks that each woven site's bytes decode to the value the generic encoder would send
  `[generation-methods M14, M16]` `[codecs-in-scripts §4.3, §7.3]`.
- **Decision: the interpreter's form.**
  - **Problem.** The runtime path's interpreter (`Rows.write`/`Rows.read` over the IR) is 3.2–3.9x the generated
    inline form to encode, interpreted; a faster form is a second code path the differential test must also cover.
  - **Options:** the interpreter as built; a closure tree built from the IR (1.3x a generated encoder on the same
    writer for rows with strings, optionals or arrays); closures with bit positions fixed at plan time for
    fixed-width rows (1.45–1.72x the inline form to encode interpreted), at 0.9–2.0 µs and 1.5–2.9 KB more set-up
    per definition per layout `[generation-methods M14]`.
  - **Choice: the interpreter as built.** Derived from `runtime_path.out` on a 3-field row at the busy traffic
    model's 70 upstream messages a second (§4.1): the fixed-position closures would save a client
    (742 − 333) × 70 = 29 µs/s of encode, plus its downstream decode; on a runtime-path server they would save
    100 × 70 × (831 − 369) ns = 3.2 ms/s of upstream decode interpreted, or 1.2 ms/s native, at 100 players. Against
    that stands a second encoder and decoder form per codec kind, under the differential test. A game for which that
    CPU matters runs the generated path, whose inline form is 1.45–1.72x faster than the fixed-position closures to
    encode.
- **Packages:** `lync` (runtime and planner; Wally, pesde, Creator Store); the `lync` CLI (the compiler core under
  a Rust/mlua host, with Lune as the fallback and first host); the Studio plugin; `@lync/core` on npm.
- **Runtime layers**, each depending only on earlier ones: `wire` (bit I/O, integer codes, quantizers, column
  coder) → `plan` → `codec` → `transport` (remotes, frames) → `session` (handshake, tag, acks, requests) →
  `sched` (flushing, ticks, budgets) → `api` (views).

## 3. Schema and API

### 3.1 Decision: how a schema is written

- **Problem.** The schema must be readable, give exact types, run with no build, and be readable by a compiler.
- **Options:** a separate IDL (Blink, Zap: a second language and a mandatory regenerate step, the top complaint
  `[landscape §1]`); builder chains (v4: modifiers mutated or copied, types collapsed at records `[v4 §6, §8]`);
  **declarative Luau tables: definitions are option tables, records plain tables, codecs constructor calls.**
- **Choice: declarative tables.** Records need no wrapper, and the compiler reads the evaluated value, so helper
  functions and loops in the schema work. The planner checks option names: an unknown key throws
  `definitionOptionUnknown` with the definition's line. The type checker sees only `from` exactly
  (`D & { from: "client" | "server" }`); other option literals widen `[probes review-1 r1, r2, r5]`.
- **Order comes from names.** Dictionary iteration order is unspecified (`probes/design-2/field_order.out`) and
  the planner sees only the value, so record fields and union variants are ordered by name (bytewise). Lists
  (`t.enum({ ... })`) keep list order. Rotation (§3.2) permutes record field order only; union variants and enum
  items keep their order and vary only by code offsets, since permuting the indices of a sequential 32-item column
  costs 137 → 331 bits and an offset at most its first row's residual (§4.3) `[generation-methods M3]`
  (`v5-integrity.md` §2).

### 3.2 Decision: where exact types come from

- **Problem.** Type functions infer exact types only under the new solver; Roblox and luau-lsp default to the old
  one, where type functions degrade silently to error types `[landscape §3.3]` `[probes T7]`.
- **Options:** type functions only (silent error types for most users); generated code only (no runtime path);
  **both, with generated code primary.**
- **Choice: both.**
  - **Generated path.** Game code requires the shard for its side; the shard is the API, with concrete types that
    narrow on both solvers `[probes review-1 r4]`.
  - **Runtime path.** `Lync.server(schema)` / `Lync.client(schema)`, typed by type functions in a `--!nocheck`
    types module. Exact under the new solver `[probes review-1 pipe/]`, except list-form enums (widen to
    `string`, `[probes T3]`) and Roblox enums (`Codec<unknown>`, `[probes review-2 t2]`).
  - **Type functions never call `error()`** on input derived from user values: an `error()` there crashes
    luau-analyze and luau-lsp through the side-selecting view `[probes review-2 crash_r1lib]`. They return a marker
    type that names the problem, such as `"[Lync] expected a codec at chat.data"` `[probes review-2 crash_fix]`.
  - **What the build proved about these types** (`f1fbfd7:src/types.luau`, `f1fbfd7:test/types/`; luau-analyze
    0.740 and luau-lsp 1.70.1):
    - `from` is typed `{ read from: "client" | "server" }` in `D & { read from: … }`. The new solver keeps the
      literal; the old solver drops `read` fields there, sees `D & {}` and accepts the literal instead of widening it
      to `string`.
    - Sides are picked with the built-in `index<{ client: …, server: … }, From>`, not a type function. A
      type-function selector given side tables that hold error types (an unknown `Vector3`, say) crashed
      luau-analyze (exit 139) at the first method call through a view.
    - The codec brand is `read ["[Lync] value"]: T` (§3.3); with `_value`, a record field named `_value` was taken
      for a codec.
    - The old solver rejects type functions and `read` fields, so the types module is `--!nocheck` and
      `--!nolint UnknownGlobal`. It also can't check exhaustiveness with a `local unhandled: never` closure, so
      every kind dispatch is covered by a test that runs each codec kind through it.
  - **No `read` modifier in any type game code sees.** Shards and every type Lync exports for game code (facts,
    results, field handles, telemetry batches, challenge handles) are plain records. Under the old solver a `read`
    field is an error in a checked module ("read keyword is illegal here") and is dropped when the type is imported
    from a `--!nocheck` module, so reading it fails with "Key not found" (luau-analyze 0.740,
    `probes/design-3.6/typing.out`, `read_modifier`, `read_consumer`). Values Lync hands out are immutable by
    `table.freeze` where the text says frozen, not by their type. The `D & { read from: … }` trick and the codec
    brand above stay: both live in the `--!nocheck` types module behind the runtime path, which is exact only under
    the new solver anyway, and the `from` trick relies on the old solver dropping the field.
  - **No overloads selected by a literal.** An intersection of function types selects its overload from a
    string-literal argument on both solvers, with two limits under the new solver (luau-analyze 0.740):
    - the selection fails when another argument is a table literal holding a string literal or an unannotated
      function, even when the call is correct (`probes/design-3.6/typing.out`, `overloads_options`);
    - an intersection whose overloads return different types burns the normalizer's fuel
      (`LuauNormalizerInitialFuel` = 3000, `Normalize.cpp:21`) at up to 2^N for N overloads, and past it the
      analyzer reports "Code is too complex to typecheck!" at the type: 9 overloads of one handle shape, 10 of the
      runtime path's type-function form; each 10x of fuel buys about 3.3 overloads, and no CLI flag sets it
      (`probes/field-typing/RESULTS.md` §1, `run.out`).

    So no signature Lync generates or types is an overload set chosen by a literal; field handles are read from a
    table (§3.4).
  - **What the runtime path's types cover on the old solver.** The old solver doesn't run type functions, so on
    the runtime path every type a type function computes is the error type there: payloads, handlers and field
    handles alike, with nothing reported in the game's script (`field-typing` §3, `b_consumer_128`). That is the
    runtime path's stated limit (principle 3); the generated path is exact on both.
  - **Degradation is stated where it can be detected.** `lync check` reports `runtimePathCallFound` at each call
    site of `Lync.server(` or `Lync.client(` in the scripts it scans, unless `lync.toml` sets
    `check.runtimePathCallFound = "off"`;
    the property itself is `NotScriptable`, so no tool can read it `[review-2 M11]`.
- **What both paths share on the wire.** One frame format and one planner. Layouts differ by what the planner is
  given:
  - **Generated path:** a build's private 64-bit `rotationSeed` (manifest only) draws per-record field order, code
    offsets and the tag's constants; the shard carries the public 32-bit `buildId` in its place
    (`v5-integrity.md` §2) `[generation-methods M1]`.
  - **Runtime path:** a per-server layout seed draws the same three, by `layout.vary` below.
  - **Same bytes.** At identity layouts (the identity build, `buildId` 0 and `rotationSeed` 0; `layout` 0) both
    paths write identical bytes for one schema; the differential test (§2) checks that and the nonzero cases.
  - **Mixed paths decode only at one layout.** `HELLO` carries the `buildId` (the runtime path sends 0) and which
    path sent it (§4.6). A shard from a real build meeting the runtime path differs in `buildId` and is refused as
    `buildMismatch` (`buildIdMismatch` 1). An identity-build shard meeting a runtime-path server that varies its
    layout is refused by the server at its `HELLO`, which states `path` 0 (`MISMATCH`, the fact `layoutMismatch`,
    §4.5, §4.6), so no frame of that namespace
    is sent to it and no other namespace's frames are lost with it. Nothing decodes under a layout it doesn't hold.
- **Decision: layouts on the runtime path** `[generation-methods M14]` (reopens R5).
  - **Problem.** The runtime path has no build, so nothing private exists on the client: any layout value reaches
    it in `WELCOME` or is derived from what `WELCOME` carries, where a packet tool reads it and Lync's own planner
    applies it. At seed 0 every no-build game shares one layout, so a byte script written once works against all
    of them. Downstream chunks are encoded once and copied to every recipient (§4.2), so downstream layouts may
    vary at most per server.
  - **Options:** (a) seed 0 always (today); (b) vary order, offsets and tag constants per server from IR copies;
    (c) as (b), with the upstream layout per session.
  - **Choice: (b), on by default.** It removes byte scripts carried between no-build games and servers as a class,
    the same reason the id permutation is on (§4.5), for set-up per definition per server and per connection and
    2–26 ns per bounded field per message (§4.5 gives the mechanism and cost). It prices only tools that hard-code
    a layout, not memory, code, API or hook tools. (c) prices nothing more, since a tool that reads the session's
    key reads its layout in the same pass, and costs the IR copies per player on the server (34–76 MB at 200
    definitions × 100 players), so it is not offered.
  - **Option** (`Lync.configure`, server, runtime path; §7.5): `layout.vary`, boolean, default `true` (chosen by
    principle 2: that cost against a class of tools removed; `false` gives the seed-0 layout, which byte-level tests
    against the golden frames need). Each `WELCOME` carries it as the bit `layout`; the layout seed is derived from
    the permutation nonce, never sent (§4.5). A generated server always sends 0: its layout is its build's. A
    `REKEY` keeps the layout, so decoders never switch inside a session. `layout.vary` is read once, at the server's
    first `WELCOME` of any namespace, so one server never holds two layouts (encode-once, §4.2); a later
    `Lync.configure` with a different value throws `callOptionMismatch` at its caller, the one exception to §7.5's
    rule that a late call never throws.
- **A shard from another schema is an error.** A shard embeds its `buildId`, the seed-0 schema hash and the schema's
  path in its body, and a SHA-256 digest of its body on line 1 (`v5-tooling.md` §1.1). In Studio, requiring a shard
  evaluates the schema and throws `shardSchemaMismatch` on a mismatch; `lync check` fails the same way.
- **`patch` typing.** A wrong value type is a compile error; a misspelled key is a caller error (`patchKeyUnknown`)
  `[probes T4, review-1 r3, r4]`.

### 3.3 Codecs

Every codec is a constructor call returning a plain table, so `{ read ["[Lync] value"]: T }` inference holds
`[probes T1]`; the brand is a key no record field can be `[review-m1 m4]`.
Constructors take no option tables. Values are exact unless declared otherwise.

| Codec | Luau type | Single-row encoding (§4.3) | Rules |
|---|---|---|---|
| `t.bool()` | `boolean` | 1 bit, 1 = true | |
| `t.int(min, max)` | `number` | u(⌈log2(max − min + 1)⌉) of v − min | integers with −2^52 ≤ min ≤ max ≤ 2^52 − 1; refuses fractions and out-of-range |
| `t.int()` | `number` | EG-0 of zigzag(v) | integers with −2^52 ≤ v ≤ 2^52 − 1, so zigzag(v) ≤ 2^53 − 1, the largest EG code (§4.1) |
| `t.number(min, max, step)` | `number` | q in u(⌈log2(n + 1)⌉) | see "Quantizers" below |
| `t.f32()`, `t.f64()` | `number` | u32, or u64 as low then high u32, of the IEEE-754 bits | NaN and ±inf refused; `t.f32` rounds to the nearest f32 (its declared precision) and refuses values beyond the f32 range |
| `t.angle(step)` | `number` (radians) | q in u(⌈log2 n⌉), n from "Quantizers" | q = ⌊wrap(v)·n/2π + 0.5⌋ mod n with wrap into [0, 2π); decodes to q·2π/n |
| `t.string(maxBytes)` | `string` | length u(⌈log2(maxBytes + 1)⌉); bytes in the tail | maxBytes 1–65,535 |

**Quantizers, exactly** (`probes/design-3/number_steps.out`):
- `t.number(min, max, step)`: r = (max − min)/step must be within 1e-9 × max(1, r) of an integer n, which is fixed
  at declaration; otherwise `numberStepIndivisible` (so `t.number(0, 0.3, 0.1)` has n = 3, and `(0, 1, 0.35)` is
  refused). `step = 1` with an integer `min` is `numberIntegerGridUnsupported` (use `t.int`). Encode refuses v
  outside [min, max], then q = min(⌊(v − min)/step + 0.5⌋, n); decode gives min(min + q·step, max), so the top code
  decodes to a value its own encoder accepts (`t.number(0, 0.3, 0.1)`'s code 3 is 0.3, not 0.30000000000000004)
  `[review-m1 M1]`. Maximum error step/2.
- `t.angle(step)`: r = 2π/step; n = r rounded to the nearest integer when within 1e-9 × max(1, r) of it, else ⌈r⌉
  (`2π/1000` gives 1000, not 1001) `[review-3 m5]`.
- **Octahedral** (`t.direction`): with s = |x| + |y| + |z|, p = (x/s, y/s); if z < 0, p = ((1 − |p.y|)·sgn(p.x),
  (1 − |p.x|)·sgn(p.y)) with sgn(0) = +1. Each component c of p is q = ⌊(c + 1)/2 · (2^bits − 1) + 0.5⌋. Decode:
  c = 2q/(2^bits − 1) − 1 for both, z = 1 − |cx| − |cy|; if z < 0, (cx, cy) = ((1 − |cy|)·sgn(cx),
  (1 − |cx|)·sgn(cy)) using the values before replacement; the result (cx, cy, z) is normalised. 10 bits: 0.2369°
  maximum error; 12: 0.05924° (worst case by search, `test/wire/quant.spec.luau` at commit `f1fbfd7`; the 20,000-sample figures in
  `[compression §4.5]` were 0.23° and 0.057°).
- **Smallest-three** (`t.rotation`): from `GetComponents()`'s matrix R (row-major R00 … R22), the quaternion is
  taken by the branch with the largest of (R00 + R11 + R22, R00, R11, R22), ties in that order: trace branch
  w = √(1 + tr)/2, x = (R21 − R12)/4w, y = (R02 − R20)/4w, z = (R10 − R01)/4w, and the standard diagonal branches.
  It is negated if needed so the dropped (largest-magnitude) component is ≥ 0; ties drop the lowest index in x y z w
  order. The three kept components are written in x y z w order, skipping the dropped one; each c ∈ [−1/√2, 1/√2]
  is q = ⌊(c·√2 + 1)/2 · (2^bits − 1) + 0.5⌋. Decode inverts, sets the dropped component to √max(0, 1 − Σ c²), and
  builds the CFrame from the quaternion. The encoder uses the axis-aligned form when every matrix entry is within
  1e-6 of 0 or ±1; the 24 such matrices are indexed in ascending lexicographic order of their nine entries
  (R00 … R22, with −1 < 0 < 1). Maximum error with canonical encoding:
  7 bits 2.8969°, 8 bits 1.4575° (every first code evaluated); 9: 0.7255°, 10: 0.3664°, 11: 0.1836°, 12: 0.0921°,
  13: 0.0459°, 14: 0.0230°, 15: 0.0115° (worst found by sampling near-ties, not proven maxima), about
  375° / (2^bits − 1) (`test/codec/rotation_full.luau` at commit `f1fbfd7`; data in `probes/build/`). Canonical encoding raises the 9-bit maximum from 0.5187°
  (plain smallest-three, by search) because a moved code decodes to a neighbouring code's rotation.

**Decision: quantizers are idempotent on their own codes.**
- **Problem.** Decoding a `t.rotation` code and encoding the result changes the code for about 1.5% of codes at
  7 bits and 0.02% at 15: after quantization a kept component can outgrow the reconstructed dropped one, so the
  re-encoder drops a different component. Idempotence matters when the server relays a client's value (each
  non-idempotent hop adds up to one more quantization error), and for canonical decode (accepted codes the encoder
  never produces are a second byte sequence for one value). Change detection compares Luau values, and the
  differential test shares one encoder, so neither depends on it.
- **Options:** (a) the decoder refuses a code whose reconstructed dropped component isn't the largest under the tie
  rule, and the encoder never emits one. This fails in f32 near-ties, because the decoded `CFrame` is stored in f32
  and re-extracted; (b) define round trips of lossy codecs as "within the declared error", which keeps relay error
  growth; **(c) define canonical as idempotent and check exactly that.**
- **Choice: (c).**
  - **Rule.** For every quantizer, encode(decode(q)) = q for every code q the decoder accepts.
  - **`t.rotation`.** Let E(q) = encode(decode(q)), where decode builds the f32 `CFrame`. Near-equal components make
    E cycle: about 1% of codes at 7 bits and 0.006% at 15 form 2-cycles {q, q′} with neither fixed (milestone 1
    measurement, 200,000 rotations per width). So a code is **canonical** when E(q) = q, or when E(E(q)) = q and
    q < E(q), comparing (flag, index, a, b, c) lexicographically: the fixed point, or the lower member of a 2-cycle.
    The decoder checks this and refuses any other code (rule 6), so an axis-aligned rotation is accepted only in the
    axis form. The encoder iterates q ← E(q) from its first code and stops at a fixed point, or at a 2-cycle,
    returning its lower member; past 4 steps it raises `internal`. Then encode(decode(q)) = q for every accepted q,
    so relaying never drifts. Milestone 1 verifies there are no longer orbits: exhaustively at 7 and 8 bits, and over
    10^7 random rotations at 9–15 (verified in milestone 1: no failures, no orbit beyond a 2-cycle, at most 3 steps).
    Decode with the check costs 2.2–2.7x a plain decode with real `CFrame`s (9 bits: 1.09 against 0.43 µs
    interpreted, 0.36 against 0.13 µs native; `probes/build/results/rotation-3a222e0.json`); an earlier table
    stand-in for `CFrame` gave 3.5x.
  - **`t.direction`.** The fold edge decodes several codes to one direction (at 8 bits, 511 of 65,536 codes are not
    fixed points: (0, 0), (0, 255), (255, 0) and (255, 255) all decode to (0, 0, −1)) `[review-m1 M2]`. A code is
    canonical by rotation's rule (a fixed point of E, with E's decode rounded to f32 as `Vector3` stores it, or the
    lower member of a 2-cycle by (x, y)); the decoder checks it and refuses any other code (rule 6). The encoder's
    first code is not always canonical: a component just below zero with z < 0 lands on the negative side of the
    fold (0.26% of random directions at 8 bits, 0.063% at 10, 0.016% at 12, 0.0009% at 16). So the encoder iterates
    E like rotation's; measured, every such code reaches a fixed point in one step and no 2-cycle exists
    (exhaustive at 8 bits, 10^6 directions at each of 8, 10, 12 and 16), and past 4 steps it raises `internal`.
  - **`t.number`** (with the clamp above), **`t.angle`** and **`t.color3`** have every code a fixed point. Property
    tests check every quantizer exhaustively: every code of `t.color3`, of `t.direction` at 8 bits and of
    `t.rotation` at 7 and 8 bits, and every code of a declared grid for `t.number` and `t.angle` (including the
    `number_steps` cases).
  - **Cost:** one more smallest-three encode per decoded rotation (two for a code in a 2-cycle), and one more
    octahedral encode per decoded direction and per encoded direction (the encoder checks its first code).
- **`t.vector3` and `t.cframe` positions are stored in f32.** A component may exceed a bound by at most the f32
  spacing at that bound, and then takes the end code. The planner refuses a `step` that isn't larger than the f32
  spacing at max(|min|, |max|) (`vectorStepOutOfRange`), so every decoded component re-quantizes to its own code. The
  f32 spacing at M is 2^(⌊log2 M⌋ − 23).

**Codec rules:**
- Every count and length has a declared maximum. Every array count, map count and run count is charged to the
  decode element budget before anything is allocated (§4.8).
- Codec methods are non-generic and return the same codec type `[probes T1]`, except where the table below gives
  a different client type. They are the only codec methods; each is hashed (§4.7), since the client acts on it.
- There's no flags codec: boolean record fields already pack to 1 bit.

**Decision: claims** `[checks-telemetry C4, C5]` `[anticheat-design §3.2]`.
- **Roles.** A leaf of a client-sent payload is an *input* (the client's own control or choice) or a *claim* (what
  the client asserts about the world: a hit target, a shot origin, an amount gained). Unmarked leaves are inputs.
  A leaf's role is the nearest marker on it or on a codec enclosing it in the payload, so `{ … }:claim()` marks a
  record and an inner `:input()` overrides it. `:input()` has one effect: it silences the build diagnostic
  `freeFormRoleMissing` on its leaves (`v5-tooling.md` §3), which flags a free-form leaf (an unbounded float or
  integer, a bounded one with more codes than the lint's threshold, a string, buffer, instance or custom codec)
  that carries no marker. Hash: a wrapper codec, type 26 `role`, role u8 (1 input, 2 claim), then the codec (§4.7):
  2 B of hash input per marker, nothing at run time.
- **Codec equality.** Wherever the design compares two codecs (`refers`, `about` and `reactsTo` keys, the
  `refersMissing` and `aboutMissing` lints), two codecs are equal when their §4.7 serializations are equal after every
  `role` wrapper and every `:intern` marker is removed: markers change who must verify a value and how it travels,
  never which values it holds. So `t.int(1, 2 ^ 40):claim()` equals the key codec `t.int(1, 2 ^ 40)`.
- **Problem.** A claim leaf of `data` must not reach a game handler unverified. The verifiers (a validator, or a
  check on the leaf, `v5-checks.md`) are declared at run time on the server view, so the shared schema cannot see
  them, and Lync drops only malformed input: it may not drop canonical messages because of what the game forgot
  to declare.
- **Options:**
  - (a) drop every message of a definition with an unverified claim leaf before validators, and report a native
    fault (the research's form): Lync acts on canonical input, and messages that arrive before the game's
    declarations run are dropped;
  - (b) deliver and report natively: unverified claims reach handlers, so the marker guarantees nothing;
  - **(c) refuse the handler:** `connect` or `handle` on such a definition throws.
- **Choice: (c).** On the server view, `connect` or `handle` on a definition whose `data` holds a claim leaf with no
  verifier throws the caller error `claimUnverified` at that call:
  `[Lync] claimUnverified: arena.strike:connect data.target must have a validator or a check, got none` (no fix is
  given: there are two, §7.1). A claim leaf is verified when the definition has a validator, or when one of the
  checks `within`, `monotonic`, `maxTotal`, `derive` or `maxRate` (`v5-checks.md`) is declared on the leaf's own
  field handle (§3.4). No other declaration verifies (`refers`, `reactsTo`, `challengeAnswer`, telemetry). Leaves
  inside arrays, maps and union variants, and leaves of codecs no check takes, are verified only by a validator.
  Nothing is declared away (a validator is set once, §3.5; checks have no removal), so verification never lapses once
  the handler is accepted. No input is acted on, the error names the line to change, and its only cost is an order:
  verifiers before the handler. Lync doesn't order scripts, so verifiers and handler go in one script, or the
  handler's script requires the module that declares the verifiers. Messages decoded before a handler exists have no
  handler (§3.5). Claims in a `reply` have no run-time requirement: answers have no validator step, and the code that
  called `invoke` checks its result.
- **What it guarantees, exactly:** no message holding a claim leaf reaches `connect` or `handle` unless, when the
  handler was accepted, the definition had a validator or a check on that leaf. A check passes a message without
  evaluating it when its game function returns nil (`checksSkipped`), when the message is not drawn
  (`messagesPerCheck`), or inside a `resetChecks` window (`v5-checks.md`). A validator that always returns `true`
  defeats it, and so does marking a claim `:input()`; Lync can tell neither apart.

**String tables** `[strings §1, §5]`. Which strings repeat is the game's knowledge, so tables and the fields that
use them are declared, and every value the server sends in a marked field enters by one rule, with no count or
guess:
- **A table** is a schema entry, `names = Lync.strings({ maxEntries = 64 })`, owned by its namespace (two
  namespaces never share one). Options are in §3.4.
- **A field** joins it with `t.string(n):intern(names)`, the only way a value enters; any set of fields of the
  namespace may share one table, so the grouping is the developer's. Every value the server sends in such a field
  becomes an entry the first time it is sent, while the table has room; a value past a cap travels as a literal
  (counted, no fact). The server owns one table per (server, namespace, table), with entry ids drawn at random
  among free ids, and reclaims an entry when no connected player holds it; nothing a client holds is evicted
  (`[strings §1.2, §1.4]`; wire form in §4).
- **Placement:** `:intern` on a codec other than `t.string` (a `t.buffer` entry would need a copy per decode, since
  buffers are mutable), or inside the `data` of an unreliable server-sent event (an unreliable frame can arrive
  before the reliable frame defining the entry) or of a sealed event (the definition would reach the client only at
  the reveal, and at `hideLength = true` a reference saves no byte), is `internMisplaced`. `:intern(x)` with `x` not
  a `Lync.strings` entry of the same schema is `internTableUnknown`; a table no codec marks is
  `stringTableFieldMissing`.
- **Types:** the client type stays `string`, so shards and `.d.ts` don't change; a table has no view. The runtime
  path's type function skips schema entries made by `Lync.strings` (unverified until milestone 1's typing proofs,
  §10).
- **Upstream**, a client references only entries it holds, on either lane, and sends a literal otherwise
  `[strings §2]`.

- Every value in the schema goes into the schema hash (§4.7), so an unmodified client can't send on a direction or
  lane its definition doesn't use.
- The worst-case encoded size of a message, the larger of its single-row and column-block encodings, is at most
  16,000 B, or 960 B for an unreliable definition (§4.9; `messageBytesExceeded`, `unreliableMessageBytesExceeded`).
- The worst-case element count of a message (§4.8) is at most 65,536 (`messageElementsExceeded`), and an array or map
  whose element costs 0 bits at its worst (`t.array({}, n)`, `t.array(t.int(5, 5), n)`) is `elementEmpty`: it
  carries nothing but its count, which a `t.int` carries.
- A schema entry not made by `Lync.event`, `Lync.request`, `Lync.collection`, `Lync.stream` or `Lync.strings` is
  `definitionWrongType`. Names are 1 to 65,535 bytes, and a namespace's 1 to 64 (`nameLengthOutOfRange`). A
  repeated enum item is `enumItemDuplicate`; a collection `key` of another codec is `collectionKeyCodecUnsupported`.
- `maxRecords` counts slots, including slots waiting out their reuse delay; `reliablePerSecond`, `acked` and the
  rest of collection behaviour are in `v5-collections.md`.
- **Streams.** `move = Lync.stream({ data = codec })` is a fourth definition kind: client-sent on the unreliable
  lane, in the namespace's up id space, taking `data` only (hash kind 5, §4.7). `data` has a fixed single-row width,
  with no string, buffer, array, map, optional, union, `t.int()`, Roblox enum, instance or custom codec in it (else
  `streamCodecUnsupported`), since copies are delta-coded per top-level field and compared by their codes across
  frames, which an instance's index into one frame's list can't be (`v5-collections.md` §15.2); a namespace's streams
  together fit 960 B at 33 copies each (`streamBytesExceeded`), so they ride one frame. The client view's
  `set(value)` latches the value sent at each state tick, and `stop()` ends sampling until the next `set`. On the
  server, `connect(function(player, input, index) … end)` receives each index once, in index order, at its playout time,
  `index` an integer state tick, and throws the caller error `playoutDepthMissing` while no depth is set (`playout`,
  below). Specified in `v5-collections.md` §15.
- An option the definition's kind, direction or lane doesn't take (the Kinds column) is
  `definitionOptionMisplaced`, at the definition's line: `sealed` on a client-sent event, a request, a collection
  or an unreliable event, or `from` on a collection or a stream, say. A value outside its Range column is
  `definitionOptionOutOfRange`. `limit` and `sealed` are tables: another type is `definitionOptionWrongType`, and
  `limit` without `perSecond` is `definitionOptionMissing`.
- **Defaults.** `ackEveryFrame` is `false` because its bytes buy something only for definitions whose server handler
  rewinds, which the client cannot see; without it `Lync.perception`'s `ackExact` is false for a frame that carried
  no full ack (`v5-collections.md` §12.5). `sealed.maxOutstanding` 1 is chosen: one pending reveal per player (the
  next round's layout); a game that pre-sends k reveals sets k. `sealed.hideLength` is `true` because a ciphertext's
  length is plaintext information disclosed before the reveal (a layout's size, an answer's length), and sealing
  exists to disclose nothing before it; a codec of fixed size pays nothing for it, and a game sets `false` where the
  length carries nothing (`v5-checks.md`) `[refusals-rejudged-1 R34]`. `sealed = {}` declares a sealed event with
  both defaults.

**`Lync.strings({ … })`**, a schema entry beside the definitions (§3.3), in the shared schema and hashed, since both
ends need its caps (the id width, and the client's decode limits) `[strings §5.4]`. Its option errors are
`definitionOptionUnknown`, `definitionOptionMissing` (`maxEntries`), `definitionOptionOutOfRange` and
`definitionOptionWrongType`, as for every schema constructor.

**Server-view declarations.** What the server does with a client's messages, and what it withholds, is declared
on the server view at run time, never in the shared schema: the client never sees it, it is not hashed, and a
retune needs no client rebuild. A declaration may be made at any time and applies to messages decoded after it.

**Decision: how a server declaration names a field** `[probes field-typing]`.
- **Problem.** Many declarations are about one field of `data` (a check on `strike.origin`, a reference from
  `strike.target` into `fighters`), and their options' types depend on that field's type (`derive`'s function
  returns it). Types must be exact on both solvers on the generated path, on the new solver on the runtime path,
  and under tsc (principle 3), for schemas with hundreds of paths. Overloads chosen by a literal fail under the new
  solver in both ways §3.2 states, and a generic `<P>(path: P)` widens the literal to `string`, so every
  type-function form taking a path argument fails on correct calls (`field-typing` §2, forms a, a′, d).
- **Options:**
  - (a) the path as each declaration's first argument, one overload per path (`Net.shot:derive("landing", { … })`):
    correct calls rejected whenever the options hold a literal or an unannotated function, and "too complex" from
    9 overloads;
  - (b) a `field(path)` method, one overload per path, each returning a handle: no option-table failure, but "too
    complex" at 9–10 paths; one unused generic per overload pushes that to 53 paths (form e), per-level overloads
    fail at 9 keys in any record (form c);
  - (c) as (b), called with explicit instantiation, `v:field<<"f2">>("f2")`: exact under the new solver at 10, 32
    and 128 paths (21.7 ms to check at 128 against an 8.1 ms empty module), but every path is written twice, and
    whether Roblox enables `<<…>>` is unchecked;
  - (d) handles carried by codec values (`Handle<T>` in each codec's type, the schema table as `fields`): exact on
    both solvers with no type function (19.2 ms new, 13.6 ms old at 128), but a record has no handle of its own,
    nested paths nest instead of being one dotted name, and server-view types ride in codec values the client
    evaluates;
  - **(e) a table of handles,** `Net.<definition>.fields`, read by key.
- **Choice: (e).** A key read is not overload selection, so it costs no normalizer fuel and widens no literal:
  `Net.strike.fields.origin`, and for a nested path the dotted key, `Net.shot.fields["hit.at"]`.
  - **Generated path:** the shard emits a concrete `fields` table type, one property per path, no type function:
    exact on both solvers.
  - **Runtime path:** a type function builds the same table type from the schema: exact under the new solver at 10,
    32 and 128 paths, correct calls clean and a wrong handle type, a wrong `fn` return, an unknown path and a
    misspelled option literal each rejected; 18.4 ms to check at 128 paths against the 8.1 ms baseline, 31.1 ms for
    Lync's module and a consumer (`field-typing` §2, §5, `b_table_N`, `b_consumer_128`). Under the old solver the
    handles are the error type, as every runtime-path type is (§3.2).
  - **roblox-ts:** the mapped type `{ readonly [P in Paths<S>]: Handle<At<S, P>> }` over the schema type, exact
    under tsc 6.0.2 `--strict` at 10, 32 and 128 paths, within tsc's start-up spread (`field-typing` §4, §5).
  - Two declarations taking two fields (a stimulus and its response, say) take two handles, and their key types must
    agree by the same check.
- **Handle types come from the field's codec, not its Luau type.** `t.vector3` and `t.direction` are both
  `Vector3`, and `t.int(-100, 100)` and `t.int(0, 100)` both `number`, yet they take different declarations
  (`aim` takes a direction, `maxTotal` no signed field). So each path's handle type is emitted from its codec and
  has exactly the declarations that codec takes; a wrong one is a type error ("Key not found"), not a run-time
  `fieldCodecUnsupported`. Its T is the field's type with the optionals on its path removed, since a declaration is not
  evaluated for a message in which the path is absent. `refers` and `about` take `Collection<K>`, K the
  collection's key type, on a field of type K, K? or { K } (checked on both solvers,
  `probes/review-3.6-core-api/review.out`, `field_kind`, `field_kind_fixed`). On the runtime path each codec type
  carries its kind beside the value brand (§3.3), in the `--!nocheck` types module, so the type function picks each
  handle's methods by kind (unverified until milestone 1's typing proofs, §10).
- **`fields`.** A server-view property of every definition with `data`. Its keys are the paths of `data` through
  records and optionals, dots between names (`"origin"`, `"hit"`, `"hit.at"`), and `""` for `data` itself when it is
  not a record; arrays, maps and union variants are not reachable. Each handle exists once per (definition, path),
  created at first read; a declaration made on a field is always a method of that field's handle. A key that names
  no field is a type error where the path's types are checked, and on both paths throws `fieldPathUnknown` at the
  read (the table's metatable miss, as for `methodSideMismatch`, no cost on hits). Every declaration made through a handle throws at its caller,
  with one code set: `fieldCodecUnsupported` (a codec the declaration doesn't take), `keyCodecMismatch` (a key codec
  unequal by §3.3's codec equality to the one it must equal), `declarationMisplaced` (a definition outside the
  declaration's scope), and §7.1's option codes (`callOptionUnknown`, `callOptionMissing`,
  `callOptionOutOfRange`, `callOptionWrongType`). An option of a definition's own declaration that names fields, one
  or several, takes path strings instead: `interest`'s `position`, `atom`'s `fields`, `rewind`'s `fields`. Each is
  typed as the union of the paths it accepts, so a path of another definition, depth or codec is a type error (new
  solver, a concrete union and a type function's union alike: `probes/open-semantics-3.6/position_path.out`);
  untyped, a path naming no field throws `fieldPathUnknown` at the call, and one whose codec the option doesn't take
  `fieldCodecUnsupported`. A handle there would check less: its type comes from its codec, not from its definition
  or its depth, so another definition's handle, or a nested field's, would pass the type check.

### 3.5 Using it

Game code requires the shard for its side, or calls `Lync.client(schema)` / `Lync.server(schema)`; both return the
same API. Shards go to a replicated folder (client) and `ServerScriptService` (server)
`[client-security-build §2.1]`. There's no `start()`: the runtime starts on first use, and `require` never yields.
The shared schema module replicates on both paths, except a staged namespace's, which replicates at its release by
`Lync.release(view, folder)` (`v5-tooling.md`, `v5-collections.md` §13.2): the runtime path evaluates it, and
Studio's `shardSchemaMismatch` check reads it. Leaving it out of a generated build would hide nothing, because the
client shard already holds every definition's name and codec, traps included, to encode or decode it
`[codecs-in-scripts §7.4]`.

```luau
-- server
local Lync = require(ReplicatedStorage.Packages.Lync)
local Net = require(ServerScriptService.Net)

Net.chat:validate(function(player, text)
	return string.find(text, "%S") ~= nil
end)
Net.chat:connect(function(player, text)
	Net.announce:fire(Lync.all, { kind = "round", number = 3 })
end)
Net.strike.fields.target:refers(Net.fighters) -- v5-integrity.md
Net.strike:validate(function(player, strike) -- verifies the claim strike.target, so connect is accepted
	return Net.fighters:get(strike.target) ~= nil
end)
Net.strike:connect(function(player, strike) end)
Net.buy:handle(function(player, request)
	return PRICES[request.item] -- game code: PRICES
end)
Players.PlayerAdded:Connect(function(player)
	Net.fighters:set(player.UserId, { name = player.Name, team = "red", health = 100, position = Vector3.zero, look = CFrame.identity })
	Net.fighters:patch(player.UserId, { health = 90 })
end)
Net.round:set({ endsAt = 600, phase = "play" })

-- client
local Net = require(ReplicatedStorage.Net.client)
Net.chat:fire("gg")
local shot = Net.strike:asDecoded({ target = 1, aim = camera.CFrame.LookVector }) -- aim as the server decodes it
shot.target = Targeting.pick(shot.aim) -- game code (camera, Targeting): the claim, from the decoded aim
Net.strike:fire(shot)
local result = Net.buy:invoke({ item = "sword" })
if result.ok then
	print(result.value)
end
Net.fighters.changed:connect(function(id, fighter, previous) end)
```

- **Verbs.** `fire` sends; `connect` listens and returns a connection with `disconnect()`; `invoke` asks and yields
  until the result; `handle` answers; `validate` (server) returns `true` to accept or `false` to reject, and is set
  once per definition (a second call throws `validatorDuplicate` at its caller, so a validator is never replaced or
  cleared); `set`, `patch`, `remove`, `audience`, `cut`, `rebind` write a collection (server); `get`,
  `interpolated` (client) and the `added`, `changed`, `removed` signals read one (`v5-collections.md` §2, §9, §11).
  A stream's client view has `set` and `stop`, its server view `connect` (§3.4). A definition has one signal, its
  `connect`; a collection has three, so they are named. `fields` (server) holds the field handles (§3.4);
  `asDecoded` (client) returns a payload as the server will decode it (below).
- **Targets.** One `Target` type for server `fire` and `audience`: a `Player`, an array of players, a
  `Lync.group()`, `Lync.all`, or `Lync.except(target)`. A target resolves once per flush. `Lync.group(players?)`
  returns a live set with `add`, `remove`, `has`, `size`, `players`, `destroy`; leaving players are removed. These
  live on `Lync` only.
- **Results.** Requests never throw. They return `{ ok: true, value: R } | { ok: false, error: E }`, with `E` per
  side, each value one exact trigger (§5.2):
  - client `invoke`: `"timedOut"` (no answer within `timeoutSeconds` of the call), `"limited"` (the server's `limit`
    bucket for the definition was empty), `"rejected"` (the server refused the ask, §5.2), `"unanswered"` (the
    server had no `handle`, or it threw or returned a reply its codec refuses);
  - server `invoke(player, data)`, which yields like the client's: `"timedOut"`, `"rejected"`, `"unanswered"`, as
    above from the client's side, `"playerLeft"` (the player's `PlayerRemoving` fired before an answer) and
    `"serverClosing"` (a `BindToClose` callback ran before an answer). No server-sent request takes `limit` (§3.4),
    so `"limited"` is not a server outcome.

  A result is a fresh table owned by its one caller, so it is not frozen (facts are, because every observer gets
  the same table, §7.3).
- **Server results carry timing** `[clock-facts §U4]`. A server `invoke`'s result also has `roundTripSeconds`,
  `sendPingSeconds`, `answerPingSeconds` and `minPingSeconds`, defined in §5.2. The arms follow what §5.2 guarantees,
  and are written out, not intersected, so neither solver normalises an intersection of a union:

  ```luau
  export type ServerResult<R> =
  	{ ok: true, value: R, roundTripSeconds: number, sendPingSeconds: number, answerPingSeconds: number, minPingSeconds: number }
  	| { ok: false, error: "rejected" | "unanswered", roundTripSeconds: number, sendPingSeconds: number, answerPingSeconds: number, minPingSeconds: number }
  	| { ok: false, error: "timedOut" | "playerLeft" | "serverClosing", roundTripSeconds: nil, sendPingSeconds: number?, answerPingSeconds: nil, minPingSeconds: nil }
  ```

  Narrowing on `ok` exposes `value` only in the success arm; narrowing on `error` gives `number` in the second arm on
  both solvers; the old solver doesn't narrow an `else` branch to the third arm, so there a field reads `number?` and
  needs a nil test (`probes/review-3.6-core-api/review.out`, `result_arms`; the same diagnostics with these names,
  `probes/consistency-3.6-core-api/run.out`). Client results are unchanged: the measurement is about a player, which
  only the server's is, and the client would pay a clock read and a `GetNetworkPing` per ask for fields no decision
  reads; each side already has its own `invoke` signature.
- **Sealed events.** On a definition with `sealed` (§3.4), server `fire` returns a `Seal` with `reveal()` and
  `discard()`; the client's `connect` handler runs at reveal with the decoded value, so client types are those of
  any event (`v5-checks.md`). The runtime path's type function picks the return type from the options table's
  `sealed` property, which literal widening (§3.1) doesn't affect: `Seal` when its type excludes nil, `Seal?` when
  it includes nil (`sealed = if flag then {} else nil`), nothing when absent (checked under the new solver,
  `probes/review-3.6-core-api/review.out`, `sealed_fire`, `sealed_fire_fixed`). The generated path sees the value.
- **Handler arguments.** Server handlers receive the player first, matching `OnServerEvent`, and a stream's also
  receives the index (§3.4); client handlers receive the payload.
- **Wrong-side calls** are type errors on the generated path; on the runtime path the view's metatable miss throws
  `methodSideMismatch` (no cost on hits).

**Decision: a message with no handler** (`[decoy-challenge-facts §7.1]` found it unspecified).
- **Problem.** Dispatch can find no `connect` for an event, or no `handle` for an ask: a script that connects
  late, or a definition the game never handles. Lync carries every definition in frames on one remote, so the
  engine's queue for unconnected `RemoteEvent`s never applies; whatever Lync holds is memory it must bound.
- **Options:** (a) hold messages per definition until its first handler: a new bound per definition, and a late
  handler then runs on stale messages all at once; (b) dispatch to nobody and count it; (c) also report it
  natively, which turns a late `connect` into an error line in every session.
- **Choice: (b).** A script that connects in the run that first requires the view misses nothing, since `require`
  never yields and dispatch runs on a later engine event. A script that starts later (a character or tool script, at
  each spawn) misses what came before its `connect`; what it needs then is state, and belongs in a collection, whose
  `get` reads it at any time. The message is counted in `messagesUnhandled` per definition (§7.4); an ask is answered
  `unanswered` at once (§5.2), so the asker does not wait out its `timeoutSeconds`. This is the one statement of the
  dispatch rule (§5.1 points here).
- **Accepted and delivered.** A message that passes §6.1 step 6 is *accepted*; it is *delivered* when a handler
  receives it. Checks commit and `refers` reports on accepted messages; telemetry samples delivered ones, so a
  definition with no handler, a claim definition whose handler was refused included, gives game code none of its
  values.

**Decision: rounding a value as it will decode** `[server-facts §U9.6]`.
- **Problem.** A client that computes a claim from its raw aim, then sends the aim quantized, disagrees with a
  server that recomputes from the decoded aim: 0.2369° of `t.direction(10)` is 1.24 studs at 300 studs. The
  client needs the value the server's decoder will produce, exactly, including `t.f32` rounding, `Vector3`'s
  f32 storage and the canonical rotation codes of §3.3.
- **Options:** (a) a codec method `codec:asDecoded(value)`: codec methods return codecs (§3.3), and game code on the
  generated path holds views, not codecs; (b) game code quantizes by hand from the rules of §3.3: one copy of
  the quantizers per game, free to drift from Lync's; (c) **a view method,** `Net.<definition>:asDecoded(data)`.
- **Choice: (c).** On the client view of a client-sent event or request, `asDecoded(data)` returns a new value equal
  to what the server's decoder produces for `data`, for every built-in codec: decode(encode(data)), the layout aside,
  which doesn't change values. For `t.convert` and `t.custom` it is the client's own decode(encode(v)), which equals
  the server's only when the game's functions read no side-specific state; for `t.instance` it is the same instance,
  which the server may still refuse as `instanceUnresolved` or `instanceClassMismatch` (§7.3). It sends nothing.
  Every field needs an encodable value, so a claim computed from the result is set afterwards (the example's
  placeholder `target = 1`). Replies are not covered: the server recomputes nothing from an answer (§3.3, claims). A
  value the encoder refuses throws `valueRefused`, as `fire` would. Typed `(self, data: T) -> T` on both paths. Cost:
  at most one encode and one decode of the payload, without bit I/O; generated shards emit it for each client-sent
  definition whose `data` holds a quantized or f32 leaf (bytecode per definition unmeasured), and share one copying
  function for the rest.

## 4. Wire

### 4.1 Remotes, frames and bits

- **Remotes.** One `RemoteEvent` named `Reliable` and one `UnreliableRemoteEvent` named `Unreliable`, created by the
  server under `ReplicatedStorage.Lync` on first use, carry every namespace. Each call carries one buffer, plus an
  instance array when the frame references instances `[landscape §2.1]`. A client that finds no remotes 10 s after
  first use reports `remotesMissing` (§7.3) and keeps waiting.
- **Calling `FireServer`.** The client transport reads `FireServer` from each remote once, when it finds that
  remote (and again for a remote that replaces it), and calls the captured function with the remote as `self`: a
  plain `CALL` with no `NAMECALL`, 44.0 against 45.1 ns per call at `-O2` and 34.6 against 43.0 at `-O1`
  `[client-self-checks U1]`. A spy hooking the remote's `__namecall` no longer sees Lync's calls; an in-place
  `hookfunction` still does, so this is no integrity measure and changes no byte.
- **Per flush, per player:** at most one reliable frame, split at 16,384 B (both directions; the engine's own limit
  is unmeasured, §10), and unreliable frames of at most 1000 B each including header and tag, the documented drop
  limit `[compression §1]`. Reliable frames are ordered per connection `[state-sync §5.1]`. A split is decided by
  counting each frame kind's longest header (5 kinds: downstream reliable, event and state; upstream reliable and
  unreliable; the longest, upstream unreliable with an ack and a receipt, is 51 bits), so a frame may split up to
  7 B before its limit; the limit is never exceeded. A downstream frame also splits before its element count
  (§4.8) would pass the client decode allowance of 4,194,304, so an unmodified server never writes a frame a client
  refuses by rule 10.
- **Bit order** (`probes/design-3/bitorder.out`). Bit i of the bit section is bit (i mod 8), value 2^(i mod 8), of
  byte ⌊i/8⌋. A field u(w) holding an unsigned integer is written least significant bit first. This is the order of
  Luau's `buffer.writebits`/`readbits` (up to 32 bits per call; wider fields are written as low 32 bits, then the
  rest). Multi-byte values that sit on byte boundaries (the tag, §4.5) are little-endian.
- **Integer codes** (`probes/design-3/golden.out`). Every EG-coded value is an integer in [0, 2^53 − 1], so all
  arithmetic below is exact in doubles `[review-3 M5]`. EG-0 of x: let z = (bit length of x + 1) − 1; write z zero
  bits, a one bit, then u(z) of (x + 1) − 2^z. Decode: count z zero bits up to the one bit, read r = u(z), return
  (2^z − 1) + r. EG-k of u is EG-0 of ⌊u/2^k⌋ followed by u(k) of u mod 2^k. z > 53 or a result above 2^53 − 1 is
  malformed (rule 2). zigzag(v) = 2v for v ≥ 0 and −2v − 1 for v < 0. EG-0 is used for every count in the
  grammar.
- **`align`** writes zero bits up to the next byte boundary.

**Frame grammar:**

```
frame      := bits align tail [tag:u32le — upstream only, §4.5]
bits       := header toc chunks

header (down, reliable)   := tick: '0' unchanged | '10' +1 | '11' u16          -- vs the last reliable frame this client received
header (down, unreliable) := '0' tick:u8                                       -- event frame: runs only; may be shared
                           | '1' seq:u12 tick:u8 in                            -- state frame: rows only; per player (§4.4)
header (up, reliable)     := caller:u1 ack rcv:u8
header (up, unreliable)   := seq:u12 caller:u1 ack receipt
ack                       := '0' | '1' seq:u12 received:u16                    -- newest state-frame seq received; received bit i is seq − 1 − i
receipt                   := '0' | '1' rcv:u8                                  -- '1' exactly when the frame holds an ackEveryFrame message
in                        := '0' | '1' index:u12                               -- on every state frame; '1' once a stream index was received

toc (down, reliable)   := segs(state) segs(run) segs(remove)
toc (down, event)      := segs(run)
toc (down, state)      := segs(rows)
toc (up, both)         := segs(run)
segs(x)                := n:EG0 { ns:EG0 count−1:EG0 }   -- n segments; each: namespace index, then how many chunks of kind x
chunks                 := every chunk of every segment, in toc order

run chunk     := id:u(w) count−1:EG0 [instances:EG0] rows
control chunk := type:u3 count−1:EG0 rows                -- a run chunk of namespace 0: count messages of one type
stream chunk  := id:u(w) count−1:EG0 first:u12 rp:u1 ref:u1 [back:EG0] copies   -- a stream's run chunk, upstream unreliable
strings chunk := ns:EG0 { count:EG0 { id:u(w_t) length:u(L_t) } }   -- namespace 0's state segment; one list per table of ns (§4.11)
interned value := entry:u1 ( '1' id:u(w_t) | '0' the field's plain t.string encoding )
```

- **Chunks** are the unit of shared encoding. Downstream, every chunk starts on a byte boundary (`align` before
  it), so a chunk encoded once is placed with `buffer.copy`; upstream, chunks are packed with no alignment, since
  nothing upstream is shared.
- **Segments.** Consecutive segments of one list name different namespaces; run segments are in call order, state
  and remove segments in ascending namespace order. Namespace 0 is control (§4.6): its runs are control messages,
  and its state segment holds strings chunks (§4.11), one per namespace in ascending `ns`; since it is the lowest
  namespace it precedes every other state segment, so a definition precedes every reference in its frame.
- **Order.** On the reliable lane, all state chunks, then runs in call order across namespaces, then removes, so
  every event sees every collection write made before it on the server `[state-sync §5.3]`. A run holds
  consecutive messages of one definition to one target; interleaved fires make separate runs. An encoder may end a
  run before the next message of its definition, so two adjacent runs of one definition are canonical; the
  client's released join hold writes each held message as a run of its own (§5.3).
- **Run chunk.** `instances` is present only when the definition's `data` or `reply` can contain a `t.instance`
  (§4.2); rows follow §4.3, except that a sealed definition's rows are `v5-checks.md` §9.3's sealed rows, always
  single rows. A **control chunk** holds `count` consecutive control messages of one type, each row
  being that type's fields (§4.6); its tail values follow the general rule (§4.2). A chunk is at most 16,256 B; a
  run that would exceed it continues as a new run chunk, so every chunk fits an empty frame `[review-3 m2]`.
- **State, remove and row chunks** carry collection data; their contents are in `v5-collections.md` §3. A state
  chunk begins with `kind:u1` (0 rows, 1 byte-aligned pieces), and every add and every row of a rows chunk carries
  `gen:u2 seg:u1` right after its slot: the slot's generation, sent so the client stores it rather than counting
  adds, and the record's segment bit, which flips at a `cut(key)` so no interpolation or rewind spans it. In a state
  frame, an `acked` collection's rows travel as the acked rows chunk of `v5-collections.md` §5.1 in the rows chunk's
  place: one column block per frame, whose `gen` and `seg` columns cover only rows with no baseline (nb = 0), the
  others taking their newest baseline's. Milestone 2 frames always write zero such segments and send no state
  frames.
- **Stream chunks** are the run chunks of a stream definition (`Lync.stream`, `v5-collections.md` §15.2) in the
  upstream unreliable toc's run segments, riding the flush's first unreliable frame: `count` consecutive indices
  from `first`, `rp` the parity of the client's applied `stateRate` changes, `ref` 1 when the first copy is coded
  against the acked index first − 1 − `back`, then the copies (`v5-collections.md` §15.3).
- **Caller bit.** `caller` is 1 when the frame holds the message of a probed call whose source check failed
  (`v5-integrity.md` §4), else 0; it is 0 in untagged frames. It is also the high bit of the tag input's lane byte
  (§4.5), so it is covered at every `tag.coverBytes`, and the server reads it before the tag to hash each candidate
  once.
- **Receipt.** `rcv` is the number of downstream reliable frames the client's listener has received on this
  connection, refused ones included, mod 256, when it encodes the frame. It is on every upstream reliable frame, so
  it shows nothing about which definitions game code watches, and on an unreliable frame exactly when the frame
  holds a message of an `ackEveryFrame` definition (`receipt` `'1'`; `'1'` on any other frame is rule 7), so that
  message's reliable horizon is read from its own frame (`v5-collections.md` §12.3). It is client-stated, and tells
  the server which reliable state a client held when it sent, which state-frame acks don't `[server-facts U10.2]`.
  - **Extension.** Let S be the number of reliable frames the server has passed to the engine for that player (a
    `FireAllClients` frame counts once for each recipient, a split frame once per part), and P the extended receipt of
    the newest earlier frame on the same lane that carried one (0 before the first): the client's count only grows and
    each lane keeps its send order (reliable frames by count, unreliable by seq), so the receipt is at least P. The
    server takes the value in [P, S] congruent to `rcv` mod 256. It is **exact** when S − P < 256; otherwise (256 or
    more frames sent since that earlier frame, a 4.3 s downstream stall at 60 frames a second) the server takes the
    lowest candidate and marks the receipt inexact, and an unreliable frame older by seq than that earlier frame
    (reordered) takes the candidate in (S − 256, S] and is inexact. A consumer reads only an exact receipt as exact:
    `reactionBeforeStimulus` decided by the receipt (`byReceipt` 1), the rewind's `receivedExact`, the D in force
    (§4.6). The one reader of unaccepted frames, the `REKEY` resend test (§4.5), takes the highest candidate instead.
- **Ack.** Within a flush the client sends its reliable frame first, then its unreliable frames. The first of them
  carries an ack (`'1' …`) when a state frame arrived since the last ack sent, else `'0'`. A frame holding a message of
  an `ackEveryFrame` definition (§3.4), or a stream chunk, also carries `'1' …` whenever any state frame has arrived, so
  the server reads that message's perceived tick, or each stream index's, from its own frame `[interest-rewind §11.3]`
  (`v5-collections.md` §15.3). A client whose namespace has an `acked` collection acks only state frames it decoded and
  accepted, so the server never names a baseline the client didn't store (`v5-collections.md` §5.1). With nothing else
  to send, the client sends an unreliable frame holding no chunks once 2 new state frames are unacked, or the oldest
  unacked one is 100 ms old `[review-redundancy-2 4]`.
- **Stream ack.** `in` is on every state frame: `'1' index` once the server has received a stream index from that
  client, the newest such index, else `'0'`. The client extends it to the value in (K − 4096, K], K its state tick;
  a client that has sent no stream index reads and discards it. Its presence depends on no connection state, so an
  unreliable state frame decoded before the reliable `WELCOME` of a namespace has the same header length on both
  ends (`v5-collections.md` §15.5).
- **Ticks.** The downstream reliable tick is coded against the last reliable frame *that client* received; a
  client's first reliable frame, and a frame shared by players whose last ticks differ, use `'11' u16`, which is
  T mod 2^16. The unreliable `tick:u8` is T mod 2^8. The client extends either to the value nearest its own
  estimate ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋, which a `RATE` keeps continuous (§4.6)
  `[review-redundancy-2 14]`.
- **Sizes.** For the busy traffic model (upstream 60 input and 10 action messages a second in 70 frames;
  downstream 60 reliable and 20 unreliable frames a second), framing costs 374 B/s up with a 16-bit tag and 160 B/s
  down `[probes review-redundancy-2 wire_overhead_2]`. On top of that, upstream: the 32-bit tag (§4.5) adds 2 B per
  frame (140 B/s); `rcv` 1 B per reliable frame (10 B/s); `caller` 0 or 1 B per frame, 1 B exactly when the bit
  section would otherwise end on a byte boundary (at most 70 B/s), and `receipt` likewise per unreliable frame
  (at most 60 B/s); so at most 654 B/s up. A frame holding an `ackEveryFrame` message or a stream chunk adds 28
  bits when it would have carried `'0'`, and an unreliable `ackEveryFrame` one 8 more for `rcv`. The segment toc
  adds a namespace index (1 bit for namespace 0, 3 for 1–2) per segment. Downstream, `in` adds 1 bit to every state
  frame, 13 once a stream index was received (`v5-collections.md` §15.5).

### 4.2 Shared encoding, instances and the tail

- **Encode once.** Downstream, each run, state chunk and row chunk addressed to several players is encoded once
  per flush and copied into each player's frame. When every recipient of a flush's frame would get identical bytes,
  one call goes through `FireAllClients`; this is decided from targets and tick headers, never by comparing
  buffers. Unreliable event frames carry no per-player field, so they can be broadcast too; state frames are per
  player by construction (§4.4) `[review-2 B3]` `[review-redundancy-2 3]`. Downstream layouts are one per build (and,
  on the runtime path, one per server, §4.5), never per session or per player, since a per-recipient layout would
  encode each shared chunk once per layout and end `FireAllClients` `[generation-methods §0.2]`. Shared chunks carry
  interned strings as references or literals, never definitions; definitions go in each recipient's own strings
  chunk (§4.11), and frames are identical across recipients only when their definition lists are equal, decided from
  the lists. A sealed message's chunk and its reveal are identical for every recipient (`v5-checks.md` §9.3). The
  one per-recipient difference inside a shared chunk is a tail patch: with `canary.varyPerViewer`, on by default, the
  chunk is encoded once and each viewer's copy has 4 tail bytes rewritten (67 ns per viewer native,
  `v5-integrity.md` §9); a frame holding such a copy, or a decoy viewer's re-encoded chunk (§8 there), leaves
  `FireAllClients` for that flush, so by default frames holding canary adds do.
- **Instances are chunk-local.** A chunk lists its own instances (`instances` in its header); indices are
  u(⌈log2 c⌉) into that list, where c is the chunk's count. The frame's instance array is the concatenation of every
  chunk's list in chunk order, so a chunk's bits never depend on the frame it lands in `[review-2 B3]`. A chunk lists
  each distinct instance once, in order of first reference. The frame's instance array is always passed as the
  remote call's second argument, empty when the frame has none.
  - **Encoders.** Instances are collected before the chunk is encoded, by a walk over the codec's instance leaves
    only, which costs 3.4% of an encode. The encode itself never adds to the list: an unlisted instance is
    `internal`.
  - **Committed count.** The list's count is fixed at each encode's entry, and a failed encode truncates the list
    back to it. So rows are collected and encoded one at a time (or one run at a time), never collected ahead: one
    refused row would otherwise drop the instances of the rows collected after it.
  - **Decoders** take a chunk's instances from the frame's array by offset and the count in the chunk header,
    never from `#list`, because unreplicated instances arrive as nil.
- **Rollback.** After a refused or raising encode, the writer and the instance list are as they were at its entry,
  so a throwing `t.convert` can't corrupt the rest of a flush. Two mechanisms give that, by codec:
  - **Check, then write**, in generated encoders of definitions whose codec has no `t.convert` or `t.custom` leaf:
    every value is checked before the first bit is written, so a refusal has nothing to undo and no `pcall` runs.
    This saves the 45–110 ns per call the rollback `pcall` costs interpreted `[codecs-in-scripts §6.3]`.
  - **Mark and `pcall`** everywhere else (a `t.convert` or `t.custom` leaf, whose game code can raise mid-encode, and
    the runtime path's interpreter, which writes as it walks): the encoder marks the writer and the instance list on
    entry, runs the encode in one `pcall`, and on a refusal or a raise (game code, or `internal`) restores both and
    then raises. 0.1–0.3 µs per encode (milestone build).
- **The tail** holds string and buffer bytes, read backwards from the end of the frame (before the tag). Reading
  a value of n bytes takes the n bytes ending at the tail cursor, in forward order, and moves the cursor back by n.
  So a chunk's tail segment is its values in reverse decode order, and the frame's tail is the chunks' segments in
  reverse chunk order. A shared chunk is stored as its bits plus its tail segment.
- **Bits and tail meet exactly:** the byte after the aligned bit section is the first byte of the tail.

### 4.3 Decision: how values become bits

- **Problem.** Roblox zstd-compresses remote payloads above a threshold at a level, neither documented nor
  measured; the design assumes compression from 100 B `[compression §1]`, pending §10. Bit-packing defeats zstd;
  byte alignment wastes bits.
- **Options:** byte-aligned layouts leaning on zstd; dense bit-packing (v4); **fixed-width bits for single rows and
  a column coder for multi-row data.**
- **Choice: the third.** Without temporal prediction it is 1.2–1.8x smaller than the best byte-aligned layout under
  modelled engine zstd in five traffic models and ties the sixth `[compression §2.1]`; its output doesn't compress
  further, so the engine's level changes nothing measured for it, where byte-aligned layouts lose 40–75% of their
  gain between levels −5 and 1 `[compression §2.4]`; strings stay in the byte tail, where engine compression still
  applies `[compression §2.5]`. Only cross-frame compression context could overturn this (§10).

**Single rows.** A run of fewer than `columnMinRows` messages writes each message in its codec's single-row
encoding (§3.3), one after another; request, control and sealed runs always do. Inside a single row, an array or map with at
least `columnMinRows` elements is written as its count followed by a column block over its elements. A stream chunk
is never a column block: its copies follow `v5-collections.md` §15.3's copy grammar (§4.1). An acked rows chunk is
always one column block, whatever its row count, its leaf columns coded on residuals against each row's prediction
from its baselines instead of the previous row (`v5-collections.md` §5.1).

**Column blocks.** A run of `columnMinRows` or more messages (and such an array or map) is written as columns.
`columnMinRows` is a protocol constant, 3; the decoder knows the form from the count, so no flag is sent. The
milestone 1 benchmark set it: bits of n single rows against one column block, summed over `strike`, `announce`,
`fighters` and a `{ t.int(0, 100) }` record, 200 draws (`f1fbfd7:test/codec/min_rows.luau`). At n = 3 the block is
smaller in 3 of 4 value patterns:

| n | constant | ±1 noise | Gaussian σ = 50 | 10% sparse |
|---|---|---|---|---|
| 1 | 174.7/295.1 | 174.8/295.7 | 174.6/280.2 | 174.5/294.3 |
| 2 | 348.3/351.0 | 349.1/407.7 | 349.9/425.5 | 348.9/356.9 |
| 3 | 523.1/352.9 | 523.6/467.4 | 523.7/535.5 | 523.7/382.2 |
| 4 | 697.9/353.3 | 698.1/517.9 | 698.2/642.8 | 697.9/403.2 |

- **Flattening**, depth first in field order:
  - a record: its fields' columns in order;
  - `t.optional(c)`: a bool presence column, then c's columns over the present rows only;
  - `t.union`: a variant-index column, then each variant's columns, in variant order, over that variant's rows;
  - `t.array(c)`: a count column, then c's columns over every element of every row, in row order;
  - `t.map(k, v)`: a count column, then k's columns and v's columns over every pair;
  - `t.string`, `t.buffer`: a length column; bytes go to the tail in row order;
  - an interned `t.string` (§4.11): as a `t.union` of variant 0, the literal (the `t.string`'s columns), and
    variant 1, the entry (an id column on [0, `maxEntries` − 1]);
  - `t.vector3`: x, y, z columns; `t.color3`: R, G, B; `t.direction`: two code columns; `t.cframe`: position's
    columns, then rotation's;
  - `t.rotation`: the flag column, then the axis-index column over the rows whose flag is 1, then the dropped-index column and
    three component columns over the others;
  - `t.convert(base)`: base's columns;
  - `t.f32`, `t.f64`, `t.custom`: a raw column, values in single-row encoding one after another, no mode;
    `t.vector3f32`: three raw columns, x, y, z.
- **Integer columns** (every other column) are coded on residuals `[review-3 M5]`. Each column's codes are an
  interval of n integers: `t.int()` and Roblox enums use the value itself on [−2^52, 2^52 − 1] (n = 2^53); every
  other column uses the unsigned integer its single-row encoding writes, on [0, n − 1] (`t.int(min, max)`: v − min,
  n = max − min + 1; quantizers: q; enums, variants, instances: the index; lengths and counts: 0 … max; bools:
  false 0, true 1). Each code's residual is code − previous code (the first row against 0), wrapped modulo n into
  [−⌊n/2⌋, ⌈n/2⌉ − 1], then zigzagged; so a bool's residual is its XOR with the previous row. Decode adds and wraps
  back into the interval. Zigzag maps [−⌊n/2⌋, ⌈n/2⌉ − 1] onto exactly [0, n − 1], so a residual whose zigzag is n or
  more is refused (rule 2), and every residual's zigzag is at most 2^53 − 1.
- **Exactness to n = 2^53** (`f1fbfd7:src/wire/column.luau`). The first row is wrapped like every other row: its
  residual against 0 is a difference, never `(code + ⌊n/2⌋) mod n`. Decode wraps before it adds: if r > top −
  previous the code is previous + (r − n), if r < lo − previous it is previous + (r + n), else previous + r. The
  first build added first and wrapped after, so a sum passed 2^53 and rounded for every n > 2^52, and the codec
  carried a workaround until the fix. A property test covers intervals at and near 2^53 (n = 2^53, 2^53 − 1,
  2^52 + 1, lo = −2^52) against an exact `math.fmod` reference.
- **Offsets** (`v5-integrity.md` §2; on the runtime path, §4.5's `layout`). Where offsets apply, a bounded code q
  travels as w = (q + c) mod n, c fixed per codec site, in single rows and columns alike; a column's codes are the
  w. Since residuals are taken modulo n, c cancels in every residual but the first row's.
- **Decision: the first row of a column under offsets** `[generation-methods M3]`.
  - **Problem.** The first row's baseline decides whether an offset acts inside column blocks at all, and the
    encoder, which a modified client controls, decides when messages travel as a block: any run of
    `columnMinRows` or more, any array or map of that many elements.
  - **Options:** **first row against 0** (the rule above): c sits in the first residual, so every value of the
    block needs c to decode; against c: the residual stream equals the identity's, so zero bits, and a decoder
    that ignores c reads the block exactly (`probes/generation-methods/column_offset.out`).
  - **Choice: against 0.** Against c, a forger escapes every offset by sending three messages in one run, so
    offsets would price nothing on either lane. Cost, 64-row columns, 200 trials, bits against the identity:
    sequential n = 32 137.0 → 185.1, ±1 walk n = 32 135.9 → 150.4, sparse 10% n = 101 89.3 → 96.8, constant
    n = 4096 14.0 → 22.1, sequential n = 4096 137.0 → 214.2, sequential n = 4 137.0 → 73.2, uniform equal; only
    where offsets apply, never at seed 0 or with `layout` 0. It is a protocol constant (§4.9).
- **A column over zero rows** (an optional absent in every row, an unused variant) writes nothing, not even a mode.
- **Per column, `mode:u2`:**
  - `0` zero: every residual is 0;
  - `1` Exp-Golomb: `k:u4`, then each zigzagged residual as EG-k;
  - `2` sparse: `k:u4 m:EG0`, then m pairs `gap:EG0 value:EG-k` (rows skipped since the previous non-zero row, then
    zigzag − 1);
  - `3` frame of reference: `base:EG0 width:u6` (0–53), then each zigzagged residual minus base as u(width).
- **Free choices.** Mode and k, and literal or reference for an interned value, are the encoder's choice: any
  valid choice decodes. The reference encoder, which
  golden frames follow, picks the fewest bits, ties going to the lower mode, then the lower k; sparse writes every
  non-zero residual; frame of reference uses the minimum as base and the smallest width. It costs every mode and
  every k (a log2-of-mean shortcut lost 6–14% `[compression §2.3]`).
- **Measured** (64-row columns; `probes/build/results/579015b.json`, `c91960e.json`):
  - The full k search costs 2.2–2.6x a k = 0 encode on the worst patterns (±1 noise, Gaussian σ = 50),
    interpreted and native, and 1.0–1.4x on constant and sparse columns. That is under the plan's 3x threshold, so
    the one-histogram fallback `[compression §3.2]` isn't used.
  - A batched reader with a 12-bit lookup table, its cursor in a local, decodes EG-0 at 43–47 ns per value
    interpreted and 23–29 ns native, against 86–94 ns interpreted for a call per value.

### 4.4 Sequences

**Decision: one shareable unreliable frame and one acked one** `[review-3 M1]`.
- **Problem.** Broadcast needs identical bytes for every recipient (`FireAllClients`), so no per-player field;
  notify needs a per-player sequence whose consecutive values are that player's consecutive frames, or the 16-bit
  ack window and sequence extension fail (draft 3's server-wide seq advanced by about 100 between one player's
  frames at 100 players).
- **Options:** a per-player seq on every unreliable frame (notify works; no unreliable broadcast); a server-wide seq
  (broadcast works; notify and extension fail); **two frame kinds: event frames with no seq, and state frames with a
  per-player seq.**
- **Choice: two kinds.** Only `:newest()` rows are repaired, and a viewer's rows are chosen for that viewer anyway,
  so only state frames need acks; unreliable events are never resent, so their frames need no seq and stay
  shareable. Cost: on a state tick when a player gets both rows and unreliable events, one more remote call and a
  9-bit header; nothing otherwise.
- **State-frame `seq`** counts each player's state frames from 0. The ack and notify cover state frames only.
- **Upstream unreliable `seq`** counts each client's unreliable frames from 0; it feeds the replay window (§4.5).
- **Stored sequences are extended.** Any 12-bit value a peer stores (a row's seq, the newest acked seq) is first
  extended to a full counter: the value nearest the newest seq received in that sequence, from 2047 behind it to 2048
  ahead. Counters start at 0 and are never negative: before the first value the newest is −1, and an extension
  below 0 takes the value 4096 higher. Consecutive values are one player's consecutive frames, so this fails only
  after 2048 consecutive losses; idle records never age out `[review-redundancy-2 1]` `[review-2 M2]`.

### 4.5 Integrity on the wire (milestone 2)

The tag, the replay window, the id permutation and the key derivation are part of the frame format, so they ship
with it. The per-build values they read (the tag's initialisation constants, the secret S, the variant masks) are
drawn in `v5-integrity.md` §2 (milestone 5); at build seed 0 each is its identity, which is what
milestone 2 builds and what the golden set (§4.10) fixes. The rest of client-side integrity is in
`v5-integrity.md` (§6.2).

- **Build identity** `[generation-methods M1]`. Each build run draws a public `buildId` (u32) and a private
  `rotationSeed` (64 bits), both from OS entropy. `buildId` is what `HELLO` carries and the server compares (§4.6);
  it is in the shard bodies and the manifest. `rotationSeed` is written only to `manifest.json`, which never ships,
  and every per-build value is a function of it (`v5-integrity.md` §2), so a tool holding `buildId` and Lync's
  source learns none of them. `buildId` 0 with `rotationSeed` 0 is the identity build (tests). The runtime path has
  no build: it sends `buildId` 0, and its varied layout is `layout` below. The per-build streams draw from
  xorshift32 (x ^= x << 13; x ^= x >> 17; x ^= x << 5, mod 2^32; each output the state after a step).
- **Session key** `[generation-methods M8]`. The first `WELCOME` carries two nonces: an 8-byte key nonce, drawn per
  connection from an entropy-seeded `Random.new()`, and a 4-byte permutation nonce, drawn once per server at start
  and never 0 (redrawn), used below. The key is the 64-bit output of HalfSipHash-2-4 keyed by the build's secret S
  (64 bits, in both shards, `v5-integrity.md` §2) over (key nonce ‖ `01`), as two little-endian u32, low first;
  S = 0 (seed 0, and the runtime path) is the identity: the key is the nonce itself. A tool that reads `WELCOME`
  with a receive hook then needs S from the shard each build as well: the key is a 64-bit unknown without it. Cost:
  zero bytes; one derivation per connection and per `REKEY` on each side: 14 SipRounds against the tag's 6 for an
  input this short, about 1.3–1.7 µs interpreted and 0.24–0.34 µs native (one straight-line form measured 1.95×
  and 1.74× the 1-3 fixed cost of 0.89 µs and 196 ns, `probes/review-3.6-wire/derive_rounds.luau`).
- **Keyed tag** `[client-security §3.1]`. The client counts its upstream reliable frames from 0 across namespaces,
  advancing before each `FireServer` and keeping the count if the call raises; the count is never sent. Every
  tagged upstream frame ends with `u32le` = H(input) XOR m, where:
  - input = count as u32le (reliable; unreliable: the extended seq mod 2^32), the lane byte (0 reliable,
    1 unreliable, plus 128 when the frame's `caller` bit is 1, §4.1), the frame's length before the tag as u32le,
    its instance count as u16le, then the first min(`tag.coverBytes`, length) bytes of the frame from byte 0;
  - H is HalfSipHash-1-3's 32-bit output under the key (as two little-endian u32), with the reference rotation
    amounts and round counts (§4.9) and the build's two initialisation constants (`v5-integrity.md` §2; the
    reference `0x6c796765`, `0x74656462` at seed 0 and on the runtime path, except `layout`'s constants below);
  - m is the player's variant mask: 0 without per-player variants, else the mask of the variant the server assigned
    to the connection, one mask per connection and per build run, delivered from `ServerStorage.LyncVariants.<v>`
    (`v5-integrity.md` §2.4). A client holding no mask yet tags nothing; its tagged frames wait (§5.3).
- **Verification.** The candidates are the expected count e and e + 1 … e + 4 (reliable), or the extension x of the
  received seq (§4.4) and x − 4,096, x + 4,096, the two counters with the same low 12 bits beside it (unreliable). At
  each, the server hashes the input once, with the frame's own `caller` bit, and XORs the result with the tag: the
  player's own mask accepts the frame, and acceptance at e + j sets e to e + j + 1 and, for j ≥ 1, reports
  `reliableFramesMissing`; another variant's mask is remembered. With no acceptance the frame is dropped, e unchanged,
  as `tagVariantMismatch` when some candidate gave another variant's mask (`v5-integrity.md` §2), else `tagMismatch`.
  - **Hashes per frame:** at most 5 on the reliable lane and 3 on the unreliable lane, one per candidate, at any
    key state; plus up to 5 or 3 table lookups with variants (+0.24 µs native per failing 64 B frame
    `[generation-methods M13]`).
  - **Budget-refused frames are not hashed.** A reliable frame refused at §6.1 step 2 advances e by 1 without a tag
    check when it is tagged, which the header in clear tells (below: its extended `rcv` counts the frame that
    carried the connection's first `WELCOME`); an untagged one leaves e unchanged. While a `REKEY` is pending, a
    tagged one whose extended `rcv` is below F, the frame that carried that `REKEY` (Rekey, below), was tagged under
    the old key and also leaves e, now the new key's count, unchanged. Every tagged reliable frame an
    unmodified client sends took the next count, so e stays in step (a gap from raising calls is found by the
    lookahead on the next checked frame); a frame that took no count, forged or replayed, can only put e ahead of
    its own sender, whose later frames then fail toward `tagMismatchesExceeded`. Draft 3.5
    hashed them so the count stayed in step, which let a client make the server hash 16 KB frames at the engine's
    rate, about 500 calls a second, outside every budget: 656 µs per 16 KB frame native, 328 ms/s per player
    `[probes inbound-budgets claim 2]`.
  - **Bound.** So the tag CPU one client can cause is set by its budgets (§7.5): per second at most
    (5 × Br + 3 × Bu) × b + (5 × Fr + 3 × Fu) × f, with Br, Bu the byte and Fr, Fu the frame `perSecond` of the
    reliable and unreliable lanes, b the cost per covered byte and f per hash. Measured native b and f: 4.0 ns and
    196 ns for the milestone's form, 2.2 ns and 122 ns for a generated unrolled form; interpreted 30.7 ns and
    890 ns, and 28.5 ns and 757 ns `[probes inbound-budgets claim 2]`. At the default budgets (Fr 60, Fu 120,
    Br 8,192, Bu 16,384) that is 0.49 ms/s per player with the milestone's form and 0.28 ms/s unrolled when every
    frame fails, and 0.13 and 0.08 ms/s when every frame is accepted, plus the bursts once per refill.
- **Untagged frames.** Before a client has received its first `WELCOME` it sends only untagged frames that hold only
  `HELLO`s, with `caller` 0; they don't advance the count on either end, so the first tagged frame has count 0
  `[review-3 M7]`. With F_w the number of the downstream reliable frame that carried the connection's first
  `WELCOME` (§4.1's count, 1 for the first frame), a reliable frame is untagged exactly when no `WELCOME` has been
  sent or its extended `rcv` is below F_w; it must then decode canonically as untagged `HELLO`s with `caller` 0,
  else it is refused (rule 7). Every other frame is tagged.
- **Accepted reliable frames.** The server counts the reliable frames it has accepted from the player on this
  connection (tag accepted at §6.1 step 3), from 0, one integer per player, never reset by `REKEY` (unlike e); it is
  the reliable frame key that `v5-checks.md` §3.1 and §8.2 use.
- **Rekey.** `tagMismatchesExceeded` is 8 consecutive reliable frames failing the tag with no reliable frame accepted
  between them; the run restarts at 0 after each `tagMismatchesExceeded`. On a `tagMismatchesExceeded` the server sends
  `REKEY` with a fresh 8-byte nonce when none to that player is pending, or when one is pending and the eighth failing
  frame's extended `rcv` (highest candidate, §4.1) is at least F, the number of the downstream frame that carried the
  pending one; that `REKEY` replaces it. Otherwise it sends none (`rekeySent` 0). On sending, the server derives the new
  key as above, sets e = 0, records F, and from then on verifies that player's frames on both lanes under the new key
  only. A `REKEY` is pending until a reliable frame is accepted under its key. The client, decoding `REKEY`, derives the
  key, restarts its count at 0 and tags every later frame with it. No acknowledgement is sent: a frame that verifies
  under the new key shows that the client holds it.
  - **Why the receipt decides a resend.** With `rcv` below F the failures are frames the client sent before the
    `REKEY` reached it, still in flight, which a second `REKEY` would not help. With `rcv` at or above F the client
    received the frame and still fails: its `FireServer` raised on 5 or more frames again after it switched, or it
    refused that frame (§4.8), so it holds an older key. Without the resend that client's reliable lane would stay
    dropped for the session (draft 3.6's first text, review B1).
  - **Why the old key can stop at once.** On an unmodified client `tagMismatchesExceeded` means the count left the
    lookahead (`FireServer` raising on 5 or more consecutive frames, §7.3), so no later reliable frame under the old key
    can match. Reliable and unreliable frames the client tagged under the old key before it decoded `REKEY` are dropped
    as `tagMismatch`: the frames of one round trip (12 reliable frames at 200 ms and 60 frames a second), which can
    raise a further `tagMismatchesExceeded` with `rekeySent` 0.
  - **What a client can hold the server in.** A client that never switches keeps one `REKEY` pending: one flag, one
    key and F on the server, no extra hashing, and a further `REKEY` only per 8 failing frames that state `rcv` ≥ F. Draft 3.5 tried both keys while a
    `REKEY` was pending and cleared it only on `REKEY-ACK`, which the client need never send, so 8 bad tags doubled
    every later frame's hashing for the session (652 µs per 16 KB frame native).
  - **Bound.** Each `REKEY` after the first needs 8 failing reliable frames (the run restarts at each
    `tagMismatchesExceeded`): at the default `inbound.reliable.frames` (60/s, burst 240) at most 7.5 `REKEY` a second
    sustained and 30 from the burst, 10 B each, all to the player whose frames failed `[refusals-rejudged-2 R27]`. An
    unmodified client is rekeyed one `tagMismatchesExceeded` after each episode, against up to 60 s under draft 3.5's
    spacing.
- **Decision: tag width** `[refusals-rejudged-3 R28]`.
  - **Problem.** A sender without the key guesses the tag. The server tries one input at each of 5 counts per reliable
    frame and 3 extensions per unreliable frame (the caller bit is read in clear, and the old key is dropped at a
    `REKEY`, so neither adds inputs; another variant's mask is dropped as `tagVariantMismatch`, so masks add none), and
    Lync applies no consequence to failures, so a guessing sender is limited only by the frame budgets: 5 × R + 3 × U
    candidate tags a second for R reliable and U unreliable frames a second, 660 at the defaults (60 and 120, §7.5) and
    8000 at the range maxima (1000 and 1000).
  - **Options:** 16 bits (the research's choice: 2 B; one crafted frame accepted every 99.3 s at the defaults,
    after about 18,000 `tagMismatch` occurrences); **32 bits** (4 B; one acceptance per 75.3 days at the defaults
    and 6.2 days at the range maxima, after 1.17 × 10^9 `tagMismatch` occurrences at the defaults); a 64-bit output
    (HalfSipHash's 8-byte mode: 8 B, 934 B/s up for the busy model, §4.1's 654 + 280, and +3–10% per frame at 1 KB
    or more, +16–39% at 64 B or less `[probes security-costs #8]`). Trying two or four inputs per candidate, as a caller bit or a caller
    and identity bit inside the hash would, halves or quarters each 32-bit interval: 3.1 days and 37.3 h at the
    range maxima (`probes/refusals-rejudged/r3_tagwidth.out`).
  - **Choice: 32 bits,** the hash's natural output, at no CPU cost over 16. The research's argument for 16 bits
    ("32 bits only matters if acceptance were treated as authentication") assumed failures would be acted on; Lync
    only reports them, so the width alone has to bound acceptance. 64 bits is not taken: an accepted keyless frame
    gives its tool one frame of its choosing, which Lync's own API gives the same client with no guessing, and the
    chance `tagVariantMismatch` it would remove (one per 7.1 h at N = 256 variants at the defaults) arrives beside about
    4.6 × 10^6 `tagMismatch` occurrences from the same player, which identify it. Cost: 2 B more per upstream frame than
    16 bits, 140 B/s for the busy model (§4.1).
- **Decision: where the caller bit travels** `[client-self-checks U7]`.
  - **Problem.** The caller probe's source result has to reach the server for every frame, on both lanes, so that a
    fact can name the frame and its definition; a tool below the encoder must not be able to clear it at any
    `tag.coverBytes`; and it must neither loosen the keyless bound above nor raise the hashes a frame can cost.
  - **Options:** a count in `REPORT` (draft 3.5: reliable lane only, no per-frame evidence, editable past a small
    cover); a bit in the tag input's lane byte only (zero bytes, but the server must try both values at every
    candidate: up to 10 hashes per reliable frame and 6 per unreliable, and one keyless acceptance per 37.7 days at
    the defaults instead of 75.3, 3.1 days at the range maxima instead of 6.2);
    **a header bit that the lane byte repeats.**
  - **Choice: the header bit.** One hash per candidate, the keyless bound unchanged, and covered at
    `tag.coverBytes` 0 because the lane byte is always hashed. Cost: 0 or 1 B per upstream frame (§4.1). The identity
    probe's result stays in `REPORT` (`v5-integrity.md` §4): a second bit would buy per-frame evidence for a count
    `REPORT` already delivers within one flush (§5.1).
- **Replay window** `[client-security §3.2]`. The server extends each upstream unreliable `seq` (§4.4), verifies the
  tag at the extension and the two candidates beside it (Verification, above), then applies a 64-frame RFC 4303 bitmap: newer slides the window,
  unseen inside is accepted, seen inside is dropped (`unreliableSeqDuplicate`), and 64 or more behind the newest is
  dropped (`unreliableSeqOutOfRange`). Cost: 1.5 B per frame beyond the
  tag; 24 ns native per frame `[probes review-redundancy-2 inbound_hotpath]`.
- **Per-server id permutation** `[client-security §3.4]`. For each namespace and id space (§4.6), both ends
  derive a 64-bit space key K, the HalfSipHash-2-4 64-bit output keyed by S over (permutation nonce ‖ `02` ‖ the
  low 32 bits of the namespace's schema hash as u32le ‖ the space number as u8: 1 up, 2 down, 3 collections), and
  run Fisher–Yates from the last index down: for i = count − 1 … 1, j = (HalfSipHash-1-3's 32-bit output keyed by K,
  with the reference constants, over i as u32le) mod (i + 1), and the entries at i and j swap. Wire id =
  permutation[canonical id]. A permutation nonce of 0 is the identity (tests; a server never draws it). Every
  connection of a server derives the same tables from the per-server nonce, so downstream ids are one table per
  server.
  - **Decision: what seeds the shuffle** (review M2).
    - *Problem.* A capture holder who lacks S, or an on-client tool that learns one (canonical, wire) pair from its
      own sends, must not recover the tables by search; and one space's table must not give another's.
    - *Options:* a 32-bit seed under xorshift32, one seed for all three spaces XORed with the space number (draft
      3.6's first text: one known pair rejects a wrong candidate after one step, so 2^32 candidates fall in 15.6 s of
      one core native at 3.64 ns each, and one space's seed gives the other two,
      `probes/review-3.6-wire/perm_search.luau`); **a 64-bit key per space from the derivation, driving a keyed
      PRF per step.**
    - *Choice: the 64-bit key per space.* Each draw is one PRF output under K, so a known pair tests a guess of K
      at one hash: 2^64 guesses, about 3.6 × 10^4 years of one core at 61 ns each (the generated loop's fixed cost,
      `[probes inbound-budgets claim 2]`), whether the search targets K or S; and spaces differ in the PRF input, so
      one key says nothing of another. On the runtime path S = 0 and the keys follow from `WELCOME` as before, which
      prices only tools that hard-code a layout (§3.2). Cost: no bytes per frame, 4 B per server's first `WELCOME`
      (the nonce); count − 1 hashes of 4 B per space and three derivations per namespace, once per server and once
      per client connection: 61–196 ns per id native, 0.76–0.96 µs per id interpreted by form, so at most 0.04 and
      0.19 ms for 200 ids, against draft 3.5's 21 ns per id `[probes inbound-budgets claim 2]`. Mixing a per-build value into the
      seed `[generation-methods M4]` is not needed: K is per build through S.
- **Runtime-path layout** `[generation-methods M14]` (the decision is §3.2's). Each `WELCOME` carries `layout` u1
  for its namespace: 1 when the server's side of the namespace is the runtime path with `layout.vary` on (§7.5),
  else 0. With 1, both ends apply `v5-integrity.md` §2's field order, offsets and tag constants with the layout seed
  in place of `rotationSeed`; the layout seed is the 64-bit output of HalfSipHash-2-4 under a zero key over
  (permutation nonce ‖ the 6 ASCII bytes `layout`). S and masks stay at their identity. The layout
  is per server, upstream and downstream, so encode-once and `FireAllClients` hold, and a `REKEY` keeps it.
  - **Cost:** per definition, once per server and once per client connection, an IR copy of 1.5–4.3 µs interpreted
    and 0.8–3.0 µs native holding 1.7–3.8 KB; offsets +2 to +26 ns per bounded field per message; order and tag
    constants 0. One bit per `WELCOME`.
  - **A generated view can't follow it,** so the handshake refuses it on both ends: `HELLO` states its view's path
    (§4.6), and a server whose side of the namespace has `layout.vary` on answers a `HELLO` from a generated view
    with `MISMATCH` (the fact `layoutMismatch`). An unmodified server never sends `layout` 1 to a
    generated view; a generated view's decoder refuses a `WELCOME` that does (rule 3).

### 4.6 Namespaces, ids and control

- **Namespace index.** The server numbers namespaces 1, 2, … in the order of their first server-side use; the index
  is server-wide and reaches the client in `WELCOME`. A staged namespace's first server-side use is its release
  (`Lync.release(view, folder)` uses `view` first, then replicates the folder, `v5-collections.md` §13.2), so it
  takes the next index then
  and costs one namespace index in each toc segment that names it `[interest-rewind §12.3]`.
- **Id spaces.** Each namespace has three, numbered from 0 in definition-name order (ask before answer for a request):
  **up** (client events, streams, asks of client requests, answers of server requests), **down** (server events, asks of
  server requests, answers of client requests) and **collections**. A trap is an ordinary definition the developer
  declares (`v5-integrity.md` §3), so it takes its id like any other. Site ids of a woven build follow the generic up
  ids in canonical order (`v5-tooling.md` §5.5). All are permuted (§4.5). Ids are u(⌈log2 count⌉) of their space, so
  site ids cost ⌈log2(D + S)⌉ − ⌈log2 D⌉ bits per upstream run (D definitions, S sites) `[codecs-in-scripts §7.3]`. An
  id outside the receiving direction's space, or a message on a lane its definition doesn't use, is malformed (rule 7)
  `[review-redundancy-2 10]` `[review-3 M4]`.
- **Control messages** travel in control chunks of namespace 0 (§4.1), only on the reliable lane. Protocol version:
  1, which is everything this draft specifies: the version counts released protocols, and none has been released.

| Type | Direction | Fields |
|---|---|---|
| 0 `HELLO` | up | version u8; `buildId` u32; schema hash as two u32 (low, high); `idTableHash` u32 (`v5-tooling.md` §5.5; 0 exactly when `weave.ids` is `"generic"`, else the hash with 0 replaced by 1); `path` u1 (0 a generated view, 1 the runtime path); namespace name, length u(7) (1–64 B), bytes in the tail |
| 1 `WELCOME` | down | namespace index EG0; `layout` u1 (§4.5); in the connection's first `WELCOME` only: epoch f64, `stateRate` u6, `delay` u8 (4 ms units), key nonce as two u32, `tag.coverBytes` u15, permutation nonce u32, `callerProbe.callsPerProbe` u8, `callerProbe.maxProbesPerSecond` u6, `report.checkListenerCaller` u1, `report.runSelfCheck` u1 (`v5-integrity.md` §5), `clock.beaconSeconds` u4 (tenths of a second); until milestone 5, `callsPerProbe`, the two `report` bits and `clock.beaconSeconds` are 0 (off) and `maxProbesPerSecond` is 0 and ignored |
| 2 `MISMATCH` | down | none |
| 3 `REKEY` | down | key nonce as two u32 |
| 4 `DEPTH` | down | a stream's definition id u(w) of the up space, depth u5 (state ticks; `v5-collections.md` §15.2): sets the client's resend window for that stream (milestone 4) |
| 5 `REPORT` | up | `probes`, `identityMismatches`, `outerFramesMissing`, `framesMalformed`, `listenerCallerMismatches`, `selfCheckMismatches`, `selfCheckItem`, `selfCheckCase`, EG0 each (milestone 5, `v5-integrity.md` §4, §5) |
| 6 `BEACON` | up | ⌊`GetServerTimeNow()` × 1000⌋ mod 2^16 as u16 (milestone 5, `v5-integrity.md` §6) |
| 7 `RATE` | down | epoch f64, `stateRate` u6, `delay` u8 |

- **`delay`** is the interpolation delay D the server chose for that client, in 4 ms units, 0–1.02 s. The first
  `WELCOME` carries the initial D₀ = max(⌈500 / `stateRate`⌉, ⌈250 × `interpolation.minDelaySeconds`⌉) units, that is
  ⌈max(2 / `stateRate`, `minDelaySeconds`) / 4 ms⌉, with 250 × `minDelaySeconds` taken as the nearest integer when
  within 1e-9 of it (§4.9's tolerance), so it is computed exactly (25 at `stateRate` 20 and the default 0.1 s); the
  client only ever takes D from the wire. The client applies a `RATE`'s `delay` when it decodes the frame; the server
  reads which D was in force for an upstream message from that frame's receipt, when exact (§4.1, `v5-collections.md`
  §11.1, §12.3). The server sends `RATE` to every client when `state.ticksPerSecond` changes (applied no sooner than 4 s
  after the previous change, `v5-collections.md` §15.6) and to one client when its D changes, at most once a second: 78
  bits of fields, about 11 B per `RATE` with its chunk header `[interest-rewind §11.3]`.
- **`RATE` keeps the state tick continuous:** its epoch is now − T / the new `stateRate`, T the current tick, so ticks
  before and after it compare and the tick extensions of §4.1 stay valid.
- **When the client sends `REPORT` and `BEACON`.** Once the connection's frames can be tagged (after its first
  `WELCOME` and, with variants, once the mask is installed, `v5-integrity.md` §2.4), a `REPORT` with a non-zero
  `identityMismatches`, `outerFramesMissing`, `framesMalformed`, `listenerCallerMismatches` or
  `selfCheckMismatches` `[refusals-rejudged-3 R1]` `[refusals-rejudged-4 R18]`, and a due `BEACON`, are pending
  reliable data for §5.1's flush rule; at most one of each per frame, at most 60 `REPORT` frames a second, and one
  `BEACON` per `clock.beaconSeconds` period.
- **Sizes, tag included.** A `REPORT` alone is 19 bits of header, toc and chunk header plus 2⌊log2(c + 1)⌋ + 1 bits
  per field value c, rounded up to bytes, plus the 4 B tag: 8 B when one count is 1 and the rest 0, 14 B for the
  five counts at 60 and the self-check fields 0, 18 B for all six counts at 60 with a self-check failure at item
  202, case 3; `selfCheckItem` is below the item list's length and `selfCheckCase` below 5 (`v5-integrity.md` §5).
  `probes` makes nothing pending, so it grows between reports
  without bound (2.16 × 10^6 after 10 h at 60 probes a second, 43 bits). A `BEACON` alone is 9 B; with a `REPORT`,
  41 bits plus the `REPORT`'s field bits, rounded up, plus the tag: 11 B with one count of 1 and 17 B with five
  counts at 60 (`probes/design-3.6/golden_wire.luau`, SIZES) `[refusals-rejudged-2 R26]`
  `[clock-facts, the BEACON gap]`.
- **Effect during decode.** A control message takes effect as it is decoded, for the rest of its frame: a client
  decodes the chunks after a `WELCOME` with that namespace welcomed and, for the first `WELCOME`, the key, the
  permutation and the layout applied `[review-3 M3]`.
- **Field rules** (`f1fbfd7:src/transport/control.luau`):
  - A control chunk's rows are charged to `inbound.decodeUnits`, one element each at its row's decode units (§4.8,
    §7.5).
  - A `HELLO` name over 64 bytes is rule 2; a name of 0 bytes is rule 3.
  - Rule 3 refuses a `WELCOME` namespace index of 0, a `stateRate` outside 10–60, a `tag.coverBytes` over 16,384, a
    `clock.beaconSeconds` field of 1–4 (tenths), a `maxProbesPerSecond` of 0 with `callsPerProbe` above 0 (from
    milestone 5), a `layout` 1 in a generated view's `WELCOME`, and an epoch that is NaN or infinite, in `WELCOME`
    and in `RATE`; and a `DEPTH` id that is not a stream's.
  - A nonce is two u32, low first.
- **Handshake.** Namespace names are 1–64 bytes. A client view's first use sends `HELLO`; with per-player variants
  it still comes from the shared client shard at once, since variants differ only in the tag mask, which the
  server takes from its own assignment (§4.5). The server answers each `HELLO` in arrival order with `WELCOME` or
  `MISMATCH`, so the client matches answers to its `HELLO`s by order; it never sends a `WELCOME` before the
  namespace's `HELLO`, since the round trip that would save is the one in which the identity fields below are
  checked. A `HELLO` naming a namespace the server hasn't loaded yet is held for up to 10 s, then answered
  `MISMATCH` (the fact `helloNamespaceUnknown`); so the server must use every namespace within 10 s of a client's
  `HELLO` for it, since answers go in order and a longer hold would delay every later answer. Every namespace on a
  connection must come from one build run, or every one from the runtime path (`v5-integrity.md` §2.1). A mismatch
  of version, `buildId` (against the server's, and against the connection's first accepted `HELLO`), schema hash or
  `idTableHash` is `MISMATCH` (the fact `buildMismatch`); a `path` 0 `HELLO` for a namespace whose server side has
  `layout.vary` on (§4.5) is `MISMATCH` (the fact `layoutMismatch`). On any `MISMATCH` the client reports
  `mismatchReceived` natively once (§7.2; `MISMATCH` has no fields, so the client can't tell which of the three
  facts the server recorded) and drops that namespace's sends; the server reports the fact and drops its own sends
  to that player's namespace. A `WELCOME`
  comes before the held sends it releases (§5.3).
- **Hash.** HalfSipHash-2-4, zero key, 64-bit output, over the canonical serialization of §4.7 at seed 0. Per
  definition hashes are not sent; Studio and `lync check` name the differing definitions. No hash of the shard's
  code is sent: in the default `build.rotationSeed = "release"` an unmodified client's would always equal the server's
  expectation, a modified client sends any value, and a planner change that alters bytes is a protocol version
  change instead (§4.9) `[build-checks §4]`.

### 4.7 Schema hash input

The canonical serialization is a byte string; everything little-endian:
- `str` = u16 length + bytes; `num` = the f64 bits (−0 written as 0; NaN and ±inf are declaration errors);
  `u8`, `u16` as named; a boolean is a `u8`, 0 false and 1 true. Every codec parameter that is a number (bounds,
  steps, maxima, bit counts) is a `num` `[review-3 M6]`.
- Schema: `u8 1` (serialization version), namespace `str`, entry count u16 (definitions and string tables), then
  each entry in name order. A string table (`Lync.strings`, §4.11) is name `str`, kind u8 4, `maxEntries` `num`,
  `maxBytes` `num` (resolved), and nothing else. A definition is name `str`, kind u8 (1 event, 2 request,
  3 collection, 5 stream; 4 is the string table), `from` u8 (1 client, 2 server; collections 2, streams 1), lane
  u8 (1 reliable, 2 unreliable; requests and collections 1, streams 2), then the options in the order `data`,
  `reply`, `key`, `limit.perSecond`, `limit.burst`, `timeoutSeconds`, `maxRecords`, `priority`,
  `reliablePerSecond`, `ackEveryFrame`, `sealed`, `acked`, each as a presence u8 followed by its value: a codec, a
  `num`, a boolean, or for `sealed` its `sealed.maxOutstanding` `num` then `sealed.hideLength` boolean. An option
  the kind takes is present with its resolved value, defaulted or not (`timeoutSeconds` 10, `ackEveryFrame` false
  and `acked` false when omitted); an option the kind doesn't take, and an omitted option with no default (`data`,
  `limit`, `key`, `reliablePerSecond`, `sealed`), is absent. `ackEveryFrame` is taken by client-sent events and
  requests, `sealed` by server-sent reliable events, `acked` by collections (§3.4, `v5-collections.md` §5.1), and a
  stream takes `data` only, of a fixed single-row width (`streamCodecUnsupported`) whose namespace's chunks fit
  (`streamBytesExceeded`, `v5-collections.md` §15.2).
- Codec: a type u8, then parameters: 1 bool; 2 int (min `num`, max `num`); 3 unbounded int; 4 number (min, max,
  step); 5 f32; 6 f64; 7 angle (step); 8 string (max); 9 buffer (max); 10 vector3 (min, max, step); 11 vector3f32;
  12 direction (bits); 13 rotation (bits); 14 cframe (two codecs); 15 color3; 16 list enum (count u16, `str` each);
  17 Roblox enum (enum name `str`); 18 instance (class `str`, empty when absent); 19 optional (codec); 20 array
  (codec, max); 21 map (key codec, value codec, max); 22 union (count u16, then name `str` + each variant as a full
  codec, type 23); 23 record (count u16, then per field: name `str`, codec, `newest` u8, visibility u8 with 0 none,
  1 `:owner()`, 2 `:team()`, 3 `:gated()`); 24 custom (name `str`, version `num`); 25 convert (base codec;
  functions are not hashed); 26 role (u8: 1 `:input()`, 2 `:claim()`; then the codec); 27 intern (the table's name
  `str`, then the codec).
- Everything that changes bytes or what a decoder accepts is in it, so an unmodified client can't send on a
  direction, lane or form its definition doesn't use; server-view declarations (`:trap()`, `:refers()`, checks,
  `reactsTo`, `playout`) change neither and are not hashed. Serialization version 1 covers all of the above: like the
  protocol version, it counts released forms, and none has been released.
- Golden vector G6 (§4.10) fixes the bytes and the hash.

### 4.8 Canonical decode

A decoder returns a rule number rather than raising; any rule refuses the whole frame (`frameMalformed`, evidence
`rule`). Refusing whole frames is what makes skipping unnecessary: no lengths, so one chunk breaking a rule can't
desynchronise the tail `[review-1 B1]` `[review-redundancy 6]`. The rules:
1. the call is not one buffer plus at most one array of `Instance` or `nil`;
2. a count, length, index, EG code or quantized code past its maximum (a value equal to the maximum is legal); an
   offset code w outside its code interval (§4.3; the decoder checks w, then inverts it, then applies rules 3 and 6
   to q `[generation-methods M3]`); a column residual whose zigzag is n or more, n the column's interval size
   (§4.3; for sparse mode the value + 1, for frame of reference the base plus the u(width) value); an EG code with
   z > 53 or a value above 2^53 − 1; a string reference whose id is ≥ `maxEntries`, or names an entry not sent to
   this player (upstream) or not held (downstream); a strings chunk count above `maxEntries`; a definition of an
   id ≥ `maxEntries`, of an id already held, of a value another held entry of the table has, or bringing the
   table's held bytes past `maxBytes` (§4.11); downstream, an acked row that acceptance would apply naming a
   baseline tick the client doesn't hold, an age outside 1 … 31 or ages summing past 31, nb = 2, or nb = 3 in a
   collection with no linear leaf (`v5-collections.md` §5.1); upstream, a stream chunk with count above 33 or
   `back` above 63, or a second chunk of one stream in one frame (`v5-collections.md` §15.6);
3. a value outside its declared range or a refused value (§3.3), a control field outside its range (§4.6), or a
   stream chunk's `ref` 1 naming an index the server doesn't hold (`v5-collections.md` §15.3);
4. non-zero padding; bits and tail that don't meet exactly; a read of bits or tail past the bytes the frame has; or
   a tagged frame shorter than its 4 B tag;
5. map keys not strictly ascending, or definition ids not strictly ascending within a table's list (§4.11);
6. smallest-three components whose squares sum past 1, a non-canonical rotation code (§3.3), a zero direction,
   or a non-canonical toc (two adjacent segments of one namespace, or state or remove segments not in ascending
   namespace order); or a strings chunk whose every count is 0, two for one namespace, or not in ascending `ns`;
7. an id outside the receiving space; a message on a lane its definition doesn't use (a reliable event, an ask or an
   answer in an unreliable frame, an unreliable event in a reliable frame, a control chunk or rows in the wrong frame
   kind); a chunk for a namespace not welcomed when it is decoded, including a strings chunk, or one for a namespace
   with no table; a `receipt` `'1'` on an unreliable frame with no `ackEveryFrame` message; a frame that is untagged
   by §4.5's rule and is not untagged `HELLO`s with `caller` 0; outcome 3 (`limited`) in an upstream answer row
   (§5.2); or a control type in the wrong direction, or at a time the protocol doesn't allow (`BEACON` while beacons
   are off);
8. an upstream reliable frame over 16,384 B, or an unreliable frame over 1000 B;
9. an instance-list entry that no index references, that repeats an earlier entry, or that is out of the order of
   first reference; or a string definition that no later chunk of its frame references;
10. the frame's decode allowance goes negative (decode units on the server, elements on a client). The server
    reports it as `inboundDecodeUnitsExceeded`, not `frameMalformed`; a client counts it in `framesMalformed` (below).

Messages of a sealed definition follow `v5-checks.md` §9.3 and §9.6, whose refusals use rules 2, 3, 4 and 7; a
plaintext that breaks a rule at its reveal refuses the frame holding the reveal. The toc's counts (`n`,
`count − 1`) are never allocated by: each segment and chunk takes at least one bit, so the frame's length bounds
them, and a count past it fails rule 4.

The decoder runs under one `pcall` per frame; any raise inside it refuses the frame as `decoderRaised` and reports
natively (a Lync bug), so refusals cost a return, never a 2–3 µs raise `[diagnostics §9]`. The client's decoder
applies the same rules to downstream frames, with rule 10's allowance fixed at 2^22 elements per frame instead of a
bucket of decode units (below). Exp-Golomb codes are unique for a given k. Column mode, k, frame-of-reference base
(any base up to the minimum) and width (any width that fits), and literal or reference for an interned value are
free choices `[review-m1 t5]`. The instance array needs no cap of its own: each entry is charged 8 B at §6.1 step 2.

**Decision: bounding decode work** `[review-m1 B1]`.
- **Problem.** Bytes don't bound decoded elements. Column mode 0 codes a constant column in 0 bits per element, and
  0-bit elements (`{}`, `t.int(a, a)`) cost nothing in any mode. So `t.array(t.array({}, 65535), 7996)` decodes 3 bytes
  into 4.2 million tables (2.1–2.7 s, 384 MB), and `t.array(t.bool(), 65535)` puts about 16 s of decode in one
  16,384 B frame `[probes review-m1 p2]`. A run count alone can also promise millions of empty messages.
- **Options:**
  - (a) A static worst case per definition, refused at declaration. It bounds one message, but not how many
    messages a frame's run counts promise.
  - (b) A per-frame budget proportional to frame bytes, as in the v5 attempt's "decode allocation ≤ 1024 B per
    frame byte + 16 KiB". Constant columns an unmodified encoder writes reach about 21,845 elements per byte, so
    either the ratio admits the 3-byte frame above or it refuses those columns.
  - **(c) Both static rules, and a per-player bucket of decode units on the server that charges counts before
    allocation.**
- **Choice: (c).**
  - **An element** is one message of a run, one array element or one map pair; a control row and a new stream index
    are elements too (§4.6, `v5-collections.md` §15.7). **A decode unit** is §7.5's unit of decode price: an element
    whose own leaf count is L costs w = ⌈p(L) / 100 ns⌉ units, w computed per element kind by the planner.
  - **A message's worst case** W = 1 + E(data), where E(record) = Σ E(field), E(optional c) = E(convert c) = E(c),
    E(union) = the largest variant's, E(array c, max) = max × (1 + E(c)), E(map k v, max) = max × (1 + E(k) + E(v)),
    and every other codec is 0. A `t.custom`'s decode allocates in game code.
  - **At declaration:** W ≤ 65,536 elements (`messageElementsExceeded`), so `t.array(t.bool(), 65535)` fits; and
    no `elementEmpty` (§3.4).
  - **At run time, on the server only:** a per-player bucket of decode units, `inbound.decodeUnits` (§7.5). A frame's
    decode starts with an allowance of the bucket's whole units. The decoder subtracts each run, array and map count
    × that element kind's weight w (§7.5) before it allocates, and refuses the frame with rule 10 when the allowance
    goes negative. The units a frame used are then taken from the bucket, whether it was accepted or refused.
  - **Clients don't enforce the bucket.** The reason is who writes a client's downstream and what a refusal does
    there, not trust `[refusals-rejudged-2 R32]`: only the game's own server writes it through the engine (the other
    writer is an executor on that client injecting into its own view, which the refused-frame and injected-frame
    counts cover, `v5-integrity.md` §5), and a refused reliable frame loses events, answers and collection writes
    with no resend, so the client diverges for the rest of the session. A bucket would turn a server's heavy but
    canonical output, such as relays of every player's messages, into that divergence. The server counts what it
    sends instead (`elementsSent`, §7.4).
  - **The client's fixed allowance.** Its reader still starts each frame with an allowance of 2^22 (4,194,304)
    elements (§4.9); past it the frame is refused with rule 10 and counted (`framesMalformed`, §7.4), never
    reported as a fact, and an unmodified server splits before it (§4.1). The allowance bounds counts,
    not time: one frame at 2^22 elements decodes in 57–65 ms (a `false` bool column) to 175–190 ms (empty records)
    interpreted on the CLI, and 2.1–2.7 s with 384 MB for 4.2 million nested tables kept live
    (`probes/refusals-rejudged/r2_costs.out` §D, `[probes review-m1 p2]`). So it stops a count near 2^53 of
    zero-bit rows from running without end; a frame within it can hold a client for tenths of a second to seconds,
    and only the game's server can send one.
  - **Cost:** a multiply, a subtraction and a comparison per count, 3.1–3.4 ns native and about 13 ns interpreted
    for the subtraction and comparison (the multiply unmeasured). At the defaults (§7.5), a player can make the
    server decode at most `inbound.decodeUnits.perSecond` decode units a second beyond a burst of
    max(2 × U_max, 81,920), U_max the most units one client-sent message can cost; a unit is 100 ns of the bound's
    price, p(L) = 2,000 + 133 × L ns native per element of L leaves; measured per element, 440 ns with no payload
    to 7,611 ns at 128 fields native, 590–14,980 ns interpreted `[probes inbound-budgets claim 1]`. The budget
    derivation is §7.5's.

### 4.9 Constants

None is a knob `[review-redundancy-2 7]`. **Protocol constants** change bytes or what a decoder accepts, so they are
versioned by the protocol version in `HELLO`. **Runtime constants** change behaviour on one end only. A derivation
reads "chosen, unmeasured" where no measurement produced the value. **The planner's output is protocol:** after
the first release, any planner change that alters a frame for some (schema, `buildId`, `rotationSeed`) is a
protocol constant change and bumps the protocol version, and the golden set enforces it, since a changed vector
with an unchanged version fails CI `[build-checks §4.2]`; ROT (§4.10) is the vector that covers the per-build draws,
which no seed-0 vector does. Until then, version 1 is whatever this draft specifies. This is why `HELLO` carries no
code hash (§4.6).

### 4.11 String tables

`research/strings.md` is the source of this section `[strings §1–§2]`. The declaration surface (`Lync.strings`,
`:intern`, `internMisplaced`) is §3.3–§3.4's.

- **What enters.** A table is a schema entry, `names = Lync.strings({ maxEntries = 64 })`, owned by its namespace.
  A `t.string` field joins it with `:intern(names)`. Every value the server sends in an interned field becomes an
  entry the first time it is sent, while the table has room; nothing is counted or guessed. Which fields intern is
  the developer's declaration. Not allowed in an unreliable server-sent event's `data` (below) or a sealed event's.
- **Decision: who owns a table.**
  - *Problem.* A shared chunk's bits can't depend on its recipient (§4.2), and a table shared across recipients must
    not tell one recipient what another was sent: a cell chunk's recipients are the viewers near it, so a
    "define k" inside it would tell a viewer holding k that a co-recipient lacks k, which interest exists to
    withhold.
  - *Options:* per-connection tables (exact, but a chunk carrying an interned value becomes per-viewer and leaves
    `FireAllClients`); one server table with definitions inside shared chunks (one encoding, but the co-recipient
    leak above); **one server table per (namespace, table), definitions only in each recipient's own strings
    chunk.**
  - *Choice: the last, with entry ids drawn uniformly at random among free ids.* Shared chunks carry only
    references or literals, so they say nothing about co-recipients, and a viewer's strings chunk depends only on
    what it holds. With random ids, the id of the next definition a viewer receives is uniform over the ids it
    doesn't hold, whatever other players hold, so it can't tell how many entries exist or whether a value went to
    anyone before; the one bit it learns about others is that a table is full, from a literal outside the join hold.
    Random ids cost column bits only: +26 bits per 121-add catch-up at `maxEntries` 64, +94 B at 4,096.
- **Server state** per (server, namespace, table): id → string and string → id maps, a free-id list and a holder
  count per id; per (player, table) a bitset of the ids committed to that player.
- **Wire** (§4.1's grammar). An interned value is `entry:u1`, then `'1'` `id:u(w_t)` or `'0'` the field's plain
  `t.string` encoding, with w_t = ⌈log2 `maxEntries`⌉ of its table t; in column blocks it flattens as a two-variant
  union (§4.3). A strings chunk, downstream only and in namespace 0's state segment, is `ns`, then one list per table
  of that namespace in table order (tables numbered from 0 in name order): `count`, then `count` definitions, each
  an id u(w_t) and a length u(L_t), L_t = ⌈log2(m_t + 1)⌉ with m_t the largest `maxBytes` of the `t.string` codecs
  marked with t, the bytes in the tail (§4.2). One strings chunk per namespace per frame, ids strictly ascending
  within a list.
- **Who gets which definition.** At each flush, for every chunk the server encodes and every recipient r of it (known
  before encoding: targets, partition members, the viewers whose block covers a cell): for each interned value s,
  if s is no entry and the table has room, it becomes one at a random free id; if s is an entry and r's bit for it
  is 0, its definition joins r's strings chunk for this flush and the bit is set. The shared chunk writes `entry`
  `'1'` and the id. When the chunk goes to every player welcomed for the namespace and the entry's holder count
  equals their number, the per-recipient tests are skipped (bits are set only for welcomed players). A strings chunk
  is encoded once per distinct definition list in a flush; a recipient with a different list makes that flush per
  player, as catch-up and canary copies do.
- **Splits.** Each part of a split frame carries the definitions for the references in that part; the first part
  referencing an entry carries it.
- **The `WELCOME` frame.** A namespace's chunks can't precede its `WELCOME` (rule 7), and the `WELCOME` is a run,
  after every state chunk, so the frame carrying a player's `WELCOME` for N carries no definition for N. The
  server's join hold encodes held messages of N with literals, so its byte charge stays the exact encoded size, and a
  player whose `WELCOME` for N goes in this flush is not a recipient of N's shared chunks of this flush: what they
  carry for it joins its hold. From the next frame, references.
- **Decision: the unreliable lane.** An unreliable frame can arrive before the reliable frame holding a definition,
  so a reference in it is exact only for an entry the server knows the client decoded, and only an exact receipt
  says so; an inexact one would make an unmodified client refuse the frame. So `:intern` inside an unreliable
  server-sent event is `internMisplaced` rather than a silent literal; none of the four traffic models has such a
  field. Client-sent unreliable events may carry references: a client references only what it holds.
- **Literal or reference** is the encoder's choice: both decode. The reference encoder writes a literal exactly when
  the value is no entry and the table is at a cap, or the message is held.
- **Caps** (shared schema, hashed): `maxEntries` (ids) and `maxBytes` (the sum of live entries' lengths). A value
  becomes an entry only when live entries < `maxEntries` and live bytes + its length ≤ `maxBytes`; otherwise it
  travels as a literal (counter `stringLiteralsCapped`). No fact and no refusal at a cap.
- **Reclamation, never eviction of a held entry.** An id's holder count rises when a player's bit is set and falls
  for each set bit when that player's connection ends; at 0 the id returns to the free list and its string leaves
  both maps, applied at the start of a flush. Exact: a client references only ids it holds, every held id has its
  bit set, bits are never cleared during a connection, and a reused id reaches only players whose bit for it is 0,
  who never held the old value. No message is sent. LRU or explicit eviction would need an acknowledgement per
  eviction, since a reference sent before the client learned of it would resolve to the new string.
- **Survival.** Reliable downstream is ordered and lossless for the connection, so loss and reorder don't touch
  tables; `REKEY` doesn't (tables don't depend on key or count); a join is a new connection with an empty bitset and
  an empty client table; an audience or interest change clears no bit. A staged namespace's tables exist from its
  release.
- **The client** stores an entry when it decodes a definition in a reliable frame its decoder accepts (frames are
  refused whole, so a refused frame stores none) and keeps it for the connection. Rule 2 and rules 5–7 and 9 refuse
  what an unmodified server never writes: it sends a definition only to a player whose bit is 0, a player's held
  set is a subset of the live entries, and the definition precedes every reference on an ordered lane. A refused
  reliable frame (a Lync bug) loses its definitions, so later references fail too: the divergence §4.8 states for
  refused reliable frames.
- **Upstream references** (R33 form A, made exact). A client-sent interned value is the same form: `entry:u1`, then
  `id:u(w)` or the literal. The field names its table, so no table number is sent. A client may reference an entry
  as soon as it holds it, on either lane, with no acknowledgement: the server set the player's bit when it committed
  the definition, before the client could receive it. Before a namespace's `WELCOME` a client holds nothing, so its
  join hold holds literals. The server checks `id` < `maxEntries` and the player's bit (rule 2) and delivers its own
  string for the id, so steps 5–6 of §6.1 (canary matching, map key order, checks, validators, `limit`) see a
  `string` like any other. An upstream reference pins no server memory: it names an entry the server created from
  its own sends, and the per-player state is the fixed-size bitset. A client reaches table contents only through
  game code that relays client text into an interned downstream field, bounded by the caps; such fields are left
  unmarked. A table interns client-originated strings only that way (R33's form B, client-originated tables, is not
  adopted: no upstream traffic model gives its cap).
- **Cost** `[strings §3]`. Bytes, per recipient on the docs' models: the shooter's kill feed 51.86 → 6.82 B/s at
  `maxEntries` 64, the mmo's names 24.18 → 5.04 B/s, the tycoon's labels 80.48 → 22.54 B/s at 256. A literal costs
  1 bit more than a plain `t.string`, a reference 1 + w bits, a definition w + L_t bits more than the literal it
  replaces, so a value pays from its second sending to one player. Server, native: a reference 25.4–27.0 ns
  against 34.6–37.2 for a plain encode, 5.6–6.0 ns per further recipient's bit test, entry creation about
  150–170 ns; client decode of a reference 79.9–83.5 ns interpreted against 130–138 for a literal. Memory: 64 B per
  live entry and 4 B per id on the server plus ⌈`maxEntries` / 8⌉ B per player; 32–64 B per held entry on a client.
  Nothing for a frame without definitions or a namespace without tables.

## 5. Delivery

### 5.1 Flushing and state ticks

**Decision: who decides when frames leave.**
- **Problem.** v4 made the developer call `flush()` every frame; that caused a missed-flush detector,
  `Connect(Lync.flush)` throwing, and start-order rules `[v4 §8]`. Some cases still need control: before a
  destructive action, fixed-tick games, tests.
- **Options:** manual only; automatic only; **automatic by default, an explicit "send now" and a manual scheduler.**
- **Choice: the third.**
  - **Server.** It flushes at every `RunService.PostSimulation`.
  - **Client: a flush accumulator that keeps its remainder.** The client holds a (seconds), 1/60 at start. At
    each `PostSimulation` step, a ← min(a + Δ, 2/60), where Δ is the `os.clock()` time since the previous step;
    if then a ≥ 1/60, the step is a flush step: a ← a − 1/60, and the client flushes if anything is pending. A
    flush step with nothing pending still uses its 1/60, so the flush steps depend on frame times alone.
    - **Bound** (derived): at most one automatic flush per step, and at most 60·t + 2 in any t seconds, since a
      never exceeds 2/60. The cap carries one slot past a long frame and never two, so a hitch is not followed by
      a catch-up burst.
    - **Rates.** Modelled frame times (`probes/checks-telemetry/telemetry_samples.out` part A2): 60.0 Hz at a
      steady 60, 120, 144 or 240 FPS, 58.3 Hz at 60 FPS with 3% frame spikes, and every step below 60 FPS
      (29.1 Hz at 30 FPS) `[checks-telemetry T4 cause 1]`. Real frame-delta noise at a 60 FPS cap is unmeasured
      (§10).
    - **Rejected readings.** "At least 1/60 s since the last automatic flush" (draft 3.5's words) skips every
      frame that came in just under 1/60 s: 40.0 Hz at a steady 60 FPS and 47.8 Hz at 144 FPS in the same model,
      below the 60 Hz that §4.9 and §7.5 derive from. A slack threshold ("at least 0.9/60 s") gives 60.0 Hz at
      60 FPS but 47.8 Hz at 144 FPS.
  - **Pending data** is anything game code sent and, on the client after the connection's first `WELCOME`, two
    control messages of Lync's own: a `REPORT` with a non-zero count that `v5-integrity.md` §4 makes pending, and
    a due `BEACON` (`clock.beaconSeconds` of `os.clock()` time since the last frame carrying one was passed to
    `FireServer`, or since the first `WELCOME` for the first; its stamp is read when the frame is encoded).
    Either makes the flush send a reliable frame, with the game's data or alone; neither counts toward
    `flushMissing` or enters the join hold (§5.3). Both ride the one reliable frame per flush, so they add no
    frames beyond the bound above: at most 60·t + 2 forced frames in t seconds for `REPORT`, one per
    `clock.beaconSeconds` period for `BEACON` (sizes in §4.6) `[refusals-rejudged-2 R26]` `[clock-facts, the BEACON
    gap]`. Without them, a client that sends only unreliable data, or sends nothing, never delivers its counts,
    and fewer than 3 reliable sends a second give the beacon fit in 0–0.6% of epochs (`beacon_sim.out`,
    simulated).
  - **Late sends** after the flush point leave with the next flush step (up to 1/60 s of latency at 60 FPS and
    above, one frame below it).
  - **`Lync.flush()`** sends everything pending now: no arguments, idempotent, safe in handlers; for before
    `Player:Kick()`, before a teleport, and at the end of a custom tick. It doesn't touch the accumulator, so each
    call that sends a reliable frame is one frame beyond the 60·t + 2 bound, against `inbound.reliable.frames`
    (60 a second, burst 240, §7.5): a client that calls it steadily needs that budget raised by its call rate.
  - **Shutdown and leaving.** `BindToClose` flushes; a leaving player's pending frame is flushed first.
  - **`Lync.scheduler("manual")`**: frames leave only on `Lync.flush()`, Lync's own `REPORT` and `BEACON`
    included. When the 3rd consecutive `PostSimulation` step ends with game data pending and no `Lync.flush()`
    since it became pending, `flushMissing` is reported, once per wait: the next report needs a flush first.
- **Dispatch.** Each frame's messages are delivered in frame order, at an engine event, to the connections the
  definition has when the frame is dispatched. A message with none is the decision "a message with no handler" of
  §3.5, the one statement of that rule (`messagesUnhandled`; an ask is answered `unanswered`).

**Decision: how state ticks relate to flushes** `[review-1 B2]`. Reliable collection state goes every flush (or at
`reliablePerSecond`), so a `set` before a `fire` is always seen first; `:newest()` rows and the scheduler run on state
ticks. A flush is a state tick when T = ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋ has advanced since the
previous one; T may skip when frames slow. The rest is in `v5-collections.md`.

Under Server Authority, simulation input belongs in `InputActions` and remotes are off the synchronized timeline
`[state-sync §8.1]`: Lync carries intents, claims and state outside the simulation, and `Lync.tick()` (the current
state tick; on the client, the tick of the frame being dispatched) bridges the two. Unreliable messages may be lost
and are never resent.

### 5.2 Requests

- **Slots.** 16 per direction per connection, each with a 1-bit epoch. An ask row is `slot:u4 epoch:u1 payload`; an
  answer row is `slot:u4 epoch:u1 outcome:u2 [reply]`, outcome 0 value, 1 `rejected`, 2 `unanswered`,
  3 `limited`. Outcome 3 is downstream only: in an upstream answer row it is malformed (rule 7, §4.8), since no
  server-sent request takes `limit`. Request and answer runs are always single-row. An `invoke` that finds no free
  slot waits, its timeout already running from the call.
- **Every ask that is read is answered** `[review-2 B1]`:
  - the value;
  - `limited` when the server's `limit` bucket for the definition is empty (`limitExceeded`). It tells the asker to
    retry after about 1/`perSecond` s, and reveals nothing the client doesn't know, since it holds the same `limit`;
  - `rejected` when the answering side drops it after reading its slot because `validate` returned `false`,
    threw or yielded (§6.1's callback rule), a check's policy dropped it (`v5-checks.md`), the definition is a trap,
    or the ask holds a reference that doesn't resolve (`enumValueUnresolved`, `instanceUnresolved`,
    `instanceClassMismatch`, §7.3).
    These causes share one outcome on purpose: a trap must be indistinguishable from a `validate` refusal to the
    client that fired it (`v5-integrity.md` §3), so `rejected` is never split;
  - `unanswered` when the definition has no `handle` at dispatch (§3.5), or the handler threw or returned a reply
    the `reply` codec refuses (nil included, for a reply that isn't optional; reported natively as `valueRefused`
    at the definition).

  The answering side stops waiting for a handler `timeoutSeconds` after the ask's decode and sends nothing: the
  asker's timer started at its `invoke`, before the ask left, so it has already expired, and its result is
  `timedOut`.

  `handle` is a delivery, outside §6.1's callback rule, and may yield. A throwing `handle` is detected without
  `xpcall`: the wrapper marks the slot answered on return, and a slot whose
  thread is dead and unanswered threw (its error is reported natively by the engine); handlers that yielded are
  checked by `coroutine.status` once per flush `[diagnostics §1.4]`.
- **Frames that are dropped whole** (budget, tag, malformed) never reach their slots, so the asking side reclaims a
  slot when its caller times out and flips the slot's epoch. Every slot's epoch starts at 0.
- **Ending without an answer, server side.** A server `invoke(player, …)` pending when the player's
  `PlayerRemoving` fires returns `playerLeft`; one pending when a `BindToClose` callback runs returns
  `serverClosing` (whichever comes first). A client `invoke` ends only by an answer or its `timeoutSeconds`.
- **Checks, in order** `[review-3 m1]`. On the answering side, an ask for a slot in flight with the other epoch
  replaces the abandoned ask, whose answer is discarded; with the same epoch it is `requestSlotMismatch` case 3. On
  the asking side, an answer whose epoch differs from the slot's current epoch answers a request that already timed
  out: discarded and counted (`answersTimedOut`), not a fact. Otherwise, an answer for a free slot is
  `requestSlotMismatch` case 1,
  and one whose id is not the answer id of the slot's request is case 2.
- **Timing on server results** `[clock-facts §U4.1–§U4.2]`. By §7.3's one clock and one origin, which
  `requestAnswerBelowPing` and the reaction facts also read (`v5-integrity.md` §7.1), so a result, a fact and its
  evidence agree for one answer:
  - t_s is `os.clock()` at the flush that passed the ask's frame to `FireClient` (for a held ask, the flush that
    released it), not the `invoke` call; t_r is `os.clock()` at the decode of the frame holding the answer (§6.1
    step 4).

  | Field | Value | nil when |
  |---|---|---|
  | `roundTripSeconds` | t_r − t_s | no answer arrived |
  | `sendPingSeconds` | `Player:GetNetworkPing()` sampled at t_s | the ask never left (`timedOut` while waiting for a slot or in the join hold; `playerLeft` or `serverClosing` before its flush) |
  | `answerPingSeconds` | `Player:GetNetworkPing()` sampled at t_r | no answer arrived |
  | `minPingSeconds` | the ping bound at t_r (§7.3, `v5-integrity.md` §7.1): the number `requestAnswerBelowPing` scales by `answerTiming.pingFraction` | no answer arrived |

  An answer with outcome `rejected` or `unanswered` from the client has all four, which is why §3.5's type gives
  that arm `number` fields. An answer to a request that already timed out has no result (`answersTimedOut`).
  `requestAnswerBelowPing` fires on exactly the answers whose result shows `roundTripSeconds` <
  `answerTiming.pingFraction` × `minPingSeconds`.
  - **Resolution.** t_s is read at `PostSimulation`, and whether the engine sends in that frame is unmeasured (§10):
    up to one server frame (16.7 ms at 60 Hz) of `roundTripSeconds` may be server-side. t_r waits for the engine to
    run Lync's handler, quantized to the server frame. On the client, the ask waits for its next frame (up to 1/fps)
    and the answer for the next automatic flush (§5.1). `GetNetworkPing` is smoothed by an unmeasured constant (§10).
    The docs give the simulated distributions `[clock-facts §U4.3]`, marked simulated.
  - **Cost:** two numbers per slot (256 B per player for 16 slots, the same reads `requestAnswerBelowPing` takes per
    ask), one `GetNetworkPing` per answer (engine cost unmeasured, §10), and +15.7–25.4 ns native, +40–47 ns
    interpreted per result for the four fields `[clock-facts §U4.5]`. No bytes.
- **Not used:** `RemoteFunction`, `InvokeClient`.

### 5.3 Joining and holding

**Decision: what the client's join hold counts.**
- **Problem.** Before a namespace's `WELCOME` the client can't send that namespace's messages, and with per-player
  variants it can't tag any frame before its mask is installed (§4.5; `v5-integrity.md` §2.4). Held sends must
  then leave in frames the server accepts: within the minimum reliable byte burst (49,152 B) and the minimum
  decode-unit burst (§7.5), which are per player. Draft 3.5 counted bytes only, and loosely: messages of no payload cost 0 bits, so any number of
  them fit 32,768 B and their release could pass every element burst; and messages merged into runs at release
  gain run headers and column modes that a per-message byte count doesn't hold.
- **Options:** (a) charge each held message its definition's worst-case encoded size `[generation-methods M12]`:
  an upper bound, but `chat`'s `"gg"` (§3.4) is charged 201 B for 3, so the hold fills about 70 times sooner;
  (b) charge its single-row size under the seed-0 plan `[interest-rewind §13.2]`: exact for its row, but neither
  the run headers nor the column blocks of merged runs are counted, and zero-bit messages are still free; **(c)
  hold each message as a run of its own, charge exactly those bits, release it that way, and cap decode units
  too, per connection.**
- **Choice: (c).**
  - **Charge.** Each held send is encoded at `fire` as a run of its own: its id, count − 1 = 0, its instance count
    when its definition can hold instances, and its single-row encoding (§4.1, §4.3). It is charged those bits over
    8, plus its tail bytes, plus 8 B per instance (the server's charge, §6.1), and its decode units (the
    `inbound.decodeUnits` charge, §7.5).
  - **Caps, per connection,** because the server's buckets are per player, not per namespace: the holds of all
    the connection's namespaces together hold at most 32,768 B (the sum, rounded up) and H decode units, H =
    max(U_max, 40,960), where U_max is the most decode units one message of the client's client-sent definitions
    can cost. The server's minimum unit burst is max(2 × U_max, 81,920) over every namespace it has loaded
    (§7.5), so H is at most half of it, and every declared message fits the hold.
  - **Release.** Once a namespace's `WELCOME` has arrived and, with variants, the mask is installed, its held
    runs are written in call order, each still its own run, behind the `WELCOME`'s effect. The frames then carry
    exactly the charged bits plus each frame's header, toc, alignment and tag (at most 128 B per frame, §4.9). A run
    never straddles chunks, and first-fit packing leaves at most one frame half empty or less, so a full hold takes
    at most ⌈2 × 32,768 / 16,256⌉ = 5 frames and 640 B of framing: every namespace released together fits the
    49,152 B minimum byte burst, and H units leave half the minimum unit burst for control rows and the flush's
    other sends. Released messages lose column coding: at most 32,768 B once per connection.
  - **Past a cap** the send is dropped as `joinHoldBytesExceeded` (bytes) or `joinHoldDecodeUnitsExceeded` (decode
    units). An unreliable send while the namespace waits is `unreliableHoldUnsupported`, `waitingFor` 1 for the
    `WELCOME` and 2 for the mask only (§7.3).
  - Held sends stay encoded bytes in every case: variants differ only in the tag mask, applied when a frame is
    sent (§4.5). A held message of an interned field is encoded with literals, so its charge is its exact size
    (§4.11). A `HELLO` frame refused at the server's budgets is not resent: a client view sends one `HELLO` per
    namespace per connection (§4.6). `HELLO` never waits for the mask (§4.6), so a join with variants takes max(variant arrival, first
    use + one `HELLO`/`WELCOME` round trip) instead of their sum `[generation-methods M12]`; the arrival time is
    unmeasured (§10). A mask not installed 10 s after the first `WELCOME` is `variantMissing`
    (`v5-integrity.md` §10); the client keeps waiting.
- **Server.** Every target resolves at flush to its players. For a player whose namespace isn't welcomed yet, the
  server holds what it would send, up to 32,768 B per player, and sends it in the frames after the `WELCOME`'s
  control chunk (the same frame or later) `[review-3 M3]`; past that it drops the send and reports
  `joinHoldBytesExceeded` with that `player` (§7.3). So `fire(Lync.all, …)` during a join reaches the joiner late rather than never, and
  `FireAllClients` covers only welcomed players `[review-2 M8]`. A server `invoke(player, …)` before `WELCOME`
  waits in the hold, its timeout running. A sealed definition's reveal and discard rows are never refused by the
  hold; a seal row the hold refuses removes the player from that seal's recipients (`v5-checks.md` §9.5). So the
  hold can pass 32,768 B by at most 256 × 22 B = 5,632 B per sealed definition (`sealed.maxOutstanding` ≤ 256 rows
  of 22 B).
- **Collections** send catch-up adds after `WELCOME` (`v5-collections.md`).

### 5.4 `limit`

- **Client.** It throttles itself to `(perSecond, burst)` per definition. Over-limit reliable fires wait in a FIFO
  of at most `burst` messages and leave as tokens return; fires past that, and over-limit unreliable fires, are
  dropped (`limitQueueExceeded` for a reliable fire past the FIFO, `unreliableLimitExceeded` for an unreliable
  one, §7.3). A held message leaves after messages fired later on other definitions, so with `limit` delivery
  order holds per definition only; an over-limit `invoke` waits with its timeout running
  `[review-2 M12, m11]`.
- **Buckets.** Every bucket (inbound budgets, `limit` on both sides) starts full and refills continuously: on each
  use, tokens = min(capacity, tokens + rate × elapsed `os.clock()` time) `[review-3 M7]`. The client checks its FIFO
  at each flush.
- **Server.** A token bucket with rate `perSecond` and capacity `burst` + `slackSeconds` × `perSecond`, counting
  arrivals; `limit.slackSeconds` is the developer's (§3.4, default 2 s). It admits at most `burst` + (T +
  `slackSeconds`) × `perSecond` messages in any T seconds; the slack absorbs retransmission releasing queued frames
  together (p99 stall 850 ms under 5% bursty loss, simulated `[state-sync §1.3]`), and a client firing at its limit
  meets `limitExceeded` only after a stall longer than `slackSeconds` + `burst`/`perSecond` (derived).
  `slackSeconds` 0 admits exactly the declared rate and burst.
- **Not counted by send time** `[refusals-rejudged-3 R21]`. A send time stated in the frame and clamped to what the
  server can check (not after arrival, not before the previous one, at most `slackSeconds` old) gives a modified client
  exactly the arrival bucket's ceiling and an unmodified client no fewer drops (derived; `r3_limit.out`,
  simulated); a clock at the upstream reliable frame count / 60 drops 64–90% of an unmodified client's messages
  when it fires slower than 60 a second, and runs ahead for a client sending more frames. Neither does anything
  the slack doesn't.

### 5.5 Collections (milestone 4)

Collections replicate keyed records (or one singleton record) from server to clients. Structure and reliable
fields travel on the reliable lane, each chunk or piece encoded once per unit (an audience partition, an
interest cell, a team, or one record's piece) and copied to every viewer the unit covers; `:newest()` fields
travel as absolute rows encoded once per state tick into byte-aligned pieces, chosen per viewer by a budgeted
scheduler and repaired by notify. Prediction against acked baselines is the `acked` option (`v5-collections.md` §5.1). Records are
addressed by slot after their add. The full design, including the measured `:newest()` decision, catch-up, slots,
the scheduler, audiences, interest, visibility classes, scoped events, interpolation, rewind, staged namespaces
and input streams (`Lync.stream`, §15 there), is in `v5-collections.md`.

## 6. Security

### 6.1 Inbound pipeline (server)

In this order; no work proportional to a frame's size is done before the frame is paid for:
1. **Shape**, in constant time: the first argument is a buffer and the second, if present, a table, on one of
   Lync's remotes (`frameMalformed`, rule 1). Every call is counted here, before any budget (`framesReceived`, §7.4).
2. **Budgets.** Per player and lane, the frame bucket; then the byte bucket, charged `buffer.len` + 8 B per
   instance-list entry while the list is walked (each entry an `Instance` or `nil` at the next integer key, else
   rule 1), so the walk stops as soon as the charge passes the bucket's tokens: it reads at most tokens / 8 entries
   (`inboundFramesExceeded`, `inboundBytesExceeded`). A refused frame goes no further: it is never hashed or decoded. A refused
   reliable frame that its header in clear shows tagged advances the expected tag count by one, an untagged one
   leaves it (§4.5). Decode units are charged to `inbound.decodeUnits` during step 4 (§4.8, rule 10,
   `inboundDecodeUnitsExceeded`; units, §7.5).
3. **Integrity.** For a tagged frame, the tag, one hash per candidate count under the player's variant mask (at
   most 5 per reliable frame and 3 per unreliable frame; `tagMismatch`, `tagVariantMismatch`,
   `reliableFramesMissing`); on the unreliable lane, the replay window (§4.5; `unreliableSeqDuplicate`,
   `unreliableSeqOutOfRange`). An untagged frame (its header in clear says so, §4.5) is not hashed.
4. **Decode the whole frame** (§4.8) before delivering any of it, charging decode units before each count's
   allocation. An untagged frame must decode canonically as untagged `HELLO`s only, under the same charge, else rule
   7. Ids go through the permutation; a woven site's id is mapped to its definition here, so everything below sees
   the definition (`v5-tooling.md`). An ack naming a seq never sent to this player is ignored (`ackSeqUnknown`).
   A stream chunk's new indices are charged and stored here; steps 5–7 run for each index at its playout, in index
   order, and `limit` doesn't apply to streams (`v5-collections.md` §15.4).
5. **Per message, Lync's rules and report-only checks:** control messages; answers (`requestSlotMismatch`,
   `requestAnswerBelowPing`); enum and instance resolution (`enumValueUnresolved`, `instanceUnresolved`,
   `instanceClassMismatch`); reachability (`unreferencedMessageReceived`, `genericIdMessageReceived`); `limit`
   (`limitExceeded`); traps (`trapMessageReceived`: dropped); then the report-only checks, which never drop
   (`decoyKeyReceived`, `canaryReceived`, `reactionBeforeStimulus`, `reactionBelowFloor`,
   `reactionStimulusMissing`, and challenge answers: closing a challenge, or `challengeAnswerUnmatched`;
   `v5-integrity.md`). Dropped asks are answered `limited` (over `limit`) or `rejected` (§5.2); a trap's ask over
   `limit` is answered `limited` as any definition's is (`v5-integrity.md` §3).
6. **Per message, the developer's rules** (`v5-checks.md` §1.4): every declared check in declaration order
   (`withinExceeded`, `monotonicOutOfOrder`, `maxTotalExceeded`, `deriveMismatch`, `maxRateExceeded`), dropping
   the message when a failing check has `"drop"`; then the validator; then the checks' commit, for every message
   that passes step 6 (*accepted*, §3.5), whether or not a handler then receives it. Each check function and the
   validator runs by the callback rule below; `false` from the validator, or a throw or yield of either, drops the
   message (an ask is answered `rejected`) and counts `validatorsReturnedFalse`, `validatorsRaised`,
   `validatorsYielded`, `checkFunctionsRaised` or `checkFunctionsYielded`. The claim requirement is not a step: it
   is enforced when `connect` or `handle` is called (§3.3), so no message is dropped for it.
   - **6b. Sample** telemetry, on messages that pass step 6 and whose definition has a connection at step 7, one
     entry per frame (`v5-checks.md` §8.3).
7. **Delivery** to handlers in pooled threads; a message whose definition has no handler is counted
   (`messagesUnhandled`) and an ask is answered `unanswered` (§3.5, §5.2).

The report-only checks of step 5 see every message that passed `limit` and isn't a trap's, including those step 6
then drops, as they already see messages a validator refuses; the answer, resolution and reachability codes come
before `limit` and also see messages it drops.

**Decision: how Lync runs game callbacks.**
- **Problem.** Lync calls game functions whose result it needs before it can go on: validators and check functions
  in step 6, the collection callbacks of its state tick (`focus`, `predicate`, `weight`, class bindings and
  gates, `v5-collections.md` §8.7), decoy behaviors (`v5-integrity.md` §8) and canary `format` functions
  (`v5-integrity.md` §9). Luau lets a coroutine yield across
  `pcall`, so a function that yields on Lync's own thread suspends the pipeline or the tick for every player, and
  a re-entrancy flag sees it only at the next entry `[v5-collections.md §8.7]`.
- **Options:** `xpcall` on Lync's thread (28.3 ns per call; misses a yield until too late); a new thread per call
  (245.3 ns); **a reused runner thread per call site** (101.5 ns) (CLI, interpreted, best of 5 × 2 × 10^6 calls,
  `v5-checks.md` §1.7; native and Roblox's build unmeasured).
- **Choice: the runner,** one rule for every such function. Lync resumes the site's runner with the function and
  its arguments; the runner calls it and yields a completion marker with its results. After the resume, exactly
  one of three holds:
  - **returned:** the marker came back; the results are used;
  - **threw:** the resume returned false: reported natively as the site's raise code (`validatorRaised`,
    `checkFunctionRaised`; `v5-collections.md` §8.7 and `v5-integrity.md` §8–§9 name the others, §7.1 lists them),
    and a new runner is made;
  - **yielded:** the resume returned without the marker: reported natively as the site's yield code
    (`validatorYielded`, `checkFunctionYielded`, …); Lync calls `task.cancel` on the runner, which closes it so neither game code nor the
    engine resumes it (documented, creator-docs `task`), and makes a new one. Whatever the function did before it
    yielded stays done.
  On a throw or a yield the call gets its declared fallback at once: a validator's or check function's message is
  dropped (an ask answered `rejected`); a collection callback takes its declaration's `onError` or the fallback its
  file states. Native reports are spaced per (code, definition) per `observe.windowSeconds` (§7.2). Cost: about 73 ns per
  call over `xpcall`, plus one thread creation per fault.
- **Not covered:** handlers (`connect`), `handle` and observers. They are deliveries, not decisions: Lync needs no
  result from them before going on, they already run in pooled threads, and they may yield (a `handle` waits on a
  `DataStore`, say; §3.5, §5.2, §7.3).

**Measured** on the milestone build, native (interpreted): a frame holding only a header costs 1.9–2.2 µs

### 6.2 Client-side integrity

Client-side integrity is first-class. Each measure is judged by the cost it imposes on tampering against its own
runtime, wire, size and developer cost, and by principle 2 that cost is weighed, never a veto by itself: where it
matters, an option controls it. "A modified client with full memory access can defeat it" is not a reason on its
own. For the measures whose inputs vary per build, server, session or player (the tag and its key, the
permutation, layouts, per-build values, variant masks), a counter written against one has to be rebuilt or re-run
against the next; for the others the counter can be the same in every Lync game, and each measure's section states
which ("Universal counter", `v5-integrity.md`), so a game knows what a fact from it costs a tool. Every measure only
reports; none replaces a server check or applies a consequence.

The table lists each measure once, with the server-side facts and the withholding that price the same tools; the
server's own checks of what it receives are §6.1.

  given only when there is exactly one.
- **What names and text may say.** Code names, evidence and counter names, `[Lync]` messages, registry pages
  (prose, fixes and examples) and the published docs state what was observed, the requirement it was checked
  against, what Lync did, and the documented causes. They never characterise a sender's intent, trustworthiness or
  skill, or a value's quality, and never recommend a consequence for a player. The registry test enforces a
  backstop on every code name, evidence field name, page body and `example`, case-insensitively at word
  boundaries: `anomal*`, `abuse*`, `attack*`, `bad`, `cheat*`, `exploit*`, `flagged`, `honest*`, `hostile`,

  page passing it can still break the rule, and adding a code includes checking its page against the rule.

  list (`Missing`, `Unknown`, `Duplicate`, `Mismatch`, `OutOfRange`, `OutOfOrder`, `WrongType`, `Unsupported`,
  `Misplaced`, `Exceeded`, `Malformed`, `Refused`, `Unresolved`, `Unmatched`, `Unverified`, `Raised`, `Yielded`,
  `Below…`, `Before…`, `Received`, `Reported`, `Found`, `Failed`, `Shadowed`, `Indivisible`, `Empty`, `Disabled`);
  outcome codes come from the outcome family's list; a fact whose evidence is client-stated starts with `client`, and no other does;

  `clockMilliseconds`); identifiers use Roblox's spelling (`behavior`). The registry test checks each by regex beside the word list;
  `internal` is the one code outside it.
- **Positions.** Caller errors walk `debug.info` to the first frame outside Lync and its shards, never
  `error(msg, 2)`, whose meaning differs between Studio (-O1) and live (-O2) `[diagnostics §1.1]`; the walk costs
  133–492 ns interpreted and 191–619 ns native for 1–5 Lync frames on the stack `[diagnostics §1.3]`, only on
  failure. Schema constructors record `debug.info(2, "sl")` (the line where the call starts) once, and declaration
  errors use it. A woven call site (`v5-tooling.md`) passes its own source line to the cold `fail()` as a constant,
  so its caller errors skip the walk: one `LOADN` in the cold branch `[codecs-in-scripts §5]`.
- **Values** are rendered by one `show()` on the failure path only: strings quoted, escaped and cut at 40 bytes;
  buffers as their size; instances as `Instance(ClassName)`, never their names `[diagnostics §3.2]`. Checks call a
  cold `fail()` and never format eagerly (+95–117 ns per value otherwise `[diagnostics §9]`).
- **Lync throws strings only**: a table error breaks `xpcall(f, debug.traceback)` `[diagnostics §1.2]`.

### 7.3 Facts

**The event.** `Lync.observe(fn)` returns a connection. Each fact is delivered to each observer in a pooled thread,
so a throwing observer is reported natively and a yielding one holds only itself. A fact is frozen:
`{ code, player?, namespace?, definition?, count, firstTime, lastTime, evidence }`, discriminated on `code` so
`evidence` narrows in Luau and TypeScript on both solvers `[probes review-2 t3]`. `player` is the sender on the
server, the player concerned for a server-local fact (a held send, a missed flush), and nil for a client's local
facts; names come from the receiving side's schema; `firstTime`/`lastTime` are `GetServerTimeNow()`; evidence is numbers only (`lane` is 0 reliable, 1 unreliable).

**Decision: one clock and one origin for server timings.**
- **Problem.** `requestAnswerBelowPing`, `challengeAnswerBelowPing`, the reaction facts, a server request
  result's `roundTripSeconds` and a challenge's `closeElapsedSeconds` each compare a time from a server send to a
  client's reply with a ping bound, and the same reply can feed two of them (a result and its
  `requestAnswerBelowPing`). The research timed them on two clocks from two origins: server
  `os.clock()` from the flush that passed the frame to the engine `[clock-facts U4.1]` `[server-facts U10.4]`, and
  `GetServerTimeNow()` from the `Lync.challenge` call `[decoy-challenge-facts §6]`. Two clocks give one reply two
  values, and the call origin adds up to one server frame of Lync's own wait to the client's time.
- **Options:** (a) `os.clock()`, from the sending flush; (b) `GetServerTimeNow()`, from the call; (c) each feature
  its own.
- **Choice: (a), for every duration Lync measures on the server.** `os.clock()` is the server's local clock with
  sub-microsecond resolution (documented), and `GetServerTimeNow()` is synchronised time that Lync's beacon already
  keeps out of its arrivals so as to add no slope of its own `[clock-facts U3.2 rule 1]`. Rules:
  - **t_s** is `os.clock()` at the flush that passed the frame holding the stimulus to the engine (for a held send,
    the flush that released it). For a challenge, whose token rides a message of the game's own that Lync doesn't
    identify, t_s is the server's first flush step after the `Lync.challenge` call, whether or not it passes a frame
    to that player: the earliest flush that can
    carry the token. Game code sending it later lengthens the measured time, which can miss a
    `challengeAnswerBelowPing`, never make one.
  - **t_r** is `os.clock()` when the frame holding the reply is decoded (§6.1 step 4).
  - **The bound** is one per player, `[server-facts U10.4]`'s: the minimum over the last 10 s of
    `Player:GetNetworkPing()` samples and of Lync's own ack round trips (`v5-integrity.md` §7.1).
  - **Instants** shown to game code (`firstTime`, `lastTime`, a challenge's `deadlineTime`, an atom's `serverTime`) are
    `GetServerTimeNow()`; no duration is a difference of two clocks.

Each fact has one row, in one file. Facts never carry bytes from a client. **One code per subject and fix:** a
trigger gets its own code when its subject or its fix differs; triggers with one subject and one fix share a code,
with an evidence field naming which one fired and the known causes listed per value (`requestSlotMismatch` `case`,
`buildMismatch`'s four flags, `unreliableHoldUnsupported` `waitingFor`). `v5-tooling.md` §3.2 states the same rule
for build codes.

**Delivery limits** protect the server; they never hide an occurrence `[diagnostics §5.2]`:
- **Coalescing.** A key is (player, code, namespace, definition), and for the five check facts also
  `checkIndex`, whose closing fact carries `peakObserved` and `peakBound` (`v5-checks.md` §1.5); its window opens
  at its first occurrence, which is delivered at once, and closes `observe.windowSeconds` later (`os.clock()`
  seconds; `firstTime` and `lastTime` are `GetServerTimeNow()`). If more occurred, one fact at close carries their `count` and the last occurrence's
  evidence. Windows are swept once per flush.
- **Caps.** At most `observe.maxFactsPerPlayer` facts per player per window and `observe.maxFacts` per server.
  Occurrences past a cap are counted per player and code; at window close each such player gets one
  `observeCapExceeded`, exempt from the caps. Memory per player: at most `maxFactsPerPlayer` keys plus one count
  per code.
- **Caps' windows** are per player, each opening at that player's first occurrence after its last window closed.
- **One record, three outputs.** Recording an occurrence also increments its code's counter
  (`factsRecorded.<code>`, uncapped) and feeds the console, so facts, counters and console can't disagree; the facts state is built with the
  counters and the console. A `Fact` is frozen when delivered.
- Each occurrence costs a key lookup and an increment: 20.5 ns native `[diagnostics §9]`.

### 7.5 Configuration

One server-only call; never in shared code or `lync.toml`. It never throws for being late, with one exception:
options carried in `WELCOME` apply to connections first welcomed after the call; server-only options apply from
the next flush; `state.ticksPerSecond` applies at the next state tick at least 4 s after the previous applied
change (a sooner value waits; §4.9, `v5-collections.md` §15.6), and every connected client gets it in `RATE`
`[review-2 M6]`. The exception is `layout.vary`, read once at the server's first `WELCOME`: a later call giving it
another value throws `callOptionMismatch` (§3.2). A key it doesn't take throws `callOptionUnknown`; a value out of
range or a fraction for an integer option, `callOptionOutOfRange`; a value of another Luau type,
`callOptionWrongType`; each at the caller (§7.1). Server-only policy kept in `ConfigService` stays game
code that calls `Lync.configure` after its own read, since Lync's start never yields `[generation-methods M11]`.

```luau
Lync.configure({ state = { ticksPerSecond = 20, bytesPerSecond = 16000 }, observe = { windowSeconds = 30 } })
```

Every bucket option is `{ perSecond: number (real), burst: integer }`.

**Decision: the inbound budget defaults** `[probes inbound-budgets claims 1–4]` `[reviews v5-3.6-runtime §7.5]`.
- **Problem.** The five inbound buckets are what bound the server CPU one player can cause, but draft 3.5's
  defaults had no basis: at them, a client sending the costliest frames the buckets admit costs 24.2 ms/s per
  player native on a busy-like schema (242% of one core at 100 players), 78 ms/s with a 32-field `t.bool()`
  record and 155 ms/s with a 128-field one, while the busy model (§4.1) itself costs 0.32 ms/s. An element's CPU
  depends on its codec (440 ns with no payload, 7,611 ns for 128 fields, 8.9 µs for 64 empty arrays), so a budget
  that counts every element alike either refuses narrow traffic or admits wide traffic unbounded, and the widest
  element and the longest message of a schema, taken from different definitions, multiply in one frame.
- **Decode units.** The `inbound.decodeUnits` bucket counts decode units, not elements. Each element (a message of a
  run, an array element, a map pair, §4.8; a control row too) costs w = ⌈p(L) / 100 ns⌉ units, where
  p(L) = p_0 + p_1 × L and L is that element's own leaf count: each scalar leaf 1, `t.vector3`, `t.color3` and
  `t.vector3f32` 3, `t.direction` 2, `t.rotation` 4, `t.cframe` 7, an optional's presence 1 more, a union's tag 1,
  each array or map field (present or not) 2, counting outside the elements nested in it. The planner computes w
  per element kind of every codec a client writes: event and ask `data`, the `reply` of server-asked requests, each
  stream's index (its `data`; `v5-collections.md` §15.4), and Lync's upstream control rows. The decoder subtracts count × w before it allocates (rule 10, §4.8); one multiply
  per count. A narrow message then pays its own price, and one frame's cost is bounded by its allowance in units,
  whatever the schema.
- **The bound.** Per player and second, for budgets Fr, Fu (frames), Br, Bu (bytes) and E (units per second):

  CPU ≤ (1 + μ) × (c_f,r·Fr + c_f,u·Fu + c_b,r·Br + c_b,u·Bu + 100 ns·E + C_s), plus each bucket's burst at its
  price once per refill; one frame costs at most (1 + μ) × (c_f + c_b × its charge + 100 ns × its units + its
  copy parses).

  C_s is the redundant-copy parse term of input streams, 0 for a schema with none: Fu × Σ_streams 33 × c_copy, at
  most 33 copies per stream per frame (rule 2), c_copy 64.7 ns native for a 42-bit stream, so 0.26 ms/s per such
  stream at Fu 120 (`v5-collections.md` §15.7). A stream's new indices are charged decode units like any element;
  its redundant copies are charged bytes only and take this term instead, since a copy charged at its index's
  weight (28 units, 2,798 ns) would cost 43–98× its parse and refuse an unmodified 60 Hz stream's frames
  (`v5-collections.md` §15.7).

  | Price | Value (provisional) | What it is |
  |---|---|---|
  | c_f,r | 3.76 µs (+0.24 with variants) | a reliable frame with only a header, accepted at e + 4 after 5 hashes, the costliest per-frame path |
  | c_f,u | 2.9 µs (+0.24 with variants) | an unreliable frame with only a header, failing all 3 candidates, each hashed |
  | c_b,r | 23.75 ns/B | a reliable frame at e + 4, 5 hashes over the covered bytes plus byte-linear decode (a 15,906 B string), 23 ns/B, plus the instance-list walk, 6 ns per 8 B entry |
  | c_b,u | 13.95 ns/B | 3 hashes over a 1,000 B unreliable frame, 13.2 ns/B, plus the walk |
  | p_0, p_1 | 2,000 ns, 133 ns | an upper fit over every median measured: a message alone in a frame, one-message runs, random 32-field `t.bool()` columns (133 ns a field), constant 128-field columns; arrays and maps at weight 2 cover 64 empty arrays per message (8.9 µs) |
  | μ | 0 (provisional) | the margin over the measured fits, set by `probes/inbound-bound-2/RESULTS.md` (0, 10% or 25%) |

  Values are those of `[probes inbound-budgets claims 1–2]` corrected by the review's re-measurement
  (`probes/review-3.6-runtime/`), on the CLI (Luau 0.742, milestone decoder, native), and are provisional:
  `probes/inbound-bound-2/RESULTS.md` re-measures every price over the full shape set (arrays, maps, unions,
  strings and buffers at e + 4, untagged `HELLO`s, instance lists) and sets μ; it was still being written at this
  draft, and its figures replace these. The defaults below follow from the prices by the rule
  stated, so a new price changes the numbers, not the rule.
  - **Not in the bound:** game code (validators, check functions, handlers) and declared checks (47–84 ns each,
    `v5-checks.md`); the runner thread per game function (about 73 ns, §6.1); `REKEY`, at most 7.5 a second
    (§4.5), each a key derivation (0.31 µs native, derived) and one engine call (unpriced, §10); frames refused at
    the frame bucket, which cost the constant-time shape check and one bucket read, at most the engine's call rate
    (about 500 calls a second per client per remote type, documented `[client-security §2.1]`) × at most 1.0 µs
    (the measured non-hash, non-decode part of a header-only frame, an upper bound): ≤ 1.0 ms/s per player; and the
    server build (Roblox's native code generator, or interpreted modules if Lync's don't run native: interpreted
    milestone figures are 1.7–2.0× the native, §10).
- **Options for the target:** (a) 1 ms/s per player (10% of one core with 100 players all at every limit): with
  frames at Lync's automatic schedule (0.57 ms/s), it leaves byte budgets of about 1,024 and 5,120 B/s (6× the
  busy model's) and 3,300 units a second (1.7× the busy model's 1,950), provisional; (b) **2 ms/s per player (0.2%
  of one core per player at every limit; 20% with 100 such players)**; (c) no target, as in draft 3.5.
- **Choice: (b), chosen,** for about 5× room over the busy model on units and 19–48× on bytes, against (a)'s 1.7×
  and 6×. What would change it: Roblox server measurements of the prices (§10). A game with fewer players at once
  can raise every budget by the same factor for the same total; that is the game's choice.
- **Allocation** (rule, then provisional figures):
  - frames: `reliable.frames` 60/s, the automatic flush bound (§5.1); `unreliable.frames` 120/s, two per
    automatic flush (574 µs);
  - bytes: `reliable.bytes` 8,192 B/s (48× the busy model's 170 B/s); `unreliable.bytes` 16,384 B/s (19× its
    850 B/s) (423 µs);
  - units: `inbound.decodeUnits.perSecond` = ⌊(2,000 µs / (1 + μ) − frames − bytes − C_s) / 100 ns⌋ rounded down to
    a multiple of 1,000: 10,000 units/s at μ = 0 with no stream (7,000 with one 42-bit stream), against the busy
    model's 1,950 (60 `move6` inputs at 28 units, 10 actions at 27);
  - **Bursts** (chosen): 240 reliable and 240 unreliable frames (a 4 s reliable stall at 60/s); 49,152 B reliable
    (a released join hold plus framing, §5.3); unreliable 32,768 B, minimum 1,000 + 8 × N_u, N_u the most
    instance-list entries an unmodified client's unreliable frame of the loaded schema can carry (planner); units
    max(2 × U_max, 81,920), U_max the most units one client-sent message can cost, so every declared message fits
    and the per-connection join hold (at most half of it, §5.3) fits; 81,920 is 4,096 elements of no payload. A
    full refill costs at most (1 + μ) × (0.90 + 1.17 + 0.70 + 0.46 ms + 100 ns × the unit burst): 8.2 ms of units
    at 81,920, and 100 ns × 2 × U_max for a schema with a long message (2 × 1.44 × 10^6 units, 288 ms, for one
    `t.array(t.bool(), 65535)`). That is also the most one frame can cost, and `report.md` lists U_max, the unit
    burst and its cost per namespace (`v5-tooling.md`).
  - **Schema.** "The schema" is every namespace loaded on the server; a namespace loading with a larger U_max or
    N_u raises the bursts, and one declaring a stream lowers the units default by its C_s, from the next flush; a
    value the game set is never changed.
- **The client's allowance stays in elements** (2^22 per frame, §4.8, §4.9). Units price one player's cost to a
  shared server against a target; a client decodes only what the game's own server writes, so its allowance only
  stops an unbounded count, and pricing it in units would need device decode costs, which are unmeasured (§10).

## 8. Extensions and tools

- **Seams.** `t.custom({ encode, decode, maxBits | maxBytes, luauType, tsType, name, version })` declares a leaf
  codec; `t.convert(base, decode, encode)` transforms one, inferring both ways `[probes review-2 t1]`. Runtime
  seams: `transport` (remotes, or in-process for tests), `scheduler`, `clock`, `roster`, the observer, and a test
  seam that pins the key nonce, the permutation nonce, the seeds and string entry ids (the golden fixtures: key
  nonce `00 … 07`, permutation nonce 0, §4.10) and claims console and native-report output. A seam with nothing registered
  is bound at start to Lync's default, which the hot paths call through a local with no nil test; its cost against
  a direct call is unmeasured (milestone 2's benchmarks run with the default seams). There is no middleware:
  rejection is `validate` and the declared checks, observation the observer, transformation game code.
- **The `transport` seam is where whole-frame transforms go** `[refusals-rejudged-3 R39]`. Its interface is
  `send(player, lane, frame, instances)`, `broadcast(lane, frame, instances)` (the `FireAllClients` call) and
  `receive(handler)` with the raw remote arguments. A game wrapping it sees Lync's frames after splitting and
  tagging, so frames, golden vectors, hash and types don't change. Its docs state four facts: a wrapped `receive`
  runs game code on raw remote arguments before §6.1's shape and budget checks, so what it costs on that input is
  outside Lync's bound (§7.5); wrappers that differ between client and server fail every frame, as `tagMismatch`
  (reliable) and `frameMalformed` or `tagMismatch` (unreliable), which those facts list as a cause; with a
  registered seam the client's listener-caller check is off, so `listenerCallerMismatches` stays 0
  (`v5-integrity.md` §5); and a client wrapper that alters downstream frames makes the client refuse them, counted
  in `framesMalformed` and reported as `clientFramesMalformed`.
  No per-frame hook beside it: compression is the engine's, and per field `t.custom`'s; concealment from the
  recipient is sealed delivery's (`v5-checks.md`).
- **Specified elsewhere, built in the milestones of §10:** collections with acked rows, interest, visibility
  classes, scoped events, interpolation, rewind, staged namespaces and input streams (`v5-collections.md`; interest is built in, so the
  `scheduler` seam no longer serves it); client-side integrity and the server facts beside it
  (`v5-integrity.md`); checks, `derive`, claims, telemetry and sealed delivery (`v5-checks.md`).
- **Tools** (milestones 3 and 6: shards, `.d.ts`, `manifest.json`, `report.md`, `lync.toml`, the CLI and its output
  formats and exit codes, the Studio plugin, inspector and profiler adapter) are specified in `v5-tooling.md`.

## 9. Testing

- **Headless CI** on the CLI host: unit and property tests (seeded, shrinking); the differential test of both paths
  (§2); golden frames (`.bin` plus a JSON index, at seed 0 and identity permutation, reached in a running world
  through the test seam's key nonce `00 … 07` and permutation nonce 0, §4.10, §8) and golden hashes; an
  in-process two-sided world over a simulated network with loss, delay, duplication and reorder (below); modified
  clients in that world (raw sender, replayer, forger, key extractor, API driver, injector) asserting that each fact
  fires on exactly its trigger, and never for an unmodified client outside its known causes; type tests under both
  solvers for Luau and TypeScript.
- **Diagnostics are asserted by code, position and evidence, never by prose** `[diagnostics §10]`:
  `expectThrow(fn, { code, at, subject, path })` and `expectFact(world, { code, player, count, evidence })`. Every
  `[Lync]` line and native report must be claimed by the test. Each registry page's `example` is a golden message,
  compared byte for byte. CI fails on a code that is used but unregistered, registered but never raised, untested,
  or deleted rather than retired, on a code name that breaks §7.1's name grammar, and on any `example` that breaks
  its message grammar.
- **The simulated network** (`f1fbfd7:test/support/net.luau`, `world.luau`). Per client link and direction, seeded
  (xorshift128 seeded through murmur3's finalizer), on a virtual clock that delivers what is due and then runs every
  runtime's step. Reliable frames keep their order; a stall holds every frame due during it until it ends, then
  releases them in order. Unreliable frames over the size limit are dropped, then they pass a Gilbert–Elliott burst
  state and independent loss, each arriving after latency plus its own jitter (so they reorder), with a chance of
  a second copy. The default network model (`Net.DEFAULT`):

  | Parameter | Unit | Default | Meaning |
  |---|---|---|---|
  | `latency` | s | 0.05 | one-way base delay |
  | `jitter` | s | 0.02 | uniform extra delay per frame |
  | `loss` | fraction | 0.05 | unreliable frames dropped independently |
  | `burst` | `{ enter, leave }` per frame | `{ 0, 1 }` (off) | the loss state drops every unreliable frame |
  | `duplicate` | fraction | 0 | unreliable frames delivered twice |
  | `stall` | `{ chance per s, seconds }` | `{ 0.05, 0.3 }` | stalls start as a Poisson process |
  | `fps` | Hz | 60 | the client's step rate; 30, 144 and 240 test the flush accumulator |
  | `frameNoiseFraction` | fraction | 0.01 | each step's duration drawn uniformly within ± this share of 1/`fps` |
  | `unreliableLimit` | B | 1000 | larger unreliable frames are dropped, as the engine does |

  Its own tests check rates within 0.01 absolute of their settings over 10^5 frames. Unmodified clients on the
  default model must raise no fact; that includes `monotonic` on the unreliable lane, where 1.31–1.33% of frames
  arrive behind a later one and only ordering by frame key keeps the check silent
  `[checks-telemetry C2]` (`monotonic_reorder.out`). Each known cause in §7.3, `v5-integrity.md` §10 and
  `v5-checks.md` gets its own run, which must raise exactly its fact, and so does each modified-client case.
- **Runtime rules with their own tests:** the flush accumulator flushes within 1% of 60 times a second over 60 s
  at 60–240 FPS with the default noise and every step at 30 FPS, and never more than 60·t + 2 in t seconds (§5.1);
  a join hold of zero-bit messages stops at H units, a message of U_max units is always held, full holds of two
  and three namespaces welcomed in one frame are released within the minimum budgets, and the frames carry exactly
  the charged bits (§5.3); under the automatic scheduler a forced `REPORT` or `BEACON` frame leaves within one
  flush step of falling due, under the manual scheduler at the next `Lync.flush()`, and in neither case counts
  toward `flushMissing` (§5.1); a budget-refused tagged reliable frame is not hashed and the sender's next frame
  verifies at e, and a budget-refused untagged one leaves e (§6.1); a validator or check function that yields is
  cancelled and its message dropped in the same pipeline pass (§6.1).
- **The inbound bound is a test.** The inbound benchmark (`probes/inbound-bound-2/` as the reference) times every
  frame kind of its shape set on each commit: header-only frames at e and at e + 4, failing tags on both lanes with
  every candidate hashed, dense and constant records of 1–128 fields, records of empty arrays and maps in row and
  column form, a union of its widest variant, strings and buffers at e + 4, untagged `HELLO` frames, and long
  instance lists. Each shape's median over its runs is compared with §7.5's bound for that frame, (1 + μ) × (c_f +
  c_b × its charge + 100 ns × its units), measured as ratios to a header-only frame timed in the same run, so the
  test doesn't depend on the host; it fails when a ratio passes the bound's.
- **In-engine golden set:** Lync's own CI decodes the golden set in a Roblox server through an Open Cloud Luau
  Execution task, per Lync release and on each engine version it can reach; the result depends only on those two
  versions, so game release pipelines don't run it (`v5-tooling.md`).
- **Fixtures:** the runtime-path server of golden-frame and seed-0 shard tests sets `layout.vary = false`
  (§3.2); woven builds are gated in CI on compiling, an unchanged line count per script, and a per-site byte
  differential against the generic encoder (`v5-tooling.md`) `[codecs-in-scripts §4.3]`.
- **Test names describe inputs by origin and rule,** under §7.1's rule for names: "encoder output decodes with
  rule 0", "frames breaking rule 6", "a modified client firing a trap".
- **Heavy specs** (10^6 random directions per width, exhaustive rotations) run behind an environment switch; the
  default run uses 10^4.
- **In-engine tests** in Studio for what only Roblox shows (§10).
- **Benchmarks:** the four game models' traffic; CPU interpreted (client) and native (server); bytes before and
  after an engine-compression estimate; per commit as JSON. A public comparison runs the QuickNet v0.3.4 thread's
  benchmark (1000 fires per frame for 10 s; FPS and Kbps for entities, booleans, strings, numbers, a dictionary
  and `Vector3`) against Blink, Zap and ByteNet `[landscape §1.7]`. The target: v5's FPS at least and Kbps at most
  each library's, in every column.

# Lync v5: design

Draft 2, 2026-10-15. Revises draft 1 against two reviews (`.data/docs/reviews/v5-design-1.md`, cited as
`[review-1 Bn/Mn/mn/Tn]`, and `v5-design-1-redundancy.md`, cited as `[review-redundancy n]`) and the author's
decisions; every finding's outcome and every client-side refusal re-evaluated are in `v5-changes.md`. Built on the
research in `.data/docs/research/` (cited as `[brief §n]`) and the experiments in `.data/docs/probes/` (draft 2's
own probes are in `probes/design-2/`). Each decision states the problem, the options that were viable, and the
choice. Nothing here is implemented yet.

## 0. What v5 is

Typed buffer networking for Roblox, in Luau and roblox-ts:
- **One schema, two sides.** A schema written once in Luau declares every event, request and replicated
  collection.
- **A compiler** turns the schema into straight-line codecs and a typed API for each side, in Luau and `.d.ts`.
- **A runtime** batches everything into one frame per player per lane per flush.
- **The server owns the truth.** Every inbound byte is budgeted, decoded strictly, rate-limited and checked.
- **The client is defended too.** Client-side integrity measures make tampering cost work that has to be redone per
  build, per server or per session, and turn it into facts the server sees (§6.2).
- **Lync reports facts, never verdicts.** Every refusal and anomaly becomes one typed observer event with an exact
  trigger and numeric evidence; what to do about it is the game's code (§6.3).

The same schema also runs with no build step. At build seed 0 that path produces the same bytes and the same API
(§3.2 lists exactly what the two paths share), is about 4x slower `[probes T P1]`, and gets exact types only under
the new type solver.

## 1. Principles

When two of these conflict, the earlier one wins.

1. **Server authority.** Nothing a client sends is trusted. Client-side measures raise the cost of tampering and
   produce facts the server checks; they never replace a server check.
2. **Correct before fast before small.** Byte savings that cost correctness or robustness are refused. Fast
   paths are measured.
3. **Exact types on both Luau solvers and roblox-ts.** No payload, handler, reply or patch is `any`. The generated
   shards meet this on both solvers. The no-build path meets it under the new solver only, and Lync says so loudly
   wherever a project relies on it under the old one (§3.2).
4. **One way to do each thing.** One naming convention, one error model, one shape for analogous features.
5. **Precise, never simplified.** No presets, tiers or labels in place of definitions. Every option has a name,
   type, unit, range, default and documented cost. Every observed fact has an exact trigger and its known honest
   causes.
6. **Declarations in declarative formats, behaviour in Luau.** Build configuration is TOML, generated artefacts
   are JSON, and handlers, validators and runtime settings are Luau. The schema is Luau because the no-build path
   needs it as a live value.
7. **The library comes first.** Tooling and extensions are built on stable seams of a working runtime and
   compiler, never before them. The first v5 attempt shipped 19k lines of harness and no library
   `[v5-attempt §10]`.
8. **Every claim is measured or marked unverified.** Performance and size claims cite a probe; Roblox behaviour
   cites docs or a Studio measurement, or is listed in §11.

## 2. Architecture

```
schema module (Luau)
      │  evaluated by
      ▼
planner (pure Luau, one implementation) ──► IR: definitions, layouts, ids, limits, hash
      │                                         │
      ├─► runtime interpreter (no build)        ├─► codegen ──► client shard, server shard (Luau)
      │                                         │              .d.ts, manifest.json, report.md
      ▼                                         ▼
runtime: transport · scheduler · sessions · integrity · observer
```

- **One planner.** The planner is shared by the runtime, the CLI and the Studio plugin, so the generated path
  and the runtime path cannot disagree on a single bit `[client-security-build §1.1]`. A differential test
  encodes random values through both paths and compares bytes, at seed 0 and at fixed nonzero seeds given to the
  runtime planner through the test seam (§7.1).
- **Packages:**
  - `lync`: runtime and planner. Wally, pesde and the Creator Store.
  - `lync` CLI: the compiler core under a host. The shipped host is a Rust binary embedding Luau through `mlua`,
    installed with rokit; Lune is the fallback host and the first one used (milestone 3). Lute 1.0 is not ready
    `[client-security-build §1.2]`.
  - Lync Studio plugin: embeds the planner for diagnostics, the inspector, and regeneration in Studio-only
    projects (§8.3).
  - `@lync/core` on npm: roblox-ts declarations for the runtime.
- **Layers inside the runtime**, each depending only on the ones before it: `wire` (bit reader and writer,
  integer codes, quantizers, column coder) → `plan` (planner, IR) → `codec` (interpreter for the IR) →
  `transport` (remotes, frames) → `session` (handshake, acks, integrity) → `sched` (flushing, state ticks,
  budget) → `api` (views).

## 3. Schema and API

### 3.1 Decision: how a schema is written

- **Problem.** The schema must be readable, give exact types, be evaluable at runtime with no build, and be
  readable by a compiler.
- **Options:**
  1. A separate IDL file, as Blink and Zap do. Concrete types and an easy compiler, but a second language,
     mandatory codegen, and the regenerate step is the top complaint about both `[landscape §1]`.
  2. Luau builder chains, as v4 does. Familiar, but modifiers mutated in some places and copied in others, and
     the types collapsed at records `[v4 §6, §8]`.
  3. **Luau declarative tables: definitions are option tables, records are plain tables, codecs are
     constructor calls.**
- **Choice: option 3.**
  - Records need no wrapper.
  - The compiler reads the evaluated value rather than parsing source, so helper functions and loops in the
    schema just work.
  - Option names are checked by the planner, not the type checker: an unknown option key throws at evaluation
    with the definition path (`arena.chat: unknown option "rtae"`). On the runtime path the type checker sees
    only `from` exactly (`D & { from: "client" | "server" }`); other option literals widen and option typos pass
    it `[probes review-1 r1, r2, r5]`.
- **Consequence: order comes from names, not source.** Luau dictionary iteration order is unspecified (a six-field
  literal iterates in a different order from its declaration: `probes/design-2/field_order.out`), and the planner
  only sees the value. Record fields and union variants are therefore ordered by name (bytewise) at seed 0; a
  nonzero build seed permutes that order (§6.2.4). Renaming a field can change the layout, and always changes the
  schema hash. Lists (`t.enum({ ... })`) keep their list order.

### 3.2 Decision: where exact types come from

- **Problem.** Type functions infer exact types from schema values, but only under the new type solver. Roblox
  still checks `--!strict` scripts with the old solver unless `Workspace.UseNewLuauTypeSolver` is enabled, and
  luau-lsp defaults to the old solver too. On the old solver, type functions degrade silently to error types
  `[landscape §3.3]` `[probes T7]`.
- **Options:**
  1. Type functions only: no build step, but silent error types for most users.
  2. Generated code only: concrete types everywhere, but no runtime path.
  3. **Both, with generated code primary.**
- **Choice: option 3.**
  - **Generated path.** Game code requires the generated shard for its side. The shard *is* the API: its types are
    concrete and need no solver features, and its codecs are straight-line code. Result unions and `kind` unions
    narrow on both solvers `[probes review-1 r4]`.
  - **Runtime path.** Game code calls `Lync.server(schema)` or `Lync.client(schema)`, typed through type functions
    in a separate types module marked `--!nocheck` and `--!nolint UnknownGlobal` `[probes T7]`. Under the new
    solver it gives exact handlers, rejects wrong-side calls and wrong union variants
    `[probes review-1 pipe/]`, except that list-form enums widen to `string` `[probes T3]`. Under the old solver
    payloads are error types.
  - **Degradation is loud.** The plugin and `lync check` warn when a runtime-path project's place has
    `UseNewLuauTypeSolver` off, and the selene `std` file flags `Lync.server(`/`Lync.client(` in `--!strict`
    scripts.
- **What the two paths share on the wire.** For one schema and one build seed, both paths produce identical
  bytes: the frame layout and headers (§4.1), every code and quantizer (§3.3, §4.3), definition ids before the
  per-server permutation, the protocol version, and the schema hash. The build seed changes exactly two things:
  the order of fields within each record and the upstream tag's initialisation constants (§6.2.4). The runtime
  path always runs at seed 0. `HELLO` carries the seed, so a session whose two ends differ in seed (a seeded shard
  on one side, the runtime path on the other) is refused like any schema mismatch, never decoded wrongly.
- **Stale shards are an error, never a fallback.** A shard embeds its seed, the seed-0 schema hash and the schema
  module's path. In Studio (`RunService:IsStudio()`), requiring a shard evaluates the schema with the runtime
  planner and throws `[Lync] arena shard is stale: run lync build` on a hash mismatch; `lync check` fails CI the
  same way. Live servers skip the check: both shards come from one build, so they agree with each other. Draft 1's
  silent fallback to the runtime path is gone: it ran the live schema under the stale shard's types
  `[review-1 M6]`.
- **Consequence for syntax.** Schema syntax is designed for people, not bent around inference limits:
  `t.enum({ "red", "blue" })` is exact in generated code even though the runtime path widens it.
- **`patch` typing, stated exactly.** On both paths a wrong value type in `patch` is a compile error; a misspelled
  key is not (Luau tables are not exact) and is a caller error thrown at the caller's line (§3.8)
  `[probes T4, review-1 r3, r4]`.
- **Unproven, assigned to milestone 1:** the `D & { from: ... }` signature on `Lync.request`, which raised a
  spurious error through the full pipeline and was clean in isolation `[probes review-1 pipe/buyonly.luau, r6,
  r7]`; and the readability of side-split errors (the target is a message naming the definition; today's
  runtime-path messages are cyclic expansions `[probes T6]`).

### 3.3 Codecs

Every codec is a constructor call returning a plain table, so `{ read _value: T }` inference holds `[probes T1]`.
Constructors have no option tables. Scalar accuracy is `(min, max, step)` in the value's own unit (radians for
angles, as in every Luau and Roblox angle API). Rotation and direction accuracy is in bits per component, because
their maximum error has no closed form; the docs list the measured error per bit count `[compression §4.4, §4.5]`.
Values are exact unless declared otherwise.

| Codec | Luau type | Single-row wire | Notes |
|---|---|---|---|
| `t.bool()` | `boolean` | 1 bit | |
| `t.int(min, max)` | `number` | ⌈log2(max − min + 1)⌉ bits of `v − min` | refuses fractions and out-of-range |
| `t.int()` | `number` | zigzag, Exp-Golomb order 0 | any integer with \|v\| ≤ 2^53; codes like `t.int(min, max)` inside columns, differs only in validation and single-row width |
| `t.number(min, max, step)` | `number` | q = ⌊(v − min)/step + 0.5⌋ in ⌈log2(⌊(max − min)/step⌋ + 1)⌉ bits | refuses v outside [min, max] before rounding (no silent clamp); decodes to min + q·step; `step = 1` with an integer `min` is a declaration error naming `t.int` |
| `t.f32()`, `t.f64()` | `number` | 32 or 64 bits IEEE | NaN and ±inf are always refused |
| `t.angle(step)` | `number` (radians) | n = ⌈2π/step⌉ steps per turn; q = ⌊wrap(v)·n/2π + 0.5⌋ mod n | decodes to q·2π/n in [0, 2π) |
| `t.string(maxBytes)` | `string` | length in ⌈log2(maxBytes + 1)⌉ bits; bytes in the tail (§4.1) | |
| `t.buffer(maxBytes)` | `buffer` | as `t.string` | |
| `t.vector3(min, max, step)` | `Vector3` | three `t.number(min, max, step)` | all three arguments required |
| `t.vector3f32()` | `Vector3` | 3 × 32 bits | the unquantized form has its own name |
| `t.direction(bits)` | `Vector3` (unit) | octahedral, `bits` per axis (8–16) | 10 bits: 0.23° max, 12: 0.057° `[compression §4.5]`; zero vector refused |
| `t.rotation(bits)` | `CFrame` (rotation only) | 1 flag bit; then a 5-bit index of the 24 axis-aligned rotations, or smallest-three: 2-bit index + 3 × `bits` (7–15) | 9 bits: 0.45° max `[compression §4.4]` |
| `t.cframe(position, rotation)` | `CFrame` | the two codecs in order | the decoder builds the CFrame once `[compression §4.5]` |
| `t.color3()` | `Color3` | 3 × 8 bits, ⌊c·255 + 0.5⌋ | refuses channels outside [0, 1] |
| `t.enum({ "a", "b" })` | `"a" \| "b"` | ⌈log2(n)⌉ bits; index = list order | |
| `t.enum(Enum.Material)` | `Enum.Material` | the item's `Value`, zigzag Exp-Golomb order 0 | a `Value` the receiving engine lacks drops only its message (`unknownEnum`, §6.3) |
| `t.instance(className?)` | `Instance` (generated path: the class, e.g. `Player`) | index into the frame's instance array, ⌈log2(arrayLength)⌉ bits | `IsA` checked on both ends; a required instance that arrives `nil` (streaming) drops only its message |
| `t.optional(codec)` | `T?` | presence bit + codec | allowed anywhere, including array elements and map values; `t.optional(t.instance(...))` is the nil-tolerant form |
| `t.array(codec, maxCount)` | `{ T }` | count in ⌈log2(maxCount + 1)⌉ bits, then rows | column-coded from `columnMinRows` rows (§4.3) |
| `t.map(key, value, maxCount)` | `{ [K]: V }` | count, then pairs in strictly ascending key order | keys: integers, enums or strings (bytewise) |
| `t.union({ name = record, ... })` | discriminated on `kind` | variant index ⌈log2(n)⌉ bits, variants by name | a variant with its own `kind` field is a declaration error |
| `{ field = codec, ... }` | record | fields by name (§3.1) | |
| `t.custom(spec)`, `t.convert(base, decode, encode)` | user `T` | extension seams (§7.1) | |

Rules:
- Every count and length has a declared maximum. The decoder checks it against the remaining bits before it
  allocates anything.
- Codec methods are non-generic and return the same codec type, which keeps type-function inference working
  `[probes T1]`. The core has one, `:newest()` (§3.6); the planner rejects it anywhere but a collection's top-level
  fields, naming the path. Extensions add their own markers and list them (§7.2: `:maxHz(hz)`, `:claim()`), with
  the same placement check.
- There's no flags or bitfield codec. Boolean fields in a record already pack to 1 bit each.
- Wire mappings that need golden vectors (octahedral, smallest-three, the axis-aligned table) are fixed by
  milestone 1's golden frames.

### 3.4 Definitions

```luau
-- ReplicatedStorage/Net/schema.luau
local Lync = require(ReplicatedStorage.Packages.Lync)
local t = Lync.types

return Lync.schema("arena", {
	chat = Lync.event({
		from = "client",
		data = t.string(200),
		limit = { perSecond = 5, burst = 5 },
	}),
	strike = Lync.event({
		from = "client",
		lane = "unreliable",
		data = {
			target = t.int(1, 2 ^ 40),
			aim = t.direction(11),
		},
	}),
	announce = Lync.event({
		from = "server",
		data = t.union({
			round = { number = t.int(1, 99) },
			winner = { team = t.enum({ "red", "blue" }) },
		}),
	}),
	buy = Lync.request({
		from = "client",
		data = { item = t.enum({ "sword", "shield" }) },
		reply = t.int(0, 100_000),
		timeout = 10,
	}),
	fighters = Lync.collection({
		key = t.int(1, 2 ^ 40),
		maxRecords = 64,
		data = {
			name = t.string(20),
			team = t.enum({ "red", "blue" }),
			health = t.int(0, 100),
			position = t.vector3(-2048, 2048, 1 / 32):newest(),
			look = t.rotation(9):newest(),
			title = t.optional(t.string(16)),
		},
	}),
	round = Lync.collection({ -- no key: a singleton
		data = { endsAt = t.int(0, 2 ^ 31), phase = t.enum({ "lobby", "play" }) },
	}),
})
```

| Option | event | request | collection | Type, unit, range | Default |
|---|---|---|---|---|---|
| `from` | required | required | — (always server) | `"client" \| "server"` | — |
| `data` | payload | payload | record | codec | no payload |
| `lane` | ✓ | — (reliable) | — (§5.2) | `"reliable" \| "unreliable"` | `"reliable"` |
| `limit` | client events | client requests | — | `{ perSecond: number (messages/s, > 0), burst: integer (messages, 1–1000) }` | none; `burst` defaults to `max(1, ⌈perSecond⌉)` |
| `reply` | — | ✓ | — | codec | no payload |
| `timeout` | — | ✓ | — | seconds, 0.1–300 | 10 |
| `key` | — | — | ✓ | codec (`t.int`, `t.enum`, `t.string`) | none: one record, 0-bit key |
| `maxRecords` | — | — | ✓ | records, 1–65,536 | 1024 |
| `priority` | — | — | ✓ | weight, > 0 (§5.4) | 1 |

- `from` and each definition's lane go into the schema hash, so a message sent in the wrong direction or on the
  wrong lane is rejected with certainty at no cost `[client-security §3.6]`.
- `limit` applies to client-sent definitions only. The client holds over-limit fires and sends them as the bucket
  refills; the server enforces it with slack for network bunching (§6.1).
- The worst-case encoded size of every unreliable definition must fit an unreliable frame (§4.1), and every
  client-sent definition must fit 16,384 B; otherwise evaluation throws.
- Integrity declarations that must not be visible to clients (traps, decoys, canaries, reference fields) are made
  on the server view, never in the shared schema (§6.2).

### 3.5 Using it

Game code requires the shard for its side (generated path) or calls `Lync.client(schema)`/`Lync.server(schema)`
(runtime path); both return the same API. Shards go to a replicated folder (client) and `ServerScriptService`
(server) `[client-security-build §2.1]`. There's no `start()`: the runtime starts on first use and `require` never
yields. `flush()` is never required (§5.1).

**Server:**

```luau
local Lync = require(ReplicatedStorage.Packages.Lync)
local Net = require(ServerScriptService.Net)

Net.chat:validate(function(player, text)
	return string.find(text, "%S") ~= nil
end)

Net.chat:connect(function(player, text)
	Net.announce:fire(Lync.all, { kind = "round", number = 3 })
end)

Net.buy:handle(function(player, request)
	return PRICES[request.item]
end)

Net.fighters:set(player.UserId, {
	name = player.Name,
	team = "red",
	health = 100,
	position = Vector3.zero,
	look = CFrame.identity,
})
Net.fighters:patch(player.UserId, { health = 90 })
Net.fighters:audience(player.UserId, redTeam) -- any Target; default Lync.all
Net.fighters:remove(player.UserId)
Net.round:set({ endsAt = 600, phase = "play" })
```

**Client:**

```luau
local Net = require(ReplicatedStorage.Net.client)

Net.chat:fire("gg")

local result = Net.buy:invoke({ item = "sword" })
if result.ok then
	print(result.value)
end

Net.fighters.added:connect(function(id, fighter) end)
Net.fighters.changed:connect(function(id, fighter, previous) end)
Net.fighters.removed:connect(function(id) end)
local fighter = Net.fighters:get(id)
```

**Verbs.** One per action, and the same everywhere:
- `fire` sends; `connect` listens and returns a connection with `disconnect()`.
- `invoke` asks and yields until the result; `handle` answers.
- `validate` is a server-only check: return `true` to accept, `false` to reject.
- `set`, `patch`, `remove` and `audience` write a collection (server only); a singleton's take no key.
- `get` and the `added`, `changed` and `removed` signals read a collection. A definition has one signal, so it is
  the definition's `connect`; a collection has three, so they are named.
- `trap`, `refers`, `decoys` and `canary` declare integrity measures on the server view (§6.2).

**Targets.** One `Target` type serves server `fire` and `audience`: a `Player`, an array of players, a
`Lync.group()`, `Lync.all`, or `Lync.except(target)`. `Lync.except(x)` returns the same object for the same `x`. A
target resolves once per flush, not per message. `Lync.group(players?)` returns a live set with `add`, `remove`,
`has`, `size`, `players` and `destroy`; leaving players are removed automatically. These names live on `Lync` only;
shards do not re-export them.

**Results.** Requests never throw. They return
`{ ok: true, value: R } | { ok: false, error: "timeout" | "rejected" | "unanswered" | "left" | "shutdown" }`:
- `rejected`: the server refused it (`limit` or `validate`), answered at once rather than timing out `[v4 §8]`;
- `unanswered`: the answering handler threw, returned nothing, or exceeded `timeout` on the answering side;
- `timeout`: no answer arrived within `timeout` on the asking side;
- `left`, `shutdown`: the other side's player left, or the server is closing.

Requests go both ways: a server `invoke(player, data)` yields the calling thread like the client's.

**Handler arguments.** A server handler receives the player first, matching `OnServerEvent` (this overrides the
attempt brief's payload-first rule `[v5-attempt §11]`). A client handler receives the payload.

**Collection reads.** Records are copy-on-write: each change builds the next frozen record once; `get` returns it
without copying, and `changed` passes the previous frozen record as `previous` at no extra cost (7 ns per `get`
against 166 ns and 320 B for clone-on-read; 182 ns and 320 B per change, interpreted
`[probes review-redundancy get_snapshot]`). A record with both reliable and `:newest()` fields changes on two
lanes, so `changed` can fire twice in one state tick; a collection that needs one atomic change per tick declares no
`:newest()` fields.

**Type errors** name the side: shards simply don't have the other side's methods.

### 3.6 Collection field marker

`:newest()` on a top-level collection field returns the same codec type, so inference is unaffected. The field is
sent on the unreliable lane on state ticks, newest value wins, and losses are repaired by notify (§5.3). It requires
a fixed-width codec (no strings, buffers, arrays, maps, optional or unbounded integers); the planner rejects others.
Everything else about delivery is declared on the collection.

### 3.7 roblox-ts

- The schema is Luau in both ecosystems: a roblox-ts project keeps `schema.luau` beside its TypeScript, and the
  compiler emits `.d.ts` plus the Luau shards from the same IR, so they can't drift (v4 hand-wrote its `.d.ts`).
  Whether rbxtsc carries a `.luau` file through to its output unchanged is verified in milestone 3.
- Declarations follow the side split, use dot calls (`this: void`), `size()` and `entries()` adapters, and
  `LuaTuple` only where Roblox requires it `[v4 §2.3, §6]`.
- Type tests run on both sides in CI.

### 3.8 Errors

- **Declaration mistakes** throw when the schema is evaluated, naming the definition path
  (`arena.fighters.data.position`). Under the compiler, the same message is a build error.
- **Caller mistakes** throw at the caller's line, found by walking `debug.info` to the first frame outside Lync
  `[v5-attempt §7]`. The message says what and where:
  `[Lync] arena.buy:invoke data.item must be one of "sword" | "shield", got "axe"`. Misspelled `patch` keys are
  caller mistakes.
- **User callbacks** each run in a pooled thread, so their errors surface with native tracebacks and never
  break Lync's loop. A pooled resume costs 88–131 ns interpreted against 319–451 ns for a fresh coroutine
  `[probes review-redundancy dispatch]`.
- **Bad input from other players** is never thrown or printed per message. It becomes an aggregated observer
  `anomaly` (§6.3).

## 4. Wire

### 4.1 Remotes and frames

- **Remotes.** Each namespace has one `RemoteEvent` and one `UnreliableRemoteEvent`, created by the server under
  `ReplicatedStorage.Lync.<namespace>`. The client view connects when they appear; until then it holds sends like
  any pre-handshake send (§4.4). Each call carries one buffer, plus an instance array when the frame references
  instances `[landscape §2.1]`.
- **Per flush, per player, per namespace:** at most one reliable frame downstream; unreliable frames split at
  1000 B, the documented drop limit `[compression §1]`. Upstream reliable frames split at 16,384 B. Reliable
  remotes are ordered across instances per connection `[state-sync §5.1]`, so frames of several namespaces keep
  call order.
- **Shared encodings.** Downstream, each partition's state section and each event run is encoded once per flush,
  starting on a byte boundary with zero padding, and a player's frame is assembled with `buffer.copy`. When a flush
  has no content addressed to a subset of players, one frame goes to everyone through `FireAllClients`; this is
  decided from the targets, never by comparing buffers.
- **Definition ids.** Each namespace numbers its ids from 1 in name order: every event and collection takes one,
  every request two (`ask`, `answer`). Id 0 is control (§4.4). Ids are ⌈log2(count + 1)⌉ bits. The per-server
  permutation (§6.2.3) maps ids 1…count onto themselves, so it never changes the width.

**Frame layout:**

```
frame        := header body tail [tag:16 — upstream only, §6.2.1]
tail         := strings and buffers, written backwards from the end: the first is last (no offset needed)

header, downstream reliable   := tick: '0' same as previous reliable frame | '10' +1 | '11' u16
header, downstream unreliable := seq:12 tick:16
header, upstream reliable     := ack
header, upstream unreliable   := seq:12 ack
ack          := '0' | '1' seq:12 received:16     -- newest downstream unreliable seq, and the 16 before it

body, reliable down := states:EG0 { collectionId section } runs:EG0 { run } removes:EG0 { collectionId section }
body, otherwise     := runs:EG0 { run }  [newest rows on downstream unreliable state ticks, §5.3]
run          := id count−1:EG0 rows          -- consecutive messages of one definition to one target, in call order
```

- **Order on the reliable lane:** state adds and updates → runs (events, requests, answers) → removes. Every event
  sees every collection write made before it on the server `[state-sync §5.3]`.
- **No section lengths, no skipping** `[review-1 B1]` `[review-redundancy 6]`. Skipping a bad section cannot work
  with one shared byte tail: the decoder would not know how many tail bytes the skipped section owned. So a
  malformed frame is refused whole (§6.1), which costs an honest client nothing (a malformed upstream frame that
  passed the tag is a bug or an attacker), and the downstream client never skips (the server is trusted). The
  per-list counts replace draft 1's `kind:u3 length` at 1 bit per empty list, against 11 bits per section.
- **The ack is sent once, when new** `[review-1 m9]` `[review-redundancy 5]`. It goes in the first upstream frame
  of a flush and only when a downstream unreliable frame has arrived since the last ack sent; otherwise it is the
  1-bit `'0'`. When a flush has nothing else to send but owes an ack, the client sends an unreliable frame holding
  only its header. There is no fixed-rate heartbeat.
- **Sizes.** Upstream headers fall from 886 to 353 B/s for a busy player, downstream from 353 to 130 B/s,
  against draft 1's layout `[probes review-redundancy wire_overhead]`.

### 4.2 Decision: how values become bits

- **Problem.** Roblox zstd-compresses buffers of roughly 100 B and up (threshold, level and fallback
  undocumented). Bit-packing defeats zstd; byte alignment wastes bits.
- **Options:**
  1. Byte-aligned layouts that lean on zstd. That was the landscape study's tentative pick.
  2. Plain dense bit-packing, as v4 and the attempt did.
  3. **Fixed-width bits for single rows, and a column coder for multi-row sections: column by column, residuals
     against a baseline, with an integer code and parameter chosen per column per frame.**
- **Choice: option 3.**
  - Without temporal prediction (`col_bits_adapt`, the core's coder) it is 1.2–1.8x smaller than the best
    byte-aligned layout under the modelled engine zstd in five traffic models and ties the sixth
    `[compression §2.1]`.
  - Its output doesn't compress further, so the unknown engine level barely affects it.
  - Strings and buffers sit in the byte tail, where large bursts still get engine compression `[compression §2.5]`.
- **Hedge.** The layout is one module behind the IR, and `HELLO` carries a protocol version. Only the engine
  keeping compression context across frames could overturn this choice; the Studio probe settles it
  (`probes/compression/studio/`, §11).

### 4.3 Column coder

- **When it applies.** Only to a multi-row section: a reliable collection section of `columnMinRows` or more
  records, an array of that many elements, or an event run of that many messages. Fewer rows use single-row fixed
  widths (§3.3), and `:newest()` rows never use it (§5.3). Column headers cost about 6–7 bits per column per frame,
  so they pay only over several rows. `columnMinRows` is a protocol constant set by the milestone 1 benchmark
  (draft value 4); the decoder knows which form follows from the count, so no flag is sent.
- **Baseline per column.** Collection updates: the value last sent to the partition. Adds, arrays and runs: the
  previous row (the first row against the field's minimum). Values are coded as zigzagged residuals.
- **Per column, a 2-bit mode:** zero (all residuals 0); Exp-Golomb with order k (4 bits); sparse (EG-0 gaps to
  non-zero rows, EG-k values, k in 4 bits); frame-of-reference (EG-0 minimum residual, 6-bit width, then values).
  Bools use the same modes on the bit XOR baseline.
- **Encoder.** It costs every mode and every k, one pass per k over 30–100 values. A log2-of-mean shortcut lost
  6–14% on two stream types `[compression §2.3]`. The k search's server cost is unmeasured (estimated to double or
  triple the 15 ns per value native encode); milestone 1's benchmark measures it, and costing every k from one
  histogram of residual bit lengths is the fallback `[compression §3.2]`.
- **Decoder.** A 12-bit lookup table for Exp-Golomb, at 35–58 ns per value interpreted and 11–13 ns native
  `[compression §3.2]`.
- **Not in the core:** guarded linear prediction. It halves position bits only where a baseline the receiver
  holds exists for every row `[compression §4.3]`; that is the `acked` extension (§5.3, §7.2).

### 4.4 Handshake

Control messages travel as runs of id 0 on the namespace's reliable remote, with a 3-bit type. Connection-level
messages (`REKEY`, `REKEY-ACK`, `REPORT`, `BEACON`) travel in the first namespace whose handshake completed.

| Type | Direction | Content |
|---|---|---|
| `HELLO` | client → server, the namespace's first frame, untagged | protocol version (8 bits), build seed (32 bits, §6.2.4), schema hash (64 bits) |
| `WELCOME` | server → client | state tick epoch (f64, `GetServerTimeNow` of tick 0), `stateRate` (8 bits); in the connection's first `WELCOME`: integrity key (64 bits), `tagCover` (16 bits), id permutation seed (32 bits, 0 = identity), `clockBeacon` (8 bits, tenths of a second), caller probe share (8 bits, 1/255 steps) and maximum (8 bits) |
| `MISMATCH` | server → client | none: the client view prints one error and drops its sends |
| `REKEY` | server → client | new integrity key (64 bits) |
| `REKEY-ACK` | client → server | none |
| `REPORT` | client → server | counts since the previous `REPORT`, EG-0 each: caller probes, elevated callers, foreign callers, refused downstream frames (§6.2.7, §6.2.8) |
| `BEACON` | client → server | ⌊`GetServerTimeNow()` × 1000⌋ mod 2^16 (§6.2.9) |

- **Hash.** HalfSipHash-2-4 with a zero key and 64-bit output over the IR's canonical serialization at seed 0,
  which folds in every definition's direction and lane. It is pure Luau, so the CLI and plugin compute it.
  Per-definition hashes are not sent: a client and server of one place version always match, so a mismatch is a
  stale or forged build, which Studio and `lync check` diagnose by name (§3.2).
- **`REPORT`** is sent in the next reliable frame after any count changes, at most once per flush.
- **Joining.** Until `WELCOME` arrives, the client holds reliable fires up to 65,536 encoded bytes and drops
  unreliable ones; a reliable fire past the cap is dropped and reported (`holdFull`, §6.3). A late joiner gets
  catch-up adds for every record it can see (§5.2). Sending `WELCOME` unsolicited at `PlayerAdded` would save the
  join round trip, but only if reliable events queue for a listener that connects later (§11).

### 4.5 Strings

Strings and buffers go inline: a length in the bit section and the bytes in the tail. Static vocabularies belong in
`t.enum`. Interning and templates cut string bytes 1.8x and 6.5x on the tycoon model `[compression §5]`, but a
per-connection table breaks encode-once and `FireAllClients`, fills with one-off lines, and pins up to 92 MB
upstream `[probes review-redundancy wire_overhead]` `[review-1 M5]` `[review-redundancy 4]`; they move to the
`strings` extension (§7.2), with per-audience tables, intern on second sight, a byte cap and server-to-client only.

### 4.6 Canonical decode

A decoder refuses the frame, as `malformed` with the rule's number as evidence (§6.3), on:
1. a call that is not one buffer plus at most one array of `Instance` or `nil` values;
2. any count, length or index at or past its maximum;
3. a value outside its declared range, or a quantized code past its last step;
4. non-zero padding bits, or a bit section and tail that do not meet exactly (no slack bytes);
5. map keys that are not strictly ascending;
6. smallest-three components whose squares sum past 1, or a zero direction;
7. an unknown id or a run count of zero;
8. anything after the last list;
9. an instance array entry that no instance index references.

Exp-Golomb codes are unique for a given k. Column mode and k are free encoder choices: any valid choice decodes.
The instance array needs no separate cap: each entry is charged 8 B at step 2 of §6.1, so the default byte burst
bounds it at 8,192 entries.

## 5. Delivery and state

### 5.1 Flushing and state ticks

**Decision: who decides when frames leave.**
- **Problem.** Batching needs a flush point. v4 made the developer call `flush()` every frame, which caused three
  of its worst pain points: a missed flush caught only by a 1-second detector, `Connect(Lync.flush)` throwing
  because the frame time was read as a budget, and start-up order rules `[v4 §8]`. Some cases still need control:
  sending before a destructive action, games on their own fixed tick, and tests.
- **Options:** manual only (v4); automatic only; **automatic by default, with an explicit "send now" and a manual
  scheduler.**
- **Choice: the third.**

**Behaviour:**
- **Default.** One flush per frame at `RunService.PostSimulation`. It connects on first use and does no work when
  nothing is pending.
- **Late sends** after the flush point leave with the next frame, adding up to one frame of latency. Roblox gives a
  server no way to run last in a frame, so this is stated rather than hidden.
- **`Lync.flush()`** sends everything pending now. It takes no arguments, is idempotent, and is safe inside
  handlers. Its documented uses are before `Player:Kick()`, before a teleport, and at the end of a custom tick.
- **Shutdown and leaving.** `BindToClose` flushes automatically. A leaving player's pending frame is flushed before
  the session is dropped.
- **`Lync.scheduler("manual")`** is for fixed-tick games and tests. Frames leave only on `Lync.flush()`. Pending data
  older than 2 frames' worth of `PostSimulation` steps is reported once per player as `missedFlush` (§6.3), without
  a timer.

**Decision: how state ticks relate to flushes** `[review-1 B2]`.
- **Problem.** `:newest()` state and the scheduler should run at `stateRate` (20 Hz), but events flush every frame.
  Draft 1 sent all state only on state ticks, so `set` followed by `fire` in a non-tick frame delivered the event
  first, breaking §4.1's order guarantee.
- **Options:** all state on state ticks (draft 1, broken); all state every frame (the scheduler at 60 Hz:
  `[state-sync §3.5]` puts it at 35–90 ms/s at 20 Hz, so three times that); **reliable state every flush,
  `:newest()` state on state ticks.**
- **Choice: the third**, as the research recommended `[state-sync §3.8]`.
  - Every flush carries structural changes (add, remove, audience) and reliable field changes, coalesced since the
    previous flush, never deferred by the budget. The order guarantee is then exact for all reliable state.
  - A flush is a **state tick** when T = ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋ has advanced since the
    previous state tick. The rule is the same under both schedulers, ticks stay on the wall clock when frames
    slow down (T may skip), and the client maps T to time as epoch + T/`stateRate`. State ticks run the scheduler
    and send `:newest()` rows.
  - Reliable and `:newest()` fields of one record are not atomic across lanes (§3.5).
- **Measurement.** Whether a remote fired at `PostSimulation` leaves in that frame's network step is unknown
  `[state-sync §11]`; if it doesn't, the default flush point moves earlier (§11).

### 5.2 Replication models

Each case uses the model that won on the measured trade-off `[state-sync §1, Implications]`:

| What | Lane | Model |
|---|---|---|
| events, requests, answers | declared lane (requests reliable) | runs in call order; never budget-limited, but charged to the budget first |
| collection structure and reliable fields | reliable | every flush: changes since the last flush, encoded once per audience partition, no acks (ordered delivery keeps the client equal to the last sent state) |
| `:newest()` fields | unreliable | state ticks: absolute values encoded once per tick; per-viewer pending sets; notify repair (§5.3) |

- **Catch-up.** A viewer gaining sight of a record (join, audience change) receives an add with every field,
  `:newest()` values included, in its own reliable section; losing sight is a remove. A catch-up add carries the
  partition's baseline (the values last sent to the partition) and precedes the partition's update section in the
  same frame, so the shared update applies on top of it. Adds are column-coded multi-row sections, so a join's
  catch-up is one compact section.
- **Records by slot.** A key travels once, in the add. Updates, removes and rows address a record by slot
  (⌈log2(`maxRecords`)⌉ bits) plus a 2-bit generation. A freed slot is reused only after 2 s, so a mismatched
  generation tells "newer" from "older". A client holds at most one early row per slot whose generation it hasn't
  added yet, applies it when the add arrives, and drops rows for older generations.
- **Unreliable events** may be lost and are never resent: "unreliable" means exactly that. Redundant input streams
  are the `inputs` extension (§7.2). Under Server Authority, simulation input belongs in `InputActions`, and
  remotes are off the synchronized timeline `[state-sync §8.1]`: Lync carries intents, claims and state outside
  the simulation, and `Lync.tick()` (the current state tick, or on the client the tick of the frame being
  dispatched) bridges the two.

### 5.3 Decision: how `:newest()` rows are coded

- **Problem.** Notify chooses a different row subset per viewer (pending sets, budget, priority). Prediction needs a
  baseline the receiver holds; on a lossy lane that is a per-viewer acked baseline. Encoding once per tick and
  predicting exclude each other `[review-1 B3]` `[review-redundancy 3]`.
- **Measured** (`probes/design-2/newest_layout.out`, the compression study's traffic models, every field treated as
  `:newest()`, persisting records only; mean bytes of state per frame for one viewer):

| Model | absolute rows, encode once | per-viewer column FOR | predicted vs the viewer's acked baseline | predicted vs a partition baseline (slowest viewer, ~250 ms) |
|---|---|---|---|---|
| shooter, 30 players, 20 Hz | 350 | 282 | 127 | 164 |
| shooter, 30 players, 60 Hz | 350 | 282 | 120 | 158 |
| shooter, 100 players, 20 Hz | 1190 | 939 | 420 | 543 |
| racing, 12 cars, 60 Hz | 243 | 227 | 152 | 173 |
| mmo, ~68 visible, 20 Hz | 249 | 172 | 57 | 83 |

- **Options:**
  1. **Absolute rows, encoded once per tick** (Tribes notify `[state-sync §1.4]`). A viewer's frame is
     `buffer.copy` of byte-aligned row chunks (5.7% padding against bit-contiguous rows, 350 against 331 B). Any
     delivered row is self-contained. 1.6–4.4x the bytes of option 3.
  2. Per-viewer column frame-of-reference over absolutes: per-viewer encoding for a 7–31% saving. Dominated.
  3. Prediction against each viewer's acked baselines: the fewest bytes, but per-viewer encoding with a k search
     (a varint delta alone is 47.7 against 24.9 ns per record copied, native; 237 against 43.5 interpreted
     `[state-sync §3.6]`), plus baseline history per viewer and a baseline agreement protocol.
  4. Prediction against a partition-wide baseline: encode once per partition, 1.1–1.45x option 3, but no per-viewer
     selection, and one slow member ages everyone's baseline.
- **Choice: option 1 in the core; prediction is not kept for `:newest()` rows.** Principle 2 ranks fast above
  small: option 1 encodes once per tick, keeps no history, and cannot desynchronise. Its cost is honest: a
  100-player shooter's 1190 B per tick is 1.5x the default budget, so the scheduler defers and records update at
  about 13 Hz instead of 20. Option 3 is the `acked` extension for the one collection where bytes dominate, at
  2.3–2.8x fewer bytes on the shooters.
- **Repair (notify).** Per viewer, a ring of the last 17 downstream unreliable frames records which rows each
  carried, in a buffer (the ack covers 17 frames, so a larger ring is never read `[review-redundancy 19]`). A frame
  is lost when an ack shows a newer frame received and not it; its rows become pending again if no later frame
  carried them. A frame that leaves the ring unacked counts as lost. Reordering can cause a spurious resend, never
  a stale value: the client applies a record's row only if its frame seq is newer (12-bit serial arithmetic).

### 5.4 Scheduling and budget

- **Budget.** At each state tick the scheduler may write up to `stateBudget` × Δt − charged bytes of `:newest()`
  rows to a player, never less than `stateFloor` × `stateBudget` × Δt. Δt is the time since the previous state tick
  (at most 2/`stateRate`); charged is every byte sent to that player since then (reliable frames and unreliable
  events). Defaults `[state-sync §3.2]`: 16,000 B/s, floor 0.25 (§6.4).
- **Selection.** Per viewer, pending records wait in one FIFO per collection, ordered by the tick they became
  pending. The scheduler repeatedly takes the head with the largest `priority` × age (age in state ticks) until
  the next row doesn't fit; a collection's rows are fixed-width, so then none of it fits and the others continue.
  This is exact, does no per-tick work for records not sent, and costs 1.2–5.8x less than per-tick accumulators
  with a 40-bucket pass (100 × 1000 records: 0.74 against 4.2 ms per tick native) `[probes review-redundancy
  sched_fifo]`. Age grows without bound, so every pending record is eventually first; there is no separate
  starvation floor.
- **Over budget.** Lync defers. It never lowers precision at runtime. Pending is a flag, so the backlog is bounded by
  the record count `[state-sync §3.9]`.
- **Not in the core:** distance, owner and first-send boosts, per-field rate caps. They need per-viewer weights that
  change each tick, which is what the `interest` extension brings (with the bucket pass it then needs).

### 5.5 Audiences

- Each record has an audience `Target`, `Lync.all` by default. Records with the same target value share a
  partition, encoded once for all its members. Groups are live; changes apply at the next flush as catch-up adds
  and removes.
- **No audience-by-field shortcut.** A game that partitions by team keeps one group per team, and the encoding is
  shared exactly as a field partition would be. A field shortcut would be a second way to say the same thing.
- **`interest` (extension)** refines an audience per viewer: it intersects the audience and never widens it. Cells
  cost about 0.01 ms per pass against 4–7 ms for exact membership at 200 players × 10k entities `[state-sync §7]`.

### 5.6 Requests

- **Slots.** Each direction of a connection has 16 request slots. An `ask` carries its 4-bit slot; its `answer`
  carries the slot and a 2-bit outcome (value, `rejected`, `unanswered`). An invoke that finds all 16 slots busy
  waits on the asking side, its `timeout` already running. The slot is explicit rather than implied by order
  because the two ends free a slot at different times (the answering side when it sends the answer, the asking side
  when it receives it), so implicit numbering would let them disagree.
- **Every ask is answered.** The answering side sends the value, `rejected` (limit or validate) or `unanswered`
  (handler threw, returned nothing, or ran past `timeout`). A slot is released only by its answer, or when the
  player leaves; an asking-side timeout resolves the caller but keeps the slot. So a late answer can never land on
  a reused slot, and an answer for a slot not in flight is exactly `unknownReply`.
- **Not used:** `RemoteFunction` and `InvokeClient` `[skill reference: InvokeClient yields forever]`.

## 6. Security

Two halves, each first-class: the server pipeline (§6.1) bounds and checks everything that arrives; client-side
integrity (§6.2) raises the cost of producing what arrives and turns tampering into facts. Both report through one
observer event (§6.3), and neither applies a consequence.

### 6.1 Inbound pipeline (server)

In this order, and nothing is decoded before it is paid for:

1. **Shape.** One buffer, plus at most an array of `Instance` or `nil` values, on a namespace's remote. Anything
   else is refused (`malformed`, rule 1).
2. **Budgets.** Per player and lane, token buckets for frames and bytes (`inbound`, §6.4), charging
   `buffer.len` + 8 B per instance before any decode (`overBudget`). An over-budget reliable frame is still
   tag-checked (step 3), so the counter stays in step, then dropped.
3. **Integrity.** The frame tag; on the unreliable lane, the replay window (§6.2.1, §6.2.2).
4. **Strict, canonical decode of the whole frame** (§4.6), before anything is delivered. Each id is mapped through
   the server's permutation and checked as it is read: unknown (`malformed`), wrong direction (`wrongDirection`),
   wrong lane (`wrongLane`). Any failure refuses the frame whole; because no frame skips, the tail cursor never
   desynchronises `[review-1 B1]` `[review-redundancy 6]`. An ack naming a downstream unreliable frame never sent
   to that player is ignored and the frame kept (`impossibleAck`).
5. **Per message**, in order: control messages are handled (`REPORT`, `BEACON`, `REKEY-ACK`, a repeated `HELLO`);
   `trap` (dropped); an `answer` for a slot not in flight (`unknownReply`, dropped) or one that arrived too early
   (`earlyAnswer`, delivered); `unknownEnum`, `instanceMissing` and `instanceClass` (dropped); `limit`
   (`overLimit`, dropped; an ask is answered `rejected`); then the report-only facts `unreachable`,
   `decoyReferenced` and `canaryEchoed`. An over-limit message was decoded: without lengths its bytes must be read
   to reach the next message, and they were already paid for at step 2.
6. **Validators.** Server `validate` functions run in protected calls. `false` drops the message (`validateFalse`;
   an ask is answered `rejected`); a throw does the same and is reported as `validatorError`.
7. **Delivery.** Handlers run in pooled threads.

**`limit` on the server** is a token bucket with rate `perSecond` and capacity `burst + perSecond × limitSlack`. The
client throttles itself to `(perSecond, burst)`, holding over-limit fires in a FIFO of at most `burst` messages and
dropping fires past that (`limitQueueFull`). The slack absorbs reliable retransmission releasing queued frames
together: the p99 stall under 5% bursty loss is 850 ms in simulation with an assumed RTO `[state-sync §1.3]`. The
server counts arrivals, not send times: upstream frames carry no time, and a client-stated time could not be
trusted.

### 6.2 Client-side integrity

**What it is for.** An executor reads and rewrites every Lync table, upvalue and constant on its client and can call
Lync's own API `[client-security §1.2]`. Client-side measures cannot make a forged message impossible. They price
each route an attacker can take, and every route they price is checked again on the server. The routes
`[client-security §1.4]`:

| Route | What the attacker does | Measures that price it |
|---|---|---|
| Raw sender (A0), packet injector (A7) | fires Lync's remotes or edits packets below Lync's encoder | tag (§6.2.1), replay window (§6.2.2), plus the server's shape and budget checks |
| Replayer (A1) | resends captured frames | tag (reliable), replay window (unreliable) |
| Static forger (A2) | builds frames from the published format, reused across servers or builds | tag, id permutation (§6.2.3), field-order rotation (§6.2.4) |
| Extractor (A3) | reads the key, counter and permutation from memory and encodes itself | the counter lockstep (any slip is `tagMismatch` or `frameGap`), permutation per server, rotation per build |
| API driver (A4) | calls `Net.x:fire()` from executor code | traps (§6.2.5), reachability (§6.2.6), caller probe (§6.2.7) |
| Injector of inbound frames (A6) | fires Lync's client listener with fake frames | refused-frame report (§6.2.8) |
| Raw-state reader (A5, A8) | reads replicated state from memory: ESP, radar, aim, collection bots | decoys (§6.2.11), canaries (§6.2.12) |
| Clock and timing tools | accelerates the client clock; pre-answers server prompts | clock beacon (§6.2.9), early answers (§6.2.10) |

**How each measure is judged.** By the cost it imposes on tampering against its runtime, wire, size and developer
cost; both are stated per measure. "An attacker with full memory access can defeat it" is true of every client
measure and is never a reason on its own. Nor is "a universal counter exists": Lync varies what an attacker's tool
depends on per build (§6.2.4), per server (§6.2.3) and per session (the key, §6.2.1), so a counter written against
one of them has to be rebuilt or re-run against the next. Measures aimed at the API route (traps, reachability,
decoys, canaries) are specific to each game by construction, because the developer chooses them.

**What every measure shares.** None authenticates a client, none replaces a server check, and none triggers a
consequence: each produces anomalies (§6.3). Lync never tells the client what was observed. The runtime options of
§6.2.1–§6.2.3 and §6.2.7–§6.2.10 go in the one server-only `Lync.configure` call (§6.4), and the client receives
what it needs in `WELCOME`; §6.2.11's option goes in its `decoys` call; build-time options go in `lync.toml`
(§8.2). Server-view declarations (`trap`, `refers`, `decoys`, `canary`) are never in the
shared schema, so a client reading the schema learns nothing from them.

#### 6.2.1 Keyed tag over the implicit counter (upstream reliable)

- **Protects** against raw senders, replays, injection and edits below Lync's encoder (a `FireServer` hook, a
  `raknet` send hook, a spy's edit-and-resend), and blocked calls, which show as counter gaps
  `[client-security §3.1]`.
- **Mechanism.** At a connection's first `WELCOME` the server draws a 64-bit key from an entropy-seeded
  `Random.new()`. The client counts its upstream reliable frames from 0, across namespaces, advancing the count
  before each `FireServer` and keeping it if the call raises; the count is never sent. Each frame ends with a
  16-bit tag: HalfSipHash-1-3 over the count, the frame length, the instance count and the first `tagCover` bytes.
  The server verifies at its expected count e, then at e + 1 … e + `tagLookahead`. A match at e + j accepts the
  frame and reports `frameGap` when j ≥ 1. No match drops the frame, reports `tagMismatch` and leaves e unchanged,
  so an injected frame never desynchronises the honest stream. `desyncAfter` consecutive failures with no valid
  frame between them report `desync` and send `REKEY` (at most once per `rekeyInterval`); the client switches key
  and resets its count when it handles `REKEY` and answers `REKEY-ACK` before its next reliable frame.
- **Tamper cost.** A forger must read the key from memory each session and keep the count in lockstep with Lync's
  own sends; any interleaving error is a `tagMismatch` or `frameGap`. On the generated path the tag function, key
  and counter live in the client shard, whose tag constants rotate per build (§6.2.4), so tooling that finds or
  reimplements them is rebuilt per release. An attacker who calls Lync's API produces valid tags; that route is
  priced by §6.2.5–§6.2.7.
- **Cost.** 2 B per upstream reliable frame; 10 B per `REKEY`. 3.2 µs per 64 B frame interpreted and 0.48 µs
  native; 37 and 5.5 µs per 1024 B `[probes review-redundancy halfsiphash_cost]`. A client sending 64 B frames at
  60 Hz pays about 0.2 ms/s. 16 bits accept a keyless forger with probability 2^-16 per frame, every rejection
  reported; a wider tag only matters if acceptance were authentication, which it is not.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `tagCover` | integer, B | 0–65,535 | 1024 | tag CPU per covered byte, both ends |
| `tagLookahead` | integer, frames | 0–16 | 4 | at most this many extra PRFs, failure path only |
| `desyncAfter` | integer, frames | 2–64 | 8 | — |
| `rekeyInterval` | number, s | 10–600 | 60 | 10 B per `REKEY` |

#### 6.2.2 Sequence and replay window (upstream unreliable)

- **Protects** against replays of unreliable frames, which spies with `UnreliableRemoteEvent` support and
  `raknet` hooks can resend `[client-security §1.3, §3.2]`.
- **Mechanism.** Each upstream unreliable frame carries a 12-bit sequence and the same 16-bit tag, computed over
  the sequence extended to its full value. The server extends the 12 bits to the value nearest its highest accepted
  sequence, verifies the tag (retrying the two neighbouring extensions on failure), then applies an RFC 4303
  bitmap of `replayWindow` frames: newer than the highest slides the window; inside and unseen is accepted; inside
  and seen is dropped as `duplicate`; older than the window is dropped as `staleSeq`.
- **Tamper cost.** As §6.2.1, and the attacker must also allocate sequences Lync does not use.
- **Cost.** 3.5 B per upstream unreliable frame; about 20–50 ns per frame for the bitmap, estimated
  `[client-security §3.2]`; one bitmap per player.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `replayWindow` | integer, frames | 32, 64, 128, 256 | 64 | `replayWindow` bits per player |

#### 6.2.3 Per-server id permutation

- **Protects** against byte scripts and hand-built encoders written against another server: frames they build
  decode as other definitions here, and fail the tag anyway `[client-security §3.4]`.
- **Mechanism.** At start the server draws a 32-bit seed from an entropy-seeded `Random.new()` and sends it in the
  connection's first `WELCOME`. For each namespace both ends run Fisher–Yates over ids 1…count with xorshift32
  seeded by the seed XOR the low 32 bits of the namespace's schema hash (never Roblox `Random`, whose algorithm is
  undocumented `[client-security-build §2.2]`). The permutation is the same for every player of a server, so
  encode-once and `FireAllClients` hold. Seed 0 is the identity, for golden tests through the test seam.
- **Tamper cost.** A byte-level tool must read this server's seed or table from memory in every session; on the
  generated path the table lives in the client shard, so locating it is per-build work too. Calling Lync's API
  instead leads to the routes §6.2.5–§6.2.7 price.
- **Cost.** 0 B per frame, 4 B per connection, id widths unchanged; building the table costs about 50 ns per
  definition once per namespace per server, estimated `[client-security §3.4]`.

| Option | Type | Range | Default | Cost |
|---|---|---|---|---|
| `permuteIds` | boolean | — | `true` | as above |

#### 6.2.4 Per-build field-order rotation (generated path)

- **Protects** against static encoders and decoders built against an earlier build: they stop working on the next
  release `[client-security-build §2.3]`.
- **Mechanism.** A nonzero `[build] seed` permutes each record's field order (from the seed-0 name order, §3.1)
  and, with `[rotate] tag`, replaces the HalfSipHash initialisation constants of the upstream tag with seed-derived
  ones. Ids do not rotate per build; the per-server permutation covers them. The seed travels in `HELLO`, and a
  seed mismatch is refused like a hash mismatch (§3.2). The runtime path always runs at seed 0.
- **Tamper cost.** Static tooling is rebuilt per release, or written to re-derive the layout and constants from each
  build's shard, which ties it to the shard's code shape.
- **Cost.** Zero at run time: seeded shards compile to the same opcode sequences, differing only in constants and
  the order of field writes `[client-security-build §2.3]`. Zero bytes: columns and fixed-width rows don't depend on
  field order, and the tail follows it. Developer cost: a fresh seed per release (`seed = "release"` in CI, or the
  plugin's "Prepare release"), and offline decoding of a capture needs the build's seed, which the shard header,
  the manifest and every `HELLO` carry.

| Option (`lync.toml`) | Type | Range | Default | Cost |
|---|---|---|---|---|
| `build.seed` | integer or `"release"` | 0–2^32 − 1; `"release"` draws a fresh seed per CI release | 0 (canonical) | as above |
| `rotate.fields` | boolean | — | `true`; applies only when the seed is nonzero | none at run time |
| `rotate.tag` | boolean | — | `true`; applies only when the seed is nonzero | none at run time |

#### 6.2.5 Traps

- **Protects** against API drivers who browse the schema and call tempting names (`AdminGrant`), the only wire-level
  measure Roblox's guidance calls "a very high-confidence signal" `[client-security §3.5]`.
- **Mechanism.** `Net.x:trap()` on the server view of an ordinary client-sent definition. The shared schema shows
  nothing special. Any arrival is reported as `trap` and dropped; a trap has no handler (`connect` or `handle` on
  it is a caller error). In Studio the arrival also prints one line naming the trap.
- **Tamper cost.** The attacker must read the game's client code to learn which definitions honest code fires, per
  game.
- **Cost.** One id; it adds an id bit to the namespace only when the count crosses a power of two. Developer cost:
  choosing plausible names.

#### 6.2.6 Reachability (generated path)

- **Protects** against API drivers firing a client-sent definition that no client code fires: every such
  definition acts as a trap without being declared `[client-security-build §4.2]`.
- **Mechanism.** The build scans the project's client-reachable scripts (and `Packages/`) for references to each
  client-sent definition: every `view.name` reference counts. Any escape of a view or namespace table (a computed
  index, passing it as a value, storing or returning it) marks the namespace incomplete, and nothing is inferred for
  it; the report says so. The server shard holds the set of referenced definitions. A message of any other
  client-sent definition is delivered and reported as `unreachable`.
- **Tamper cost.** The attacker must fire only what honest client code references, learned per game.
- **Cost.** One table index per message on a definition the decoder already looked up; no bytes; build time.
  Developer cost: code outside the project (an asset loaded at run time) is outside the guarantee.

| Option (`lync.toml`) | Type | Range | Default | Cost |
|---|---|---|---|---|
| `check.reachability` | boolean | — | `true` | as above |

#### 6.2.7 Caller probe (client)

- **Protects** against API drivers whose calls come from executor threads or executor chunks. Executor threads run
  at identity 8 by default; game scripts run at 2, and modules at their requirer's identity
  `[client-security §1.2, §2.1]`. Honest client code has no `loadstring`, so its functions' sources are the game's
  own scripts.
- **Mechanism.** Each client `fire` or `invoke` is probed with probability `callerProbe.share`, at most
  `callerProbe.maxPerSecond` probes per second. A probe does two things:
  - **identity:** reads, in `pcall`, one member that fails at identity 2 and succeeds at identity 8; success
    counts the call as elevated;
  - **source** (generated path): reads `debug.info` source of the first frame outside Lync and checks it against
    the build's list of client scripts that reference the definition (§6.2.6), after mapping Roblox's clones of
    starter containers to their copies (`StarterPlayerScripts` to `PlayerScripts`, `StarterCharacterScripts` to
    the character, `StarterGui` to `PlayerGui`, `StarterPack` to `Backpack`); no match counts the call as foreign.
    It is skipped for incomplete namespaces.
  Counts travel in `REPORT` and are reported as `callerIdentity` and `callerSource`. Which member the identity
  probe reads is chosen per build from the members Studio confirms in milestone 5.
- **Tamper cost.** The attacker must lower its thread identity before calling, and load its code under the chunk
  name of a script the build lists for that definition (read from this build's shard), or patch Lync. A script
  that does neither reports itself with probability 1 − (1 − share)^calls: 64% after 20 calls and 99.4% after 100
  at the default share. A patched Lync stops sending the counts, which the server cannot tell from an honest
  client, so the measure prices naive drivers, not careful ones.
- **Cost.** The honest path is the failing `pcall`: 2.2–3.3 µs per identity probe interpreted
  `[client-security §2.2]`, and 57–72 ns for the source read; at the default maximum, at most 34 µs per second.
  Wire: a `REPORT` of a few bytes when counts change. Developer cost: in Studio, the command bar and plugins run
  elevated and from foreign chunks, so their fires are counted. Unverified, measured in milestone 5 (§11): a
  suitable member and its cost on devices; whether Roblox logs a capability failure caught by `pcall`; and that
  honest sources follow the clone mapping above. If the last fails, the source check is removed.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `callerProbe.share` | number, fraction of calls | 0–1 | 0.05 | probes per call |
| `callerProbe.maxPerSecond` | integer, probes/s | 0–60 | 10 | ≤ 3.3 µs per probe on the client |

#### 6.2.8 Refused-frame report (client)

- **Protects** the game's knowledge of injection into a client's own view: frames fired into Lync's client
  listener by `firesignal` or `getconnections` that are not canonical are refused by the client decoder
  `[client-security §1.4 A6]`.
- **Mechanism.** The client decoder is as strict as the server's (§4.6). Each downstream frame it refuses is
  counted, and counts travel in `REPORT`, reported as `clientRefusedFrame`.
- **Tamper cost.** The injector must build canonical frames for this build and server, or suppress the report by
  patching Lync.
- **Cost.** None beyond decode, which is already strict; `REPORT` bytes only when it fires. The only honest cause is
  a Lync bug, in which case the client also lost a server frame.

#### 6.2.9 Clock beacon (opt-in)

- **Protects** against tools that accelerate the client's local clock. `GetServerTimeNow` never steps back and
  stays within 0.6% of the local clock, so an accelerated client drifts against the server
  `[client-security §4 T1]`.
- **Mechanism.** The client sends `BEACON` at most once per `clockBeacon` seconds. Per player the server keeps, per
  5 s window, the minimum of arrival time − stamp, and every 5 s fits a Theil–Sen slope over the last
  `clockWindow` seconds of minima. `clockRate` is reported when the slope exceeds `clockRateLimit` in `clockConfirm`
  consecutive fits. The first 30 s after join are ignored (time sync settling), and an arrival gap over 2 s
  restarts the estimate (device sleep).
- **Tamper cost.** The attacker must keep Lync's stamps on unaccelerated time, which means patching Lync or its
  clock read.
- **Cost.** About 4 B per beacon (run header and 16-bit stamp); one 12-point fit per 5 s per player. Default off
  until the Roblox loss and jitter measurements (§11) confirm the noise estimate on mobile.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `clockBeacon` | number, s | 0 (off) or 0.5–10 | 0 | about 4 B per beacon |
| `clockRateLimit` | number, fraction | 0.01–0.5 | 0.03 | — |
| `clockWindow` | number, s | 30–600 | 60 | — |
| `clockConfirm` | integer, fits | 1–10 | 3 | — |

#### 6.2.10 Early answers

- **Protects** server-asked requests against answers sent before the ask could arrive: a bot that predicts a timed
  prompt wins by up to one round trip `[client-security §4 T3]`.
- **Mechanism.** For each server `invoke`, Lync records the send time and samples `Player:GetNetworkPing()`. An
  answer arriving sooner than `earlyAnswerFactor` × the smallest ping sampled for that player in the last 10 s is
  delivered and reported as `earlyAnswer`. An answer for a slot not in flight at all is `unknownReply`.
- **Tamper cost.** The attacker must answer after receipt, through Lync's handler, giving up the round trip.
- **Cost.** One clock read and one ping read per server ask; no bytes. Honest cause: `GetNetworkPing` is smoothed
  and can lag a sudden improvement.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `earlyAnswerFactor` | number, fraction of the minimum ping | 0 (off) to 1 | 0.5 | as above |

#### 6.2.11 Decoys

- **Protects** against raw-state readers: ESP, radar, aimbots and collection bots that act on records the honest
  UI never shows `[anticheat-design §2]`.
- **Mechanism.** `Net.fighters:decoys(behaviour, { maxPerViewer = n })` on the server view. Each state tick, Lync
  calls `behaviour(viewer, tick)` for each viewer; it returns `{ [Key]: Record }` or `nil`. Lync diffs the result
  against the viewer's previous decoys and sends adds, updates and removes into that viewer's own sections only,
  exactly as catch-up adds travel, with slots from the same allocator. Nothing marks a decoy on the wire or on the
  client. A returned key equal to a live record's key is a caller error. `Net.strike:refers("target", "fighters")`
  declares that a client-sent field holds keys of a collection; a delivered message whose referenced key is a decoy
  sent to that player is reported as `decoyReferenced`.
- **Tamper cost.** A cheat must reproduce the game's notion of visibility to filter decoys out, per game and per
  behaviour. Two colluding accounts comparing key sets can spot a decoy in a collection where every viewer sees
  every record; where audiences or `interest` already make viewers' record sets differ, a decoy is one more such
  difference.
- **Cost.** Per decoy: the bytes of one record at its update rate, sent to one viewer and encoded for that viewer
  alone; one behaviour call per viewer per state tick. Developer cost: the behaviour must place decoys where honest
  rendering and honest logic never use them; honest aim assist or "target everything" code produces honest
  `decoyReferenced` facts.

| Option | Type, unit | Range | Default | Cost |
|---|---|---|---|---|
| `maxPerViewer` | integer, records | 1–16 | 1 | as above, per decoy |

#### 6.2.12 Canaries

- **Protects** against raw-state readers that send hidden values back, and attributes leaks: a canary found outside
  the game names its record and server `[anticheat-design §2.2, §6]`.
- **Mechanism.** `Net.inventory:canary("promoCode")` on the server view marks a top-level `t.string` or `t.buffer`
  field of a collection. On each add Lync fills it with min(16, maxBytes) random characters from `[A-Za-z0-9]`
  (strings) or random bytes (buffers), unique per record per server; `set` or `patch` of it is a caller error.
  Every inbound string or buffer value from a player is looked up among the canary values sent to that player; a
  hit is delivered and reported as `canaryEchoed`.
- **Tamper cost.** The reader must learn, per game, which fields the UI never shows and never send them.
- **Cost.** The field's bytes in each add (it never changes after); one hash lookup per inbound string or buffer
  value; one set entry per canary value a player was sent. Developer cost: the UI must never show or send the
  field.

#### 6.2.13 Refused on the client

Each is re-judged in `v5-changes.md` under the rule above; the reason that still holds:
- **Hook and environment checks** (`debug.info` "[C]" tests, arity, error text, stack-walking `getfenv`): the
  standard tools already pass them, since spies wrap their hooks in `newcclosure` by default and hook in place, so
  they price nothing; they have a false-positive history; and `getfenv` deoptimises every script it touches and is
  barred from the Creator Store `[client-security §2.2, §5]` `[client-security-build §6.1]`.
- **Downstream tags and a client replay window:** they protect only the view of the client that is tampering, and
  cost the server a PRF per recipient per frame and every `FireAllClients` `[client-security §3.1]`.
- **Masking or whitening frames:** everything it hides is readable through the typed API, whose names game code
  fixes so no generation can vary them; every forge it blocks the tag already blocks; it costs CPU per byte on both
  ends and +62% to +272% bytes on the string tail `[client-security §3.7]`.
- **Per-session upstream id shuffling:** the per-session read it forces is the same memory read the tag key
  already forces, in the same pass; it costs a decode table per player `[client-security §3.4]`.
- **Generated hidden trap ids:** they arrive as unknown ids, already refused and reported as `malformed`
  `[review-redundancy 14]`.
- **Per-viewer slot permutation** as a decoy companion or watermark: keys travel in adds, so a key comparison finds
  what the slot permutation hides; it costs per-viewer slot encoding `[anticheat-design §2.2, §6]`.
- **Low-order watermarks in quantized values:** visible jitter, and rounding removes them `[anticheat-design §6]`.
- **Per-player shard variants, codecs scattered into game scripts, obfuscators, darklua renaming, script
  self-attestation:** platform and distribution limits, recorded per measure in `v5-changes.md`.

### 6.3 Anomalies

**The event.** `Lync.observe(fn)` returns a connection. Observer events are a discriminated union on `kind`:
`frame` (bytes sent or received per definition, for the inspector) and `anomaly`, which covers every refusal and
every observed irregularity, on both sides. An `anomaly` is discriminated on `reason`, so `evidence` narrows per
reason in Luau and TypeScript:
- `player`: the sender on the server (the recipient for `missedFlush`); the local player on the client;
- `reason`: one of the exact triggers below;
- `namespace?` and `definition?`: names from the receiving side's own schema, never from client bytes;
- `count`: occurrences this event stands for; `first` and `last`: `GetServerTimeNow()` of the first and last;
- `evidence`: frozen, numbers only; `lane` in evidence is 0 for reliable and 1 for unreliable.

Lync takes no action beyond the one listed, which is the same for any bad input: it drops the frame or message, or
delivers and reports. It never kicks, bans, throttles beyond declared limits, delays, or tells the client, following
Roblox's guidance to be proportional and reversible and never to ban on client-side detection alone
`[client-security §6.4]`. Nothing is weighed, scored or labelled; "known honest causes" are documentation.

| Reason | Exact trigger | Action | Evidence | Known honest causes |
|---|---|---|---|---|
| `overBudget` | a frame arrives when its lane's frame bucket holds < 1 token or its byte bucket < its charge (§6.1 step 2) | frame dropped | `lane`, `bytes`, `instances` | a stall longer than the bucket's burst; a budget set below the game's traffic |
| `malformed` | a §4.6 rule is broken | frame refused | `lane`, `rule` (1–9) | a Lync encoder or decoder bug |
| `wrongDirection` | an id arrives from the side its `from` excludes | frame refused | `lane` | none: direction is in the schema hash |
| `wrongLane` | an id arrives on a lane it isn't declared for | frame refused | `lane` | none: lane is in the schema hash |
| `tagMismatch` | a tag fails at e … e + `tagLookahead` (§6.2.1, §6.2.2) | frame dropped | `lane`, `expected` | a Lync bug, which shows as repeated `desync` instead |
| `frameGap` | the tag matches at e + j, j ≥ 1 | frame accepted | `skipped` (j) | `FireServer` raising on the client |
| `desync` | `desyncAfter` consecutive tag failures with no valid frame between | `REKEY` sent unless one was sent within `rekeyInterval` | `failures`, `rekeySent` (0 or 1) | unknown engine reconnect behaviour |
| `duplicate` | an upstream unreliable sequence already marked in the window | frame dropped | `seq` | transport duplication (unverified whether Roblox duplicates) |
| `staleSeq` | an upstream unreliable sequence older than the window | frame dropped | `seq`, `behind` | reordering deeper than `replayWindow` |
| `impossibleAck` | an ack's sequence is newer than the newest downstream unreliable frame sent to the player, or its `received` bits name a frame never sent | ack ignored, frame kept | `seq` | none |
| `repeatedHello` | a `HELLO` after the namespace's first | ignored | `hashChanged` (0 or 1) | none: a client sends one `HELLO` per namespace |
| `trap` | a message of a trap definition arrives | message dropped | — | the developer firing it in Studio (printed there) |
| `unknownReply` | an `answer` for a slot not in flight | message dropped | `slot` | none |
| `earlyAnswer` | §6.2.10's trigger | delivered | `roundTrip`, `minPing` (s) | smoothed ping lagging an improvement |
| `overLimit` | the server `limit` bucket is empty | message dropped; an ask is answered `rejected` | `perSecond`, `burst` | network stalls longer than `limitSlack`; a misdeclared `limit` |
| `unknownEnum` | a Roblox enum `Value` the receiving engine lacks | message dropped | `value` | engine version skew during a rollout |
| `instanceMissing` | a required instance arrives `nil` | message dropped | — | streaming |
| `instanceClass` | an instance fails its `IsA` check | message dropped | — | the instance was replaced between send and receipt |
| `validateFalse` | a server `validate` returns `false` | message dropped; an ask is answered `rejected` | — | the game's own rule |
| `validatorError` | a server `validate` throws | as `validateFalse` | — | a bug in the validator |
| `unreachable` | §6.2.6's trigger | delivered | — | client code outside the project |
| `callerIdentity` | a `REPORT` counts elevated callers (§6.2.7) | none | `probes`, `elevated` | Studio command bar and plugins |
| `callerSource` | a `REPORT` counts foreign callers (§6.2.7) | none | `probes`, `foreign` | Studio command bar and plugins; scripts cloned outside the starter containers |
| `clientRefusedFrame` | a `REPORT` counts refused downstream frames (§6.2.8) | none | `frames` | a Lync bug |
| `clockRate` | §6.2.9's trigger | none | `slope`, `fits` | none above the 0.6% clock contract |
| `decoyReferenced` | §6.2.11's trigger | delivered | `sentAgo` (s) | honest aim assist or "target everything" code |
| `canaryEchoed` | §6.2.12's trigger | delivered | `sentAgo` (s) | game UI that shows or sends the field |
| `missedFlush` | under the manual scheduler, data for a player pending for more than 2 `PostSimulation` steps | none | `frames` | a custom tick slower than the frame rate |
| `holdFull` | on the client, a reliable fire before `WELCOME` past 65,536 held bytes | fire dropped | `bytes` | a client firing heavily during join |
| `limitQueueFull` | on the client, an over-limit fire when the throttle FIFO holds `burst` messages | fire dropped | `burst` | game code firing faster than its declared `limit` |
| `suppressed` | the window closes for a player with occurrences past a delivery cap | none | one number per suppressed reason: its occurrence count | — |

The `checks` extension adds `constraint` (§7.2).

**Delivery limits.** These protect the server from a flood of events; they never hide an occurrence:
- **Coalescing.** Events are keyed by (player, reason, definition). The first occurrence in a window emits
  immediately; later ones are counted and emitted once, with `count`, when the window of `observe.window` seconds
  closes.
- **Caps.** At most `observe.perPlayerEvents` events per player per window, and `observe.serverEvents` across the
  server. Occurrences past either cap are still counted per player and reason, and at window close each player with
  any gets one `suppressed` event carrying the counts; `suppressed` events are exempt from the caps, so at most one
  per player per window. State is released when the player leaves.

### 6.4 Configuration

All runtime settings live in one server-only call; the client receives what it needs in `WELCOME`. It may be called
before or after first use; options carried in `WELCOME` are fixed once the first `WELCOME` is sent, and changing
them later throws.

```luau
-- ServerScriptService, server only; never in shared code or lync.toml
Lync.configure({
	stateRate = 20,
	stateBudget = 16000,
	clockBeacon = 1,
	observe = { window = 30 },
})
```

The integrity options are defined with their measures in §6.2 (`callerProbe` is a table, as `observe` is). The
rest:

| Option | Type, unit | Range | Default | Cost and meaning |
|---|---|---|---|---|
| `stateRate` | Hz | 10–60 | 20 | state ticks per second (§5.1); scheduler CPU scales with it |
| `stateBudget` | B/s per player | 4,000–64,000 | 16,000 | ceiling on bytes per player, against which `:newest()` rows are scheduled (§5.4) |
| `stateFloor` | fraction of `stateBudget` | 0–1 | 0.25 | share kept for `:newest()` rows when events and reliable state use the budget |
| `inbound.reliable.frames` | `{ perSecond, burst }`, frames | 1–1000, 1–10,000 | 120, 240 | an honest client sends one reliable frame per flush (60/s) plus splits |
| `inbound.reliable.bytes` | `{ perSecond, burst }`, B | 1,024–1,048,576 each | 32,768, 65,536 | `burst` must be at least 16,384 (the upstream frame cap) |
| `inbound.unreliable.frames` | `{ perSecond, burst }`, frames | as above | 240, 480 | |
| `inbound.unreliable.bytes` | `{ perSecond, burst }`, B | as above | 32,768, 65,536 | |
| `limitSlack` | s | 0–10 | 2 | extra server bucket capacity, `perSecond × limitSlack` |
| `observe.window` | s | 5–600 | 30 | coalescing window (§6.3) |
| `observe.perPlayerEvents` | events per player per window | 1–64 | 16 | |
| `observe.serverEvents` | events per window | 16–4096 | 256 | |

Inbound defaults are judgement anchored on one frame per flush; they are revisited with the Roblox measurements in
§11. Build-time options live in `lync.toml` (§8.2).

## 7. Extensions

Extensions plug into fixed seams. A seam with nothing registered compiles out, so no branch is paid per message.
Each is specified to principle 5 (every option with type, unit, range, default and cost) before it is built.

### 7.1 Seams

- **Codecs.** `t.custom({ ... })` declares a leaf codec through the bit writer and reader: `encode(w, value)`,
  `decode(r)`, `maxBits` (or `maxBytes` for tail data), a Luau type and a TypeScript type name for codegen, and a
  name and version that go into the hash. `t.convert(base, decode, encode)` transforms an existing codec, typed both
  ways (a `UDim` from two numbers).
- **Runtime:** `transport` (remotes by default; in-process for tests), `scheduler` (frame or manual; the row selector
  is replaceable, for `interest`), `clock`, `roster` (players), the observer, and a test seam that pins the
  integrity key and the permutation and build seeds.
- **No middleware.** Rejection is `validate`, observation is the observer, and transformation belongs in game code.
  Draft 1's `onReceive` was a fourth rejection path outside the pipeline `[review-redundancy 8]`.

### 7.2 First-party extensions (milestone 7)

Each is opt-in and lists what it took from the core:

- **`interest`:** per-viewer relevance with cells and hysteresis, distance priority with the accumulator and
  40-bucket pass, ownership (`owner`, an owner boost, owner-only fields), per-field rate caps `:maxHz(hz)` rounded to
  a divisor of `stateRate`, and look-ahead reveal `[state-sync §7, anticheat-design §1]`.
- **`acked`:** `:newest()` rows predicted with Unity's guarded linear predictor against each viewer's acked
  baselines, values from a shared per-tick history, for one collection (§5.3).
- **`inputs`:** client input streams: every input since the last ack, delta-coded, capped at a declared number of
  copies; the upstream unreliable sequence doubles as input index and the downstream frames carry its newest
  value; a server jitter buffer with a declared depth in state ticks `[state-sync §4.1]`.
- **`rewind`:** lag-compensated hit verification over rewind rings, keyed by the client's perceived tick from its
  newest ack.
- **`checks`:** declared constraints (`within`, `monotonic`, `maxTotal`) with syntax, units and scope, each with a
  failure policy of `drop` or `clamp`; every failure is reported as `constraint` with the policy in its evidence,
  whichever policy applies. The `:claim()` marker declares a client-sent field a claim (unmarked fields are
  inputs), and a definition with claim fields must have `validate`, which is where the claim is checked
  `[anticheat-design §3.2, §4.2]`.
- **`strings`:** interning and templates (§4.5).
- **`interpolation`:** the client buffer: delay `max(2/rate, 0.1 s) + 2 × jitter`, extrapolation capped at 0.25 s
  `[state-sync §6.3]`.
- **`telemetry`:** schema-marked feature streams exported in batches to the developer's backend.

| client shard, server shard per namespace | Luau, readable, MIT header, each definition commented with its schema origin | the game |
| type declarations | `.d.ts` | roblox-ts |
| `manifest.json` | JSON: definitions, seed, hashes, ids, worst-case sizes, reachability | CI, the server shard (facts compiled in) |
| `report.md` | Markdown rendered from the manifest | developers |

The inspector and `lync replay` decode frames through the planner, given the build seed from the shard or the
captured `HELLO` and the server's permutation seed from the capture, so there is no debug map: it would be
reproducible from the same three inputs `[client-security-build §5.6]`.

### 8.2 `lync.toml`

TOML with a published JSON Schema, read the same way by the CLI and the plugin `[client-security-build §5]`:

```toml
#:schema https://lync.dev/schema/lync.toml.json
format = 1

[build]
seed = 0                        # 0 = canonical; "release" = a fresh seed per CI release (§6.2.4)

[[namespace]]
schema = "src/shared/Net/schema.luau"
client = "src/shared/Net/client"
server = "src/server/Net"
dts = "types/net.d.ts"          # optional

[rotate]
fields = true                   # applies only when seed != 0
tag = true                      # applies only when seed != 0

[check]
rawRemotes = "warn"             # "off" | "warn" | "error": client code touching RemoteEvents directly
reachability = true             # §6.2.6

[output]
manifest = "build/lync-manifest.json"
report = "build/lync-report.md"
```

Studio-only projects keep the same TOML text in a plugin-managed `StringValue` in ServerStorage; the vendored TOML
parser uses no `const`, whose availability in Studio scripts is unverified.

### 8.3 Hosts

- **CLI:** `lync build`, `lync watch`, `lync check` (milestone 3); `lync diff <old> <new>` (flags breaking wire
  changes) and `lync replay <capture>` (milestone 6). `watch` stays in milestone 3 because, outside Studio-only
  projects, it is the only regenerate-on-edit path, and without it every schema edit trips the stale-shard error.
- **Studio plugin:** schema diagnostics in the script editor, the network inspector, and a "Prepare release" action
  that writes a fresh build seed. It regenerates on schema edit only when the configuration lives in its
  `StringValue`; with a filesystem `lync.toml`, `lync watch` is the one writer, so Rojo never syncs two generators'
  output. No plugin can hook publish or save `[client-security-build §1.4]`.
- **CI:** `lync check` fails on stale shards and type tests; release builds run with `seed = "release"` and publish
  through Open Cloud `[client-security-build §1.8]`.

### 8.4 Inspector and profiler

- **Studio inspector:** bytes per definition and per player per second, live decoded frames, budget, and anomalies,
  from the observer. It can capture and replay.
- **PacketProfiler adapter:** registers Lync as a traffic layer, so frames show decoded in the community's inspector
  `[landscape §5]`.
- **MicroProfiler labels** are opt-in.

### 8.5 Repo tooling

Never shipped: StyLua and selene with a Lync `std` file (which also lints games' use of Lync, §3.2); Moonwave;
Markdown guides; GitHub Actions; Python for simulations and capture analysis.

    asserting that each anomaly fires on exactly its trigger and never for the honest client;
  - type tests of consumer code under both solvers, for Luau and TypeScript.
- **In-engine tests** in Studio or through Open Cloud Luau execution (unverified for this use), for what only Roblox
  can show: remotes, budgets, compression and the caller probe.
- **Benchmarks:** random-per-frame traffic from the four game models; CPU interpreted (client) and native (server);
  bytes before and after an engine-compression estimate; results per commit as JSON; and a public comparison
  against Blink, Zap and ByteNet on the community's benchmark, which v5 has to win `[landscape §1.7]`.

## 12. Deliberately dropped

Client-side measures refused or kept out are in §6.2.13.

- **Event `newest` option:** latest-wins without repair is the worst measured scheme (342 ticks stale
  `[state-sync §1.7]`); a singleton collection with `:newest()` replaces it.
- **`timestamped` and the sub-tick offset:** the frame tick dates downstream messages and the newest ack dates
  upstream ones, at no cost per message.
- **Runtime demotion of oversized unreliable items:** the planner refuses them, so demotion was dead code.
- **`report.json` and `debugmap.json`:** `manifest.json` is the machine-readable file, and the planner reproduces
  the debug map (§8.1).
- **The roblox-ts transformer:** a second schema language.
- **Compiler plugins and the `rans` extension:** no plugin exists to design the seam against; trained entropy coding
  gains 2–10% `[compression §6]`.
- **Suspicion weights, scores, decay and `Lync.suspicion`:** Lync reports facts; weighing them is the game's code
  (§6.3).
- **Quiet-mitigation hooks** (`rejectClaims`, `inboundDelay`): consequences are the game's code, built on the
  observer.
- **The unreliable-event deadline:** events are never budget-deferred, so they never wait.
- **`:initial()`:** a reliable field that is never changed after the add already costs nothing after it.
- **Draft 1's settled points that still stand:** no audience-by-field shortcut (§5.5); `limit` lives in the shared
  schema so honest clients throttle themselves (§3.4); the primitive is `collection` ("set" clashes with `:set()`,
  "store" suggests DataStore, "replica" clashes with ReplicaService, "state" is too vague).

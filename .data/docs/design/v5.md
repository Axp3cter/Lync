## 0. What v5 is

Typed buffer networking for Roblox, in Luau and roblox-ts:
- **One schema, two sides.** A schema written once in Luau declares every event, request and replicated
  collection.
- **A compiler** turns it into straight-line codecs and a typed API per side, in Luau and `.d.ts`.
- **A runtime** batches everything into at most one frame per player per lane per flush, over one remote pair.
- **The server owns the truth.** Every inbound byte is budgeted, decoded strictly, rate-limited and checked.
- **The client is defended too.** Client-side integrity measures make tampering cost work that has to be redone per
  build, per server or per session, and report what they observe to the server.
- **Lync reports facts, never verdicts.** What it observed reaches game code as typed facts with exact triggers
  and numeric evidence; what to do about them is the game's code.

The same schema also runs with no build step: the same API and wire format, with layouts varied per server (§3.2),
and exact types only under the new type solver. Its interpreter, as milestone 1 built it, encodes a row 1.7–1.9x
slower than a generated encoder on the same bit writer and 3.2–3.9x slower than the generated inline form
interpreted (4.5x to decode a 3-field row), and 2.4–2.9x slower native `[generation-methods M14]`
(`probes/generation-methods/runtime_path.out`).

## 1. Principles

When two conflict, the earlier one wins.

1. **Server authority.** Nothing a client sends is trusted. Client-side measures raise the cost of tampering and
   report what they observe; they never replace a server check.
2. **Correct before fast before small.** Byte savings that cost correctness are refused. Fast paths are measured.
   For a security measure, runtime, wire and size cost is a trade-off, never a veto: each measure states what it
   protects and what it costs, and is adopted when the protection is worth the cost. Where the cost matters, an
   option with a stated range and cost controls it, rather than the measure being left out.
3. **Exact types on both Luau solvers and roblox-ts.** No payload, handler, reply or patch is `any`. Generated
   shards meet this on both solvers; the no-build path under the new solver only (§3.2).
4. **One way to do each thing.** One naming convention, one error model, one shape for analogous features.
5. **Precise, never simplified.** No presets, tiers or labels in place of definitions. Every option has a name,
   type, unit, range, default and cost; every fact has an exact trigger and its known causes on an unmodified
   client.
6. **Declarative formats for declarations, Luau for behaviour.** Build configuration is TOML, generated artefacts
   are JSON, and handlers, validators and runtime settings are Luau. The schema is Luau because the no-build path
   needs it as a live value.
7. **The library comes first.** Tooling and extensions build on stable seams of a working runtime and compiler.
8. **Every claim is measured or marked unverified.** Roblox-only claims are listed in §10 until measured.

**Unmodified client:** a client running this build's Lync runtime and shard as published, whose game code reaches
Lync only through its API. The design uses this term wherever it describes what a client can produce; it never
classifies players. A client that is not unmodified is a *modified client*; the term names the code it runs, not
the person.

## 2. Architecture

```
schema module (Luau) ──evaluated by──► planner (pure Luau) ──► IR: definitions, layouts, ids, limits, hash
                                          │                       │
                                          ├─► runtime interpreter ├─► codegen ──► shards (Luau), .d.ts, manifest.json
                                          ▼
runtime: wire · plan · codec · transport · session · sched · api
```

- **One planner**, shared by the runtime, the CLI and the Studio plugin, so the two paths cannot disagree on a bit
  `[client-security-build §1.1]`. The planner takes per-record layout seeds as input: the build draws them from
  its `rotationSeed`, the runtime path from its per-server layout seed (§3.2). A differential test encodes random
  values through both paths and compares bytes, at seed 0 and at fixed nonzero seeds with field order, code offsets
  and generated traps on, passed through that same input; it also checks that each woven site's bytes decode to the
  value the generic encoder would send `[generation-methods M14, M16]` `[codecs-in-scripts §4.3, §7.3]`.
- **Decision: the interpreter's form.**
  - **Problem.** The runtime path's interpreter (`Rows.write`/`Rows.read` over the IR) is 3.2–3.9x the generated
    inline form to encode, interpreted; a faster form is a second code path the differential test must also cover.
  - **Options:** the interpreter as built; a closure tree built from the IR (1.3x a generated encoder on the same
    writer for rows with strings, optionals or arrays); closures with bit positions fixed at plan time for
    fixed-width rows (1.45–1.72x the inline form to encode interpreted), at 0.9–2.0 µs and 1.5–2.9 KB more set-up
    per definition per layout `[generation-methods M14]`.
  - **Choice: the interpreter as built.** At the busy traffic model's 70 upstream messages a second (§4.1), the
    fixed-position closures save (742 − 333) × 70 = 29 µs/s of client CPU on a 3-field row (derived from
    `runtime_path.out`), against a second encoder form per codec kind. A game for which that matters runs the
    generated path, which is 1.7–1.9x faster again.
- **Packages:** `lync` (runtime and planner; Wally, pesde, Creator Store); the `lync` CLI (the compiler core under
  a Rust/mlua host, with Lune as the fallback and first host); the Studio plugin; `@lync/core` on npm.
- **Runtime layers**, each depending only on earlier ones: `wire` (bit I/O, integer codes, quantizers, column
  coder) → `plan` → `codec` → `transport` (remotes, frames) → `session` (handshake, tag, acks, requests) →
  `sched` (flushing, ticks, budgets) → `api` (views).

## 3. Schema and API

### 3.1 Decision: how a schema is written

- **Problem.** The schema must be readable, give exact types, run with no build, and be readable by a compiler.
- **Options:** a separate IDL (Blink, Zap: a second language and a mandatory regenerate step, the top complaint
  `[landscape §1]`); builder chains (v4: modifiers mutated or copied, types collapsed at records `[v4 §6, §8]`);
  **declarative Luau tables: definitions are option tables, records plain tables, codecs constructor calls.**
- **Choice: declarative tables.** Records need no wrapper, and the compiler reads the evaluated value, so helper
  functions and loops in the schema work. The planner checks option names: an unknown key throws
  `unknownOption` with the definition's line. The type checker sees only `from` exactly
  (`D & { from: "client" | "server" }`); other option literals widen `[probes review-1 r1, r2, r5]`.
- **Order comes from names.** Dictionary iteration order is unspecified (`probes/design-2/field_order.out`) and
  the planner sees only the value, so record fields and union variants are ordered by name (bytewise). Lists
  (`t.enum({ ... })`) keep list order. Rotation (§3.2) permutes record field order only; union variants and enum
  items keep their order and vary only by code offsets, since permuting the indices of a sequential 32-item column
  costs 137 → 331 bits and an offset at most its first row's residual (§4.3) `[generation-methods M3]`
  (`v5-integrity.md` §2).

### 3.2 Decision: where exact types come from

- **Problem.** Type functions infer exact types only under the new solver; Roblox and luau-lsp default to the old
  one, where type functions degrade silently to error types `[landscape §3.3]` `[probes T7]`.
- **Options:** type functions only (silent error types for most users); generated code only (no runtime path);
  **both, with generated code primary.**
- **Choice: both.**
  - **Generated path.** Game code requires the shard for its side; the shard is the API, with concrete types that
    narrow on both solvers `[probes review-1 r4]`.
  - **Runtime path.** `Lync.server(schema)` / `Lync.client(schema)`, typed by type functions in a `--!nocheck`
    types module. Exact under the new solver `[probes review-1 pipe/]`, except list-form enums (widen to
    `string`, `[probes T3]`) and Roblox enums (`Codec<unknown>`, `[probes review-2 t2]`).
  - **Type functions never call `error()`** on input derived from user values: an `error()` there crashes
    luau-analyze and luau-lsp through the side-selecting view `[probes review-2 crash_r1lib]`. They return a marker
    type that names the problem, such as `"[Lync] expected a codec at chat.data"` `[probes review-2 crash_fix]`.
  - **What the build proved about these types** (`f1fbfd7:src/types.luau`, `f1fbfd7:test/types/`; luau-analyze
    0.740 and luau-lsp 1.70.1):
    - `from` is typed `{ read from: "client" | "server" }` in `D & { read from: … }`. The new solver keeps the
      literal; the old solver drops `read` fields there, sees `D & {}` and accepts the literal instead of widening it
      to `string`.
    - Sides are picked with the built-in `index<{ client: …, server: … }, From>`, not a type function. A
      type-function selector given side tables that hold error types (an unknown `Vector3`, say) crashed
      luau-analyze (exit 139) at the first method call through a view.
    - The codec brand is `read ["[Lync] value"]: T` (§3.3); with `_value`, a record field named `_value` was taken
      for a codec.
    - The old solver rejects type functions and `read` fields, so the types module is `--!nocheck` and
      `--!nolint UnknownGlobal`. It also can't check exhaustiveness with a `local unhandled: never` closure, so
      every kind dispatch is covered by a test that runs each codec kind through it.
  - **No `read` modifier in any type game code sees.** Shards and every type Lync exports for game code (facts,
    results, field handles, telemetry batches, challenge handles) are plain records. Under the old solver a `read`
    field is an error in a checked module ("read keyword is illegal here") and is dropped when the type is imported
    from a `--!nocheck` module, so reading it fails with "Key not found" (luau-analyze 0.740,
    `probes/design-3.6/typing.out`, `read_modifier`, `read_consumer`). Values Lync hands out are immutable by
    `table.freeze` where the text says frozen, not by their type. The `D & { read from: … }` trick and the codec
    brand above stay: both live in the `--!nocheck` types module behind the runtime path, which is exact only under
    the new solver anyway, and the `from` trick relies on the old solver dropping the field.
  - **Selecting by a string literal.** An intersection of function types selects its overload from a string-literal
    argument on both solvers. Under the new solver the selection fails when another argument is a table literal
    holding a string literal or an unannotated function, even when the call is correct (luau-analyze 0.740,
    `overloads_options`); a call whose only arguments are the literal and values of already-known types selects
    correctly on both. So no generated or runtime-path signature overloads on a literal and takes an option table
    in the same call: server declarations about one field go through a field handle (§3.4).
  - **Degradation is stated where it can be detected.** `lync check` reports `solverOff` at each call site of
    `Lync.server(` or `Lync.client(` in the scripts it scans, unless `lync.toml` sets `check.solverOff = "off"`;
    the property itself is `NotScriptable`, so no tool can read it `[review-2 M11]`.
- **What both paths share on the wire.** One frame format and one planner. Layouts differ by what the planner is
  given:
  - **Generated path:** a build's private 64-bit `rotationSeed` (manifest only) draws per-record field order, code
    offsets and the tag's constants; the shard carries the public 32-bit `buildId` in its place
    (`v5-integrity.md` §2) `[generation-methods M1]`.
  - **Runtime path:** a per-server layout seed draws the same three, by `layout.vary` below.
  - **Same bytes.** At identity layouts (the identity build, `buildId` 0 and `rotationSeed` 0; `layout` 0) both
    paths write identical bytes for one schema; the differential test (§2) checks that and the nonzero cases.
  - **Mixed paths decode only at one layout.** `HELLO` carries the `buildId`, and the runtime path sends 0. So a
    shard from a real build meeting the runtime path differs in `buildId` and is refused as `schemaMismatch`
    (`seedDiffers` 1); an identity-build shard meeting a runtime-path server that varies its layout refuses the
    namespace itself on `layout` 1 (§4.5). Nothing decodes under a layout it doesn't hold.
- **Decision: layouts on the runtime path** `[generation-methods M14]` (reopens R5).
  - **Problem.** The runtime path has no build, so nothing private exists on the client: any layout value reaches
    it in `WELCOME` or is derived from what `WELCOME` carries, where a packet tool reads it and Lync's own planner
    applies it. At seed 0 every no-build game shares one layout, so a byte script written once works against all
    of them. Downstream chunks are encoded once and copied to every recipient (§4.2), so downstream layouts may
    vary at most per server.
  - **Options:** (a) seed 0 always (today); (b) vary order, offsets and tag constants per server from IR copies;
    (c) as (b), with the upstream layout per session.
  - **Choice: (b), on by default.** It removes byte scripts carried between no-build games and servers as a class,
    the same reason the id permutation is on (§4.5), for set-up per definition per server and per connection and
    2–26 ns per bounded field per message (§4.5 gives the mechanism and cost). It prices only tools that hard-code
    a layout, not memory, code, API or hook tools. (c) prices nothing more, since a tool that reads the session's
    key reads its layout in the same pass, and costs the IR copies per player on the server (34–76 MB at 200
    definitions × 100 players), so it is not offered.
  - **Option** (`Lync.configure`, server, runtime path; §7.5): `layout.vary`, boolean, default `true` (chosen by
    principle 2: that cost against a class of tools removed; `false` gives the seed-0 layout, which byte-level tests
    against the golden frames need). Each `WELCOME` carries it as the bit `layout`; the layout seed is derived from
    the permutation seed, never sent (§4.5). A generated server always sends 0: its layout is its build's. A
    `REKEY` keeps the layout, so decoders never switch inside a session.
- **Stale shards are an error.** A shard embeds its `buildId`, the seed-0 schema hash and the schema's path in its
  body, and a SHA-256 digest of its body on line 1 (`v5-tooling.md` §1.1). In Studio, requiring a shard evaluates
  the schema and throws `staleShard` on a mismatch; `lync check` fails the same way.
- **`patch` typing.** A wrong value type is a compile error; a misspelled key is a caller error (`unknownPatchKey`)
  `[probes T4, review-1 r3, r4]`.

### 3.3 Codecs

Every codec is a constructor call returning a plain table, so `{ read ["[Lync] value"]: T }` inference holds
`[probes T1]`; the brand is a key no record field can be `[review-m1 m4]`.
Constructors take no option tables. Values are exact unless declared otherwise.

| Codec | Luau type | Single-row encoding (§4.3) | Rules |
|---|---|---|---|
| `t.bool()` | `boolean` | 1 bit, 1 = true | |
| `t.int(min, max)` | `number` | u(⌈log2(max − min + 1)⌉) of v − min | integers with −2^52 ≤ min ≤ max ≤ 2^52 − 1; refuses fractions and out-of-range |
| `t.int()` | `number` | EG-0 of zigzag(v) | integers with −2^52 ≤ v ≤ 2^52 − 1, so zigzag(v) ≤ 2^53 − 1, the largest EG code (§4.1) |
| `t.number(min, max, step)` | `number` | q in u(⌈log2(n + 1)⌉) | see "Quantizers" below |
| `t.f32()`, `t.f64()` | `number` | u32, or u64 as low then high u32, of the IEEE-754 bits | NaN and ±inf refused; `t.f32` rounds to the nearest f32 (its declared precision) and refuses values beyond the f32 range |
| `t.angle(step)` | `number` (radians) | q in u(⌈log2 n⌉), n from "Quantizers" | q = ⌊wrap(v)·n/2π + 0.5⌋ mod n with wrap into [0, 2π); decodes to q·2π/n |
| `t.string(maxBytes)` | `string` | length u(⌈log2(maxBytes + 1)⌉); bytes in the tail | maxBytes 1–65,535 |
| `t.buffer(maxBytes)` | `buffer` | as `t.string` | |
| `t.vector3(min, max, step)` | `Vector3` | three `t.number(min, max, step)`, x y z | f32 rules below |
| `t.vector3f32()` | `Vector3` | three `t.f32()` | |
| `t.direction(bits)` | `Vector3` (unit) | octahedral, two u(bits), bits 8–16 | normalises any finite non-zero input; refuses zero |
| `t.rotation(bits)` | `CFrame` | flag 1 bit; flag 1: u5 index of the 24 axis-aligned rotations; flag 0: u2 index of the dropped component + three u(bits), bits 7–15 | refuses a CFrame with a non-zero position (pass `cf.Rotation`); canonical codes only (below) |
| `t.cframe(position, rotation)` | `CFrame` | position codec, then rotation codec | |
| `t.color3()` | `Color3` | three u8, ⌊c·255 + 0.5⌋, R G B | refuses channels outside [0, 1]; decodes to q/255 |
| `t.enum({ "a", "b" })` | `"a" \| "b"` | u(⌈log2 n⌉) of the list index | 1–65,535 items |
| `t.enum(Enum.Material)` | `Enum.Material` | EG-0 of zigzag(item.Value) | an unknown `Value` is `unresolved` (§7.3) |
| `t.instance(className?)` | `Instance` (generated: the class) | u(⌈log2 c⌉) index into the chunk's instance list (§4.2) | `IsA` checked on both ends; each instance listed once per chunk |
| `t.optional(codec)` | `T?` | presence bit (1 = present), then the codec | not directly inside an optional, as an array element or as a map value (`optionalPlacement`): each would give a second encoding of one value, or a pair Luau can't hold |
| `t.array(codec, maxCount)` | `{ T }` | count u(⌈log2(maxCount + 1)⌉), then elements | maxCount 1–65,535 |
| `t.map(key, value, maxCount)` | `{ [K]: V }` | count as `t.array`, then pairs, keys strictly ascending | keys: integers, list enums (by index), strings (bytewise) |
| `t.union({ name = record, ... })` | union on `kind` | u(⌈log2 n⌉) variant index (name order), then the record | a variant with its own `kind` field is a declaration error |
| `{ field = codec, ... }` | record | fields in order (§3.1) | |
| `t.custom(spec)`, `t.convert(base, decode, encode)` | user `T` | extension seams (§8) | |

u(0) is zero bits: a `t.int(5, 5)` or a one-item enum costs nothing.

**Quantizers, exactly** (`probes/design-3/number_steps.out`):
- `t.number(min, max, step)`: r = (max − min)/step must be within 1e-9 × max(1, r) of an integer n, which is fixed
  at declaration; otherwise `numberStep` (so `t.number(0, 0.3, 0.1)` has n = 3, and `(0, 1, 0.35)` is refused).
  `step = 1` with an integer `min` is `numberStepIsInt` (use `t.int`). Encode refuses v outside [min, max], then
  q = min(⌊(v − min)/step + 0.5⌋, n); decode gives min(min + q·step, max), so the top code decodes to a value its
  own encoder accepts (`t.number(0, 0.3, 0.1)`'s code 3 is 0.3, not 0.30000000000000004) `[review-m1 M1]`. Maximum
  error step/2.
- `t.angle(step)`: r = 2π/step; n = r rounded to the nearest integer when within 1e-9 × max(1, r) of it, else ⌈r⌉
  (`2π/1000` gives 1000, not 1001) `[review-3 m5]`.
- **Octahedral** (`t.direction`): with s = |x| + |y| + |z|, p = (x/s, y/s); if z < 0, p = ((1 − |p.y|)·sgn(p.x),
  (1 − |p.x|)·sgn(p.y)) with sgn(0) = +1. Each component c of p is q = ⌊(c + 1)/2 · (2^bits − 1) + 0.5⌋. Decode:
  c = 2q/(2^bits − 1) − 1 for both, z = 1 − |cx| − |cy|; if z < 0, (cx, cy) = ((1 − |cy|)·sgn(cx),
  (1 − |cx|)·sgn(cy)) using the values before replacement; the result (cx, cy, z) is normalised. 10 bits: 0.2369°
  maximum error; 12: 0.05924° (worst case by search, `test/wire/quant.spec.luau` at commit `f1fbfd7`; the 20,000-sample figures in
  `[compression §4.5]` were 0.23° and 0.057°).
- **Smallest-three** (`t.rotation`): from `GetComponents()`'s matrix R (row-major R00 … R22), the quaternion is
  taken by the branch with the largest of (R00 + R11 + R22, R00, R11, R22), ties in that order: trace branch
  w = √(1 + tr)/2, x = (R21 − R12)/4w, y = (R02 − R20)/4w, z = (R10 − R01)/4w, and the standard diagonal branches.
  It is negated if needed so the dropped (largest-magnitude) component is ≥ 0; ties drop the lowest index in x y z w
  order. The three kept components are written in x y z w order, skipping the dropped one; each c ∈ [−1/√2, 1/√2]
  is q = ⌊(c·√2 + 1)/2 · (2^bits − 1) + 0.5⌋. Decode inverts, sets the dropped component to √max(0, 1 − Σ c²), and
  builds the CFrame from the quaternion. The encoder uses the axis-aligned form when every matrix entry is within
  1e-6 of 0 or ±1; the 24 such matrices are indexed in ascending lexicographic order of their nine entries
  (R00 … R22, with −1 < 0 < 1). Maximum error with canonical encoding:
  7 bits 2.8969°, 8 bits 1.4575° (every first code evaluated); 9: 0.7255°, 10: 0.3664°, 11: 0.1836°, 12: 0.0921°,
  13: 0.0459°, 14: 0.0230°, 15: 0.0115° (worst found by sampling near-ties, not proven maxima), about
  375° / (2^bits − 1) (`test/codec/rotation_full.luau` at commit `f1fbfd7`; data in `probes/build/`). Canonical encoding raises the 9-bit maximum from 0.5187°
  (plain smallest-three, by search) because a moved code decodes to a neighbouring code's rotation.

**Decision: quantizers are idempotent on their own codes.**
- **Problem.** Decoding a `t.rotation` code and encoding the result changes the code for about 1.5% of codes at
  7 bits and 0.02% at 15: after quantization a kept component can outgrow the reconstructed dropped one, so the
  re-encoder drops a different component. Idempotence matters when the server relays a client's value (each
  non-idempotent hop adds up to one more quantization error), and for canonical decode (accepted codes the encoder
  never produces are a second byte sequence for one value). Change detection compares Luau values, and the
  differential test shares one encoder, so neither depends on it.
- **Options:** (a) the decoder refuses a code whose reconstructed dropped component isn't the largest under the tie
  rule, and the encoder never emits one. This fails in f32 near-ties, because the decoded `CFrame` is stored in f32
  and re-extracted; (b) define round trips of lossy codecs as "within the declared error", which keeps relay error
  growth; **(c) define canonical as idempotent and check exactly that.**
- **Choice: (c).**
  - **Rule.** For every quantizer, encode(decode(q)) = q for every code q the decoder accepts.
  - **`t.rotation`.** Let E(q) = encode(decode(q)), where decode builds the f32 `CFrame`. Near-equal components make
    E cycle: about 1% of codes at 7 bits and 0.006% at 15 form 2-cycles {q, q′} with neither fixed (milestone 1
    measurement, 200,000 rotations per width). So a code is **canonical** when E(q) = q, or when E(E(q)) = q and
    q < E(q), comparing (flag, index, a, b, c) lexicographically: the fixed point, or the lower member of a 2-cycle.
    The decoder checks this and refuses any other code (rule 6), so an axis-aligned rotation is accepted only in the
    axis form. The encoder iterates q ← E(q) from its first code and stops at a fixed point, or at a 2-cycle,
    returning its lower member; past 4 steps it raises `internal`. Then encode(decode(q)) = q for every accepted q,
    so relaying never drifts. Milestone 1 verifies there are no longer orbits: exhaustively at 7 and 8 bits, and over
    10^7 random rotations at 9–15 (verified in milestone 1: no failures, no orbit beyond a 2-cycle, at most 3 steps).
    Decode with the check costs 2.2–2.7x a plain decode with real `CFrame`s (9 bits: 1.09 against 0.43 µs
    interpreted, 0.36 against 0.13 µs native; `probes/build/results/rotation-3a222e0.json`); an earlier table
    stand-in for `CFrame` gave 3.5x.
  - **`t.direction`.** The fold edge decodes several codes to one direction (at 8 bits, 511 of 65,536 codes are not
    fixed points: (0, 0), (0, 255), (255, 0) and (255, 255) all decode to (0, 0, −1)) `[review-m1 M2]`. A code is
    canonical by rotation's rule (a fixed point of E, with E's decode rounded to f32 as `Vector3` stores it, or the
    lower member of a 2-cycle by (x, y)); the decoder checks it and refuses any other code (rule 6). The encoder's
    first code is not always canonical: a component just below zero with z < 0 lands on the negative side of the
    fold (0.26% of random directions at 8 bits, 0.063% at 10, 0.016% at 12, 0.0009% at 16). So the encoder iterates
    E like rotation's; measured, every such code reaches a fixed point in one step and no 2-cycle exists
    (exhaustive at 8 bits, 10^6 directions at each of 8, 10, 12 and 16), and past 4 steps it raises `internal`.
  - **`t.number`** (with the clamp above), **`t.angle`** and **`t.color3`** have every code a fixed point. Property
    tests check every quantizer exhaustively: every code of `t.color3`, of `t.direction` at 8 bits and of
    `t.rotation` at 7 and 8 bits, and every code of a declared grid for `t.number` and `t.angle` (including the
    `number_steps` cases).
  - **Cost:** one more smallest-three encode per decoded rotation (two for a code in a 2-cycle), and one more
    octahedral encode per decoded direction and per encoded direction (the encoder checks its first code).
- **`t.vector3` and `t.cframe` positions are stored in f32.** A component may exceed a bound by at most the f32
  spacing at that bound, and then takes the end code. The planner refuses a `step` that isn't larger than the f32
  spacing at max(|min|, |max|) (`vectorStep`), so every decoded component re-quantizes to its own code. The f32
  spacing at M is 2^(⌊log2 M⌋ − 23).

**Codec rules:**
- Every count and length has a declared maximum. Every array count, map count and run count is charged to the
  decode element budget before anything is allocated (§4.8).
- Codec methods are non-generic and return the same codec type `[probes T1]`, except where the table below gives
  a different client type. They are the only codec methods; each is hashed (§4.7), since the client acts on it.
- There's no flags codec: boolean record fields already pack to 1 bit.

| Method | Allowed on (else the declaration error) | Effect | Client type | Wire | Specified in |
|---|---|---|---|---|---|
| `:newest()` | a collection's top-level field (`newestPlacement`) of fixed width: not a string, buffer, array, map, `t.int()`, Roblox enum, instance or custom codec (`newestWidth`) | sent unreliably with repair | `T` | none of its own | `v5-collections.md` |
| `:claim()`, `:input()` | any codec in a client-sent payload: `data` of a `from = "client"` event or request, `reply` of a `from = "server"` request (`rolePlacement`) | the leaf's role, below | `T` | 0 B | below |
| `:owner()`, `:team()`, `:gated()`, `:seen()` | a collection's top-level field where `:newest()` is allowed, at most one of the four per field (`visibilityPlacement`) | the field's visibility class: which viewers receive it | `T?` | `:gated()`: 1 presence bit per update | `v5-collections.md` |

**Decision: claims** `[checks-telemetry C4, C5]` `[anticheat-design §3.2]`.
- **Roles.** A leaf of a client-sent payload is an *input* (the client's own control or choice) or a *claim* (what
  the client asserts about the world: a hit target, a shot origin, an amount gained). Unmarked leaves are inputs.
  A leaf's role is the nearest marker on it or on a codec enclosing it in the payload, so `{ … }:claim()` marks a
  record and an inner `:input()` overrides it. `:input()` has one effect: it silences the build diagnostic
  `freeFormField` on its leaves (`v5-tooling.md` §3), which flags a free-form leaf (an unbounded float or
  integer, a bounded one with more than 2^16 codes, a string, buffer, instance or custom codec) that carries no
  marker. Hash: a wrapper codec, type 26 `role`, role u8 (1 input, 2 claim), then the codec (§4.7): 2 B of hash
  input per marker, nothing at run time.
- **Problem.** A claim leaf of `data` must not reach a game handler unverified. The verifiers (a validator, or a
  check on the leaf, `v5-checks.md`) are declared at run time on the server view, so the shared schema cannot see
  them, and Lync drops only malformed input: it may not drop canonical messages because of what the game forgot
  to declare.
- **Options:**
  - (a) drop every message of a definition with an unverified claim leaf before validators, and report a native
    fault (the research's form): Lync acts on canonical input, and messages that arrive before the game's
    declarations run are dropped;
  - (b) deliver and report natively: unverified claims reach handlers, so the marker guarantees nothing;
  - **(c) refuse the handler:** `connect` or `handle` on such a definition throws.
- **Choice: (c).** On the server view, `connect` or `handle` on a definition whose `data` holds a claim leaf with no
  verifier throws the caller error `claimUnverified` at that call:
  `[Lync] claimUnverified: arena.strike:connect data.target must have a validator or a check, got none` (no fix
  is given: there are two, §7.1). A claim leaf is verified when the definition has a validator, or when a check of
  any kind is declared on the leaf's field handle or on that of a record enclosing it (§3.4). Nothing is declared
  away, so verification never lapses once the handler is accepted. No input is acted on, the error names the line
  to change, and its only cost is an order: verifiers before the handler. Messages decoded before a handler
  exists have no handler (§3.5). Claims in a `reply` have no run-time requirement: answers have no validator step,
  and the code that called `invoke` checks its result.
- **What it guarantees:** no message holding a claim reaches `connect` or `handle` without a game validator or a
  Lync check having seen it. A validator that always returns `true` defeats it, and so does marking a claim
  `:input()`; Lync can tell neither apart.

### 3.4 Definitions

```luau
-- ReplicatedStorage/Net/schema.luau
local Lync = require(ReplicatedStorage.Packages.Lync)
local t = Lync.types

return Lync.schema("arena", {
	chat = Lync.event({ from = "client", data = t.string(200):input(), limit = { perSecond = 5, burst = 5 } }),
	strike = Lync.event({
		from = "client",
		lane = "unreliable",
		data = { target = t.int(1, 2 ^ 40):claim(), aim = t.direction(11) },
	}),
	announce = Lync.event({
		from = "server",
		data = t.union({
			round = { number = t.int(1, 99) },
			winner = { team = t.enum({ "red", "blue" }) },
		}),
	}),
	buy = Lync.request({
		from = "client",
		data = { item = t.enum({ "sword", "shield" }) },
		reply = t.int(0, 100_000),
		timeout = 10,
	}),
	fighters = Lync.collection({
		key = t.int(1, 2 ^ 40),
		maxRecords = 64,
		data = {
			name = t.string(20),
			team = t.enum({ "red", "blue" }),
			health = t.int(0, 100),
			position = t.vector3(-2048, 2048, 1 / 32):newest(),
			look = t.rotation(9):newest(),
			title = t.optional(t.string(16)),
		},
	}),
	round = Lync.collection({ -- no key: a singleton
		data = { endsAt = t.int(0, 2 ^ 31), phase = t.enum({ "lobby", "play" }) },
	}),
})
```

- Every value in the schema goes into the schema hash (§4.7), so an unmodified client can't send on a direction or
  lane its definition doesn't use.
- The worst-case encoded size of a message, the larger of its single-row and column-block encodings, is at most
  16,000 B, or 960 B for an unreliable definition (§4.9; `messageTooLarge`, `unreliableTooLarge`).
- The worst-case element count of a message (§4.8) is at most 65,536 (`elementsTooMany`), and an array or map
  whose element costs 0 bits at its worst (`t.array({}, n)`, `t.array(t.int(5, 5), n)`) is `zeroWidthElement`: it
  carries nothing but its count, which a `t.int` carries.
- A schema entry not made by `Lync.event`, `Lync.request` or `Lync.collection` is `notADefinition`. Names are 1 to
  65,535 bytes, and a namespace's 1 to 64 (`nameLength`). A repeated enum item is `duplicateName`; a collection
  `key` of another codec is `mapKey`.
- `maxRecords` counts slots, including slots waiting out their reuse delay; `reliableRate` and the rest of
  collection behaviour are in `v5-collections.md`.
- An option the definition's kind, direction or lane doesn't take (the Kinds column) is `optionPlacement`, at the
  definition's line: `sealed` on a client-sent event, a request, a collection or an unreliable event, say.
- **Defaults.** `perceived` is `false` because its bytes buy something only for definitions whose server handler
  rewinds, which the client cannot see; without it a rewind result says `exact = false`. `sealed.outstanding` 1 is
  chosen: one pending reveal per player (the next round's layout); a game that pre-sends k reveals sets k.
  `sealed.hideLength` is `true` because a ciphertext's length is plaintext information disclosed before the
  reveal (a layout's size, an answer's length), and sealing exists to disclose nothing before it; a codec of fixed
  size pays nothing for it, and a game sets `false` where the length carries nothing (`v5-checks.md`)
  `[refusals-rejudged-1 R34]`. `sealed = {}` declares a sealed event with both defaults.

**Server-view declarations.** What the server does with a client's messages, and what it withholds, is declared
on the server view at run time, never in the shared schema: the client never sees it, it is not hashed, and a
retune needs no client rebuild. A declaration may be made at any time and applies to messages decoded after it.

**Decision: how a server declaration names a field.**
- **Problem.** Many declarations are about one field of `data` (a check on `strike.origin`, a reference from
  `strike.target` into `fighters`), and their options' types depend on that field's type (`derive`'s function
  returns the field's type). Exact types on both solvers and roblox-ts are required (principle 3), and the new
  solver fails to select an overload by a literal path when the same call takes an option table (§3.2).
- **Options:** (a) the path as the first argument, one overload per path (`Net.shot:derive("landing", { … })`):
  rejects correct calls under the new solver; (b) the path as a union of literals with options typed per
  declaration kind, not per field: exact field types are lost (`fn` returns `unknown`); **(c) a field handle:**
  `Net.<definition>:field(path)` selects by the literal alone and returns a handle typed by the field, on which
  each declaration is one non-overloaded method.
- **Choice: (c).** Verified on luau-analyze 0.740, both solvers, and tsc 6.0.2 `--strict`: correct calls are
  clean; a wrong return type, a misspelled option literal, a collection of another key type and an unknown path
  are each one error (`probes/design-3.6/typing.out`, `field_handle`). The runtime path's type function builds the
  same overloads from the schema (`field_handle_typefn`, new solver). Two declarations taking two fields (a
  stimulus and its response, say) take two handles, and their key types must agree by the same check.
- **`field(path)`.** `path` names a field of `data` through records and optionals with dots (`"origin"`,
  `"hit.origin"`); `""` names `data` itself when it is not a record. Arrays, maps and union variants are not
  reachable. An unknown path throws `unknownField` at the caller. One handle per (definition, path), created on
  first call; it is the only way a declaration names one field. Options that list several fields (`atom`'s
  `fields`, `rewind`'s `fields`) take path strings, typed as unions of the paths each accepts.

| Declaration | On | Specified in |
|---|---|---|
| `validate(fn)` | client-sent event, client request | §3.5, §6.1 |
| `trap()` | client-sent event or request | `v5-integrity.md` |
| field handle: `within`, `monotonic`, `maxTotal`, `derive`; definition: `resetChecks(player)` | client-sent event, client request | `v5-checks.md` |
| field handle: `aim()`, `series()`; definition: `series()` (timing only), `atom({ … })` | client-sent event, client request | `v5-checks.md` |
| field handle: `refers(collection)`, `reactsTo(stimulus, options)`, `answers()` | client-sent event, client request | `v5-integrity.md` |
| collection: `decoys`; field handle: `canary()` | collection | `v5-integrity.md` |
| collection: `interest`, `owner(fn)`, `team(fn)`, `rewind`; field handle: `gate(fn)` | collection | `v5-collections.md` |
| field handle: `about(collection)` | server-sent event | `v5-collections.md` |

The calls these declarations enable (`perceived`, `rewound`, `held`, `reportInteraction`, `Lync.challenge`, the
telemetry streams) are specified with them.

### 3.5 Using it

Game code requires the shard for its side, or calls `Lync.client(schema)` / `Lync.server(schema)`; both return the
same API. Shards go to a replicated folder (client) and `ServerScriptService` (server)
`[client-security-build §2.1]`. There's no `start()`: the runtime starts on first use, and `require` never yields.
The shared schema module replicates on both paths: the runtime path evaluates it, and Studio's `staleShard` check
reads it. Leaving it out of a generated build would hide nothing, because the client shard already holds every
definition's name and codec, traps included, to encode or decode it `[codecs-in-scripts §7.4]`.

```luau
-- server
local Lync = require(ReplicatedStorage.Packages.Lync)
local Net = require(ServerScriptService.Net)

Net.chat:validate(function(player, text)
	return string.find(text, "%S") ~= nil
end)
Net.chat:connect(function(player, text)
	Net.announce:fire(Lync.all, { kind = "round", number = 3 })
end)
Net.strike:field("target"):refers(Net.fighters) -- v5-integrity.md
Net.strike:validate(function(player, strike) -- verifies the claim strike.target, so connect is accepted
	return Net.fighters:get(strike.target) ~= nil
end)
Net.strike:connect(function(player, strike) end)
Net.buy:handle(function(player, request)
	return PRICES[request.item]
end)
Net.fighters:set(player.UserId, { name = player.Name, team = "red", health = 100, position = Vector3.zero, look = CFrame.identity })
Net.fighters:patch(player.UserId, { health = 90 })
Net.round:set({ endsAt = 600, phase = "play" })

-- client
local Net = require(ReplicatedStorage.Net.client)
Net.chat:fire("gg")
local shot = Net.strike:round({ target = 1, aim = camera.CFrame.LookVector }) -- aim as the server decodes it
shot.target = Targeting.pick(shot.aim) -- game code: the claim, computed from the decoded aim
Net.strike:fire(shot)
local result = Net.buy:invoke({ item = "sword" })
if result.ok then
	print(result.value)
end
Net.fighters.changed:connect(function(id, fighter, previous) end)
```

- **Verbs.** `fire` sends; `connect` listens and returns a connection with `disconnect()`; `invoke` asks and yields
  until the result; `handle` answers; `validate` (server) returns `true` to accept or `false` to reject; `set`,
  `patch`, `remove`, `audience` write a collection (server); `get` and the `added`, `changed`, `removed` signals
  read one. A definition has one signal, its `connect`; a collection has three, so they are named. `field`
  (server) returns a field handle (§3.4); `round` (client) returns a payload as the server will decode it (below).
- **Targets.** One `Target` type for server `fire` and `audience`: a `Player`, an array of players, a
  `Lync.group()`, `Lync.all`, or `Lync.except(target)`. A target resolves once per flush. `Lync.group(players?)`
  returns a live set with `add`, `remove`, `has`, `size`, `players`, `destroy`; leaving players are removed. These
  live on `Lync` only.
- **Results.** Requests never throw. They return `{ ok: true, value: R } | { ok: false, error: E }`, where `E` is
  `"timeout"` (no answer within `timeout`), `"limited"` (the server's `limit` bucket for the definition was empty),
  `"rejected"` (the answering side refused it, §5.2), `"unanswered"` (no handler, or the handler threw, returned a
  reply its codec refuses, or ran past `timeout`), `"left"` or `"shutdown"`. Requests go both ways: server
  `invoke(player, data)` yields like the client's. A result is a fresh table owned by its one caller, so it is not
  frozen (facts are, because every observer gets the same table, §7.3); freezing would cost 12–33 ns per result
  `[clock-facts §U4.5]`.
- **Server results carry timing** `[clock-facts §U4]`. A server `invoke`'s result also has `roundTrip`,
  `pingAtSend`, `pingAtAnswer` and `minPing`, in seconds, defined in §5.2: all four are `number` in the success arm
  and `number?` in the failure arm, nil where the moment they measure didn't happen. Written out in both arms, not
  intersected, so neither solver normalises an intersection of a union:

  ```luau
  export type ServerResult<R, E> =
  	{ ok: true, value: R, roundTrip: number, pingAtSend: number, pingAtAnswer: number, minPing: number }
  	| { ok: false, error: E, roundTrip: number?, pingAtSend: number?, pingAtAnswer: number?, minPing: number? }
  ```

  Narrowing on `ok` exposes `value` only in the success arm, and arithmetic on a failure arm's field needs a nil
  test, on both solvers (`probes/design-3.6/typing.out`, `result_types`). Client results are unchanged: the
  measurement is about a player, which only the server's is, and the client would pay a clock read and a
  `GetNetworkPing` per ask for fields no decision reads; each side already has its own `invoke` signature.
- **Sealed events.** On a definition with `sealed` (§3.4), server `fire` returns a `Seal` with `reveal()` and
  `discard()`; the client's `connect` handler runs at reveal with the decoded value, so client types are those of
  any event (`v5-checks.md`). The runtime path's type function picks the return type from whether the options
  table has a `sealed` property, which literal widening (§3.1) doesn't affect; unverified until milestone 1's
  typing proofs (§10).
- **Handler arguments.** Server handlers receive the player first, matching `OnServerEvent`; client handlers
  receive the payload.
- **Wrong-side calls** are type errors on the generated path; on the runtime path the view's metatable miss throws
  `wrongSide` (no cost on hits).

**Decision: a message with no handler** (`[decoy-challenge-facts §7.1]` found it unspecified).
- **Problem.** Dispatch can find no `connect` for an event, or no `handle` for an ask: a script that connects
  late, or a definition the game never handles. Lync carries every definition in frames on one remote, so the
  engine's queue for unconnected `RemoteEvent`s never applies; whatever Lync holds is memory it must bound.
- **Options:** (a) hold messages per definition until its first handler: a new bound per definition, and a late
  handler then runs on stale messages all at once; (b) dispatch to nobody and count it; (c) also report it
  natively, which turns a late `connect` into an error line in every session.
- **Choice: (b).** A script that requires a view can connect before its first yield, and that precedes every
  dispatch, since `require` never yields and dispatch runs on a later engine event. What a script that starts
  later needs is state, and belongs in a collection, whose `get` reads it at any time. The message is counted
  in `messagesUnheard` per definition (§7.4); an ask is answered `unanswered` at once (§5.2), so the asker
  does not wait out its `timeout`.

**Decision: rounding a value as it will decode** `[server-facts §U9.6]`.
- **Problem.** A client that computes a claim from its raw aim, then sends the aim quantized, disagrees with a
  server that recomputes from the decoded aim: 0.2369° of `t.direction(10)` is 1.24 studs at 300 studs. The
  client needs the value the server's decoder will produce, exactly, including `t.f32` rounding, `Vector3`'s
  f32 storage and the canonical rotation codes of §3.3.
- **Options:** (a) a codec method `codec:round(value)`: codec methods return codecs (§3.3), and game code on the
  generated path holds views, not codecs; (b) game code quantizes by hand from the rules of §3.3: one copy of
  the quantizers per game, free to drift from Lync's; (c) **a view method,** `Net.<definition>:round(data)`.
- **Choice: (c).** On the client view of a client-sent event or request, `round(data)` returns a new value equal
  to what the server's decoder produces for `data`: decode(encode(data)), the layout aside, which doesn't
  change values. It sends nothing. Every field needs an encodable value, so a claim computed from the result is
  set afterwards (the example's placeholder `target = 1`). Replies are not covered: the server recomputes nothing
  from an answer (§3.3, claims). A value the encoder refuses throws `valueRefused`, as `fire` would. Typed
  `(self, data: T) -> T` on both paths. Cost: at most one encode and one decode of the payload, without bit
  I/O; generated shards emit it for each client-sent definition whose `data` holds a quantized or f32 leaf
  (bytecode per definition unmeasured), and share one copying function for the rest.

### 3.6 roblox-ts

The schema is Luau in both ecosystems: the compiler emits `.d.ts` beside the Luau shards from one IR. Declarations
follow the side split, use dot calls (`this: void`) and `LuaTuple` only where Roblox requires it `[v4 §2.3, §6]`.
Whether rbxtsc carries `schema.luau` through unchanged is checked in milestone 3. API misuse surfaces as tsc's own
errors; the `.d.ts` JSDoc names each definition's schema line, and each server result field's definition and its
absent case (§5.2).
- **Field handles** are one overload per path, `field(this: void, path: "origin"): Field<StrikeData, Vector3>;`,
  and each declaration a plain method of `Field<D, T>`; checked with tsc 6.0.2 `--strict` beside the Luau form
  (§3.4).
- **Server results** use `readonly` fields, which TypeScript has on every checker:

  ```ts
  type ServerResult<R, E extends string> =
  	| { readonly ok: true; readonly value: R; readonly roundTrip: number; readonly pingAtSend: number;
  	    readonly pingAtAnswer: number; readonly minPing: number }
  	| { readonly ok: false; readonly error: E; readonly roundTrip?: number; readonly pingAtSend?: number;
  	    readonly pingAtAnswer?: number; readonly minPing?: number };
  ```

  (`probes/design-3.6/result_types.ts`: narrowing on `ok` and the `undefined` test behave as in Luau.)

## 4. Wire

### 4.1 Remotes, frames and bits

- **Remotes.** One `RemoteEvent` named `Reliable` and one `UnreliableRemoteEvent` named `Unreliable`, created by the
  server under `ReplicatedStorage.Lync` on first use, carry every namespace. Each call carries one buffer, plus an
  instance array when the frame references instances `[landscape §2.1]`. A client that finds no remotes 10 s after
  first use reports `remotesMissing` (§7.3) and keeps waiting.
- **Calling `FireServer`.** The client transport reads `FireServer` from each remote once, when it finds that
  remote (and again for a remote that replaces it), and calls the captured function with the remote as `self`: a
  plain `CALL` with no `NAMECALL`, 44.0 against 45.1 ns per call at `-O2` and 34.6 against 43.0 at `-O1`
  `[client-self-checks U1]`. A spy hooking the remote's `__namecall` no longer sees Lync's calls; an in-place
  `hookfunction` still does, so this is no integrity measure and changes no byte.
- **Per flush, per player:** at most one reliable frame, split at 16,384 B (both directions; the engine's own limit
  is unmeasured, §10), and unreliable frames of at most 1000 B each including header and tag, the documented drop
  limit `[compression §1]`. Reliable frames are ordered per connection `[state-sync §5.1]`. A split is decided by
  counting each frame kind's longest header (5 kinds: downstream reliable, event and state; upstream reliable and
  unreliable; the longest, upstream unreliable, is 42 bits), so a frame may split up to 6 B before its limit; the
  limit is never exceeded. A downstream frame also splits before its element count (§4.8) would pass the client
  decode allowance of 4,194,304, so an unmodified server never writes a frame a client refuses by rule 10.
- **Bit order** (`probes/design-3/bitorder.out`). Bit i of the bit section is bit (i mod 8), value 2^(i mod 8), of
  byte ⌊i/8⌋. A field u(w) holding an unsigned integer is written least significant bit first. This is the order of
  Luau's `buffer.writebits`/`readbits` (up to 32 bits per call; wider fields are written as low 32 bits, then the
  rest). Multi-byte values that sit on byte boundaries (the tag, §4.5) are little-endian.
- **Integer codes** (`probes/design-3/golden.out`). Every EG-coded value is an integer in [0, 2^53 − 1], so all
  arithmetic below is exact in doubles `[review-3 M5]`. EG-0 of x: let z = (bit length of x + 1) − 1; write z zero
  bits, a one bit, then u(z) of (x + 1) − 2^z. Decode: count z zero bits up to the one bit, read r = u(z), return
  (2^z − 1) + r. EG-k of u is EG-0 of ⌊u/2^k⌋ followed by u(k) of u mod 2^k. z > 53 or a result above 2^53 − 1 is
  malformed (rule 2). zigzag(v) = 2v for v ≥ 0 and −2v − 1 for v < 0. EG-0 is used for every count in the
  grammar.
- **`align`** writes zero bits up to the next byte boundary.

**Frame grammar:**

```
frame      := bits align tail [tag:u32le — upstream only, §4.5]
bits       := header toc chunks

header (down, reliable)   := tick: '0' unchanged | '10' +1 | '11' u16          -- vs the last reliable frame this client received
header (down, unreliable) := '0' tick:u8                                       -- event frame: runs only; may be shared
                           | '1' seq:u12 tick:u8                               -- state frame: rows only; per player (§4.4)
header (up, reliable)     := caller:u1 ack rcv:u8
header (up, unreliable)   := seq:u12 caller:u1 ack
ack                       := '0' | '1' seq:u12 received:u16                    -- newest state-frame seq received; received bit i is seq − 1 − i

toc (down, reliable)   := segs(state) segs(run) segs(remove)
toc (down, event)      := segs(run)
toc (down, state)      := segs(rows)
toc (up, both)         := segs(run)
segs(x)                := n:EG0 { ns:EG0 count−1:EG0 }   -- n segments; each: namespace index, then how many chunks of kind x
chunks                 := every chunk of every segment, in toc order

run chunk     := id:u(w) count−1:EG0 [instances:EG0] rows
control chunk := type:u3 count−1:EG0 rows                -- a run chunk of namespace 0: count messages of one type
```

- **Chunks** are the unit of shared encoding. Downstream, every chunk starts on a byte boundary (`align` before
  it), so a chunk encoded once is placed with `buffer.copy`; upstream, chunks are packed with no alignment, since
  nothing upstream is shared.
- **Segments.** Consecutive segments of one list name different namespaces; run segments are in call order, state
  and remove segments in ascending namespace order. Namespace 0 is control (§4.6): its runs are control messages.
- **Order.** On the reliable lane, all state chunks, then runs in call order across namespaces, then removes, so
  every event sees every collection write made before it on the server `[state-sync §5.3]`. A run holds
  consecutive messages of one definition to one target; interleaved fires make separate runs.
- **Run chunk.** `instances` is present only when the definition's `data` or `reply` can contain a `t.instance`
  (§4.2); rows follow §4.3. A **control chunk** holds `count` consecutive control messages of one type, each row
  being that type's fields (§4.6); its tail values follow the general rule (§4.2). A chunk is at most 16,256 B; a
  run that would exceed it continues as a new run chunk, so every chunk fits an empty frame `[review-3 m2]`.
- **State, remove and row chunks** carry collection data; their contents are in `v5-collections.md`. Milestone 2
  frames always write zero such segments and send no state frames.
- **Caller bit.** `caller` is 1 when the frame holds the message of a probed call whose source check failed
  (`v5-integrity.md` §4), else 0; it is 0 in untagged frames. It is also the high bit of the tag input's lane byte
  (§4.5), so it is covered at every `tag.cover`, and the server reads it before the tag to hash each candidate once.
- **Receipt.** `rcv` is the number of downstream reliable frames the client's listener has received on this
  connection, refused ones included, mod 256, when it encodes the frame. The server extends it to the value in
  (S − 256, S], where S is the number of reliable frames it has passed to the engine for that player (a
  `FireAllClients` frame counts once for each recipient, a split frame once per part). It is on every upstream
  reliable frame, so it shows nothing about which definitions game code watches. A client 256 or more frames behind
  (a stall of 4.3 s at 60 frames a second) extends upward, which reads a frame as received early: a fact that uses
  it (`earlyReaction`, `v5-integrity.md`) can only be missed by that, never made. It is client-stated. It tells the
  server which reliable state a client held when it sent, which state-frame acks don't `[server-facts U10.2]`.
- **Ack.** Within a flush the client sends its reliable frame first, then its unreliable frames. The first of them
  carries an ack (`'1' …`) when a state frame arrived since the last ack sent, else `'0'`. A frame holding a message
  of a `perceived` definition (§3.4) also carries `'1' …` whenever any state frame has arrived, so the server reads
  that message's perceived tick from its own frame `[interest-rewind §11.3]`. With nothing else to send, the client
  sends an unreliable frame holding only a header once 2 new state frames are unacked, or the oldest unacked one is
  100 ms old `[review-redundancy-2 4]`.
- **Ticks.** The downstream reliable tick is coded against the last reliable frame *that client* received; a
  client's first reliable frame, and a frame shared by players whose last ticks differ, use `'11' u16`. The
  unreliable `tick:u8` is the low 8 bits of the state tick T; the client extends it to the value nearest its own
  estimate ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋ `[review-redundancy-2 14]`.
- **Sizes.** For the busy traffic model (upstream 60 input and 10 action messages a second in 70 frames;
  downstream 60 reliable and 20 unreliable frames a second), framing costs 374 B/s up with a 16-bit tag and 160 B/s
  down `[probes review-redundancy-2 wire_overhead_2]`. On top of that, upstream: the 32-bit tag (§4.5) adds 2 B per
  frame (140 B/s); `rcv` 1 B per reliable frame (10 B/s); `caller` 0 or 1 B per frame, 1 B exactly when the bit
  section would otherwise end on a byte boundary (at most 70 B/s); so at most 594 B/s up. A frame holding a
  `perceived` message adds 28 bits when it would have carried `'0'`. The segment toc adds a namespace index (1 bit
  for namespace 0, 3 for 1–2) per segment.

### 4.2 Shared encoding, instances and the tail

- **Encode once.** Downstream, each run, state chunk and row chunk addressed to several players is encoded once
  per flush and copied into each player's frame. When every recipient of a flush's frame would get identical bytes,
  one call goes through `FireAllClients`; this is decided from targets and tick headers, never by comparing
  buffers. Unreliable event frames carry no per-player field, so they can be broadcast too; state frames are per
  player by construction (§4.4) `[review-2 B3]` `[review-redundancy-2 3]`. Downstream layouts are one per build (and,
  on the runtime path, one per server, §4.5), never per session or per player, since a per-recipient layout would
  encode each shared chunk once per layout and end `FireAllClients` `[generation-methods §0.2]`. The one
  per-recipient difference inside a shared chunk is a tail patch: with `canary.perViewer` the chunk is encoded once
  and each viewer's copy has 4 tail bytes rewritten (67 ns per viewer native, `v5-integrity.md` §9); a frame holding
  such a copy, or a decoy viewer's re-encoded chunk (§8 there), leaves `FireAllClients` for that flush.
- **Instances are chunk-local.** A chunk lists its own instances (`instances` in its header); indices are
  u(⌈log2 c⌉) into that list, where c is the chunk's count. The frame's instance array is the concatenation of every
  chunk's list in chunk order, so a chunk's bits never depend on the frame it lands in `[review-2 B3]`. A chunk lists
  each distinct instance once, in order of first reference. The frame's instance array is always passed as the
  remote call's second argument, empty when the frame has none.
  - **Encoders.** Instances are collected before the chunk is encoded, by a walk over the codec's instance leaves
    only, which costs 3.4% of an encode. The encode itself never adds to the list: an unlisted instance is
    `internal`.
  - **Committed count.** The list's count is fixed at each encode's entry, and a failed encode truncates the list
    back to it. So rows are collected and encoded one at a time (or one run at a time), never collected ahead: one
    refused row would otherwise drop the instances of the rows collected after it.
  - **Decoders** take a chunk's instances from the frame's array by offset and the count in the chunk header,
    never from `#list`, because unreplicated instances arrive as nil.
- **Rollback.** After a refused or raising encode, the writer and the instance list are as they were at its entry,
  so a throwing `t.convert` can't corrupt the rest of a flush. Two mechanisms give that, by codec:
  - **Check, then write**, in generated encoders of definitions whose codec has no `t.convert` or `t.custom` leaf:
    every value is checked before the first bit is written, so a refusal has nothing to undo and no `pcall` runs.
    This saves the 45–110 ns per call the rollback `pcall` costs interpreted `[codecs-in-scripts §6.3]`.
  - **Mark and `pcall`** everywhere else (a `t.convert` or `t.custom` leaf, whose game code can raise mid-encode, and
    the runtime path's interpreter, which writes as it walks): the encoder marks the writer and the instance list on
    entry, runs the encode in one `pcall`, and on a refusal or a raise (game code, or `internal`) restores both and
    then raises. 0.1–0.3 µs per encode (milestone build).
- **The tail** holds string and buffer bytes, read backwards from the end of the frame (before the tag). Reading
  a value of n bytes takes the n bytes ending at the tail cursor, in forward order, and moves the cursor back by n.
  So a chunk's tail segment is its values in reverse decode order, and the frame's tail is the chunks' segments in
  reverse chunk order. A shared chunk is stored as its bits plus its tail segment.
- **Bits and tail meet exactly:** the byte after the aligned bit section is the first byte of the tail.

### 4.3 Decision: how values become bits

- **Problem.** Roblox zstd-compresses remote payloads above a threshold at a level, neither documented nor
  measured; the design assumes compression from 100 B `[compression §1]`, pending §10. Bit-packing defeats zstd;
  byte alignment wastes bits.
- **Options:** byte-aligned layouts leaning on zstd; dense bit-packing (v4); **fixed-width bits for single rows and
  a column coder for multi-row data.**
- **Choice: the third.** Without temporal prediction it is 1.2–1.8x smaller than the best byte-aligned layout under
  modelled engine zstd in five traffic models and ties the sixth `[compression §2.1]`; its output doesn't compress
  further, so the engine's level changes nothing measured for it, where byte-aligned layouts lose 40–75% of their
  gain between levels −5 and 1 `[compression §2.4]`; strings stay in the byte tail, where engine compression still
  applies `[compression §2.5]`. Only cross-frame compression context could overturn this (§10).

**Single rows.** A run of fewer than `columnMinRows` messages writes each message in its codec's single-row
encoding (§3.3), one after another; request and control runs always do. Inside a single row, an array or map with at
least `columnMinRows` elements is written as its count followed by a column block over its elements.

**Column blocks.** A run of `columnMinRows` or more messages (and such an array or map) is written as columns.
`columnMinRows` is a protocol constant, 3; the decoder knows the form from the count, so no flag is sent. The
milestone 1 benchmark set it: bits of n single rows against one column block, summed over `strike`, `announce`,
`fighters` and a `{ t.int(0, 100) }` record, 200 draws (`f1fbfd7:test/codec/min_rows.luau`). At n = 3 the block is
smaller in 3 of 4 value patterns:

| n | constant | ±1 noise | Gaussian σ = 50 | 10% sparse |
|---|---|---|---|---|
| 1 | 174.7/295.1 | 174.8/295.7 | 174.6/280.2 | 174.5/294.3 |
| 2 | 348.3/351.0 | 349.1/407.7 | 349.9/425.5 | 348.9/356.9 |
| 3 | 523.1/352.9 | 523.6/467.4 | 523.7/535.5 | 523.7/382.2 |
| 4 | 697.9/353.3 | 698.1/517.9 | 698.2/642.8 | 697.9/403.2 |

- **Flattening**, depth first in field order:
  - a record: its fields' columns in order;
  - `t.optional(c)`: a bool presence column, then c's columns over the present rows only;
  - `t.union`: a variant-index column, then each variant's columns, in variant order, over that variant's rows;
  - `t.array(c)`: a count column, then c's columns over every element of every row, in row order;
  - `t.map(k, v)`: a count column, then k's columns and v's columns over every pair;
  - `t.string`, `t.buffer`: a length column; bytes go to the tail in row order;
  - `t.vector3`: x, y, z columns; `t.color3`: R, G, B; `t.direction`: two code columns; `t.cframe`: position's
    columns, then rotation's;
  - `t.rotation`: the flag column, then the axis-index column over the rows whose flag is 1, then the dropped-index column and
    three component columns over the others;
  - `t.convert(base)`: base's columns;
  - `t.f32`, `t.f64`, `t.custom`: a raw column, values in single-row encoding one after another, no mode;
    `t.vector3f32`: three raw columns, x, y, z.
- **Integer columns** (every other column) are coded on residuals `[review-3 M5]`. Each column's codes are an
  interval of n integers: `t.int()` and Roblox enums use the value itself on [−2^52, 2^52 − 1] (n = 2^53); every
  other column uses the unsigned integer its single-row encoding writes, on [0, n − 1] (`t.int(min, max)`: v − min,
  n = max − min + 1; quantizers: q; enums, variants, instances: the index; lengths and counts: 0 … max; bools:
  false 0, true 1). Each code's residual is code − previous code (the first row against 0), wrapped modulo n into
  [−⌊n/2⌋, ⌈n/2⌉ − 1], then zigzagged; so a bool's residual is its XOR with the previous row. Decode adds and wraps
  back into the interval. Every residual's zigzag is at most 2^53 − 1.
- **Exactness to n = 2^53** (`f1fbfd7:src/wire/column.luau`). The first row is wrapped like every other row: its
  residual against 0 is a difference, never `(code + ⌊n/2⌋) mod n`. Decode wraps before it adds: if r > top −
  previous the code is previous + (r − n), if r < lo − previous it is previous + (r + n), else previous + r. The
  first build added first and wrapped after, so a sum passed 2^53 and rounded for every n > 2^52, and the codec
  carried a workaround until the fix. A property test covers intervals at and near 2^53 (n = 2^53, 2^53 − 1,
  2^52 + 1, lo = −2^52) against an exact `math.fmod` reference.
- **Offsets** (`v5-integrity.md` §2; on the runtime path, §4.5's `layout`). Where offsets apply, a bounded code q
  travels as w = (q + c) mod n, c fixed per codec site, in single rows and columns alike; a column's codes are the
  w. Since residuals are taken modulo n, c cancels in every residual but the first row's.
- **Decision: the first row of a column under offsets** `[generation-methods M3]`.
  - **Problem.** The first row's baseline decides whether an offset acts inside column blocks at all, and the
    encoder, which a modified client controls, decides when messages travel as a block: any run of
    `columnMinRows` or more, any array or map of that many elements.
  - **Options:** **first row against 0** (the rule above): c sits in the first residual, so every value of the
    block needs c to decode; against c: the residual stream equals the identity's, so zero bits, and a decoder
    that ignores c reads the block exactly (`probes/generation-methods/column_offset.out`).
  - **Choice: against 0.** Against c, a forger escapes every offset by sending three messages in one run, so
    offsets would price nothing on either lane. Cost, 64-row columns, 200 trials, bits against the identity:
    sequential n = 32 137.0 → 185.1, ±1 walk n = 32 135.9 → 150.4, sparse 10% n = 101 89.3 → 96.8, constant
    n = 4096 14.0 → 22.1, sequential n = 4096 137.0 → 214.2, sequential n = 4 137.0 → 73.2, uniform equal; only
    where offsets apply, never at seed 0 or with `layout` 0. It is a protocol constant (§4.9).
- **A column over zero rows** (an optional absent in every row, an unused variant) writes nothing, not even a mode.
- **Per column, `mode:u2`:**
  - `0` zero: every residual is 0;
  - `1` Exp-Golomb: `k:u4`, then each zigzagged residual as EG-k;
  - `2` sparse: `k:u4 m:EG0`, then m pairs `gap:EG0 value:EG-k` (rows skipped since the previous non-zero row, then
    zigzag − 1);
  - `3` frame of reference: `base:EG0 width:u6` (0–53), then each zigzagged residual minus base as u(width).
- **Free choices.** Mode and k are the encoder's choice: any valid choice decodes. The reference encoder, which
  golden frames follow, picks the fewest bits, ties going to the lower mode, then the lower k; sparse writes every
  non-zero residual; frame of reference uses the minimum as base and the smallest width. It costs every mode and
  every k (a log2-of-mean shortcut lost 6–14% `[compression §2.3]`).
- **Measured** (64-row columns; `probes/build/results/579015b.json`, `c91960e.json`):
  - The full k search costs 2.2–2.6x a k = 0 encode on the worst patterns (±1 noise, Gaussian σ = 50),
    interpreted and native, and 1.0–1.4x on constant and sparse columns. That is under the plan's 3x threshold, so
    the one-histogram fallback `[compression §3.2]` isn't used.
  - A batched reader with a 12-bit lookup table, its cursor in a local, decodes EG-0 at 43–47 ns per value
    interpreted and 23–29 ns native, against 86–94 ns interpreted for a call per value.

### 4.4 Sequences

**Decision: one shareable unreliable frame and one acked one** `[review-3 M1]`.
- **Problem.** Broadcast needs identical bytes for every recipient (`FireAllClients`), so no per-player field;
  notify needs a per-player sequence whose consecutive values are that player's consecutive frames, or the 16-bit
  ack window and sequence extension fail (draft 3's server-wide seq advanced by about 100 between one player's
  frames at 100 players).
- **Options:** a per-player seq on every unreliable frame (notify works; no unreliable broadcast); a server-wide seq
  (broadcast works; notify and extension fail); **two frame kinds: event frames with no seq, and state frames with a
  per-player seq.**
- **Choice: two kinds.** Only `:newest()` rows are repaired, and a viewer's rows are chosen for that viewer anyway,
  so only state frames need acks; unreliable events are never resent, so their frames need no seq and stay
  shareable. Cost: on a state tick when a player gets both rows and unreliable events, one more remote call and a
  9-bit header; nothing otherwise.
- **State-frame `seq`** counts each player's state frames from 0. The ack and notify cover state frames only.
- **Upstream unreliable `seq`** counts each client's unreliable frames from 0; it feeds the replay window (§4.5).
- **Stored sequences are extended.** Any 12-bit value a peer stores (a row's seq, the newest acked seq) is first
  extended to a full counter: the value nearest the newest seq received in that sequence, from 2047 behind it to 2048
  ahead. Counters start at 0 and are never negative: before the first value the newest is −1, and an extension
  below 0 takes the value 4096 higher. Consecutive values are one player's consecutive frames, so this fails only
  after 2048 consecutive losses; idle records never age out `[review-redundancy-2 1]` `[review-2 M2]`.

### 4.5 Integrity on the wire (milestone 2)

The tag, the replay window, the id permutation and the key derivation are part of the frame format, so they ship
with it. The per-build values they read (the tag's constants, rotation set and rounds, the secret S, the variant
masks) are drawn in `v5-integrity.md` §2 (milestone 5); at build seed 0 each is its identity, which is what
milestone 2 builds and what the golden set (§4.10) fixes. The rest of client-side integrity is in
`v5-integrity.md` (§6.2).

- **Build identity** `[generation-methods M1]`. Each build run draws a public `buildId` (u32) and a private
  `rotationSeed` (64 bits), both from OS entropy. `buildId` is what `HELLO` carries and the server compares (§4.6);
  it is in the shard bodies and the manifest. `rotationSeed` is written only to `manifest.json`, which never ships,
  and every per-build value is a function of it (`v5-integrity.md` §2), so a tool holding `buildId` and Lync's
  source learns none of them. `buildId` 0 with `rotationSeed` 0 is the identity build (tests). The runtime path has
  no build: it sends `buildId` 0, and its varied layout is `layout` below.
- **Session key and permutation seed** `[generation-methods M8]`. The first `WELCOME` carries two nonces: an 8-byte
  key nonce, drawn per connection from an entropy-seeded `Random.new()`, and a 4-byte permutation nonce, drawn once
  per server at start. Both ends derive, with HalfSipHash-2-4 in its 64-bit output mode keyed by the build's secret
  S (64 bits, in both shards, `v5-integrity.md` §2):
  - key = the output over (key nonce ‖ `01`), as two little-endian u32, low first;
  - permutation seed = the low 32 bits of the output over (permutation nonce ‖ `02`), with 0 replaced by 1;
  - S = 0 (seed 0, and the runtime path) is the identity: key and seed are the nonces themselves.

  A tool that reads `WELCOME` with a receive hook then needs S from the shard each build as well. For the key that
  is a 64-bit unknown; the permutation seed stays 32 bits, so a capture holder without S can instead search it
  against canonical decode, 2^32 × 200 ids × 26 ns = 6.2 h of one core per server for 200 ids
  `[refusals-rejudged-3 R2]`. That is kept: Fisher–Yates under xorshift32 has only 2^32 permutations whatever the
  seed's width, and a byte tool on the client learns wire ids from its own sends anyway `[generation-methods M4]`.
  Cost: zero bytes;
  one derivation per connection and per `REKEY` on each side, plus one per server start for the seed: about 1.6 µs
  interpreted and 0.31 µs native each (derived: 1-3's fixed cost of 0.89 µs and 196 ns, × 1.1–1.4 for 2-4, plus
  0.3–0.4 µs and 25–40 ns for the 64-bit output `[probes security-costs #8]`; unmeasured as such).
- **Keyed tag** `[client-security §3.1]`. The client counts its upstream reliable frames from 0 across namespaces,
  advancing before each `FireServer` and keeping the count if the call raises; the count is never sent. Every
  tagged upstream frame ends with `u32le` = H(input) XOR m, where:
  - input = count as u32le (reliable; unreliable: the extended seq mod 2^32), the lane byte (0 reliable,
    1 unreliable, plus 128 when the frame's `caller` bit is 1, §4.1), the frame's length before the tag as u32le,
    its instance count as u16le, then the first min(`tag.cover`, length) bytes of the frame from byte 0;
  - H is HalfSipHash-1-3's 32-bit output under the key (as two little-endian u32), with the build's initialisation
    constants, rotation set and round counts (`v5-integrity.md` §2; the reference values at seed 0 and on the
    runtime path, except `layout`'s constants below);
  - m is the player's variant mask: 0 without per-player variants, else the mask of the variant the server assigned
    (`v5-integrity.md` §2). A client holding no mask yet tags nothing; its tagged frames wait (§5.3).
- **Verification.** The candidates are the expected count e and e + 1 … e + 4 (reliable), or the extended seq and
  its two neighbours (unreliable, §4.4). At each, the server hashes the input once, with the frame's own `caller`
  bit, and XORs the result with the tag: the player's own mask accepts the frame, and acceptance at e + j sets e to
  e + j + 1 and, for j ≥ 1, reports `frameGap`; another variant's mask is remembered. With no acceptance the frame is dropped,
  e unchanged, as `tagVariant` when some candidate gave another variant's mask (`v5-integrity.md` §2), else
  `tagMismatch`.
  - **Hashes per frame:** at most 5 on the reliable lane and 3 on the unreliable lane, one per candidate, at any
    key state; plus up to 5 or 3 table lookups with variants (+0.24 µs native per failing 64 B frame
    `[generation-methods M13]`).
  - **Budget-refused frames are not hashed.** A reliable frame refused at §6.1 step 2 advances e by 1 without a tag
    check. Every reliable frame an unmodified client sends took the next count, so e stays in step (a gap from
    raising calls is found by the lookahead on the next checked frame); a frame that took no count, forged or
    replayed, can only put e ahead of its own sender, whose later frames then fail toward `desync`. Draft 3.5
    hashed them so the count stayed in step, which let a client make the server hash 16 KB frames at the engine's
    rate, about 500 calls a second, outside every budget: 656 µs per 16 KB frame native, 328 ms/s per player
    `[probes inbound-budgets claim 2]`.
  - **Bound.** So the tag CPU one client can cause is set by its budgets (§7.5): per second at most
    (5 × Br + 3 × Bu) × b + (5 × Fr + 3 × Fu) × f, with Br, Bu the byte and Fr, Fu the frame `perSecond` of the
    reliable and unreliable lanes, b the cost per covered byte and f per hash. Measured native b and f: 4.0 ns and
    196 ns for the milestone's form, 2.2 ns and 122 ns for a generated unrolled form; interpreted 30.7 ns and
    890 ns, and 28.5 ns and 757 ns `[probes inbound-budgets claim 2]`. At the default budgets that is 1.31 ms/s per
    player with the milestone's form and 0.74 ms/s unrolled when every frame fails, and 0.33 and 0.19 ms/s when
    every frame is accepted, plus the bursts once per refill. Each compression round above 1 (`v5-integrity.md` §2)
    adds about 2.7 ns per byte native.
- **Untagged frames.** Before a client has received its first `WELCOME` it sends only untagged frames that hold only
  `HELLO`s, with `caller` 0; they don't advance the count on either end, so the first tagged frame has count 0
  `[review-3 M7]`. The server treats a frame as untagged while it has seen no tagged frame from that client and the
  frame decodes canonically as untagged `HELLO`s only.
- **Rekey.** `desync` is 8 consecutive reliable frames failing the tag with no reliable frame accepted between
  them. When no `REKEY` to that player is pending, the server sends `REKEY` with a fresh 8-byte nonce, derives the
  new key as above, sets e = 0, and from then on verifies that player's frames on both lanes under the new key
  only. The `REKEY` is pending until a reliable frame is accepted under its key; a `desync` while one is pending
  sends none (`rekeySent` 0). The client, decoding `REKEY`, derives the key, restarts its count at 0 and tags every
  later frame with it. No acknowledgement is sent: a frame that verifies under the new key shows that the client
  holds it.
  - **Why the old key can stop at once.** On an unmodified client `desync` means the count left the lookahead
    (`FireServer` raising on 5 or more consecutive frames, §7.3), so no later reliable frame under the old key can
    match. Unreliable frames the client tagged under the old key before it decoded `REKEY` are dropped as
    `tagMismatch`: at most the frames of one round trip.
  - **What a client can hold the server in.** A client that never switches keeps one `REKEY` pending: one flag and
    one key on the server, no extra hashing, and no further `REKEY` while it lasts. Draft 3.5 tried both keys while a
    `REKEY` was pending and cleared it only on `REKEY-ACK`, which the client need never send, so 8 bad tags doubled
    every later frame's hashing for the session (652 µs per 16 KB frame native).
  - **Bound.** Each `REKEY` after the first needs an accepted reliable frame and then 8 failing ones, at least 9
    reliable frames per cycle: at the default `inbound.reliable.frames` (120/s, burst 240) at most 13.3 `REKEY` a
    second sustained and 26 from the burst, 10 B each, all to the player whose frames failed
    `[refusals-rejudged-2 R27]`. An unmodified client is rekeyed one `desync` after each episode, against up to 60 s
    under draft 3.5's spacing.
- **Decision: tag width** `[refusals-rejudged-3 R28]`.
  - **Problem.** A sender without the key guesses the tag. The server tries one input at each of 5 counts per
    reliable frame and 3 extensions per unreliable frame (the caller bit is read in clear, and the old key is
    dropped at a `REKEY`, so neither adds inputs; another variant's mask is dropped as `tagVariant`, so masks add
    none), and Lync applies no consequence to failures, so a guessing sender is limited only by the frame budgets:
    5 × R + 3 × U candidate tags a second for R reliable and U unreliable frames a second, 1320 at the defaults
    (120 and 240, §7.5) and 8000 at the range maxima (1000 and 1000).
  - **Options:** 16 bits (the research's choice: 2 B; one crafted frame accepted every 49.6 s at the defaults,
    after about 18,000 `tagMismatch` occurrences); **32 bits** (4 B; one acceptance per 37.7 days at the defaults
    and 6.2 days at the range maxima, after 1.17 × 10^9 `tagMismatch` occurrences at the defaults); a 64-bit output
    (HalfSipHash's 8-byte mode: 8 B, 794 B/s up for the busy model, and +3–10% per frame at 1 KB or more, +16–39% at
    64 B or less `[probes security-costs #8]`). Trying two or four inputs per candidate, as a caller bit or a caller
    and identity bit inside the hash would, halves or quarters each 32-bit interval: 3.1 days and 37.3 h at the
    range maxima (`probes/refusals-rejudged/r3_tagwidth.out`).
  - **Choice: 32 bits,** the hash's natural output, at no CPU cost over 16. The research's argument for 16 bits
    ("32 bits only matters if acceptance were treated as authentication") assumed failures would be acted on; Lync
    only reports them, so the width alone has to bound acceptance. 64 bits is not taken: an accepted keyless frame
    gives its tool one frame of its choosing, which Lync's own API gives the same client with no guessing, and the
    chance `tagVariant` it would remove (one per 3.5 h at N = 256 variants) arrives beside about 4.5 × 10^6
    `tagMismatch` occurrences from the same player, which identify it. Cost: 2 B more per upstream frame than
    16 bits, 140 B/s for the busy model (§4.1).
- **Decision: where the caller bit travels** `[client-self-checks U7]`.
  - **Problem.** The caller probe's source result has to reach the server for every frame, on both lanes, so that a
    fact can name the frame and its definition; a tool below the encoder must not be able to clear it at any
    `tag.cover`; and it must neither loosen the keyless bound above nor raise the hashes a frame can cost.
  - **Options:** a count in `REPORT` (draft 3.5: reliable lane only, no per-frame evidence, editable past a small
    cover); a bit in the tag input's lane byte only (zero bytes, but the server must try both values at every
    candidate: up to 10 hashes per reliable frame and 6 per unreliable, and one keyless acceptance per 18.8 days);
    **a header bit that the lane byte repeats.**
  - **Choice: the header bit.** One hash per candidate, the keyless bound unchanged, and covered at
    `tag.cover` 0 because the lane byte is always hashed. Cost: 0 or 1 B per upstream frame (§4.1). The identity
    probe's result stays in `REPORT` (`v5-integrity.md` §4): a second bit would buy per-frame evidence for a count
    `REPORT` already delivers within one flush (§5.1).
- **Replay window** `[client-security §3.2]`. The server extends each upstream unreliable `seq` (§4.4), verifies the
  tag at the extension and its two neighbours, then applies a 64-frame RFC 4303 bitmap: newer slides the window,
  unseen inside is accepted, seen or older than the window is dropped (`replayed`). Cost: 1.5 B per frame beyond the
  tag; 24 ns native per frame `[probes review-redundancy-2 inbound_hotpath]`.
- **Per-server id permutation** `[client-security §3.4]`. For each namespace and id space (§4.6), both ends run
  Fisher–Yates from the last index down, j = xorshift32() mod (i + 1), with xorshift32 (x ^= x << 13; x ^= x >> 17;
  x ^= x << 5, mod 2^32) seeded by the permutation seed XOR the low 32 bits of the schema hash XOR the space number
  (1 up, 2 down, 3 collections), replaced by 0x9E3779B9 if that is 0. Every connection of a server derives the same
  seed from the per-server nonce, so downstream ids are one table per server. Seed 0 is the identity (tests). Wire
  id = permutation[canonical id]. Cost: no bytes per frame, 4 B per connection, 21 ns per id native once per
  namespace per server `[probes review-redundancy-2 inbound_hotpath]`. Mixing a per-build value into this seed
  `[generation-methods M4]` is not done: the derived seed is already per build.
- **Runtime-path layout** `[generation-methods M14]`. Each `WELCOME` carries `layout` u1 for its namespace: 1 when
  the server's side of the namespace is the runtime path with `layout.vary` on (§7.5), else 0. With 1, both ends
  apply `v5-integrity.md` §2's field order, offsets and tag constants with the layout seed in place of
  `rotationSeed`; the layout seed is the 64-bit output of HalfSipHash-2-4 under a zero key over (permutation seed as
  u32le ‖ the 6 ASCII bytes `layout`). Rotation set, rounds, S, masks and traps stay at their identity. The layout
  is per server, upstream and downstream, so encode-once and `FireAllClients` hold.
  - **Prices** tools that hard-code a no-build game's layout or the reference tag constants (static forgers, byte
    scripts carried between servers); the layout seed follows from `WELCOME`, so it prices nothing that reads it.
  - **Cost:** per definition, once per server and once per client connection, an IR copy of 1.5–4.3 µs interpreted
    and 0.8–3.0 µs native holding 1.7–3.8 KB; offsets +2 to +26 ns per bounded field per message; order and tag
    constants 0. One bit per `WELCOME`.
  - **A generated view can't follow it:** a client shard whose `WELCOME` carries `layout` 1 reports
    `schemaMismatch` natively and drops that namespace's sends, as on `MISMATCH`; so a seed-0 shard against a
    runtime-path server never decodes a layout it doesn't hold.
  - **Not per session.** A per-session layout prices nothing a per-server one doesn't (a tool that reads the key
    reads the layout in the same pass) and costs the IR copy per player on the server, 34–76 MB at 200 definitions ×
    100 players.

### 4.6 Namespaces, ids and control

- **Namespace index.** The server numbers namespaces 1, 2, … in the order of their first server-side use; the index
  is server-wide and reaches the client in `WELCOME`. A staged namespace's first server-side use is its release
  (`Lync.release(folder)` requires its server view, then replicates the folder), so it takes the next index then
  and costs one namespace index in each toc segment that names it `[interest-rewind §12.3]`.
- **Id spaces.** Each namespace has three, numbered from 0 in definition-name order (ask before answer for a
  request): **up** (client events, asks of client requests, answers of server requests), **down** (server events,
  asks of server requests, answers of client requests) and **collections**. Generated trap definitions
  (`v5-integrity.md` §3) take up ids among the real ones by name. Site ids of a woven build follow the generic up
  ids in canonical order (`v5-tooling.md` §5.5). All are permuted (§4.5). Ids are u(⌈log2 count⌉) of their space,
  so traps cost a bit per upstream run only when D + T crosses a power of two, and site ids
  ⌈log2(D + S)⌉ − ⌈log2 D⌉ bits per upstream run (D definitions, T traps, S sites)
  `[generation-methods M15a]` `[codecs-in-scripts §7.3]`. An id outside the receiving direction's space, or a
  message on a lane its definition doesn't use, is malformed (rule 7) `[review-redundancy-2 10]` `[review-3 M4]`.
- **Control messages** travel in control chunks of namespace 0 (§4.1), only on the reliable lane. Protocol version:
  1, which is everything this draft specifies: the version counts released protocols, and none has been released.

| Type | Direction | Fields |
|---|---|---|
| 0 `HELLO` | up | version u8; `buildId` u32; schema hash as two u32 (low, high); `idTableHash` u32 (`v5-tooling.md` §5.5; 0 with no site ids and no generated traps); namespace name, length u(7) (≤ 64 B), bytes in the tail |
| 1 `WELCOME` | down | namespace index EG0; `layout` u1 (§4.5); in the connection's first `WELCOME` only: epoch f64, `stateRate` u6, `delay` u8 (4 ms units), key nonce as two u32, `tag.cover` u15, permutation nonce u32, `callerProbe.oneIn` u8, `callerProbe.maxPerSecond` u6, `callerProbe.splitFrames` u1, `callerProbe.noOuterFrame` u1 (0 `"unlisted"`, 1 `"ignored"`), `clock.beacon` u4 (tenths of a second); the five `callerProbe` and `clock` fields are 0 (off) until milestone 5, `delay` until milestone 4 |
| 2 `MISMATCH` | down | none |
| 3 `REKEY` | down | key nonce as two u32 |
| 4 | — | unused: a control chunk of type 4 is rule 7 |
| 5 `REPORT` | up | `probes`, `identitySucceeded`, `refusedFrames`, `injectedFrames`, EG0 each (milestone 5, `v5-integrity.md` §4, §5) |
| 6 `BEACON` | up | ⌊`GetServerTimeNow()` × 1000⌋ mod 2^16 as u16 (milestone 5, `v5-integrity.md` §6) |
| 7 `RATE` | down | epoch f64, `stateRate` u6, `delay` u8 |

- **`delay`** is the interpolation delay D the server chose for the client (`v5-collections.md`), in 4 ms units,
  0–1.02 s; a `RATE` that changes it applies from the state tick in its frame's header. The server sends `RATE`
  when `state.rate` changes and when D changes, at most once a second for D: about 11 B per `RATE`
  `[interest-rewind §11.3]`.
- **When the client sends `REPORT` and `BEACON`.** After the first `WELCOME`, a `REPORT` with a non-zero
  `identitySucceeded`, `refusedFrames` or `injectedFrames` `[refusals-rejudged-3 R1]`, and a due `BEACON`, are
  pending reliable data for §5.1's flush rule: the
  next flush sends a reliable frame holding them, with the game's data or alone. At most one of each per frame;
  they never count toward `missedFlush` and never enter the join hold. Bounds: at most 60 frames a second for
  `REPORT`, 8–12 B each when alone (counts of 0–60, tag included), and one per `clock.beacon` period for `BEACON`,
  9 B alone, 11 B with a `REPORT` (`probes/design-3.6/golden_wire.luau`'s writer; draft 3.5's header made them 1 B
  shorter) `[refusals-rejudged-2 R26]` `[clock-facts, the BEACON gap]`.
- **Effect during decode.** A control message takes effect as it is decoded, for the rest of its frame: a client
  decodes the chunks after a `WELCOME` with that namespace welcomed and, for the first `WELCOME`, the key, the
  permutation and the layout applied `[review-3 M3]`.
- **Field rules** (`f1fbfd7:src/transport/control.luau`):
  - A control chunk's count is charged to the decode element budget (§4.8).
  - A `HELLO` name outside 1–64 bytes is rule 2.
  - Rule 3 refuses a `WELCOME` namespace index of 0, a `stateRate` outside 10–60, a `tag.cover` over 16,384, and an
    epoch that is NaN or infinite, in `WELCOME` and in `RATE`.
  - A nonce is two u32, low first.
- **Handshake.** Namespace names are 1–64 bytes. A client view's first use sends `HELLO`; with per-player variants
  it still comes from the shared client shard at once, since variants differ only in the tag mask, which the
  server takes from its own assignment (§4.5). The server answers each `HELLO` in arrival order with `WELCOME` or
  `MISMATCH`, so the client matches answers to its `HELLO`s by order; it never sends a `WELCOME` before the
  namespace's `HELLO`, since the round trip that would save is the one in which the identity fields below are
  checked. A `HELLO` naming a namespace the server hasn't loaded yet is held for up to 10 s, then answered
  `MISMATCH`; so the server must use every namespace within 10 s of a client's `HELLO` for it, since answers go in
  order and a longer hold would delay every later answer. A mismatch of version, `buildId`, schema hash or
  `idTableHash` is `MISMATCH`: the client reports `schemaMismatch` natively once and drops that namespace's sends;
  the server reports the fact `schemaMismatch` and drops its own sends to that player's namespace. A `WELCOME`
  comes before the held sends it releases (§5.3).
- **Hash.** HalfSipHash-2-4, zero key, 64-bit output, over the canonical serialization of §4.7 at seed 0. Per
  definition hashes are not sent; Studio and `lync check` name the differing definitions. No hash of the shard's
  code is sent: in the default `build.seed = "release"` an unmodified client's would always equal the server's
  expectation, a modified client sends any value, and a planner change that alters bytes is a protocol version
  change instead (§4.9) `[build-checks §4]`.

### 4.7 Schema hash input

The canonical serialization is a byte string; everything little-endian:
- `str` = u16 length + bytes; `num` = the f64 bits (−0 written as 0; NaN and ±inf are declaration errors);
  `u8`, `u16` as named; a boolean is a `u8`, 0 false and 1 true. Every codec parameter that is a number (bounds,
  steps, maxima, bit counts) is a `num` `[review-3 M6]`.
- Schema: `u8 1` (serialization version), namespace `str`, definition count u16, then each definition in name
  order: name `str`, kind u8 (1 event, 2 request, 3 collection), `from` u8 (1 client, 2 server; collections 2), lane
  u8 (1 reliable, 2 unreliable; requests and collections 1), then the options in the order `data`, `reply`, `key`,
  `limit.perSecond`, `limit.burst`, `timeout`, `maxRecords`, `priority`, `reliableRate`, `perceived`, `sealed`,
  each as a presence u8 followed by its value: a codec, a `num`, a boolean, or for `sealed` its
  `sealed.outstanding` `num` then `sealed.hideLength` boolean. An option the kind takes is present with its
  resolved value, defaulted or not (`timeout` 10 and `perceived` false when omitted); an option the kind doesn't
  take, and an omitted option with no default (`data`, `limit`, `key`, `reliableRate`, `sealed`), is absent.
- Codec: a type u8, then parameters: 1 bool; 2 int (min `num`, max `num`); 3 unbounded int; 4 number (min, max,
  step); 5 f32; 6 f64; 7 angle (step); 8 string (max); 9 buffer (max); 10 vector3 (min, max, step); 11 vector3f32;
  12 direction (bits); 13 rotation (bits); 14 cframe (two codecs); 15 color3; 16 list enum (count u16, `str` each);
  17 Roblox enum (enum name `str`); 18 instance (class `str`, empty when absent); 19 optional (codec); 20 array
  (codec, max); 21 map (key codec, value codec, max); 22 union (count u16, then name `str` + each variant as a full
  codec, type 23); 23 record (count u16, then per field: name `str`, codec, `newest` u8, visibility u8 with 0 none,
  1 `:owner()`, 2 `:team()`, 3 `:gated()`, 4 `:seen()`); 24 custom (name `str`, version `num`); 25 convert (base
  codec; functions are not hashed); 26 role (u8: 1 `:input()`, 2 `:claim()`; then the codec); 27 interned (the
  string codec a `strings` declaration makes internable upstream, then that codec).
- Everything that changes bytes or what a decoder accepts is in it, so an unmodified client can't send on a
  direction, lane or form its definition doesn't use; server-view declarations (`:trap()`, `:refers()`, checks,
  `reactsTo`) change neither and are not hashed. Serialization version 1 covers all of the above: like the
  protocol version, it counts released forms, and none has been released.
- Golden vector G6 (§4.10) fixes the bytes and the hash.

### 4.8 Canonical decode

A decoder returns a rule number rather than raising; any rule refuses the whole frame (`malformed`, evidence
`rule`). Refusing whole frames is what makes skipping unnecessary: no lengths, so one chunk breaking a rule can't
desynchronise the tail `[review-1 B1]` `[review-redundancy 6]`. The rules:
1. the call is not one buffer plus at most one array of `Instance` or `nil`;
2. a count, length, index, EG code or quantized code past its maximum (a value equal to the maximum is legal); an
   offset code w ≥ n (§4.3; the decoder checks w, then inverts it, then applies rules 3 and 6 to q
   `[generation-methods M3]`); an EG code with z > 53 or a value above 2^53 − 1; or an upstream string reference
   whose `table` is not below the number of tables the server has sent to this player, or whose `id` is not below
   the entries of that table it has sent to this player (`strings`, `v5-extensions.md`) `[refusals-rejudged-1 R33]`;
3. a value outside its declared range or a refused value (§3.3);
4. non-zero padding, or bits and tail that don't meet exactly;
5. map keys not strictly ascending;
6. smallest-three components whose squares sum past 1, a non-canonical rotation code (§3.3), a zero direction,
   or a non-canonical toc (two adjacent
   segments of one namespace, or state or remove segments not in ascending namespace order);
7. an id outside the receiving space; a message on a lane its definition doesn't use (a reliable event, an ask or an
   answer in an unreliable frame, an unreliable event in a reliable frame, a control chunk or rows in the wrong frame
   kind); a chunk for a namespace not welcomed when it is decoded; or a control type that is unused (4), in the
   wrong direction, or at a time the protocol doesn't allow (`BEACON` while beacons are off);
8. an upstream reliable frame over 16,384 B, or an unreliable frame over 1000 B;
9. an instance-list entry that no index references, that repeats an earlier entry, or that is out of the order of
   first reference;
10. the frame's decode element allowance goes negative. This is reported as `overElementBudget`, not `malformed`.

The decoder runs under one `pcall` per frame; any raise inside it refuses the frame as `decoderRaised` and reports
natively (a Lync bug), so refusals cost a return, never a 2–3 µs raise `[diagnostics §9]`. The client's decoder
applies the same rules to downstream frames, with rule 10's allowance fixed at 2^22 elements per frame instead of a
bucket (below). Exp-Golomb codes are unique for a given k. Column mode, k, frame-of-reference base (any base up to
the minimum) and width (any width that fits), and an upstream string as a reference or a literal, are free choices
`[review-m1 t5]`. The instance array needs no cap of its own: each entry is charged 8 B at §6.1 step 2.

**Decision: bounding decode work** `[review-m1 B1]`.
- **Problem.** Bytes don't bound decoded elements. Column mode 0 codes a constant column in 0 bits per element, and
  0-bit elements (`{}`, `t.int(a, a)`) cost nothing in any mode. So `t.array(t.array({}, 65535), 7996)` decodes 3 bytes
  into 4.2 million tables (2.1–2.7 s, 384 MB), and `t.array(t.bool(), 65535)` puts about 16 s of decode in one
  16,384 B frame `[probes review-m1 p2]`. A run count alone can also promise millions of empty messages.
- **Options:**
  - (a) A static worst case per definition, refused at declaration. It bounds one message, but not how many
    messages a frame's run counts promise.
  - (b) A per-frame budget proportional to frame bytes, as in the v5 attempt's "decode allocation ≤ 1024 B per
    frame byte + 16 KiB". Constant columns an unmodified encoder writes reach about 21,845 elements per byte, so
    either the ratio admits the 3-byte frame above or it refuses those columns.
  - **(c) Both static rules, and a per-player element bucket on the server that charges counts before allocation.**
- **Choice: (c).**
  - **An element** is one message of a run, one array element or one map pair.
  - **A message's worst case** W = 1 + E(data), where E(record) = Σ E(field), E(optional c) = E(convert c) = E(c),
    E(union) = the largest variant's, E(array c, max) = max × (1 + E(c)), E(map k v, max) = max × (1 + E(k) + E(v)),
    and every other codec is 0. A `t.custom`'s decode allocates in game code.
  - **At declaration:** W ≤ 65,536 (`elementsTooMany`), so `t.array(t.bool(), 65535)` fits; and no
    `zeroWidthElement` (§3.4).
  - **At run time, on the server only:** a per-player bucket `inbound.elements` (§7.5). A frame's decode starts with
    an allowance of the bucket's whole tokens. The decoder subtracts each run, array and map count before it
    allocates and refuses the frame with rule 10 when the allowance goes negative. The elements a frame used are
    then taken from the bucket, whether it was accepted or refused.
  - **Clients don't enforce the bucket.** The reason is who writes a client's downstream and what a refusal does
    there, not trust `[refusals-rejudged-2 R32]`: only the game's own server writes it through the engine (the other
    writer is an executor on that client injecting into its own view, which the refused-frame and injected-frame
    counts cover, `v5-integrity.md` §5), and a refused reliable frame loses events, answers and collection writes
    with no resend, so the client diverges for the rest of the session. A bucket would turn a server's heavy but
    canonical output, such as relays of every player's messages, into that divergence. The server counts what it
    sends instead (`elementsSent`, §7.4).
  - **The client's fixed allowance.** Its reader still starts each frame with an allowance of 2^22 (4,194,304)
    elements, the bucket's largest burst; past it the frame is refused with rule 10 and counted (`refusedFrames`,
    §7.4), never reported as a fact, and an unmodified server splits before it (§4.1). The allowance bounds counts,
    not time: one frame at 2^22 elements decodes in 57–65 ms (a `false` bool column) to 175–190 ms (empty records)
    interpreted on the CLI, and 2.1–2.7 s with 384 MB for 4.2 million nested tables kept live
    (`probes/refusals-rejudged/r2_costs.out` §D, `[probes review-m1 p2]`). So it stops a count near 2^53 of
    zero-bit rows from running without end; a frame within it can hold a client for tenths of a second to seconds,
    and only the game's server can send one.
  - **Cost:** a subtraction and a comparison per count, 3.1–3.4 ns native and about 13 ns interpreted. At the
    defaults, a player can make the server decode at most 20,000 elements a second beyond a 65,536 burst; each
    costs about 585 + 55 × F ns native on the milestone's interpreter, F the leaf fields of the widest client-sent
    record (440 ns with no payload to 7,611 ns at 128 fields; 590–14,980 ns interpreted), so the element term is
    8.8–152 ms/s per player native over 0–128 fields `[probes inbound-budgets claim 1]`. Which bucket binds decode
    CPU depends on the schema; the budget derivation is §7.5's.

### 4.9 Constants

None is a knob `[review-redundancy-2 7]`. **Protocol constants** change bytes or what a decoder accepts, so they are
versioned by the protocol version in `HELLO`. **Runtime constants** change behaviour on one end only. A derivation
reads "chosen, unmeasured" where no measurement produced the value. **The planner's output is protocol:** any
planner change that alters a frame for some (schema, `buildId`, `rotationSeed`) is a protocol constant change and
bumps the protocol version, and the golden set enforces it, since a changed vector with an unchanged version fails
CI `[build-checks §4.2]`. This is why `HELLO` carries no code hash (§4.6).

## 5. Delivery

### 5.1 Flushing and state ticks

**Decision: who decides when frames leave.**
- **Problem.** v4 made the developer call `flush()` every frame; that caused a missed-flush detector,
  `Connect(Lync.flush)` throwing, and start-order rules `[v4 §8]`. Some cases still need control: before a
  destructive action, fixed-tick games, tests.
- **Options:** manual only; automatic only; **automatic by default, an explicit "send now" and a manual scheduler.**
- **Choice: the third.**
  - **Server.** It flushes at every `RunService.PostSimulation`.
  - **Client: a flush accumulator that keeps its remainder.** The client holds a (seconds), 1/60 at start. At
    each `PostSimulation` step, a ← min(a + Δ, 2/60), where Δ is the `os.clock()` time since the previous step;
    if then a ≥ 1/60, the step is a flush step: a ← a − 1/60, and the client flushes if anything is pending. A
    flush step with nothing pending still uses its 1/60, so the flush steps depend on frame times alone.
    - **Bound** (derived): at most one automatic flush per step, and at most 60·t + 2 in any t seconds, since a
      never exceeds 2/60. The cap carries one slot past a long frame and never two, so a hitch is not followed by
      a catch-up burst.
    - **Rates.** Modelled frame times (`probes/checks-telemetry/telemetry_samples.out` part A2): 60.0 Hz at a
      steady 60, 120, 144 or 240 FPS, 58.3 Hz at 60 FPS with 3% frame spikes, and every step below 60 FPS
      (29.1 Hz at 30 FPS) `[checks-telemetry T4 cause 1]`. Real frame-delta noise at a 60 FPS cap is unmeasured
      (§10).
    - **Rejected readings.** "At least 1/60 s since the last automatic flush" (draft 3.5's words) skips every
      frame that came in just under 1/60 s: 40.0 Hz at a steady 60 FPS and 47.8 Hz at 144 FPS in the same model,
      below the 60 Hz that §4.9 and §7.5 derive from. A slack threshold ("at least 0.9/60 s") gives 60.0 Hz at
      60 FPS but 47.8 Hz at 144 FPS.
  - **Pending data** is anything game code sent and, on the client after the connection's first `WELCOME`, two
    control messages of Lync's own: a `REPORT` with a non-zero count that `v5-integrity.md` §4 makes pending, and
    a due `BEACON` (`clock.beacon` tenths of a second of `os.clock()` since the last frame carrying one was passed
    to `FireServer`, or since the first `WELCOME` for the first; its stamp is read when the frame is encoded).
    Either makes the flush send a reliable frame, with the game's data or alone; neither counts toward
    `missedFlush` or enters the join hold (§5.3). Both ride the one reliable frame per flush, so they add no
    frames beyond the bound above: at most 60·t + 2 forced frames in t seconds for `REPORT`, one per
    `clock.beacon` period for `BEACON` (sizes in §4.6) `[refusals-rejudged-2 R26]` `[clock-facts, the BEACON
    gap]`. Without them, a client that sends only unreliable data, or sends nothing, never delivers its counts,
    and fewer than 3 reliable sends a second give the beacon fit in 0–0.6% of epochs (`beacon_sim.out`,
    simulated).
  - **Late sends** after the flush point leave with the next flush step (up to 1/60 s of latency at 60 FPS and
    above, one frame below it).
  - **`Lync.flush()`** sends everything pending now: no arguments, idempotent, safe in handlers; for before
    `Player:Kick()`, before a teleport, and at the end of a custom tick. It doesn't touch the accumulator.
  - **Shutdown and leaving.** `BindToClose` flushes; a leaving player's pending frame is flushed first.
  - **`Lync.scheduler("manual")`**: frames leave only on `Lync.flush()`, Lync's own `REPORT` and `BEACON`
    included. When the 3rd consecutive `PostSimulation` step ends with game data pending and no `Lync.flush()`
    since it became pending, `missedFlush` is reported, once per wait: the next report needs a flush first.
- **Dispatch.** Each frame's messages are delivered in frame order to the definition's connections at the time of
  dispatch. A client or server message whose definition has no `connect` connection then is dropped and counted
  (`messagesUnhandled`, §7.4); Lync keeps no queue for code that hasn't connected yet. The engine's own queue
  for a `RemoteEvent` with no listener (documented: delivered in order once a handler connects
  `[refusals-rejudged-3 R1]`) never applies, because Lync's listener connects at start. A per-definition queue
  was not taken: it would hold the server's data for code that may never connect, bounded by nothing the client
  knows, and a game that requires a shard and connects in the same synchronous run of a script misses nothing.

**Decision: how state ticks relate to flushes** `[review-1 B2]`. Reliable collection state goes every flush (or at
`reliableRate`), so a `set` before a `fire` is always seen first; `:newest()` rows and the scheduler run on state
ticks. A flush is a state tick when T = ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋ has advanced since the
previous one; T may skip when frames slow. The rest is in `v5-collections.md`.

Under Server Authority, simulation input belongs in `InputActions` and remotes are off the synchronized timeline
`[state-sync §8.1]`: Lync carries intents, claims and state outside the simulation, and `Lync.tick()` (the current
state tick; on the client, the tick of the frame being dispatched) bridges the two. Unreliable messages may be lost
and are never resent.

### 5.2 Requests

- **Slots.** 16 per direction per connection, each with a 1-bit epoch. An ask row is `slot:u4 epoch:u1 payload`; an
  answer row is `slot:u4 epoch:u1 outcome:u2 [reply]`, outcome 0 value, 1 `rejected`, 2 `unanswered`,
  3 `limited`. Request and answer runs are always single-row. An `invoke` that finds no free slot waits, its
  timeout already running.
- **Every ask that is read is answered** `[review-2 B1]`:
  - the value;
  - `limited` when the server's `limit` bucket for the definition is empty (`overLimit`). It tells the asker to
    retry after about 1/`perSecond` s, and reveals nothing the client doesn't know, since it holds the same `limit`;
  - `rejected` when the answering side drops it after reading its slot because `validate` returned `false` or
    threw, a check's policy dropped it (`v5-checks.md`), the definition is a trap, or the ask is `unresolved`.
    These causes share one outcome on purpose: a trap must be indistinguishable from a `validate` refusal to the
    client that fired it (`v5-integrity.md` §3), so `rejected` is never split;
  - `unanswered` when the definition has no `handle` at dispatch (§3.5), or the handler threw, returned a reply the
    `reply` codec refuses (nil included, for a reply that isn't optional; reported natively as `valueRefused` at
    the definition), or ran past `timeout`.

  A throwing `handle` is detected without `xpcall`: the wrapper marks the slot answered on return, and a slot whose
  thread is dead and unanswered threw (its error is reported natively by the engine); handlers that yielded are
  checked by `coroutine.status` once per flush `[diagnostics §1.4]`.
- **Frames that are dropped whole** (budget, tag, malformed) never reach their slots, so the asking side reclaims a
  slot when its caller times out and flips the slot's epoch. Every slot's epoch starts at 0.
- **Checks, in order** `[review-3 m1]`. On the answering side, an ask for a slot in flight with the other epoch
  replaces the abandoned ask, whose answer is discarded; with the same epoch it is `slotConflict` case 3. On the
  asking side, an answer whose epoch differs from the slot's current epoch is a late answer after a timeout:
  discarded and counted (`lateAnswers`), not a fact. Otherwise, an answer for a free slot is `slotConflict` case 1,
  and one whose id is not the answer id of the slot's request is case 2.
- **Timing on server results** `[clock-facts §U4.1–§U4.2]`. In seconds of server `os.clock()`, the times
  `earlyAnswer` and `earlyReaction` already read (`v5-integrity.md`), so a result, a fact and its evidence agree for
  one answer:
  - t_s is the flush that passed the ask's frame to `FireClient` (for a held ask, the flush that released it), not
    the `invoke` call; t_r is the decode of the frame holding the answer.

  | Field | Value | nil when |
  |---|---|---|
  | `roundTrip` | t_r − t_s | no answer arrived |
  | `pingAtSend` | `Player:GetNetworkPing()` sampled at t_s | the ask never left (a `timeout` while waiting for a slot or in the join hold; `left` or `shutdown` before its flush) |
  | `pingAtAnswer` | `Player:GetNetworkPing()` sampled at t_r | no answer arrived |
  | `minPing` | the early-answer bound at t_r (`v5-integrity.md`): the number `earlyAnswer` compares `roundTrip` with | no answer arrived |

  An answer with outcome `rejected` or `unanswered` from the client has all four. A late answer has no result
  (`lateAnswers`). `earlyAnswer` fires on exactly the answers whose result shows `roundTrip` <
  `earlyAnswer.factor` × `minPing`.
  - **Resolution.** t_s is read at `PostSimulation`, and whether the engine sends in that frame is unmeasured
    (§10): up to one server frame (16.7 ms at 60 Hz) of `roundTrip` may be server-side. t_r waits for the engine
    to run Lync's handler, quantized to the server frame. On the client, the ask waits for its next frame
    (up to 1/fps) and the answer for the next automatic flush (§5.1). `GetNetworkPing` is smoothed by an
    unmeasured constant (§10). The docs give the simulated distributions `[clock-facts §U4.3]`, marked simulated.
  - **Cost:** two numbers per slot (256 B per player for 16 slots, the same reads `earlyAnswer` takes per ask),
    one `GetNetworkPing` per answer (engine cost unmeasured, §10), and +15.7–25.4 ns native, +40–47 ns interpreted
    per result for the four fields `[clock-facts §U4.5]`. No bytes.
- **Not used:** `RemoteFunction`, `InvokeClient`.

### 5.3 Joining and holding

**Decision: what the client's join hold counts.**
- **Problem.** Before a namespace's `WELCOME` the client can't send that namespace's messages, and with per-player
  variants it can't tag any frame before its mask is installed (§4.5; `v5-integrity.md` §2.4). Held sends must
  then leave in frames the server accepts: within the minimum reliable byte burst (49,152 B) and the minimum element
  burst (§7.5). Draft 3.5 counted bytes only, and loosely: messages of no payload cost 0 bits, so any number of
  them fit 32,768 B and their release could pass every element burst; and messages merged into runs at release
  gain run headers and column modes that a per-message byte count doesn't hold.
- **Options:** (a) charge each held message its definition's worst-case encoded size `[generation-methods M12]`:
  an upper bound, but `chat`'s `"gg"` (§3.4) is charged 201 B for 3, so the hold fills about 70 times sooner;
  (b) charge its single-row size under the seed-0 plan `[interest-rewind §13.2]`: exact for its row, but neither
  the run headers nor the column blocks of merged runs are counted, and zero-bit messages are still free; **(c)
  hold each message as a run of its own, charge exactly those bits, release it that way, and cap elements too.**
- **Choice: (c).**
  - **Charge.** Each held send is encoded at `fire` as a run of its own: its id, count − 1 = 0, its instance count
    when its definition can hold instances, and its single-row encoding (§4.1, §4.3). It is charged those bits over
    8, plus its tail bytes, plus 8 B per instance (the server's charge, §6.1), and 1 + its array and map counts in
    elements (§4.8). A namespace's hold may hold at most 32,768 B (the sum, rounded up) and 2,048 elements.
  - **Release.** Once the namespace's `WELCOME` has arrived and, with variants, the mask is installed, the held
    runs are written in call order, each still its own run, behind the `WELCOME`'s effect. The frames then carry
    exactly the charged bits plus each frame's header, toc, alignment and tag (at most 128 B per frame, §4.9): at
    most three frames and 384 B for a full hold, so a released hold fits the 49,152 B minimum byte burst; and 2,048
    elements leave half of the 4,096-element minimum burst (§7.5) for control rows and the flush's other sends.
    Released messages lose column coding: at most 32,768 B once per namespace per connection.
  - **Past a cap** the send is dropped as `sendDropped` cause 1 (bytes) or 7 (elements). An unreliable send while
    the namespace waits for `WELCOME` is cause 2, and while it waits only for the mask, cause 6 (§7.3).
  - Held sends stay encoded bytes in every case: variants differ only in the tag mask, applied when a frame is
    sent (§4.5). `HELLO` never waits for the mask (§4.6), so a join with variants takes max(variant arrival, first
    use + one `HELLO`/`WELCOME` round trip) instead of their sum `[generation-methods M12]`; the arrival time is
    unmeasured (§10). A mask not installed 10 s after the first `WELCOME` is `variantMissing`
    (`v5-integrity.md` §10); the client keeps waiting.
- **Server.** Every target resolves at flush to its players. For a player whose namespace isn't welcomed yet, the
  server holds what it would send, up to 32,768 B per player, and sends it in the frames after the `WELCOME`'s
  control chunk (the same frame or later) `[review-3 M3]`; past that it drops and
  reports `sendDropped`. So `fire(Lync.all, …)` during a join reaches the joiner late rather than never, and
  `FireAllClients` covers only welcomed players `[review-2 M8]`. A server `invoke(player, …)` before `WELCOME`
  waits in the hold, its timeout running.
- **Collections** send catch-up adds after `WELCOME` (`v5-collections.md`).

### 5.4 `limit`

- **Client.** It throttles itself to `(perSecond, burst)` per definition. Over-limit reliable fires wait in a FIFO
  of at most `burst` messages and leave as tokens return; fires past that, and over-limit unreliable fires, are
  dropped (`sendDropped`). A held message leaves after messages fired later on other definitions, so with `limit`
  delivery order holds per definition only; an over-limit `invoke` waits with its timeout running
  `[review-2 M12, m11]`.
- **Buckets.** Every bucket (inbound budgets, `limit` on both sides) starts full and refills continuously: on each
  use, tokens = min(capacity, tokens + rate × elapsed `os.clock()` time) `[review-3 M7]`. The client checks its FIFO
  at each flush.
- **Server.** A token bucket with rate `perSecond` and capacity `burst + 2 s × perSecond`, counting arrivals. The
  slack absorbs retransmission releasing queued frames together (p99 stall 850 ms under 5% bursty loss, simulated
  `[state-sync §1.3]`); a client firing at its limit exceeds it only after a stall longer than
  2 s + `burst`/`perSecond` (derived).
- **Not counted by send time** `[refusals-rejudged-3 R21]`. A send time stated in the frame and clamped to what the
  server can check (not after arrival, not before the previous one, at most 2 s old) lets a modified client accept
  exactly as many messages as the arrival bucket and an unmodified client no fewer drops (derived; `r3_limit.out`,
  simulated); a clock at the upstream reliable frame count / 60 drops 64–90% of an unmodified client's messages
  when it fires slower than 60 a second, and runs ahead for a client sending more frames. Neither does anything
  the slack doesn't.

### 5.5 Collections (milestone 4)

Collections replicate keyed records (or one singleton record) from server to clients. Structure and reliable
fields travel on the reliable lane, encoded once per audience partition; `:newest()` fields travel as absolute
rows encoded once per state tick, chosen per viewer by a budgeted scheduler and repaired by notify. Prediction
against acked baselines is the `acked` extension. Records are addressed by slot after their add. The full design,
including the measured `:newest()` decision, catch-up, slots, the scheduler, audiences, interest, visibility
classes, scoped events, rewind and interpolation, is in `v5-collections.md`.

## 6. Security

### 6.1 Inbound pipeline (server)

In this order; nothing is decoded before it is paid for:
1. **Shape.** One buffer, plus at most an array of `Instance` or `nil`, on one of Lync's remotes (`malformed`,
   rule 1).
2. **Budgets.** Per player and lane, token buckets for frames and bytes, charging `buffer.len` + 8 B per instance
   before any decode (`overFrameBudget`, `overByteBudget`). An over-budget reliable frame is still tag-checked, so
   the count stays in step. Decoded elements are charged to `inbound.elements` during step 4 (§4.8, rule 10,
   `overElementBudget`).
3. **Integrity.** The tag; on the unreliable lane, the replay window (§4.5).
4. **Decode the whole frame** (§4.8) before delivering any of it. Ids go through the permutation. An ack naming a
   seq never sent to this player is ignored (`impossibleAck`).
5. **Per message:** control messages; traps and reachability (`unreachable`, milestone 5); answers
   (`slotConflict`, `earlyAnswer`); `unresolved` (an unknown Roblox enum value, a required instance that arrived
   `nil`, an `IsA` failure); `limit` (`overLimit`); then report-only checks of milestone 5 (`decoyReferenced`,
   `canaryEchoed`). Dropped asks are answered `limited` (over `limit`) or `rejected` (§5.2).
6. **Validators**, under `xpcall` (+18–38 ns per call `[diagnostics §9]`): `false` drops the message (counted; an
   ask is answered `rejected`); a throw does the same and is reported natively as `validatorError`, at most once
   per definition per `observe.window` s (§7.2); a yield is detected by a re-entrancy flag and reported as
   `validatorYielded`.
7. **Delivery** to handlers in pooled threads.

Measured cost of steps 4–5 per message: 39 ns native, 125 ns interpreted `[probes review-redundancy-2
inbound_hotpath]`.

### 6.2 Client-side integrity

Client-side integrity is first-class. Each measure is judged by the cost it imposes on tampering against its own
runtime, wire, size and developer cost, and by principle 2 that cost is weighed, never a veto by itself: where it
matters, an option controls it. Neither "a modified client with full memory access can defeat it" nor "a
universal counter exists" is a reason on its own, because Lync varies what a counter depends on per build, per
server and per session. Every measure only reports; none replaces a server check or applies a consequence.

| Measure | What it prices | Milestone | Where specified |
|---|---|---|---|
| keyed tag over the implicit counter | raw senders, replays, injection below the encoder, blocked calls | 2 | §4.5 |
| sequence and replay window | replayed unreliable frames | 2 | §4.5 |
| per-server id permutation | byte tools built on another server | 2 | §4.5 |
| per-build field and tag rotation | static tools built on an earlier build | 5 | `v5-integrity.md` |
| traps and reachability | API drivers firing definitions unmodified client code never fires | 5 | `v5-integrity.md` |
| caller probe | API calls from executor threads or unlisted chunks | 5 | `v5-integrity.md` |
| refused-frame report | non-canonical frames injected into a client's own view | 5 | `v5-integrity.md` |
| clock beacon | clock-accelerating tools | 5 | `v5-integrity.md` |
| early answers | answers sent before a server ask could arrive | 5 | `v5-integrity.md` |
| decoys, canaries | readers of raw replicated state | 5 | `v5-integrity.md` |

The measures refused or kept out, each re-judged under the rule above, are in `v5-changes.md`. Lync never tells a
client what was observed, beyond `REKEY` and request outcomes.

## 7. Diagnostics

### 7.1 Codes and messages

- **One identifier per fact or error: a lowerCamelCase code, unique across Lync** `[diagnostics §2]`. It is the
  fact's `reason`, the result's `error`, the build diagnostic's `code` and the docs slug
  (`https://lync.dev/codes/<code>`, also `lync explain <code>`). Each code has a registry page
  `docs/codes/<code>.md` with `family`, `since`, `retired?`, `evidence` (facts) and `example` (its exact rendered
  output). Codes are never renamed or reused; codes and evidence fields change only in a major release, wording in
  any. The Luau and TypeScript code unions are generated from the registry, so a raise site with an unregistered
  code is a type error.
- **The registry page** has front matter (`family`, `since`, `retired?`, `evidence` in the order `Facts.record` takes
  it), a description, an evidence table for facts, "Known causes on an unmodified client" (copied from §7.3 or
  `v5-integrity.md` §10), an `example` block and a fix. A fix names the option, declaration or game code to change
  ("If it occurs with a cause listed above, raise `inbound.reliable.bytes`"), or states what Lync already did
  ("Nothing is required by Lync; the frame was dropped.").
  - **Examples are byte-exact.** The registry test runs each page's documented trigger and compares the message
    with the `example` byte for byte; these are the only prose comparisons in the tests.
  - **Deferral.** While the milestone that raises a code isn't built, its trigger and "named by a test" checks may
    wait. A frozen list in the registry test names each such code, and that milestone must empty the list.
  - **Codes of milestones 1–2** (53; the build had 50, `f1fbfd7:src/diag/codes.luau`, before draft 3.5 split
    `overBudget` and added `limited`):
    - declaration: `duplicateName`, `elementsTooMany`, `enumItems`, `intBounds`, `mapKey`, `messageTooLarge`,
      `missingOption`, `nameLength`, `newestPlacement`, `newestWidth`, `notACodec`, `notADefinition`,
      `numberStep`, `numberStepIsInt`, `optionalPlacement`, `paramRange`, `unionKindField`, `unknownOption`,
      `unreliableTooLarge`, `vectorStep`, `zeroWidthElement`;
    - caller: `configureRange`, `unknownTarget`, `valueRefused`, `wrongSide`;
    - fact: the 19 of §7.3;
    - outcome: `timeout`, `limited`, `rejected`, `unanswered`, `left`, `shutdown`;
    - fault: `validatorError`, `validatorYielded`;
    - internal: `internal`.
- **A family fixes a code's primary channel** (§7.2): `declaration` (`unknownOption`, `numberStep`, `newestWidth`,
  …), `caller` (`valueRefused`, `unknownPatchKey`, `wrongSide`, `recordLimit`, `unknownField`, …), `fact` (§7.3),
  `outcome` (the six results), `fault` (`validatorError`, `validatorYielded`), `build` (`staleShard`, `rawRemote`,
  `solverOff`, `configSyntax`, `configUnknownKey`, `configType`, `configRange`, `configMissing`), `internal`. Two
  facts also have a second channel: `decoderRaised` is always reported natively too, and `schemaMismatch` is
  reported natively on the client.
- **Message grammar:** `source:line: [Lync] <code>: <subject> must <requirement>, got <value>[; <fix>]`, one line,
  at most 200 bytes after the position. The subject uses the user's names (`arena.buy:invoke data.item`); a fix is
  given only when there is exactly one.
- **What names and text may say.** Code names, evidence and counter names, `[Lync]` messages, registry pages
  (prose, fixes and examples) and the published docs state what was observed, the requirement it was checked
  against, what Lync did, and the documented causes. They never characterise a sender's intent, trustworthiness or
  skill, or a value's quality, and never recommend a consequence for a player. The registry test enforces a
  backstop on every code name, evidence field name, page body and `example`, case-insensitively at word
  boundaries: `anomal*`, `abuse*`, `attack*`, `bad`, `cheat*`, `exploit*`, `flagged`, `honest*`, `hostile`,
  `illegal`, `invalid*`, `malicious`, `naive`, `suspic*`, `unexpected`, `weird`. The list is not the rule: a
  page passing it can still break the rule, and adding a code includes checking its page against the rule.
- **Positions.** Caller errors walk `debug.info` to the first frame outside Lync and its shards, never
  `error(msg, 2)`, whose meaning differs between Studio (-O1) and live (-O2) `[diagnostics §1.1]`; the walk costs
  133–492 ns interpreted and 191–619 ns native for 1–5 Lync frames on the stack `[diagnostics §1.3]`, only on
  failure. Schema constructors record `debug.info(2, "sl")` (the line where the call starts) once, and declaration
  errors use it.
- **Values** are rendered by one `show()` on the failure path only: strings quoted, escaped and cut at 40 bytes;
  buffers as their size; instances as `Instance(ClassName)`, never their names `[diagnostics §3.2]`. Checks call a
  cold `fail()` and never format eagerly (+95–117 ns per value otherwise `[diagnostics §9]`).
- **Lync throws strings only**: a table error breaks `xpcall(f, debug.traceback)` `[diagnostics §1.2]`.

### 7.2 Channels

| Class | Channel |
|---|---|
| declaration mistake | throw at the declaration's line; the same code as a build diagnostic |
| caller mistake, stale shard in Studio | throw at the caller |
| `connect`, signal and observer faults | native report from their own pooled thread |
| `handle` fault | native report, and `unanswered` to the asker (§5.2) |
| validator throw or yield | native report (spacing below); counter; message dropped; ask `rejected` |
| validator `false` | counter; ask `rejected` |
| what other players send, and local send drops | fact (§7.3) |
| `:newest()` rows deferred by the budget | counter only |
| request outcomes | result value |
| schema mismatch | client: native report once per namespace; server: fact |
| decoder raised, internal invariant | native report `decoderRaised` / `internal` (spacing below), plus the fact for `decoderRaised` |
| build and plugin findings | build diagnostic (LSP shape, `v5-tooling.md`) |

A native report is an error raised in its own thread (`task.spawn(error, message, 0)` for Lync's own), so it shows
red with a stack in Output and the Error Report and fires `ScriptContext.Error`. **Spacing:** Lync makes at most one
native report of its own per (code, definition) per `observe.window` seconds, timed from that key's previous
report; for `decoderRaised` and `internal` the definition is nil. Errors the engine reports from game code's
threads are not spaced.

### 7.3 Facts

**The event.** `Lync.observe(fn)` returns a connection. Each fact is delivered to each observer in a pooled thread,
so a throwing observer is reported natively and a yielding one holds only itself. A fact is frozen:
`{ reason, player?, namespace?, definition?, count, first, last, evidence }`, discriminated on `reason` so
`evidence` narrows in Luau and TypeScript on both solvers `[probes review-2 t3]`. `player` is the sender on the
server, the player concerned for a server-local fact (a held send, a missed flush), and nil for a client's local
facts; names come from the receiving side's schema; `first`/`last` are
`GetServerTimeNow()`; evidence is numbers only (`lane` is 0 reliable, 1 unreliable).

The `checks` extension adds `constraint`. Facts never carry bytes from a client.

**Delivery limits** protect the server; they never hide an occurrence `[diagnostics §5.2]`:
- **Coalescing.** A key is (player, reason, namespace, definition); its window opens at its first occurrence, which
  is delivered at once, and closes `observe.window` s later (`os.clock()` seconds; `first` and `last` are
  `GetServerTimeNow()`). If more occurred, one fact at close carries their `count` and the last occurrence's
  evidence. Windows are swept once per flush.
- **Caps.** At most `observe.perPlayerEvents` facts per player per window and `observe.serverEvents` per server.
  Occurrences past a cap are counted per player and reason; at window close each such player gets one
  `suppressed`, exempt from the caps. Memory per player: at most `perPlayerEvents` keys plus one count per reason.
- **Caps' windows** are per player, each opening at that player's first occurrence after its last window closed.
- **One record, three outputs.** Recording an occurrence also increments its reason's counter (`facts.<reason>`,
  uncapped) and feeds the console, so facts, counters and console can't disagree; the facts state is built with the
  counters and the console. A `Fact` is frozen when delivered.
- Each occurrence costs a key lookup and an increment: 20.5 ns native `[diagnostics §9]`.

### 7.4 Counters and console

- **Counters, not per-frame events** `[diagnostics §5.3]`. `Lync.counters(player?)` returns a frozen snapshot: per
  definition `messagesSent`, `messagesReceived`, `bytesSent`, `bytesReceived`; per reason `facts` (uncapped);
  `rowsDeferred`, `validatorErrors`, `validatorRejections`, `lateAnswers`, `heldBytes`, and on a client
  `unresolvedMessages` (downstream messages dropped as unresolved, §7.3) and `refusedFrames` (downstream frames its
  decoder refused, by any rule of §4.8). With `player`, the same totals for that player, not per definition.
  Counter names are a field, or a field and a qualifier after the first dot (`messagesSent.arena.chat`,
  `facts.overLimit`). Increments cost 3–45 ns. A snapshot copies four numbers per definition and one per reason
  into a frozen table; its time and size per definition are unmeasured (milestone 2 measures them). The inspector
  polls at 4 Hz. The docs map the names to OpenTelemetry and Prometheus, never with the
  player as a label.
- **Console.** On the server, a fact code's first occurrence in a window prints one line at once, and a summary at
  window close if more occurred: at most 2 lines per code per window, whatever the number of players. Console
  windows are `observe.window` long in `os.clock()` seconds, and a summary counts every occurrence of its window,
  the first included. The text is
  constant per code, `[Lync] overLimit: {count} in {seconds} s, {players} players, {definitions} definitions`,
  printed through `LogService:Warn(template, context)` with numbers, at most 8 `UserId`s and 8 definition names in
  the context, so it groups as one Error Report row and no client-chosen value enters the text
  `[diagnostics §1.5, §5.6]`. A client prints only its local facts, never integrity facts. Whether
  `LogService:Warn` groups by template in the Error Report is checked in milestone 2; until then the same constant
  text goes through `warn`. Every fact line is a warning: the level is the same for every code and ranks nothing.
  Warning, not `print`, because the Error Report collects "errors and warnings", not prints `[diagnostics §1.5]`.

### 7.5 Configuration

One server-only call; never in shared code or `lync.toml`. It never throws for being late: options carried in
`WELCOME` apply to connections first welcomed after the call; server-only options apply from the next flush;
`state.rate` applies at the next state tick, and every connected client gets it in `RATE` `[review-2 M6]`. A value
out of range, or a fraction for an integer option, throws `configureRange` at the caller.

```luau
Lync.configure({ state = { rate = 20, budget = 16000 }, observe = { window = 30 } })
```

Every bucket option is `{ perSecond: number (real), burst: integer }`.

| Option | Type | Unit | Range | Default | Meaning | Cost |
|---|---|---|---|---|---|---|
| `state.rate` | integer | Hz | 10–60 | 20 | state ticks per second (u6 in `WELCOME` and `RATE`) | the scheduler and rows encode run once per tick (CPU unmeasured, milestone 4) |
| `state.budget` | integer | B/s per player | 4,000–64,000 | 16,000 | downstream bytes per player against which `:newest()` rows are scheduled | up to that many bytes a second per player |
| `state.floor` | number (real) | fraction of `state.budget` | 0–1 | 0.25 | share kept for `:newest()` rows | downstream may exceed `state.budget` by up to `floor` × `budget` when reliable traffic used it |
| `inbound.reliable.frames` | bucket | frames | perSecond 1–1000, burst 1–10,000 | 120, 240 | the client sends at most 60 automatic flushes a second; the rest is room for `Lync.flush()` | a player can make the server tag-check and decode at most `perSecond` reliable frames a second beyond `burst` |
| `inbound.reliable.bytes` | bucket | B | perSecond 1,024–1,048,576, burst 49,152–4,194,304 | 32,768, 65,536 | the burst's minimum fits a released join hold plus framing | at most `perSecond` B/s beyond `burst` tagged (0.0035 µs/B native at full cover) and decoded |
| `inbound.unreliable.frames` | bucket | frames | perSecond 1–1000, burst 1–10,000 | 240, 480 | unreliable frames per player | as the reliable frames row, for unreliable frames |
| `inbound.unreliable.bytes` | bucket | B | perSecond 1,024–1,048,576, burst 1,000–4,194,304 | 32,768, 65,536 | the burst's minimum fits one unreliable frame | as the reliable bytes row, for unreliable bytes |
| `inbound.elements` | bucket | elements | perSecond 1,000–1,000,000, burst 65,536–4,194,304 | 20,000, 65,536 | decode work per player, both lanes; the burst fits any declared message | at most `perSecond` elements a second beyond `burst` decoded (CPU per element measured in milestone 2's inbound benchmark) |
| `tag.cover` | integer | B | 0–16,384 | 16,384 | bytes of each upstream frame, from byte 0, that the tag covers; 0 covers only count, lane, length and instance count (u15 in `WELCOME`) | about 0.022 µs per covered byte on the client (interpreted) and 0.0035 µs on the server (native), derived from the 1024 B figure (§4.5); at the default byte budgets, at most 0.23 ms/s per player on the server |

| `observe.serverEvents` | integer | facts per window | 16–4096 | 256 | delivery cap per server | up to that many observer calls per window, each in a pooled thread |
| `console` | boolean | — | — | true | console lines for facts (§7.4) | at most 2 lines per code per window; the cost of `warn` and `LogService:Warn` is pending (§10) |
| `profile` | boolean | — | — | false | MicroProfiler labels per flush and decode | the cost of `profilebegin` is pending (§10) |

Milestone 5's options (`callerProbe`, `clock`, `earlyAnswer`, `canary`) are in `v5-integrity.md`. Build-time options are in
`lync.toml` (`v5-tooling.md`).

## 8. Extensions and tools

- **Seams.** `t.custom({ encode, decode, maxBits | maxBytes, luauType, tsType, name, version })` declares a leaf
  codec; `t.convert(base, decode, encode)` transforms one, inferring both ways `[probes review-2 t1]`. Runtime
  seams: `transport` (remotes, or in-process for tests), `scheduler`, `clock`, `roster`, the observer, and a test
  seam that pins the key and the seeds and claims console and native-report output. A seam with nothing registered
  is bound at start to Lync's default, which the hot paths call through a local with no nil test; its cost against
  a direct call is unmeasured (milestone 2's benchmarks run with the default seams). There is no middleware: rejection is `validate`, observation the observer, transformation game
  code.
- **First-party extensions** (milestone 7: `interest`, `acked`, `inputs`, `rewind`, `checks`, `strings`,
  `interpolation`, `telemetry`) are specified in `v5-extensions.md`.
- **Tools** (milestones 3 and 6: shards, `.d.ts`, `manifest.json`, `report.md`, `lync.toml`, the CLI and its output
  formats and exit codes, the Studio plugin, inspector and profiler adapter) are specified in `v5-tooling.md`.

## 9. Testing

- **Headless CI** on the CLI host: unit and property tests (seeded, shrinking); the differential test of both paths
  (§2); golden frames (`.bin` plus a JSON index, at seed 0 and identity permutation) and golden hashes; an
  in-process two-sided world over a simulated network with loss, delay, duplication and reorder (below); modified
  clients in that world (raw sender, replayer, forger, key extractor, API driver, injector) asserting that each fact
  fires on exactly its trigger, and never for an unmodified client outside its known causes; type tests under both
  solvers for Luau and TypeScript.
- **Diagnostics are asserted by code, position and evidence, never by prose** `[diagnostics §10]`:
  `expectThrow(fn, { code, at, subject, path })` and `expectFact(world, { reason, player, count, evidence })`. Every
  `[Lync]` line and native report must be claimed by the test. Each registry page's `example` is a golden message,
  compared byte for byte. CI fails on a code that is used but unregistered, registered but never raised, untested,
  or deleted rather than retired, and on any `example` that breaks the grammar of §7.1.
- **The simulated network** (`f1fbfd7:test/support/net.luau`, `world.luau`). Per client link and direction, seeded
  (xorshift128 seeded through murmur3's finalizer), on a virtual clock that delivers what is due and then runs every
  runtime's step. Reliable frames keep their order; a stall holds every frame due during it until it ends, then
  releases them in order. Unreliable frames over the size limit are dropped, then they pass a Gilbert–Elliott burst
  state and independent loss, each arriving after latency plus its own jitter (so they reorder), with a chance of
  a second copy. The default network model (`Net.DEFAULT`):

  | Parameter | Unit | Default | Meaning |
  |---|---|---|---|
  | `latency` | s | 0.05 | one-way base delay |
  | `jitter` | s | 0.02 | uniform extra delay per frame |
  | `loss` | fraction | 0.05 | unreliable frames dropped independently |
  | `burst` | `{ enter, leave }` per frame | `{ 0, 1 }` (off) | the loss state drops every unreliable frame |
  | `duplicate` | fraction | 0 | unreliable frames delivered twice |
  | `stall` | `{ chance per s, seconds }` | `{ 0.05, 0.3 }` | stalls start as a Poisson process |
  | `fps` | Hz | 60 | the client's step rate (240 tests the flush cap) |
  | `unreliableLimit` | B | 1000 | larger unreliable frames are dropped, as the engine does |

  Its own tests check rates within 0.01 absolute of their settings over 10^5 frames. Unmodified clients on the
  default model must raise no fact. Each known cause in §7.3 and `v5-integrity.md` §10 gets its own run, which
  must raise exactly its fact, and so does each modified-client case.
- **Test names describe inputs by origin and rule,** under §7.1's rule for names: "encoder output decodes with
  rule 0", "frames breaking rule 6", "a modified client firing a trap".
- **Heavy specs** (10^6 random directions per width, exhaustive rotations) run behind an environment switch; the
  default run uses 10^4.
- **In-engine tests** in Studio for what only Roblox shows (§10).
- **Benchmarks:** the four game models' traffic; CPU interpreted (client) and native (server); bytes before and
  after an engine-compression estimate; per commit as JSON. A public comparison runs the QuickNet v0.3.4 thread's
  benchmark (1000 fires per frame for 10 s; FPS and Kbps for entities, booleans, strings, numbers, a dictionary
  and `Vector3`) against Blink, Zap and ByteNet `[landscape §1.7]`. The target: v5's FPS at least and Kbps at most
  each library's, in every column.

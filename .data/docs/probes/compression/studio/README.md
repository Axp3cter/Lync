# Lync compression probe (Roblox Studio)

Settles how Roblox compresses remote arguments. The findings file
`.data/docs/research/compression.md` (§1) lists what each test decides.

## Files

| File | Put it in | As |
|---|---|---|
| `LyncCompressionProbe.server.luau` | `ServerScriptService` | Script |
| `LyncCompressionProbe.client.luau` | `StarterPlayer > StarterPlayerScripts` | LocalScript |
| `Samples.luau` | `ReplicatedStorage`, named `Samples` | ModuleScript |

`Samples.luau` is generated by `../export_samples.py`; do not edit it by hand.

## Run

1. Use an empty baseplate. Nothing else may fire remotes.
2. In **Test > Clients and Servers**, pick **Local Server** with **1** player and
   press **Start**. (If that is not possible, plain **Play** also works, but say so.)
3. Do not touch the client window while it runs. It takes **3–6 minutes**:
   - about 1 minute of overflow-message measurements;
   - about 2 minutes of 6-second bandwidth scenarios;
   - then a short client-to-server pass.
   If the ruler falls back to delivery mode, it can take up to 15 minutes.
4. In the **server** Output, find the block between
   `=== LYNC PROBE REPORT BEGIN ===` and `=== LYNC PROBE REPORT END ===`.
5. Stop the test.

## What to report back

Paste:

1. The JSON line between the two markers, in full.
2. The `[LyncProbe]` summary lines printed after it.
3. One example of the **exact text** of an unreliable overflow message, from the
   server Output and from the client Output if one appeared there. The JSON's
   `warnings` field holds up to eight, but a screenshot is welcome if they differ.
4. Whether you used Local Server or Play, and the Studio version (Help > About).

If many `null` sizes appear in `threshold`, `samples` or `twins`, set
`FORCE_DELIVERY = true` at the top of the server script and run it again. Then paste
both reports.

## What each part answers

- **T1 ruler.** The probe fires `(tag, X, pad)` on an `UnreliableRemoteEvent`, where
  `pad` is 1100 random bytes, so every fire overflows. It then reads N from the
  overflow message ("went over by N bytes"). The on-wire size of X is N(X) − N(empty).
  `rulerCheck50` should be about 50.
  - If no message carries a number, the probe binary-searches the largest pad that
    still arrives (the client acks each fire).
- **T2 threshold and fallback.** Zero-filled and random buffers of 1–800 bytes.
  - The first zero-filled length that costs much less than its length is the threshold.
  - Random buffers above it tell whether the engine falls back to raw:
    - cost ≈ length: raw fallback;
    - cost ≈ length + 9–13: always a zstd frame.
- **T3 level and dictionary.** For ten realistic Lync frames, the probe compares:
  - the engine's on-wire size;
  - `EncodingService:CompressBuffer` at levels −7…22;
  - libzstd's sizes, precomputed in `Samples`.

  The level whose constant offset (`cMin == cMax` in `levelFit`) is the same for every
  sample is the engine's level. If every level's sizes come out larger than the engine's,
  the engine uses a dictionary or other context.
- **T4 scope of compression.**
  - The two-argument tests: `AA` (the same 400 random bytes twice), `AcopyA` (an equal copy) and `AB` (two different buffers).
    - `AA ≈ AB`: each argument is compressed separately.
    - `AA ≈ AB / 2`: the whole call is compressed as one.
  - `strings` tells whether string arguments are compressed (`aaa600` against `random600`).
  - `tables` tells whether a buffer inside a table is compressed.
- **T5 cross-call and cross-frame context.** Each scenario runs reliable or unreliable sends at Heartbeat rate for 6 s, reading
  `Stats.DataSendKbps` on the server and `Stats.DataReceiveKbps` on the client.
  - "same random 900 B every frame" ≈ "fresh random 900 B": no compression context carries
    over between calls or frames.
  - Much lower: a persistent stream or packet compressor exists.
  - The 450 B-twice case does the same test within one frame.
  - The ratio of `R fresh random 900 B/frame` to the 54,000 B/s sent also shows Stats' unit:
    kilobits or kilobytes per second.
- **T6 reliable threshold.** Zero buffers of 90, 99, 100, 101 and 110 B per frame on
  the reliable `RemoteEvent`. A step down in bandwidth marks the threshold there.
- **T7 limit after compression.** The probe sends 4000 and 20000 zero bytes and
  980/990/1000 random bytes unreliably and records which arrive.
  - Zeros arriving while random 1000 does not: the 1000 B limit is counted after compression.
- **Client to server.** A shorter T1/T2/T3 pass fired with `FireServer`, reported
  under `clientToServer`.

Nothing here is saved or published. The scripts only fire remotes inside the test
session.

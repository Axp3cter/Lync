## 1. Checks: correctness

### B1. `monotonic` and `maxRate` read the reliable key from a tag count that `REKEY` resets to 0 — blocking

- **Where.** §3.1: "**Frame key.** On the reliable lane, the frame's tag count (`v5.md` §4.5)"; §3.2: "s < s* (a late
  frame, possible only on the unreliable lane): fails when v > v* … a late frame stores nothing"; §6.2: "A late
  frame (s older than the stored key) is compared with both references"; §8.2 `key` "the frame key (§3.1)".
  Against `v5.md` §4.5 Rekey: "the server sends `REKEY` … sets e = 0 … The client, decoding `REKEY`, … restarts its
  count at 0".
- **The case** (*checked*, probe part E, the §3.2 rule run as written). A player has sent 1000 reliable frames,
  so s* = 999 and v* = 999. `FireServer` raises on 5 frames in a row (a `tagMismatch` known cause on an
  unmodified client, `v5.md` §7.3), `desync` fires, and the server sends `REKEY`. The client's next frames carry
  counts 0, 1, 2, …, all below s*, so each is "late". Under `"nondecreasing"` a late frame fails when v > v*:
  **999 of the next 1000 rising values fail** (`late` = 1), and late frames store nothing, so the state never
  recovers until the new count passes the old one. That takes as long as the session ran before the rekey: one
  hour at 60 frames/s. Under `"drop"`, every message of the definition is dropped for that hour.
- **The attack.** The same rule passes values ≤ v* on a late frame. A modified client sends 8 frames with bad
  tags (`v5.md` §4.5: no consequence, one `REKEY`), then replays stale sequence numbers, timestamps and idempotency
  keys freely: **999 of 999 stale values pass** in the probe. §3.3 names exactly these as what `monotonic`
  protects.
- **`maxRate`** after a rekey compares every frame as late against frozen p and a, whose allowances `rate` ×
  (t − t_p) + `burst` grow without bound: the check fails nothing and bounds nothing until the count catches up.
- **Telemetry.** §8.9 cause 4 tells analysis to "sort by `key`"; across a rekey the reliable keys restart, and
  sorting interleaves two sessions' frames.
- **Why it matters.** It breaks the check on an unmodified client after a documented recovery event, and hands
  any client a one-step bypass of what the check exists for.
- **Fix** (smallest). Define the reliable frame key as the server's own count of reliable frames accepted from the
  player on this connection, which `REKEY` doesn't touch (reliable frames are ordered, so this count is
  monotonic and no reliable frame is ever late). One integer per player, 0 B wire. Replace §3.1's reliable
  bullet: "On the reliable lane, the number of reliable frames the server has accepted from the player on this
  connection, counting from 0; `REKEY` doesn't reset it (`v5.md` §4.5 resets the tag count)." §8.2's `key` follows
  it. Add to Needs elsewhere (runtime, §6.1 step 3): "the accepted reliable frame count is kept per player".

### M1. The claim guarantee is false for check-only verification — major

- **Where.** §7.3: "**What it guarantees:** no message holding a claim reaches `connect` or `handle` without a game
  validator or a declared check having run on it." §7.2 counts "any check of any kind and any policy" as a
  verifier. Against: §1.7 "A function returning nil skips its check for that message, counted in
  `checksSkipped`"; §5.2 "A message not drawn is not evaluated and passes"; §1.6 "For `seconds` after the call,
  the scoped checks don't evaluate that player's messages".
- **The cases.** `strike.origin` is a claim, verified only by `within` (§7.3's example verifies `target` with a
  validator, so `origin` is covered there; drop the validator and `within` alone verifies it, which §7.2's choice
  (c) exists to allow).
  1. `rootOf(player)` returns nil while the character is respawning: the message reaches `onStrike` with no check
     run on `origin`.
  2. `Net.shot:field("landing"):derive({ …, oneIn = 10, policy = "drop" })` alone: 9 of 10 messages reach the
     handler unchecked, and no counter counts them.
  3. `resetChecks(player, { seconds = 2.2 })` after a respawn, the reliable-lane figure of §1.6, with `check` nil:
     every check of the definition, the stateless `within` and `derive` included, is suspended for 2.2 s, so
     every claim in that window reaches the handler unchecked, after every respawn.
- **Why it matters.** The guarantee is what turns the marker into protection (§7.4 "It is what makes the marker
  protect"); stated wrongly, a developer relies on it exactly where it lapses. Case 3 also hands an exemption to
  checks that keep no state and so have nothing to reseed.
- **Fix.** (a) State the guarantee exactly: "no message holding a claim reaches `connect` or `handle` unless a
  validator ran on it, or each check declared on the leaf was evaluated on it, returned nil (`checksSkipped`),
  was not drawn (`oneIn`), or was inside a `resetChecks` window (`checksExempted`)." (b) Count undrawn messages
  (`checksUndrawn`, per definition), so each way a claim passes unchecked has a count. (c) In §1.6, have `seconds`
  suspend only the kinds that keep state (`monotonic`, `maxTotal`, `maxRate`); the stateless kinds keep running
  unless `check` names one of them. This is a rule about which state needs reseeding, not a judgement.

### M2. `constraint` coalesces every check of a definition into one window — major

- **Where.** §1.5: "The fact's key is (player, reason, namespace, definition) … so failures of two checks of one
  definition coalesce in one window, whose closing fact carries the last occurrence's `check`; `count` counts
  both." Against §2.4: "start with `"deliver"`, read `observed` over a play session, then choose `"drop"`"
  (repeated in §5.3, `[server-facts §U9.9]`).
- **The case.** `strike` has `within` on `origin` (index 1) and `maxRate` on `origin` (index 2), both
  `"deliver"`. In one 30 s window a player fails `within` 40 times (the largest d is 5.9 studs) and `maxRate`
  once. Game code receives the first occurrence at once and one fact at close with `count` 41, `check` 2 and the
  `maxRate` evidence (`v5.md` §7.3: "the last occurrence's evidence"). It can't tell that 40 were `within`, and
  the 5.9 studs it needs for `maxDistance` is gone. With one check per definition, the closing fact still carries
  the last `observed`, not the largest. So the recommended tuning workflow reads at most two values per window,
  neither of them the one the bound must cover.
- **Why it matters.** Draft 3.5 root cause C (one reason or one evidence value per trigger whose cause or knob
  differs) is met for a single occurrence, but coalescing merges the kinds back together. The simplification the
  inputs flagged (§3.2: "`constraint`: one reason for four checks with different known causes") is only moved, not
  removed. Every check has its own knob.
- **Fix.** Key `constraint`'s window by (player, reason, namespace, definition, `check`). Have the closing fact
  carry, as well as the last occurrence, `largest`: the occurrence whose `observed` − `bound` was largest in the
  window, with its `observed` and `bound`. Both are exact: a maximum of reported numbers, not a statistic about a
  player. Needs elsewhere (runtime, `v5.md` §7.3): the per-reason key rule gains this one exception, or every fact
  with a per-declaration index gains it.

### M3. "One grid step" is not a safe tolerance — major

- **Where.** §5.3: "The smallest useful value on a quantized codec is one grid step's distance: `step` for
  `t.number`, √3 · `step` for `t.vector3` (0.054 studs at 1/32)"; cause 1: "A tolerance of at least one grid step
  removes this cause while the gap stays under one step." §2.2 and §5.2: "equality passes".
- **The case** (*checked*, probe part B, 0.742 interpreted and native agree). The decoder gives
  min(min + q · step, max). For adjacent codes q and q + 1, d = |decode(q + 1) − decode(q)| exceeds `step` in
  **15,248 of 60,000 pairs** for `t.number(0, 600, 0.01)` (the completion time of §7.4), 11,584 of 20,000 for
  `t.number(-1000, 1000, 0.1)` and 53,356 of 100,000 for `t.number(0, 1, 1e-5)`, by up to 1.4e-13. So `fn` and
  the client landing on neighbouring codes (cause 1, the native FMA against interpreted case: the lerp's last
  digits differ, *checked*) fails `tolerance = step` about a quarter of the time. The docs' printed "0.054 studs"
  is below √3/32 = 0.0541266, so **every** diagonal neighbour fails it (*checked*, part C); √3 · step itself
  passes at step 1/32 only because powers of two are exact.
- **Why it matters.** It produces `constraint` facts, and drops under `"drop"`, on unmodified clients at the
  tolerance the docs give for removing exactly that cause.
- **Fix.** For quantized codecs, compute d from codes, not decoded floats: `t.number` |q_v − q_r| · step;
  `t.vector3` √(Σ Δq²) · step; `t.angle` min(Δq, n − Δq) · 2π/n. Then k steps is exactly k × step and passes by
  "equality passes". It also needs no decode of r. Print the vector figure as "√3 · step (0.0541266 studs at
  1/32)", or as the expression alone. `within` keeps its float metric (its r isn't snapped).

### M4. `derive`'s snap has no domain — major

- **Where.** §5.1 step 2: "r goes through the field codec's own quantizer, the one the encoder applies …
  `t.direction` through the octahedral code … A value outside the codec's range is first limited to it"; §1.7 "A
  return of the wrong type is raised inside that call"; D2 "Lync's own code stays outside game-function
  protection". `v5.md` §3.3: the direction encoder "refuses zero" and iterates E to a fixed point, "past 4 steps it
  raises `internal`".
- **The case** (*checked*, probe part D, the octahedral rule as `v5.md` §3.3 writes it). `fn` returns
  `velocity.Unit` for a `t.direction` field, and velocity is `Vector3.zero` (a shot fired while standing still).
  `Vector3.zero` itself gives s = 0, and `Vector3.zero.Unit` (NaN components on Roblox, unverified here) gives NaN. Either way both codes are NaN,
  NaN ≠ NaN, E never reaches a fixed point, and after 4 steps the encoder raises `internal`, in Lync's snap,
  outside the `xpcall` (the value had the right type, so §1.7 doesn't catch it). §7.2 makes `internal` a native
  report, and §1.4 and `v5.md` §6.1 don't say what happens to the message, the rest of the frame or the checks
  after it. For `t.number`, a NaN r survives the snap only because the quantizer writes `min(q, n)`: Luau's
  `math.min(NaN, n)` is NaN but `math.min(n, NaN)` is n (*checked*), so an implementation that swaps the arguments
  snaps NaN to the top code, which can pass.
- **Why it matters.** A plain game value makes Lync raise `internal` on the hot path, and the result of NaN depends
  on an argument order the spec doesn't fix.
- **Fix.** In §5.1 step 1: "`fn`'s result is checked inside its `xpcall` before the snap: a non-finite number or
  component, or a zero vector for `t.direction`, is raised there and handled as a throw (§1.7)". The snap then
  only sees finite values in the codec's domain.

### m1. `maxTotal`'s exact trigger fails at exactly the cap on decimal steps — minor

- **Where.** §4.2: "The check fails when S + v > `cap`"; §4.5 `cap` "number (real)".
- **The case** (*checked*, part A). `t.number(0, 1, 0.1)`, cap 0.3, three amounts of 0.1: the third fails because
  0.1 + 0.1 + 0.1 = 0.30000000000000004 > 0.3. A running total kept by add and subtract, as the 144 B state
  ("16 sums, head, total", CT C3) suggests, drifts from the bucket sum by up to 1.4e-7 over 2 × 10^6 amounts at
  step 0.01 (part A2).
- **Fix.** Keep sums in codes for `t.number` (Σ q, with `min` × count added back), compare against `cap` converted
  once to codes at declaration, and recompute the total from the 16 buckets rather than by add/subtract. Also
  state that a `pool` whose checks mix `"drop"` and `"deliver"` loses §4.2's guarantee, which reads "while every
  failing message is dropped".

### m3. Which value a check commits, if a game function mutates `data`, is unspecified — minor

- **Where.** §1.4: checks evaluate "each on the decoded values", then validate, then "**Commit** … `monotonic` and
  `maxRate` store". `reference(player, data)`, `fn(player, data)` and the validator all receive `data`.
- **The case.** A `within` reference normalises `data.origin` in place; the validator clamps `data.amount`. Later
  checks and the commit see the changed values, and so does the handler. Does `maxRate` store the value it
  evaluated or the one present at commit?
- **Fix.** One sentence in §1.4: "each check reads its field once at evaluation; commit stores what it read; game
  functions receive the same `data` table the handler will receive". Freezing `data` costs a freeze per message
  and is the developer's choice, not needed.

### m4. D3's "check state describes what game code received" is false for messages with no handler — minor

- **Where.** §1.4 step 4: "A failing check with `"deliver"` commits too, so check state always describes what game
  code received"; §7.3: "Messages decoded before a handler exists reach no handler and are counted in
  `messagesUnheard`".
- **The case.** `collect` has `maxTotal` and no `connect` yet (a script that connects late): its messages commit,
  charging coins game code never saw, and the first delivered messages then fail early.
- **Fix.** Reword to "commit happens for every message that passes step 6, whether or not a handler receives it".
  The behaviour is fine; the stated reason isn't.

### m5. A check function's throw has no counter named — minor

- **Where.** §1.7 "a throw is reported natively as `validatorError`"; `v5.md` §7.2 row "validator, check
  `reference` or `fn` throw or yield | native report …; counter; message dropped".
- **Fix.** State that each throw or yield of a check function increments `validatorErrors` of the definition, as a
  validator's does, so the native report's spacing doesn't hide how many messages were dropped.

### M5. "No id in the buffer", while the example atom copies another player's `UserId` — major

- **Where.** §8.7: "**No user ids and no client text in the data.** A batch carries the `Player`; the buffer
  carries no id"; §8.11 (the docs page): "Lync puts no id in the buffer, and the key game code adds makes it
  personal". Against §8.6: `Net.strike:atom({ …, fields = { "origin", "target" }, … })`, with `strike.target =
  t.int(1, 2 ^ 40):claim()` (§7.3) a `fighters` key, and `v5.md` §3.5: `Net.fighters:set(player.UserId, …)`.
- **The case.** Every atom of the documented example carries, as f64 at offset 19 + 24, the `UserId` of the player
  who was struck. The terms page then tells the developer, falsely, that the export holds no id until game code
  adds one, and the T3 reading 1 the page rests on ("an identification number … or an online identifier") makes
  that field personal information about a second user, who isn't the batch's `Player` and whose erasure request
  the page's deletion rule ("keyed by `Player.UserId`") won't find.
- **Why it matters.** It is a statement about legal exposure, in the one page that exists to be accurate about
  it. The scope audit's §I lists "no … user ids" as correctly Lync's, so nothing else catches it.
- **Fix.** §8.7: "Lync adds no id. `fields` are copied as decoded, so a field that holds an id (a collection key
  such as `strike.target`, which is a `UserId` in `v5.md` §3.4) puts that id in the buffer." §8.11, new bullet:
  "an atom's `fields` may hold other players' ids; their erasure requests must find those atoms too, so index
  exported atoms by every id field as well as by the batch's player." The example can keep `target`: it shows the
  case the page must cover.

### B2. The server's join hold can split a seal from its reveal — blocking

- **Where.** §9.5: "**Recipients** are the seal's target resolved at the flush that encodes it; a player in the
  join hold receives it from the hold, as any send"; "**Outstanding** counts … seals queued to that player";
  "`reveal()` and `discard()` queue the reveal or discard message … to the seal's recipients still connected …
  Each decrements the recipients' counts." §9.6: "a reveal or discard naming no held seal (rule 7)"; "a seal while
  `outstanding` are held … (rule 2)". `v5.md` §5.3: the server holds "up to 32,768 B per player … past that it
  drops and reports `sendDropped`"; §4.8: a client refuses whole frames, and "a refused reliable frame loses events,
  answers and collection writes with no resend, so the client diverges for the rest of the session".
- **Case 1 (seal dropped, reveal kept).** Player P joins; its namespace waits for `WELCOME` and its hold already
  has 20 KB of catch-up. The game fires `nextRound` (W = 16,000 B, `hideLength` true) to `Lync.all`. P's hold
  would pass 32,768 B, so P's seal is dropped (`sendDropped` cause 1), but P was in the target at the flush, so by
  §9.5 P is a recipient. At the round start `seal:reveal()` queues 9 B to P. P's client decodes a reveal naming
  no held seal: rule 7, and the whole reliable frame is refused, with every other event, answer and collection
  write in it.
- **Case 2 (seal kept, reveal dropped).** The seal fits; by the time `reveal()` is called the hold is full, so
  the reveal is dropped. The server has already decremented P's count (on the call). P's client still holds the
  ciphertext, and at `outstanding` 1 the next seal of the definition is rule 2: refused. The server keeps
  sending seals, so **every later reliable frame that carries a seal of `nextRound` is refused, for the rest of
  P's session**.
- **Why it matters.** An unmodified server and client, in the documented join path, drive the client into
  permanent reliable-stream refusals. No fact names the cause on the server (`sendDropped` cause 1 doesn't say it
  was a seal or a reveal), and the client counts `refusedFrames`.
- **Fix.** (a) Define recipients as "the players to whom the seal row was queued, after the join hold accepted
  it"; a hold drop of the seal removes that player from the seal's recipients. (b) Reveal and discard rows to a
  recipient are never dropped by the hold's byte or element caps (each is at most 2 + 107 + 64 bits; at most
  `outstanding` ≤ 256 per definition per player, so the overrun is bounded: state it). (c) Decrement a
  recipient's count when the reveal or discard row is queued to it, not at the call. Needs elsewhere (runtime,
  `v5.md` §5.3): the exemption in (b).

### M6. The sealed row's wire is undefined for runs of 3 or more — major

- **Where.** §9.3: "Each message of a sealed definition is one row (`v5.md` §4.3's runs)". `v5.md` §4.3: "A run of
  `columnMinRows` or more messages … is written as columns"; "request and control runs always do" single rows.
- **The case.** `outstanding = 4`, and the game pre-sends four rounds in one flush: one run of four sealed
  messages. By §4.3 the run is a column block, but a sealed row is not a codec, so §4.3's flattening has nothing
  to flatten: the encoder can't write it, and two implementations would differ on whether `kind` is a column.
- **Fix.** §9.3: "Runs of a sealed definition are always single-row, as request and control runs are (`v5.md`
  §4.3)." Needs elsewhere (wire, `v5.md` §4.3's "Single rows" sentence): "request, control and sealed runs always
  do".

### M7. "2^63 expected key trials per seal" depends on S's unmeasured entropy — major

- **Where.** §9.1: "face 2^63 expected key trials per seal"; §9.4: "S … two `NextInteger(0, 2^32 − 1)` draws from a
  `Random.new()` instance created without a seed (internal entropy source …) … Roblox does not document `Random`
  as cryptographic (unverified, §11); S is never sent, and a revealed key is one PRF output under it".
- **The case.** A client records one reveal (d, i, K_i) and knows HalfSipHash. Searching S (testing each candidate
  against K_i) costs 2^(h − 1) expected trials, h the entropy of the unseeded `Random`'s internal seed, which is
  undocumented: if it is 32 or 53 bits, the search is 2^31 or 2^52 hashes, not 2^63. And a found S gives every
  later K_i on that server before its reveal, not one seal. §11 lists "whether `Random` is cryptographic", which is
  a different question from the width of its seed.
- **Why it matters.** It is the measure's one security claim, and its stated bound rests on an input the design
  doesn't name.
- **Fix.** §9.1: "2^(min(64, h) − 1) expected trials to recover S, which opens every later seal on the server; h is
  the entropy of `Random.new()`'s internal seed (unmeasured, §11)". §9.4: derive S = HalfSipHash-2-4/64 under a
  zero key over (the two `Random` draws ‖ the 16 bytes of `HttpService:GenerateGUID(false)`), so S has the entropy
  of the stronger of two independent sources at no wire or per-seal cost. §11: add "the seed entropy of an
  unseeded `Random`".

### m6. Players who join between a seal and its reveal never receive the value — minor

- **Where.** §9.5: "A player who joins later doesn't receive it." `fire` on a sealed definition always returns a
  `Seal` (§9.2), so there is no unsealed send of that definition.
- **The case.** The next round's layout is sealed at t = 0 and revealed at t = 30 s; a player joining at t = 10 s
  never runs the client handler for it and plays the round without a layout.
- **Fix.** Say so in §9.5, with the recipe: on `PlayerAdded`, `Net.nextRound:fire(player, layout)` and keep that
  seal with the round's own, revealing both at the start (or `:reveal()` at once after the start).

### m2. `order`'s default decides which values `"drop"` refuses — minor

- **Where.** §3.5: `order` default "`"nondecreasing"` (derived: the weaker rule, which raises no fact on equal
  values)". §1.3: "**No default:** a default would be Lync choosing between dropping and delivering."

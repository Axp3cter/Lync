## Blocking

### B1. `:seen()` is the same set as membership: it withholds nothing

- **Location.** §9 table, l. 362: "`:seen()` | the pair has passed every narrowing test (§8.5) at some state tick
  since the record's last add to it; without `pvs` or `predicate`, from the add". §8.3 Members, l. 256–260: a
  record is a member only when "with `pvs`, the (viewer, cell) bit of §8.5 is 1; and, with `predicate`, the pair's
  last result is true".
- **Case.** Collection with `pvs` and no predicate; field `loadout :seen()`. A record enters viewer V's block in a
  cell whose PVS bit for V is 1, so it becomes a member and gets a catch-up add. At that tick it has passed every
  narrowing test (it could not be a member otherwise), so V's seen bit is set at the add and `loadout` travels in
  the add. A cell whose bit is 0 never yields a member at all, so there is no member that has not "passed". With a
  predicate the only difference is the first evaluation: if a never-evaluated pair is evaluated at the tick it passes
  cells (the predicate line l. 315–316 reads that way), seen is set at the add; if not, the field lags the add by at
  most 1/`predicateRate` (0.1 s by default). Without narrowing the row says "from the add".
- **Why it matters.** The class exists for "a loadout before it has been seen" (l. 351). A developer who marks
  `loadout :seen()` believes it is withheld until line of sight; it reaches every member at catch-up, and the
  collection still pays the per-pair bit (12.8 KB at 100 × 1,024), the piece encoding (column coding lost) and a
  presence bit per update. IR §7 has the same definition ("passed the narrowing test … at least once since the
  record was last added"), so this is inherited, not introduced.
- **Fix.** Structural: "seen" needs a test that is narrower than membership, and deciding visibility is the
  developer's judgement under the brief's newest rule. Give `:seen()` a server binding
  `Net.c:field(path):seenWhen(fn(viewer, key, record) -> boolean)` run at `predicateRate` on member pairs only; Lync
  keeps the exact latch (set on the first true since the pair's last add, cleared on remove) and its 1 bit per
  (viewer, slot). Unbound is `seenUnbound` (as `gateUnbound`), and no viewer receives the field. Or drop `:seen()`
  and the class byte value 4.

### B2. A yielding predicate or binding suspends the server's flush; the "re-entrancy flag" detects it one flush late

- **Location.** §8.5, l. 317–319: "a yield (re-entrancy flag) as `predicateYielded` … and the pair keeps its last
  result"; §9 Bindings, l. 370–372: "one that yields as `bindingYielded`, and that tick no viewer receives the
  record's fields of that class". The interest `focus(player)` function (l. 237) is called the same way.
- **Case** (checked: `luau.py run`, Luau 0.740). Predicates and bindings run inside Lync's state-tick work. Luau
  lets a coroutine yield across `pcall`/`xpcall`, so a predicate that calls `task.wait()` or `WaitForChild`
  suspends the whole flush coroutine, not just the call. In the probe, a "flush" calling a yielding function under
  `xpcall` with a re-entrancy flag returned to its resumer with status `suspended` and never reached its end; the flag
  was seen only when the *next* flush entered, which then yielded too. On Roblox the flush runs from a
  `PostSimulation` connection: the yield leaves that tick's frames unsent for every player, and when the wait ends
  the old flush resumes and finishes against encoder buffers, budgets and membership that later flushes have since
  changed.
- **Why it matters.** The stated outcome ("the pair keeps its last result", "that tick no viewer receives") can't
  happen as specified: the call never returns. One game predicate stalls the server's networking. `v5.md` §6.1
  step 6 uses the same flag for validators (the runtime unit's), so the inbound pipeline has the same flaw.
- **Fix.** Run each predicate, binding, gate and `focus` call in its own thread: `coroutine.create` (or a reused
  thread per call site, replaced after a yield, as the decoy behaviour's pooled thread already is) then
  `coroutine.resume`; if `coroutine.status` is `"suspended"` afterwards the call yielded (exact, at the call):
  report `predicateYielded`/`bindingYielded`, `coroutine.close` the thread, and apply the stated fallback. State
  the cost (one thread creation per call, unmeasured; a reused thread costs one resume). Send the same rule to the
  runtime unit for `v5.md` §6.1's validator and checks (Needs elsewhere).

### B3. `Lync.perceived(player)` is per player, but P depends on the per-collection `delay` and `rttSlack`

- **Location.** §12.5, l. 633–637: "It depends only on the player's frame and D, not on a collection, so it lives on
  `Lync` and one value serves every collection"; the value carries `tick` (P), `low`, `high`, `rtt`, `delay`. §12.2
  table, l. 544–545: `delay` and `rttSlack` are options of each collection's `rewind`. §12.3, l. 581, 586:
  rtt = clamp(ackRtt, ping, ping + `rttSlack`); "D, the D of the newest `RATE` … or the `delay` option".
- **Case.** `fighters:rewind({})` (rendered by Lync's interpolation, D from `RATE`) and `npcs:rewind({ delay = 0.05,
  rttSlack = 0 })` (the game interpolates NPCs itself at 50 ms). In a `strike` handler, `local seen =
  Lync.perceived(player)`: `seen.tick` must be Q − D_RATE × rate for `fighters` and Q − 0.05 × rate for `npcs`, and
  `held` (hence Q) differs too because rtt is clamped by each collection's `rttSlack`. One frozen value can't hold
  both; `npcs:rewound(seen, key)` either uses the wrong P or silently recomputes a P the value doesn't show.
- **Why it matters.** The one value the API is built around is undefined whenever two collections set different
  options, and D14's reason ("the value depends on the frame and D only") is false as soon as `delay` is set.
- **Fix.** Split by what each depends on. `Lync.perceived(player)` returns frame-level inputs only: `ackSeq`,
  `ackTick`, `ackExact`, `received`, `receivedExact`, `reliableTick`, `arrival`, `ping`, `ackRtt`, `jitter`, `hMax`,
  and `rateDelay` (D from the receipt). Move `rttSlack` to `Lync.configure` (it bounds a per-player estimate, so it is
  not a collection property), so `rtt`, `held`, `heldRaw` and `applied` (Q) are per player too. Each collection's
  `rewound`, `rewoundSpan` and `held` compute P, `low` and `high` from its own `delay` and return them in the result
  (`tick`, `low`, `high`), which `rewindParts` already does for its own delay.

## Major

### M1. `"received"` mode keeps only the last M samples: an unmodified client gets `notHeld` after a reliable stall, and a stored `seen` stops working

- **Location.** §12.2, l. 557–559: "in `"received"` mode, the ticks of the last M samples the viewer had (its add and
  its acked rows), M = ⌈D × `stateRate`⌉ + 2 (4 at 20 Hz with 0.1 s)"; §12.5, l. 636–637: "It may be stored and
  used while its ticks stay in the rings"; l. 652–654: `"notHeld"` … "in `"received"` mode had no sample of it; on an
  unmodified client this happens only when the game also shows the entity through Workspace or another remote".
- **Case 1 (stall).** `strike` is a reliable `perceived` event. The reliable lane stalls 0.3 s (the test network
  model's stall, IR §11.8) while the client's unreliable frames keep arriving with acks of newer state frames. Each
  acked frame's rows push into the per-pair ring, so after 0.3 s at 20 Hz six newer samples per record have arrived
  and the M = 4 ring no longer holds any tick ≤ P of the `strike` frame, whose own ack s is 0.3 s old. `rewound`
  returns `"notHeld"` for a target the client was rendering.
- **Case 2 (stored value).** A handler stores `seen`, yields 0.5 s (a `DataStore` read), then calls
  `rewound(seen, key)`. P is well inside the truth ring (K = 27 ticks), but the per-pair ring now holds only the last
  4 samples, all newer than P: `"notHeld"`.
- **Case 3 (D moves).** M is a function of D, which the server moves per player up to 255 units (1.02 s), so M
  reaches ⌈1.02 × 60⌉ + 2 = 64 at 60 Hz; the ring's resize on a `RATE` is unspecified, and the cost table (`(4M + 1)
  B`, the 170 KB and 510 KB rows) is sized at M = 4.
- **Why it matters.** The default mode fails on unmodified clients in normal conditions, and the documented known
  cause of `notHeld` is wrong (inherited from IR §11.5).
- **Fix.** Record what the viewer had per truth-ring tick, not as a short list: one bit per (viewer, record, ring
  slot), set when an acked state frame carried that tick's row or the add landed on it; K bits per pair (27 bits,
  4 B, at 20 Hz and `maxRewind` 1 s, less than today's 17 B), covering the whole window whatever D is. The bracket
  for P is then the nearest set bits around P. Correct the cost table, and add "a reliable-lane stall" to `notHeld`'s
  causes if any remain.

### M2. `"received"` mode lets a modified client choose the samples the server interpolates between

- **Location.** §12.2 "its add and its acked rows"; §12.4, l. 614–615: "the same sampling over only the samples this
  viewer had"; §12.9 "Defeated by", l. 742–745, which names only delaying traffic and acking an older frame.
- **Case.** The ack is client-stated: `'1' seq received:u16`, 17 frames per ack. A tool clears the `received` bits
  of frames whose rows it wants excluded. Target strafing at 16 studs/s, reversing at P: true position at P is the
  turn point x = +2. The tool clears the bits of the frames carrying ticks P−1 … P+2, so the server brackets P
  between ticks P−2 and P+3, both near x = −1, and returns a position about 3 studs from the true one, where the
  tool aimed. The cleared frames are re-pended by notify and resent later, so the tool loses nothing it can't apply
  locally. The measured error table (§12.4: max 8.66 studs at 50% rows missing) bounds what the choice buys.
- **Why it matters.** This is a narrower form of R20's free choice inside a window, in the default mode, and no
  evidence of it is returned: the game can't see that the bracket spans 5 ticks instead of 1.
- **Fix.** Return the bracket in every `rewound` value (`fromTick`, `toTick`, the two sample ticks used) so the
  game sees the span as a number, and add the capability to §12.9 "Defeated by" ("withholds `received` bits to
  widen the bracket; `"truth"` is unaffected"). Keep the default if the bracket is reported; otherwise the derived
  default in the `mode` row has to weigh this, which it doesn't.

### M3. For unreliable frames the horizon H is neither "certain" nor "a lower bound"

- **Location.** §12.3, l. 583–585: "for an unreliable f, the count of reliable frames sent to p at or before t_r −
  rtt, the newest that had certainly arrived when f left (`receivedExact` false)"; §12.9, l. 737–738: "For messages
  on the unreliable lane H is a lower bound".
- **Case.** A reliable frame sent at t_r − rtt arrives at about t_r − uplink, the moment f was sent, *only without
  loss*. With one lost reliable packet the engine retransmits after its RTO (the stall above, 0.3 s), so the frame
  H names had not arrived. Concrete: a `perceived` unreliable `shot` names record k; k's remove went out 0.2 s
  before and sits in the stalled reliable stream, so the client still shows k. The server counts the remove's frame
  as arrived (H too new), finds k removed at H, and returns `"notHeld"`; R (reliable fields) and D (from the newest
  `RATE` ≤ H) are taken from frames the client hadn't decoded.
- **Why it matters.** Wrong results on unmodified clients with words claiming the error can only go one way.
- **Fix.** Make H exact for unreliable frames too: ask the wire unit to carry `rcv:u8` in every upstream unreliable
  frame that holds a `perceived` message (8 bits, beside the 28-bit ack it already forces), and set `receivedExact`
  true for those. Otherwise delete "certainly" and "a lower bound" and state H as an estimate that is too new during a
  reliable-lane stall.

### M4. Engine parts are rewound by rtt/2; the client's view lags by the full round trip

- **Location.** §12.7, l. 688–690: "[t_r − rtt/2 − `engineDelay` − `engineSpread`, t_r − rtt/2 − `engineDelay` +
  `engineSpread`]"; recipe l. 698–700.
- **Case.** The server's part is at X(t). It reaches the client after the downlink and is drawn `engineDelay` later,
  so at client send time c the client shows X(c − down − engineDelay). The message arrives at t_r = c + up, so the
  shown state is X(t_r − rtt − engineDelay). The design's interval centres on t_r − rtt/2 − engineDelay, rtt/2 too
  new. At 200 ms round trip and 16 studs/s that is 1.6 studs, outside the ±`engineSpread` (0.05 s, ±0.8 studs)
  sweep the text says is "correct for any true delay inside it". The calibration recipe compares rendered CFrames
  against a server ring "by time" with client-stated times, which folds the downlink into the fitted lag, a
  per-player quantity a per-game constant can't hold. Inherited from IR §11.4.
- **Fix.** Use [t_r − rtt − `engineDelay` − `engineSpread`, t_r − rtt − `engineDelay` + `engineSpread`], with
  `engineDelay` defined as the client-side delay only, and have the recipe subtract each test client's one-way
  estimate (rtt/2 at the sample) from the fitted lag.

### M5. The PVS bit has no hysteresis: whole cells churn when a viewer crosses a bake-cell boundary

- **Location.** §8.3 Members, l. 256–260 (hysteresis applies only to cells; "and, with `pvs`, the (viewer, cell) bit
  … is 1" is tested every tick); §8.3 Churn, l. 265–266.
- **Case.** A viewer stands in a doorway on the boundary between bake cells u1 and u2 (32 studs by default). Interest
  cell c is visible from u1 and hidden from u2. Character jitter moves the focus across the boundary every few
  ticks; every crossing removes every record filed in c and re-adds each with a full catch-up add (10–30 B each,
  §8.3's own figure), the churn the ring exists to prevent, at a granularity 8× finer than the interest cell
  (R = 256).
- **Why it matters.** The PVS's purpose is to remove bytes; at boundaries it multiplies them, and `interestLeaves`
  then reports churn the developer can't fix by raising R.
- **Fix.** Give the PVS the cells' enter/leave split. Derive a second table at the `interest` call, bit′(u, c) = OR of
  bit(u′, c) over u and its 8 neighbouring bake cells (another N × N_c bits, ×9 derivation reads). A pair *enters*
  only when bit(u, c) is 1 and *stays* while bit′(u, c) is 1, as a record enters in the block and stays in the ring.
  A viewer jittering across any one bake boundary then never toggles a cell (an OR alone would only move the
  boundary). Leak margin, stated: a cell stays held for up to one bake cell (`[[pvs]] cell` studs) of viewer travel
  after it is hidden.

### M6. Bindings and gates rerun only on changed records, so a class goes stale when its input is outside the record

- **Location.** §9 Bindings, l. 370: "Bindings run once per changed record per state tick, never per viewer, and the
  gate once per changed record."
- **Case.** `Net.fighters:team(function(key) return teamTargets[Players:GetPlayerByUserId(key).Team] end)`. A player
  switches team; nothing in their record changes, so the binding never reruns and their `:team()` fields (ammo,
  cooldowns) keep going to the old team for as long as the record stays unchanged. Likewise `owner(fn)` reading a
  vehicle seat's occupant, or a gate reading a round state.
- **Why it matters.** "A `team` binding that returns the wrong group leaks to that group" (l. 398) puts the blame on
  the binding, but here the binding is right and Lync's evaluation schedule makes the leak. The contract (a binding
  must be a function of `(key, record)` alone) is nowhere stated.
- **Fix.** State the contract in the table ("evaluated when the record changes; it must read only `key` and
  `record`"), and give the developer the exact trigger for everything else: `Net.c:rebind(key)` (server) marks the
  record for re-evaluation of every binding and gate at the next state tick. Cost: one binding call per marked
  record. A record created between state ticks also needs a rule: its bindings run before its add is encoded (today
  the add would go out before any binding ran).

### M7. Update columns' temporal baseline breaks for class fields: holders of one unit don't all hold the same value

- **Location.** §3, l. 107–111: "update columns use, per (record, field), the value last sent to the record's
  holders in that field's unit, which every holder has"; §9 Transitions, l. 390–392.
- **Case.** Field `hp :gated()` in a cell chunk of 3+ records (column-coded). Flush F1, gate true: public chunk sends
  hp = 80 to all holders. F2, gate false for record 1: public chunk sends nil, team chunk sends 78. Which baseline does
  the team chunk's residual use? The team unit never carried hp for record 1 ("value last sent … in that field's
  unit" is undefined), and the client's stored value, decoded a chunk earlier in the same frame, is already nil.
  F3, gate true again: the public chunk sends 77; its unit's last value is nil, while team holders hold 78 and the
  others nil. "Which every holder has" is false, so one group decodes a different value from the same bytes.
- **Why it matters.** Silent decode divergence between viewers, the one failure encode-once must never have.
- **Fix.** Class fields are never temporally predicted: in update columns their residuals are against the previous
  row (`v5.md` §4.3's rule for every other column), so each chunk decodes from its own bytes. Cost: the column-coding
  gain on class fields only (unmeasured; add it to §15).

### M8. Decoy slot sizing omits decoys in the reuse delay, and decoys can make a real `set` throw `recordLimit`

- **Location.** §2, l. 41–45: "It must cover live records, records removed in the last 2 s, and up to
  `Players.MaxPlayers` × `maxPerViewer` decoy slots"; l. 35–40; counter row l. 817.
- **Case.** A slot stays held until its remove plus 2 s (l. 36). A behaviour that replaces each decoy every 0.5 s
  holds 1 live + 4 delayed slots per decoy: at 100 players and `maxPerViewer` 1, 500 slots, not 100. With
  `maxRecords` 256 and 64 live records, decoy adds take the free slots first whenever they are drawn first, and the
  game's next real `set` throws `recordLimit` at the caller: gameplay code fails because of a security feature's
  churn. RR4's own sizing has the same omission, so it is inherited.
- **Why it matters.** The sizing rule is wrong by the replacement rate, and the one allocator gives decoys equal
  claim on slots real records need.
- **Fix.** State the exact bound: decoy slots ≤ Σ over viewers of (live decoys + decoys removed in the last 2 s) ≤
  `MaxPlayers` × `maxPerViewer` × (1 + 2 s × r), r the behaviour's replacements per decoy per second. Give real
  records precedence without marking slots: a `decoys` option `maxSlots` (integer, slots, 1–`maxRecords`,
  required: how many slots the game spares for decoys is its judgement; cost: one comparison per decoy add) caps the
  slots decoys hold, delayed ones included; a decoy add beyond it is `decoysUnplaced`. The cap is on count, so slots are still drawn uniformly (RR4's 0.51
  statistic is unchanged).

### M9. The scheduler weighs records by borrowed constants: Lync deciding importance, and the defaults aren't marked chosen

- **Location.** §7, l. 179–191 (distanceFactor bands, ownerBoost ×4, firstSendBoost ×4, `maxPendingAge` 2 s);
  §14 runtime constants, l. 834–836: "derivation `[state-sync §2.1, §3.3]`".
- **Case.** A racing game wants the car directly ahead weighted above the one alongside; a strategy game wants units
  under the cursor first. Lync has fixed that a record at d = R gets 0.2 of one at R/4, that the owner's record gets
  ×4, and that the first row after an add gets ×4. These are Iris's and Netcode for Entities' defaults, not values
  derived from Lync's models: the "derivation" column cites where they were copied from.
- **Why it matters.** The brief's newest rule: anything Lync would have to "weigh or decide" is the developer's; and
  "every default derived with its inputs shown, or marked chosen with what would change it". Neither is met.
- **Fix.** Make the weight the developer's input with Lync's rule kept exact around it: an `interest` option `weight`
  (`(viewer, key, record, distance: number) -> number`, or a table `{ near, far, ring, owner, firstSend }` of reals
  with range 0.001–1000) with today's values as the marked-chosen default ("Iris defaults, unmeasured on Lync's
  models; a per-game freshness measurement would change them"), and its cost (one call or multiply per (viewer,
  pending record) per tick). `maxPendingAge` stays Lync's: it is a bound, and say so ("chosen: the research's
  simulations never reached it").

### M10. Tick comparisons are undefined across a `stateRate` change and a reliable-tick wrap

- **Location.** §2 Row acceptance, l. 63–71 ("add tick A (the tick of the reliable frame that carried the add)",
  "applies when … T ≥ A"); §11.2 samples by tick; §12.2, l. 560: "A `stateRate` change restarts the rings".
- **Case 1.** T = ⌊(`GetServerTimeNow()` − epoch) × `stateRate`⌋ (`v5.md` §5.1), and `RATE` carries a new epoch and
  rate. If a 60 → 20 Hz change keeps the epoch, new T ≈ old T / 3, so every live record has T < A and the client drops
  every row until each record is re-added. Neither file states that `RATE`'s epoch keeps T continuous, nor that the
  client rebases stored A, held rows and samples.
- **Case 2.** A comes from the reliable header's `'11' u16` tick (`v5.md` §4.1), whose extension to a full counter
  isn't specified; at 60 Hz the u16 wraps after 18.2 min, after which a 16-bit A compared with an extended T makes
  T ≥ A always true, and the aliasing guard (l. 69–71) is gone.
- **Fix.** In §2: "A and every stored tick are full extended ticks; a `RATE` keeps T continuous (its epoch is
  now − T / new rate), so stored ticks stay comparable". Add both to Needs elsewhere for the wire unit (`RATE` epoch
  rule; extension of the reliable `'11' u16` tick to the value nearest the client's estimate, as for `tick:u8`).

## Minor

### m1. `"received"` sampling is not the client's sample set under reordering and held rows

- **Location.** §12.4, l. 614–615: "which is exact for §11.2 because the server runs the same function on the same
  inputs"; §11.2, l. 480: the client keeps samples "for its add and each applied row"; §2, l. 66: a row applies only
  if "q is newer than s".
- **Case.** Frames q = 10 (tick 100) and q = 11 (tick 101) both carry record r; 11 arrives first and applies; 10
  arrives next and is not applied (q older than s), so the client's samples skip tick 100. The ack marks both
  received, so the server's set has 100 and 101: at P = 100.5 the client lerps 99–101 and the server 100–101. The
  same happens when a newer held row replaces an older one (l. 67). The add is another mismatch: it carries
  `:newest()` values at its flush, while the server reads the truth ring at tick A (values at the state tick), and a
  record created after the state tick's flush has no ring slot at A at all.
- **Fix.** The client keeps every arrived row of an occupant as a sample in tick order, whether or not it applies to
  `get`; the server takes the add's sample from the values the add carried (store them beside the per-pair bits of
  M1's fix). Then "same inputs" holds.

### m2. The order guarantee for scoped events holds for reliable events only

- **Location.** §10 Order, l. 420–421: "a viewer gaining sight in the same flush receives the catch-up add before the
  event".
- **Case.** `Net.hit` is an unreliable server event with `:about`. The catch-up add goes on the reliable lane, the
  event in an unreliable event frame; the unreliable frame routinely arrives first, and the handler's `get(key)`
  returns nil.
- **Fix.** "For reliable events. An unreliable scoped event can arrive before the add of the record it names; game
  code reads `get` as nil then."

### m3. `:about` excludes requests for a reason that applies to single-target events, and tooling still flags requests

- **Location.** §10 Events only, l. 422–423: "A server request names its one player, so an ask outside that
  player's holdings is a call game code made on purpose". `v5-tooling.md` §3, `unscopedRef`: "a server-sent event
  or request … with no `:field("<path>"):about(` call".
- **Case.** `fire(player, { target = enemyKey })` also names one player and is equally "on purpose", yet is
  scoped; `invoke(player, { target = enemyKey })` is the same leak (the Riot "Start Spike Defuse" class) and can't
  be. Meanwhile `unscopedRef` warns on that request and nothing can satisfy it, so the warning can only be ignored.
- **Fix.** Either allow `:about` on server requests (a scoped-out ask completes with a new outcome; the developer
  chose to scope it), or keep the exclusion with a reason that distinguishes requests from single-target events, and
  until the tooling unit applies the change record, record the disagreement.

### m4. A throwing binding withholds while a throwing predicate keeps; the binding's wire action is unstated

- **Location.** §9, l. 371–372: "that tick no viewer receives the record's fields of that class: a class exists to
  withhold, so the error withholds"; §8.5, l. 318: the predicate's "pair keeps its last result".
- **Case.** A `team` binding throws once. Does every current team holder receive nil (a transition, then a second
  transition with values at the next tick, two full sends), or nothing (they keep their last value, which is not
  "withholding")? Either is possible from the text.
- **Fix.** One rule for both channels that Lync can follow exactly: keep the last result (the binding's previous
  output for the record; none for a new record, which withholds). State the wire effect: no transition is sent.

### m5. The interest `focus` function has no fault codes

- **Location.** §8.2 table, l. 237 (`focus` "one call per viewer per state tick"); §14 codes.
- **Case.** `focus` throws for a player whose character is mid-respawn. No code is raised and no fallback is named;
  predicates and bindings have both.
- **Fix.** `focusError`, `focusYielded` (fault, native report, run as in B2's fix); the viewer keeps its last cell,
  the rule l. 254 already gives for a nil focus.

### m6. "A viewer that has never had a focus holds nothing" contradicts "Optimistic by rule"

- **Location.** §8.3, l. 254–255 and D6; §8.1, l. 220: "Every test errs toward sending".
- **Case.** A player in a lobby (no character, no `ReplicationFocus`) whose UI lists fighters from Lync records sees
  an empty list; the stated rule says the test errs toward sending.
- **Fix.** Keep D6 (its reason is sound) but state it as the one exception to §8.1's rule, with the remedy: a game
  that shows records before spawn supplies `focus`.

### m7. "One rule" holds only to a factor of 2, and the merge favours FIFO collections

- **Location.** §7, l. 179: "One rule: the largest accumulated weight goes first"; l. 196–205: buckets "oldest first
  within a bucket"; merge key "2^(b − 20), the bucket's lower bound"; ties to the FIFO head.
- **Case.** In one bucket, a record with s = 1.9 × 2^k that became pending later goes after one with s = 1.0 × 2^k.
  Across collections, a FIFO head with s = 1.0 × 2^k beats an interest record with s = 1.99 × 2^k (its key is
  2^k). And s exceeds 2^19 before the age floor (priority 1000 × 4 × 4 per tick reaches it after 33 ticks), so bucket
  39 is ordered by age alone.
- **Fix.** State the rule as the buckets implement it: "largest ⌊log2 s⌋ first, oldest first within it; FIFO heads
  enter with key ⌊log2 s⌋", so both implementations obey one stated rule exactly.

### m8. Look-ahead files a teleported record four times its jump away

- **Location.** §8.3 Filed position, l. 246–248.
- **Case.** At 20 Hz and `lookAhead` 0.2, a record that jumps 300 studs in one tick has v = 6,000 studs/s and is
  filed 1,200 studs further along the jump for that tick; a respawn next to a group of viewers enters their block a
  tick late, and one near a block edge can leave holders for a tick. `cut(key)` exists exactly to mark such ticks.
- **Fix.** "v = 0 at the tick a `cut` takes effect", the same as a record's first tick.

### m10. Precision gaps in rewind and classes

- `Lync.perceived` for a frame from a client that has never received a state frame: s is undefined (l. 579, "else
  the newest ack held from p" has nothing to fall back on). State the result (`ackSeq` −1 and `rewound` gives
  `"expired"`, or an error code).
- `rewound` returns declared fields from the truth ring for every viewer, class fields included: a `:owner()` field
  comes back with its value for a non-owner, though the client was shown nil. State that class fields are returned as
  that viewer received them (nil outside the class at that tick), or refuse class fields in `fields`
  (`fieldCodec`).
- The truth-ring layout fixes rotation as "its `t.rotation(9)` code" (l. 550); a `t.cframe` with another rotation
  width (`t.rotation(12)` needs 38 bits) has no stated slot width. State it as "the rotation's code, rounded up to
  bytes".

### m11. Counter "reads as" columns judge, and pop-in is attributed to the wrong counter

- **Location.** §14 l. 813: "a high leave rate at steady load points to R below the sight range"; §8.3 l. 268–269:
  "pop-in is the symptom, and `interestLeaves` (§14) shows its rate".
- **Case.** "High" has no quantity and "points to" is a diagnosis. Pop-in is a record *appearing* close to a viewer,
  which is an enter, not a leave.
- **Fix.** "Reads as: removes caused by interest per viewer per second"; in §8.3, "`interestEnters` counts how often
  records appear; the distance at entry is not reported".

### m12. The ack-only rule inflates jitter, and so D, for idle clients at low `stateRate`

- **Location.** §11.1, l. 451–455 (acknowledged "the error is toward a longer delay").
- **Case.** At `stateRate` 10 an idle client acks after 100 ms or after the second frame, whichever is first; the
  two coincide, so samples split between rtt and rtt + 100 ms. jitter (mean absolute deviation) ≈ 50 ms, D target
  0.2 + 0.1 = 0.3 s, while the same link with an active client gets 0.2 s. D then depends on whether the player is
  sending, not on the network.
- **Fix.** The server can't tell which trigger sent an ack-only frame, so don't filter; state the dependence in
  §11.1 as a known effect with its size (D up to 0.1 s longer for an idle client at `stateRate` 10, derived from the
  100 ms trigger), and add it to §15's round-trip measurement.

### m13. Deferral: rows' successor and the PVS storage fallback are left open

- §8.5, l. 312–313 and §15: "Whether a string module of that size is accepted is unverified", with no fallback.
  IR §4.2 names one (a `DataStore` value, ≤ 4,194,304 characters per key). Let `pvs` take a `buffer` too, so a game
  can load it from either.

## What is good

- The generation decision (§2) is the right one and well argued: `gen` in the add, stored by the client, with
  the T ≥ A guard closing the aliasing case; it fixes the re-add fault for interest and shared decoy slots at 2 bits
  per add.

  shortcut stated.
- Reliable fields at R from the `rcv` receipt, instead of IR's Q, removes a real gap for reliable messages.
- The `seg:u1` cut bit is the cheapest exact mechanism and its limit (two cuts between samples) is stated.

  and handlers one answer.
- Option tables are complete in form (type, unit, range, default, cost) throughout, and the "no fact from
  rewind or interest" line is held consistently.

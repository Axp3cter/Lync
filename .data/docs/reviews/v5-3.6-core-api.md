## A. §0 and §2

### A1. "The generated path, which is 1.7–1.9x faster again" is the wrong ratio, and the decision prices one of four costs — minor

- **Where.** §2, "Decision: the interpreter's form": "the fixed-position closures save (742 − 333) × 70 = 29 µs/s of
  client CPU on a 3-field row … A game for which that matters runs the generated path, which is 1.7–1.9x faster
  again."
- **The case.** `runtime_path.out`, interpreted, s3: Cf 332.8 ns, G1 395.6, G2 229.1; s8: Cf 768.3, G1 915.1, G2
  446.6. The generated encoder on the same writer (G1) is slower than Cf; the inline form (G2) is 1.45–1.72x
  faster than Cf. 1.7–1.9x is I/G1, the interpreter against the generated encoder, already stated in §0.
- **What the 29 µs/s leaves out.** Client downstream decode (I 830.6 against Cf 368.5 ns, s3) and server decode of
  every client's upstream on a runtime-path server: 100 players × 70 messages/s × (830.6 − 368.5) ns = 3.2 ms/s
  interpreted, × (447.4 − 273.8) ns = 1.2 ms/s native (derived from the same file). The choice may still stand
  (a second encoder form is a second code path under the differential test), but the problem statement says the
  decision weighs CPU, and the largest CPU term is missing.
- **Fix.** "…runs the generated path, whose inline form is 1.45–1.72x faster than the fixed-position closures to
  encode (G2 against Cf)." Add the server line: "on a runtime-path server the closures would save
  100 × 70 × 462 ns = 3.2 ms/s interpreted (1.2 ms/s native) of upstream decode at 100 players, and the client its
  downstream decode, against a second encoder and decoder form per codec kind."

## B. §3.2

### B1. The client-side refusal of `layout` 1 doesn't stop the server; §3.2's "refuses the namespace itself" overstates it — major (also `v5-3.6-wire.md` M1)

- **Where.** §3.2 "Mixed paths decode only at one layout": "an identity-build shard meeting a runtime-path server
  that varies its layout refuses the namespace itself on `layout` 1 (§4.5). Nothing decodes under a layout it
  doesn't hold."
- **The case.** The wire review's M1 gives it in full: the server has welcomed the namespace and keeps sending it;
  downstream chunks have no lengths (§4.8: "no lengths"), so every frame carrying one is refused under rule 7,
  with every other namespace's events and collection writes in it, and each refusal is counted in
  `refusedFrames` and reported upstream. The core text inherits the claim.
- **Fix in §3.2** (after the wire unit's `HELLO` bit lands): "an identity-build shard meeting a runtime-path server
  that varies its layout is refused by the server (`MISMATCH`, §4.6), so no frame of that namespace reaches it."

### B2. `layout.vary` changed after the first `WELCOME` gives one server two layouts — major

- **Where.** §3.2: "`layout.vary`, boolean, default `true` … Each `WELCOME` carries it as the bit `layout`"; "The
  layout is per server, upstream and downstream, so encode-once and `FireAllClients` hold" (§4.5). §7.5: "options
  carried in `WELCOME` apply to connections first welcomed after the call", and the call "never throws for being
  late".
- **The case.** A game requires its view, players join, and a later script calls
  `Lync.configure({ layout = { vary = false } })` (a test harness, or a feature flag read after a DataStore
  yield). By §7.5's rule, connections welcomed from then on get `layout` 0 and earlier ones keep `layout` 1. A
  `fire(Lync.all, …)` must now encode each run under two layouts, which §4.2's encode-once and §4.5's
  "per server" exclude, or send one layout to clients holding the other, whose decoders then read garbage that
  may pass every rule.
- **Why it matters.** Nothing in §3.2, §4.5 or §7.5 says which happens; both outcomes are wrong.
- **Fix.** In §3.2's option bullet: "`layout.vary` is read once, at the server's first `WELCOME` of any namespace;
  a `Lync.configure` after that with a different value throws `callOptionRange` at its caller (the one exception to
  §7.5's late-call rule, which §7.5 states)." Cost: none. Runtime unit adds the sentence to §7.5.

## C. §3.3

### C1. Visibility placement: `v5.md` and `v5-collections.md` admit different fields — blocking (also `v5-3.6-collections.md` m9)

- **Where.** §3.3 codec-method table: `:owner()`, `:team()`, `:gated()`, `:seen()` allowed on "a collection's
  top-level field where `:newest()` is allowed" (fixed width, so not a string, buffer, array, map, `t.int()`,
  Roblox enum, instance or custom codec), with "`:gated()`: 1 presence bit per update". `v5-collections.md` §9:
  "A modifier goes on a top-level reliable field of a collection record … Anywhere else (… a `:newest()` field …)
  is the declaration error `visibilityPlacement`", because "Rows are one fixed-width piece per record per tick
  (§5), so a per-class `:newest()` field would need one row per class."
- **The cases.** `name = t.string(20):owner()`: collections accepts it, `v5.md` refuses it (`newestWidth` class).
  `position = t.vector3(…):newest():owner()`: `v5.md` accepts it, collections refuses it, and collections' row
  format can't carry it.
- **Fix.** Replace the row's "Allowed on" cell with collections' rule: "a top-level field of a collection record
  that is not `:newest()`, at most one of the four per field (`visibilityPlacement`)"; and the Wire cell with
  collections' presence-bit rule (one presence bit per class field per update, `v5-collections.md` §9). The change
  record's §1.1 row "placement where `:newest()` is allowed" is then "changed to collections' rule".

### C2. The role marker is a wrapper codec, so a claim-marked key never equals the collection's key codec — major

- **Where.** §3.3 claims: "Hash: a wrapper codec, type 26 `role`, role u8 (1 input, 2 claim), then the codec
  (§4.7)". Against it: `v5-integrity.md` §8 `refers` takes "a top-level field whose codec is `c`'s key codec,
  `t.optional` of it, or `t.array` of it … (another codec: `fieldCodec`)"; §7.3 `reactsTo`: "key fields whose codecs
  differ, `fieldCodec`"; `v5-tooling.md` `decoyRef`: "a leaf … whose codec serialises (`v5.md` §4.7) identically to
  C's `key` codec". §3.5's example: `Net.strike:field("target"):refers(Net.fighters)` with
  `target = t.int(1, 2 ^ 40):claim()` and `fighters`' `key = t.int(1, 2 ^ 40)`.
- **The case.** `target`'s serialization is `26 ‖ 2 ‖ int(1, 2^40)`; the key's is `int(1, 2^40)`. Compared by
  serialization (tooling's definition, and the only one written down), the §3.5 example throws `fieldCodec`;
  `decoyRef` never fires on a claim-marked key, which is exactly a hit target, the case it exists for; and
  `reactsTo` can never pair a claim-marked response key with a stimulus key (server-sent payloads and collection
  keys can't carry markers: `rolePlacement`).
- **Why it matters.** The markers were made hashed wrappers so that roles are visible to the planner; nothing told
  the three comparisons to look through them, and §3.5's own example fails.
- **Fix.** One definition, in §3.3 after the hash sentence: "**Codec equality** (for `refers`, `about`,
  `reactsTo`, `decoyRef`, `unscopedRef`): two codecs are equal when their §4.7 serializations are equal after
  every `role` wrapper (type 26) is removed." Integrity, collections and tooling then cite it in place of "is c's
  key codec" and "serialises identically".

### C3. What verifies a claim: `v5.md` and `v5-checks.md` state different rules, and neither defines "check" — major

- **Where.** §3.3: "A claim leaf is verified when the definition has a validator, or when a check of any kind is
  declared on the leaf's field handle or on that of a record enclosing it (§3.4)." `v5-checks.md` §7.2: "at least
  one check of any kind and any policy is declared on that leaf's field handle (checks take leaf codecs only, so no
  record's handle carries one) … Leaves inside arrays, maps and union variants, and leaves of codecs no check takes
  (strings, instances), are verified only by a validator."
- **The cases.** (1) "or on that of a record enclosing it": no check takes a record (`fieldKind`), so the clause
  either never applies or means something else is a check. (2) §3.4's field handle carries `refers`, `answers`,
  `reactsTo`, `aim`, `series`, `canary`, `gate`, `about` as well as the five checks; §3.3's "a check of any kind"
  doesn't say whether `Net.strike:field("target"):refers(Net.fighters)` alone verifies `target`. §3.5's comment
  ("`validate` verifies the claim strike.target, so connect is accepted") implies it doesn't; nothing says so.
  `refers` only reports decoy references, so counting it would make the marker guarantee nothing for real keys.
- **Fix.** Replace §3.3's sentence with: "A claim leaf is verified when the definition has a validator, or when one
  of the checks `within`, `monotonic`, `maxTotal`, `derive` or `maxRate` (`v5-checks.md` §2–§6) is declared on the
  leaf's own field handle. No other declaration verifies (`refers`, telemetry, `answers`, `reactsTo`). Leaves
  inside arrays, maps and union variants, and of codecs no check takes, are verified only by a validator."

### C4. The claim guarantee: two paths beyond the checks review's three — major (extends `v5-3.6-checks.md` M1)

- **Where.** §3.3: "**What it guarantees:** no message holding a claim reaches `connect` or `handle` without a game
  validator or a Lync check having seen it"; "Nothing is declared away, so verification never lapses once the
  handler is accepted." `v5-3.6-checks.md` M1 shows three check-side bypasses (a `reference`/`fn` returning nil,
  undrawn `oneIn` messages, `resetChecks` windows); its fix wording applies to §3.3 too. Two more paths:
  1. **Telemetry on a definition with no handler.** `Net.strike:atom({ fields = { "origin", "target" }, … })` is
     declared; `Net.strike:connect` throws `claimUnverified` (no verifier). Every message is then "dispatched to
     nobody" (§3.5), neither dropped nor delivered. `v5-checks.md` §8.3 samples "messages that will be delivered"
     and "Dropped messages are not sampled": whether an unheard message is sampled is undefined. If it is, the claim
     values reach game code through `Lync.telemetry.atoms` and `telemetry.read` with no verifier ever declared.
  2. **A second `validate`.** §3.5's verbs define `validate(fn)` once; a second call (replace, add, throw) and
     `validate(nil)` are unspecified. If `validate(nil)` clears the validator, as signal-style APIs often do,
     verification lapses after the handler was accepted, which "Nothing is declared away" denies.
- **Fix.** (a) §3.3's guarantee, exactly: "no message holding a claim leaf reaches `connect` or `handle` unless,
  when the handler was accepted, the definition had a validator or a check on that leaf; a check passes the message
  without evaluating it when its function returns nil (`checksSkipped`), when it is not drawn (`oneIn`), or inside
  a `resetChecks` window (`checksExempted`)." (b) §3.5 verbs: "`validate` may be called once per definition; a second
  call throws `validatorTwice` (caller)", or "replaces the validator; `nil` is `callOptionRange`" (either is exact;
  pick one). (c) §3.5's no-handler decision: "a message with no handler is not delivered: telemetry doesn't sample
  it and checks don't commit it" (see E4 for the commit half).

## D. §3.4

### D1. `field(path)` overloads: 9 or more paths make the new solver report "Code is too complex to typecheck!" — major

- **Where.** §3.2 "Selecting by a string literal … a call whose only arguments are the literal and values of
  already-known types selects correctly on both"; §3.4: "Verified on luau-analyze 0.740, both solvers, and tsc 6.0.2
  `--strict`: correct calls are clean"; §3.6 "Field handles are one overload per path". The probes had 2 to 3
  overloads.
- **The case** (*checked*, `overloads_8/9/32`, `overloads_consumer`). A checked module holding
  `type View = { field: ((self: View, path: "f1") -> H<vector>) & … }` with 9 overloads reports, under
  `--solver=new`, `TypeError: Code is too complex to typecheck! Consider simplifying the code around this area` at
  the alias; 8 is clean; the old solver is clean at 32. Selection itself survives: the consumer's wrong return type
  and unknown path are still rejected on both solvers. Paths count every record and every leaf reachable through
  records and optionals (`nested_typefn`: `hit`, `hit.at`, `hit.part`, … are 10 overloads for a 6-field schema),
  and collection records get handles too (`canary`, `gate`), so a 9-field `fighters` record already crosses it.
- **Runtime path.** The type function's intersection hits the same diagnostic at the declaration that uses it
  (`nested_typefn`, 10 paths), which in real use is the game's own script.
- **Why it matters.** Shards are checked modules (`--!strict` per `v5-tooling.md` §1.1); a typical schema puts an
  error in the shard under luau-lsp and fails a CI `luau-analyze` run on code Lync generated, against principle 3.
- **Fix.** Generated path (checked, `overloads_types` + `overloads_shard_fixed` + `overloads_consumer_fixed`):
  emit each view's overload alias into a `--!nocheck` types module and annotate the shard's view value from `any`
  (`local strike: T.Strike = view :: any`); the consumer keeps exact selection on both solvers and nothing is
  reported. Runtime path: no fix found (a generic `field<P>` over `index<>` widens the literal, `index_field`);
  state it: "exact under the new solver; for a definition with 9 or more reachable paths the analyzer also
  reports 'too complex' at the view's declaration (luau-analyze 0.740), and calls stay checked". Add the threshold
  to §10's typing proofs.

### D2. `Field<D, T>` is keyed by the Luau type, which can't decide which declarations a field takes — major

- **Where.** §3.4 (c): "returns a handle typed by the field, on which each declaration is one non-overloaded
  method"; `v5-checks.md` §8.6: "`aim` and `series` are methods of the field handle `Field<D, T>`, present only where
  T is a codec they take"; `v5-integrity.md` §8: `refers` on "`c`'s key codec, `t.optional` of it, or `t.array` of
  it"; `v5-collections.md` §10: `about` on the key type "or `t.optional` of it".
- **The cases** (*checked*, `field_kind`, both solvers).
  - `t.vector3` (a position) and `t.direction` (an aim codec) are both `Vector3`; `t.int(-100, 100)` (refused by
    `maxTotal`) and `t.int(0, 100)` are both `number`. With T the Luau type, `v:field("origin"):aim()` and
    `v:field("coins"):maxTotal({ … })` type clean and throw `fieldKind` at run time. "Present only where T is a codec
    they take" can't be written over T.
  - `target = t.optional(t.int(1, 2 ^ 40))` gives `Field<Data, number?>`; `refers(collection: Collection<T>)` then
    rejects the correct `refers(fighters)` on both solvers ("Expected … `Collection<number?>` but got
    `Collection<number>`", tables are invariant). The same for `t.array` of the key, and for `about`.
  - What T is for a path through an optional (`"hit.at"` with `hit` optional) is unstated: `Vector3` (a check isn't
    evaluated when `hit` is absent, `v5-checks.md` §1.2) or `Vector3?`.
- **Fix** (*checked*, `field_kind_fixed`, both solvers: wrong methods are "Key not found", correct `refers` on the
  optional is clean). §3.4: "Each path's handle type is emitted from the field's codec, not its Luau type: it has
  exactly the declarations that codec takes (`v5-checks.md` §2–§8, `v5-integrity.md`, `v5-collections.md`), with
  T the field's type with the optionals on its path removed. `refers` and `about` take `Collection<K>`, K the
  collection's key type, for a field of type K, K? or { K }." On the runtime path the codec types must then carry
  their kind (the brand carries only T today, §3.3), so the type function can select methods by kind; state that, or
  state that the runtime path's handles carry every method and wrong ones are `fieldKind` at run time. roblox-ts:
  the same per-codec interfaces in place of `Field<D, T>`.

### D3. The option table's Kinds column, the trigger of `optionPlacement`, is ambiguous for four options — minor

- **Where.** §3.4: "An option the definition's kind, direction or lane doesn't take (the Kinds column) is
  `optionPlacement`".
- **The cases.**
  - `limit.*` "client-sent event, request": §5.4's client bucket throttles what the client sends, and §5.2's
    `limited` is "the server's `limit` bucket"; on a `from = "server"` request neither exists. Accepted or
    `optionPlacement`?
  - `perceived` "client-sent event, request": on a server-sent request the upstream message is the answer, which
    has no handler and no synchronous call in which `Lync.perceived` works (`perceivedOutsideDispatch`), so the
    bytes buy nothing.
  - `from` "collection: always server": is `from = "server"` on a collection accepted, and `from = "client"`
    `optionPlacement` or `paramRange`?
  - `sealed`: `sealed = false` or `sealed = true` (not a table) has no stated code; `limit = { burst = 5 }` without
    `perSecond` has none (`missingOption`?).
- **Fix.** Kinds: `limit.*` and `perceived` "client-sent event, client request"; `from` "event, request
  (required); not taken by a collection (`optionPlacement`)". Rules: "`sealed` and `limit` are tables; another type
  is `paramRange`; `limit` without `perSecond` is `missingOption`."

### D5. Run-time declaration errors: three files use three code sets for one trigger — minor

- **Where.** `v5.md` §7.1: "A field whose codec a call doesn't take is `fieldKind` for every call that names a field

## E. §3.5

### E1. The §3.5 example doesn't run: `player` is unbound at the top level — minor

- **Where.** §3.5 server: `Net.fighters:set(player.UserId, { … })` and `Net.fighters:patch(player.UserId, …)` after
  the handlers, outside any function.
- **The case.** `player` is a parameter of the handler closures only; at the top level it is an unknown global
  (`UnknownGlobal` lint, and a nil index at run time). `camera`, `Targeting` and `PRICES` are free too, which reads as
  shorthand; `player` reads as the API.
- **Fix.** Wrap the two writes: `Players.PlayerAdded:Connect(function(player) Net.fighters:set(player.UserId, …)
  end)`, and mark the free names as game code (`-- game code: PRICES, Targeting`).
- **Checked otherwise:** every marker is placed as §3.3 allows; `strike`'s validator precedes its `connect` (D2's
  order); `chat`'s and `buy`'s payloads hold no claim; the example declares no check, so no required bound is
  missing; `round`'s placeholder `target = 1` is in range; `freeFormField` gives 0 with the markers.

### E2. `messagesUnheard`: the decision's premise is false for scripts that start later, and the dispatch rule has two homes — minor

- **Where.** §3.5 "Decision: a message with no handler": "A script that requires a view can connect before its
  first yield, and that precedes every dispatch, since `require` never yields and dispatch runs on a later engine
  event." §5.1 "Dispatch" (runtime-owned) states the same rule again ("dropped and counted (`messagesUnhandled`)").
- **The cases.** A `LocalScript` in `StarterCharacterScripts` or a `Tool` starts at each spawn, long after the first
  dispatch; every server-sent message between a death and the next connect is unheard. With the claim rule, a
  server whose verifiers live in one `Script` and handlers in another depends on start order between scripts, which
  Roblox does not specify (unverified here): `claimUnverified` can throw in one server and not in the next.
- **Fix.** Replace the premise with: "A script that connects in the run that first requires the view misses
  nothing; a script that starts later (character and tool scripts) misses what came before its connect, and what it
  needs then is state, in a collection." Add to §3.3's claims decision: "Verifiers and handler must be declared in
  one script, or the handler's script must require the module that declares the verifiers; Lync doesn't order
  scripts." §5.1 points to §3.5 instead of restating it.

### E3. `round(data)` is exact for built-in codecs only — minor

- **Where.** §3.5: "`round(data)` returns a new value equal to what the server's decoder produces for `data`".
- **The cases.** `t.convert(base, decode, encode)` and `t.custom` run the game's functions, on the client for
  `round` and on the server for the real decode; a `decode` that reads side-specific state (a lookup table filled
  only on the server) gives two values. `t.instance`: `round` returns the client's instance, while the server's
  decoder may yield `unresolved` (an instance that exists only on the client, §7.3).
- **Fix.** "…equal to what the server's decoder produces for `data` for every built-in codec; for `t.convert` and
  `t.custom` it is the client's own `decode(encode(v))`, and for `t.instance` the same instance, which the server
  may refuse as `unresolved`."

### E4. "Delivered" is undefined for a message with no handler — minor (with `v5-3.6-checks.md` m4)

- **Where.** §3.5: "dispatch to nobody and count it"; `v5-checks.md` commits checks "for a message that will be
  delivered", samples telemetry on "messages that will be delivered", and `refers` reports on "a delivered message"
  (`v5-integrity.md` §8).
- **The case.** A `collect` event with `maxTotal`, `series` and no `connect` yet: does it charge the window, enter
  the ring, report `decoyReferenced`? Each file reads "delivered" its own way; C4's telemetry path depends on it.
- **Fix.** One sentence in §3.5's decision: "A message that passes §6.1 step 6 is *accepted*; it is delivered when a
  handler receives it. Checks commit and `refers` reports on accepted messages; telemetry samples delivered ones."
  (or the other way; the point is one definition, used by all three files).

### E5. "The shared schema module replicates on both paths" contradicts staged namespaces — minor

- **Where.** §3.5: "The shared schema module replicates on both paths". `v5-tooling.md` `namespace.staged`: "the
  namespace's `schema` and `client` must map under `ServerStorage`" until `Lync.release`.
- **Fix.** "…replicates on both paths, except a staged namespace's, which replicates at its release
  (`v5-tooling.md`, `v5-collections.md` §13)."

### E6. The runtime path's sealed `fire` type: correct for `sealed = {}`, wrong for a conditional `sealed` — minor

- **Where.** §3.5: "The runtime path's type function picks the return type from whether the options table has a
  `sealed` property … unverified until milestone 1's typing proofs (§10)."
- **The case** (*checked*, `sealed_fire`, new solver). A type function over the captured options type returns `Seal`
  for `sealed = {}` and `sealed = { outstanding = 2, hideLength = false }`, and `nil` otherwise; `n:reveal()` on a
  plain event is an error. Verified, so the "unverified" can go. But
  `sealed = if flag then {} else nil` has the property (type `{}?`) and is typed `Seal`, while at run time a nil
  `sealed` makes a plain event whose `fire` returns nothing: `fire(…):reveal()` passes the checker and indexes nil.
- **Fix** (*checked*, `sealed_fire_fixed`): "`Seal` when `sealed`'s type excludes nil, `Seal?` when it includes
  nil, nothing when absent." Generated path unchanged (the build sees the value).

## F. §3.6 and §5.2

### F1. Request outcomes: `left` and `shutdown` have no trigger, `E` isn't given per side, and a client can answer `limited` — major

- **Where.** §3.5: "`E` is `"timeout"` …, `"limited"` …, `"rejected"` …, `"unanswered"` …, `"left"` or
  `"shutdown"`" (the last two with no definition anywhere in `v5.md`; §5.2's table uses them). §5.2: "an answer row
  is `slot:u4 epoch:u1 outcome:u2 [reply]`, outcome … 3 `limited`"; `limited` is "the server's `limit` bucket".
- **The cases.**
  - What makes a client `invoke` end `left` (the local player can't leave mid-call and observe it) or `shutdown`
    (does the client learn of `BindToClose`)? What makes a server `invoke(player, …)` end `shutdown` before its
    `timeout`? None is stated.
  - Server `invoke`: no server-sent definition takes `limit` (D3), yet `limited` is in the one `E`. A modified client
    can write outcome 3 in its answer row; no §4.8 rule refuses it, so the server result is `limited`, a value the
    game was told means its own bucket.
  - Client `invoke` can't be `left`.
- **Why it matters.** Principle 3 (exact types) and the brief (every outcome a code with an exact trigger); game
  code switching on `error` can't know which arms exist.
- **Fix.** §3.5: give `E` per side. Client: `"timeout" | "limited" | "rejected" | "unanswered" | "shutdown"`, with
  `shutdown` = "the connection closed before an answer (the server shutting down, a kick, a teleport)". Server:
  `"timeout" | "rejected" | "unanswered" | "left" | "shutdown"`, with `left` = "the player left before an
  answer" and `shutdown` = "`BindToClose` ran before an answer". §5.2: "outcome 3 in an upstream answer row is rule
  7 (§4.8)" (wire unit).

### F2. `ServerResult`'s failure arm makes game code nil-test values §5.2 guarantees — minor

- **Where.** §3.5 `ServerResult` with `roundTrip: number?` … in the one `ok: false` arm; §5.2: "An answer with outcome
  `rejected` or `unanswered` from the client has all four."
- **The case** (*checked*, `result_arms.luau` part 1, both solvers): after `not r.ok and r.error == "rejected"`,
  `local t: number = r.roundTrip` is an error, though the value is always present.
- **Fix** (*checked*, part 2 on both solvers and `result_arms.ts` with tsc): three arms discriminated on `error`:
  `{ ok: false, error: "rejected" | "unanswered", roundTrip: number, pingAtSend: number, pingAtAnswer: number,
  minPing: number }` and `{ ok: false, error: "timeout" | "left" | "shutdown", roundTrip: nil, pingAtSend: number?,
  pingAtAnswer: nil, minPing: nil }`. Narrowing on `error` gives `number` in the first on both solvers; the old solver
  doesn't narrow the `else` branch to the third arm, so there `roundTrip` reads `number?` (still a nil test, as
  today). TS the same with `?: undefined`.

### F3. `unanswered` "ran past `timeout`" is an outcome the asker can never receive — minor

- **Where.** §5.2: "`unanswered` when … the handler … ran past `timeout`"; "an `invoke` … its timeout already
  running"; "an answer whose epoch differs from the slot's current epoch is a late answer after a timeout:
  discarded and counted (`lateAnswers`)".
- **The case.** The asker's timer starts at `invoke`, before its ask leaves; the answerer's can start no earlier
  than the ask's arrival. The asker's timer always expires first, flips the epoch, and returns `timeout`; the
  `unanswered` the answerer then sends is a late answer. So each slow handler costs a row upstream and a
  `lateAnswers` count on the asker, on an unmodified game, and the listed cause is never what a caller sees.
  The answerer's timer start is also unstated.
- **Fix.** "The answering side stops waiting for a handler `timeout` s after the ask's decode and sends nothing; the
  asker's result is `timeout`." Remove "or ran past `timeout`" from §3.5's `unanswered` and §5.2's list.

## G. What is good

- **Field handles** are the right call, and the probe that drove them (`overloads_options`) is exact: path
  overloads with option tables do fail under the new solver, and selection by literal alone holds on both solvers
  at any count (D1's issue is a diagnostic, not a selection failure). Nested dotted paths through records and
  optionals work in a type function, with arrays, maps and unions unreachable (`nested_typefn`).
- **The claim requirement at `connect`/`handle`** acts on no input, costs nothing per message, and names the line.
  `v5-checks.md` now matches it, which closes most of scope A1 from the checks side.
- **No `read` in game-facing types** is verified on both solvers and the rule is applied in `v5-checks.md` §8.6.
- **`number?` in the failure arm**, written out in both arms, narrows on `ok` on both solvers and tsc (re-run); F2
  only asks for one more arm.
- **`round` as a view method** (not a codec method), sending nothing and throwing `valueRefused` like `fire`, is the
  smallest exact primitive for the claim-from-decoded-value problem.
- **`optionPlacement`** as one code for every option a kind doesn't take is the right shape; D3 is only about the
  column it reads.
- **The `layout.vary` decision** states its options, the per-session cost (34–76 MB) and why per session prices
  nothing more, and makes the option a boolean.
- §0's figures match `runtime_path.out` (I/G1 1.68–1.91 interpreted, I/G2 3.24–3.91, decode 4.52, native
  2.43–2.85).

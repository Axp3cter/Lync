## 1. Cross-cutting

### 1.1 One judging rule, applied two ways: one-time universal counters reject generated traps but admit R18, R1 and the identity probe — major

- **Location.** §1: "Each is judged by the recurring work it imposes on a modified client … 'a universal counter
  exists' are not reasons on their own: Lync varies what a counter depends on per build (§2), per server
  (permutation), per session (the key) and per player (§2.4)". §3 decision: "a driver that browses the namespace
  skips them after a one-time change to the tool: no recurring work, which is what §1 asks a measure to impose".
  §5: "one spoof of the two that returns the originals' values passes kinds 1, 2 and 4 in every Lync game and every
  build"; §5 injected frames: "It doesn't see injection fired from a thread of its own".
- **Case.** Three measures with one universal, one-time counter, each identical in every Lync game and build:
  `setthreadidentity(2)` before calling `fire` (§4 identity), `task.defer(listener, frame)` or
  `coroutine.wrap(listener)(frame)` instead of a synchronous `firesignal` (§5 injected frames; the `levels.luau`
  probe shows such a listener sees `debug.info(2, "f")` = nil, as for an engine delivery), and one `hookfunction` of
  `debug.info` and `table.isfrozen` returning the originals' values (§5 self-check). By §3's sentence each imposes
  "no recurring work" and should be rejected; §5 adopts all three. §1's per-build/server/session/player sentence is
  false for all three (and for canaries, whose format is fixed, §8 below).
- **Why it matters.** A reader can't predict an outcome from the rule, and the rule as stated in §1 promises
  per-build work for measures that have none. `v5.md` §6.2 repeats the sentence.
- **Fix.** Write §1's criterion so both decisions follow from it, for example: "A measure is adopted when its fact
  is exact (no cause on an unmodified client, or each cause listed) and its cost is stated; each section states
  'Universal counter: yes, <the counter>' or 'no'. Generated traps are rejected because choosing their names is
  the developer's (brief), not for want of recurring work." Then restrict the per-build sentence to §2's values and
  `v5.md` §4.5's key and permutation, as `reviews/v5-3.6-scope.md` A2 asks, and add the universal-counter line to
  §4, §5 and §9.

## 2. Build values and variants (§2)

### 2.1 Variant modules: two files specify different places, grains and contents — blocking

- **Location.** §2.4 "the build writes `ModuleScript`s `Variant1` … `VariantN` as children of the server shard
  (never replicated), each returning its mask as an integer literal"; the client "waits for `PlayerGui.Lync`".
  Against it, `v5-tooling.md` §1.1 "Variant modules": "N client variant modules **per namespace** at
  `ServerStorage.LyncVariants.<namespace>.<k>` … Each follows the part rule, carries line 1 with `variant k/N`", and
  §1.2's manifest `namespaces.<name>.variants`, one entry per variant part.
- **Case.** A place with namespaces `arena` and `lobby`, `build.playerVariants = 4`. Tooling writes 8 modules in
  `ServerStorage.LyncVariants`; integrity writes 4 under the server shard (which shard, with two namespaces?). The
  mask is per connection, since one upstream frame holds runs of several namespaces and carries one tag (`v5.md`
  §4.5); per-namespace modules would give a player two masks for one tag. The change record's "Needs elsewhere"
  adds "the server shard gains children `Variant1` … `VariantN`" to tooling §1.1 without deleting tooling's own
  per-namespace bullet, so both texts survive the merge.
- **Why it matters.** Implementers of the build and of the runtime would emit and look for different instances; a
  per-namespace reading is also wrong for the tag.
- **Fix.** One rule, stated in both files: one set of N modules per build run (not per namespace), at one path
  the server runtime owns (e.g. `ServerStorage.LyncVariants.<k>`, since a run with several namespaces has several
  server shards), one integer each, no part rule, line 1 and digest as tooling has them; manifest `variants` at the
  run level. Replace the "Needs elsewhere" line with that text and an explicit deletion of tooling §1.1's
  per-namespace bullet.

### 2.2 `tagVariant` doesn't name a player, and a two-account player can make it name an innocent one — major

- **Location.** §2.4: "`Lync.variantOf(player)` … so a game can log assignments and tie a `tagVariant` to the
  player who held that variant"; "the server names its source variant on each frame, which the assignment ties to
  a player"; assignment "the lowest-numbered variant no present player holds".
- **Case.** Masks are per build and shared by every server of the build; assignment is deterministic by join
  order. Account A1 joins an empty private server, is assigned variant 1 (lowest free), and reads
  `require(PlayerGui.Lync:FindFirstChildWhichIsA("ModuleScript"))` (one line, the same in every Lync game, since the
  `ScreenGui` is always named `Lync`). Account A2 joins public server Y, where player C joined first and holds
  variant 1. A2 tags its own frames with its own session key XOR m_1. Y's server reports `tagVariant` with
  `variant` 1 on A2's connection; `Lync.variantOf(C)` is 1; §2.4's sentence ties it to C, who did nothing. Without
  malice the same holds for any carried mask: the holder of u on this server is one of every player assigned u in
  any server of the build, not the source.
- **Why it matters.** It is evidence that invites a consequence against the wrong player. What the fact proves
  exactly (`generation-methods` M13: "its sender held this session's key and u's mask") is about the sender.
- **Fix (smallest).** State it exactly in §2.4 and the §10 row: "`variant` names a mask; every account assigned u
  in any server of this build has read it; the player holding u on this server is not thereby its source." Delete
  "tie a `tagVariant` to the player who held that variant". **Structural alternative** (the mask-only choice makes
  it free): a variant now holds data, not code, so the server can draw the N masks at start (entropy-seeded
  `Random`) and deliver m_v as a value (an attribute of the `ScreenGui`) instead of a build module, as M13 already
  notes for the runtime path. Then u's mask was read by someone assigned u on this server during its life, which
  the game can log, and a mask carried from another server is a `tagMismatch`. Cost: no build modules, no N × module
  bytes; the mask in the server shard becomes a per-server table; join timing unchanged (same instance
  replication, same pending measurement).

### 2.3 Per-run values against a per-connection tag: no rule that a connection's namespaces share one run or path — major

- **Location.** §2.1–§2.2: S, the tag constants and the masks are drawn per build run; `v5.md` §3.3 "Mixed paths
  decode only at one layout" is per namespace (`HELLO` per namespace compares `buildId`); `v5.md` §4.5: the tag
  uses "the build's two initialisation constants" and the key from "the first `WELCOME`'s nonce under S".
- **Case.** A place whose `arena` namespace is generated (nonzero `rotationSeed`) and whose `Packages/Inventory`
  namespace runs on the runtime path (`layout` 1, reference constants, S = 0). Each namespace's `HELLO` matches its
  own server side, so neither gets `MISMATCH`. An upstream frame holding runs of both namespaces carries one tag:
  under `arena`'s constants and S-derived key, or the runtime path's? The key itself depends on which namespace's
  `WELCOME` arrived first. Client and server implementations can pick differently and fail every mixed frame as
  `tagMismatch`, or the attacker-facing values degrade to the runtime path's public ones.
- **Why it matters.** It is a correctness hole for any game mixing a package namespace with a built one, and the
  security values of §2 are only as strong as the weakest namespace on the connection.
- **Fix.** In §2.1: "S, the tag constants and the mask are per connection: every namespace a client uses must
  come from one build run (one `buildId`), or every one from the runtime path; a `HELLO` whose `buildId` differs
  from the connection's first accepted `HELLO` is `MISMATCH` (`seedDiffers` 1)." Add it to "Needs elsewhere" for
  `v5.md` §4.6's handshake.

### 2.4 Lowest-free assignment and fixed delivery make the variant a universal read, and a low variant the common one — minor

- **Location.** §2.4 Assignment and Delivery; Prices: "Not priced: a tool that reads its own client's variant
  (**code**, **mem**: one integer in one module)".
- **Case.** The read is `PlayerGui.Lync`'s one module in every Lync game (fixed name `Lync`, child name
  `Variant<v>` revealing v). Under lowest-free, variant 1 is held by the first joiner of every server, so the masks
  of variants 1–4 cover most players in small servers; a harvested table of low masks plus the `Variant<v>` name
  is enough to tag correctly without `require`. A game whose own `StarterGui` holds a `ScreenGui` named `Lync`
  (copied into `PlayerGui` on spawn) makes the client's wait bind the wrong child.
- **Why it matters.** §2.4's "Prices **share**" reads as broader than it is; the collision is a join failure
  (`variantMissing`) with no listed cause.
- **Fix.** In Prices add "Universal counter: yes, reading `PlayerGui.Lync`". Name the child neutrally (no `v` in
  the name, e.g. `Value`), mark the server's `ScreenGui` by an attribute the client checks, and list the name
  collision under `variantMissing`. If 2.2's structural form is taken, uniform-among-free assignment costs nothing
  and removes the "low variants are common" skew; otherwise state the skew.

### 2.5 `PlayerGui` timing at `PlayerAdded` is unspecified — minor

- **Location.** §2.4 Delivery: "parented to the player's `PlayerGui`"; M7's sketch used
  `player:WaitForChild("PlayerGui")`.
- **Case.** The design gives no wait and no bound for `PlayerGui`'s existence at `PlayerAdded`, nor its order
  against the server's `WELCOME`. If the server answers `HELLO` before the `ScreenGui` is parented, the 10 s
  `variantMissing` clock runs from a `WELCOME` that preceded the variant's creation.
- **Fix.** State "the server waits for `PlayerGui` (`WaitForChild`, in the assignment thread) and parents the
  variant before it answers that player's first `HELLO`"; add `PlayerGui`'s presence at `PlayerAdded` to §12.

### 2.6 A fixed `build.seed` makes every "per build" claim per seed change — minor

- **Location.** §2.5 "16 hex digits fix `rotationSeed` … for tests and reproducible builds".
- **Case.** A developer commits `build.seed = "0123456789abcdef"` to `lync.toml` to get reproducible CI builds and
  ships them; every release then has the same order, offsets, constants, S and masks, and a public repository
  publishes the seed itself.
- **Fix.** One sentence: "Under a fixed seed every value of §2.2 is the same in every build with that seed; §2.2's
  'each build' claims hold per seed change, and a seed in a public `lync.toml` is public." `rotation.entropy`
  should record `"fixed"` for this case.

### 2.7 Streams: say what one read reveals — taste

- **Location.** §2.2 Streams.
- **Case.** Each stream's whole sequence is a function of 32 bits (the xorshift32 state): the second tag constant
  is the xorshift32 step of the first, and in an `offset:` stream with several codes (`t.color3`'s channels) one
  known value of one channel narrows the 2^32 states that a second known value then fixes. Across streams nothing
  leaks (HalfSipHash-2-4 as a PRF). `v64("session")` = S ships in every client shard as a full 64-bit output under
  the 64-bit `rotationSeed`, so one pair determines the seed up to a 2^64 search, which is the stated bound.
- **Fix.** Add the two sentences ("within a stream, one value can give the rest; across streams, none") so the
  table's "one known value of a field gives its c" isn't read as the only leak.

## 3. Traps and reachability (§3)

### 3.1 Declared traps are separable by the client's own bytecode, the test that rejected generated traps — major

- **Location.** §3 Declared trap: "Lync guarantees only the rest: no artefact, byte or answer tells it apart"; §3
  decision: generated traps rejected because a one-time tool change skips them; Prices: "a driver that fires only
  names client scripts reference passes traps and unreferenced definitions alike".
- **Case.** A trap is, by construction, a client-sent definition no unmodified client code fires, so normally no
  client script names it. Every name a client script uses as a field is a bytecode string constant (`refs.luau`:
  `GETTABLEKS … K0 ['buyItem']`), which an executor lists with `getconstants` over `getscripts()` (or reads from
  `getscriptbytecode`). So one universal tool, written once: "for each client-sent definition in the namespace,
  fire it only if some client script's constants contain its name". It skips every declared trap in every Lync game
  and build, exactly as the key-set difference skipped generated ones. The trap survives only if the developer
  puts its name in client code (a dead field access or string literal), which the design never says.
- **Why it matters.** The rejection of generated traps rests on a test that declared traps fail equally; the
  stated guarantee is about Lync's outputs, while the decisive tell is the game's own scripts. A developer reading
  "no artefact … tells it apart" will not place the reference that the trap needs.
- **Fix.** State the guarantee exactly: "Lync's outputs (schema module, shard, types, manifest, wire) treat a trap
  as any definition. Whether game code names it is the developer's: a trap no client script names is skipped by a
  driver that fires only names found in client bytecode; naming it in client code that never runs defeats that
  test." In the decision, rest the rejection of generated traps on naming being the developer's (the brief's rule)
  rather than on recurring work (1.1).

### 3.2 "No … answer tells it apart" is false after the first fire, and the pipeline order adds a second tell — minor

- **Location.** §3: "an ask is answered `rejected`, indistinguishable from a `validate` refusal"; `v5.md` §6.1 step 5
  order "traps and reachability (`unreachable`); answers …; `limit` (`overLimit`)".
- **Case.** (a) A trapped request answers `rejected` for every input; a real request without a refusing validator
  answers with its handler's reply. One ask separates them. (b) A trap declared with `limit = { perSecond = 5 }` in
  the shared schema (visible): 20 asks in one second to a real request give `limited` past the bucket; to the trap
  all 20 give `rejected`, since the trap drop runs before `limit`.
- **Why it matters.** The first fire is already reported, so (a) costs the driver one fact; still, the guarantee
  should be the exact one. (b) is avoidable.
- **Fix.** Say "nothing tells a trap apart before its first message reaches the server; its answers are `rejected`
  for every input". Move the trap drop after `limit` in `v5.md` §6.1 step 5 (Needs elsewhere, runtime), so an
  over-limit ask to a trap answers `limited` as any definition's does.

### 3.3 `basis` 1 and `basis` 2 both fire for a trap in a woven build, with no precedence — minor

- **Location.** §3 "A trapped definition reports `basis` 1, never 0"; `v5-tooling.md` §5.4 "A declared trap that no
  client code names is closed like any such definition".
- **Case.** `weave.ids = "site"`, a trap with no sites: it is closed, so a message on its generic id is the
  `basis` 2 trigger and the `basis` 1 trigger at once.
- **Fix.** "A trapped definition reports `basis` 1, never 0 or 2."

### 3.4 `basis` 2 needs closure computed after the gate — minor (to confirm with tooling)

- **Location.** §3 Generic ids: "has every unmodified call on a site id"; `v5-tooling.md` §5.4 gate: a script that
  fails `weaveUnparsed`/`weaveCompile`, or a site that fails `weaveShadowed`, stays unwoven and calls the shard.
- **Case.** If closure is decided from the scan before the gate and one site of definition D then fails
  `weaveShadowed`, D is reported closed while an unmodified client sends D on its generic id: `basis` 2 on every
  such call.
- **Fix.** One line in §3 (and tooling §5.4): "closure is computed from the sites that passed the gate".

## 4. Caller probe and `REPORT` (§4)

### 4.1 A view handed to code in another script sets the caller bit on every call, and the cause isn't listed — major

- **Location.** §4 source: "That source is looked up in the build's list of client scripts that reference the
  definition"; §3: a script references a definition when "its name appears after `.` or `:` … or as a string
  literal"; §10 `reportedSourceUnlisted` causes.
- **Case.** A common object pattern: `LocalScript` `Weapons.client.luau` runs `Weapon.new(Net.strike)`; the
  `ModuleScript` `Weapon` stores `self.remote = remote` and later calls `self.remote:fire(hit)`. The walk's first
  frame outside Lync is `Weapon`'s method, whose source is `Weapon`; `Weapon`'s text never contains `strike`, so it
  isn't on `strike`'s list, and every probed shot sets `caller` = 1. The namespace stays complete (the hand-off is an
  argument to a function defined in the scanned code, which §3 follows), so the source check stays on. §10's
  "function value a library calls" cause covers a callback, not a view passed as data.
- **Why it matters.** At `oneIn` 1 this is a `reportedSourceUnlisted` on every frame holding a shot, from every
  unmodified client of such a game, with no cause naming it.
- **Fix.** Either extend the list by the same following §3 already does: a script receiving a view (or a value
  holding one) through a followed parameter, field or return is listed for that view's definition; or add the cause
  to §10: "a view passed to code in another script that calls `fire` on it (an object storing `Net.x` and firing it
  from its own module)", and say game code removes it by naming the definition in that module. The first is exact
  and costs only build time.

### 4.2 Calls made before the first `WELCOME` have no probe parameters — minor

- **Location.** §4 Probe: `callerProbe.oneIn`, `maxPerSecond`, `noOuterFrame` reach the client in `WELCOME`
  (`v5.md` §4.6); `v5.md` §5.3: sends before `WELCOME` are held as encoded runs.
- **Case.** Client start-up code fires `Net.ready:fire()` before `WELCOME`. Whether it is probed, under which
  `noOuterFrame`, and whether the released frame's `caller` bit reflects it, is unstated; an injector that runs
  before `WELCOME` would choose this window if it is unprobed.
- **Fix.** "Before the first `WELCOME`, every call is probed under `oneIn` 1 and `noOuterFrame = "unlisted"`; the
  result is kept with the held run and sets the bit of the frame that releases it; after `WELCOME` the server's
  values apply." Or state that pre-`WELCOME` calls are unprobed, as a stated gap.

### 4.3 `REPORT`'s size bound predates its three new fields — minor

- **Location.** §4 cost "`REPORT`: a forced frame is 8–12 B with the tag" (`v5.md` §4.6 says the same); §4 now
  lists seven EG0 fields, `selfCheckItem` being an index into a list of about 200 items (EG0 of 202 is 15 bits).
- **Case.** A `REPORT` with `selfCheckFailures` 1, `selfCheckItem` 202, `selfCheckKind` 3 adds about 1 + 15 + 5
  bits plus the four old fields' minimum, so "8–12 B" no longer bounds it; §5's "3 B of fields beyond the others"
  is the right figure but the §4 bound wasn't updated.
- **Fix.** Restate the bound for seven fields (e.g. "8–15 B") and send it to the wire unit with the `REPORT` row.

### 4.4 The `coroutine.wrap` cause is wider than the case — taste

- **Location.** §4 Defaults: "a call started with no game frame on its thread (`task.spawn(view.fire, view, v)`,
  `coroutine.wrap`)"; §10 the same.
- **Case.** `coroutine.wrap(function() view:fire(v) end)()` keeps a game frame (`levels.luau`: `wrap(game)` shows
  two frames); only `coroutine.wrap(view.fire)(view, v)` has none.
- **Fix.** Write "`coroutine.wrap(view.fire)`" in both places.

## 5. Client-stated reports (§5)

### 5.1 A game that wraps the `transport` seam makes every downstream frame "injected" — major

- **Location.** §5 Injected frames: "The function Lync passes to `Reliable.OnClientEvent:Connect` … reads
  `debug.info(2, "f")` as its first statement … a synchronous call from other code leaves a function below it";
  §10 `reportedInjectedFrames` causes: "none, while §5's Studio check holds". `v5.md` §8: the `transport` seam's
  `onReceive(handler)` is "where whole-frame transforms go", and a game may wrap it.
- **Case.** A game wraps `transport` to decompress frames: its wrapper is what connects to `OnClientEvent`, and it
  calls Lync's handler from its own function. If the check sits in the handler the seam calls, `debug.info(2, "f")`
  is the game's wrapper on every frame: `injectedFrames` > 0 every flush, a forced `REPORT` and a
  `reportedInjectedFrames` fact from every unmodified client of that game. If the check sits only in the default
  transport's connected function, a wrapped transport has no check at all. The design says neither.
- **Why it matters.** A documented extension point produces a fact whose row says it has no cause on an
  unmodified client.
- **Fix.** State where the check runs: "in the function the default transport connects; with a registered
  `transport`, the check is off (`injectedFrames` stays 0) and the seam's docs say so". Add "a registered
  `transport` seam" to the row's causes if the other placement is chosen. Add the same seam cause to
  `reportedRefusedFrames` (a client-side wrapper that alters frames makes the client refuse them, as `v5.md` §7.3
  already lists for `malformed` and `tagMismatch`).

### 5.2 Their guarantees are stated exactly; whether to run them is the developer's, and there is no switch — minor

- **Location.** §5 injected frames "No option: the cost leaves no game a trade to make"; self-check "No option: the
  cost scales with the list, not with traffic".
- **Case.** Both are exact (kind 3 and 4 have no unmodified cause; the injected-frame origin is a fact once the
  Studio check passes) and both are defeated in every Lync game by one universal change (1.1). The section's
  "What it doesn't price" is honest and specific, which is what the scope rule asks of the guarantee. What the rule
  also asks is that a judgement stays the developer's: whether a fact a one-line hook removes everywhere is worth a
  console line, an observer call and a forced `REPORT` is such a judgement (`reviews/v5-3.6-scope.md` A2).
- **Fix.** Add `report.injectedFrames` and `report.selfCheck` (boolean, default `true`, server-sent in `WELCOME`,
  1 bit each; cost: the figures already in §5), and the "Universal counter: yes" line of 1.1 to each.

## 6. Clock (§6)

### 6.1 A due `BEACON` or pending `REPORT` before the variant is installed can't be tagged, and "never enters the join hold" — minor

- **Location.** §6 Client: "After the connection's first `WELCOME`, a `BEACON` … is pending reliable data … It never
  counts toward `missedFlush` and never enters the join hold"; §4 `REPORT` the same; `v5.md` §4.5 "A client holding
  no mask yet tags nothing; its tagged frames wait (§5.3)".
- **Case.** `build.playerVariants = 16`; `WELCOME` arrives at t = 0, the variant at t = 1.8 s (arrival unmeasured,
  §12). The first `BEACON` is due at t = 1.0 s and must ride a reliable frame, which needs the mask. The two rules
  contradict: the frame can't be sent, and the beacon may not wait in the hold.
- **Fix.** "`REPORT` and `BEACON` become pending only once the connection's frames can be tagged (with variants,
  once the mask is installed); the first `BEACON` is due `clock.beacon` after that moment." The estimator already
  ignores the first 30 s, so nothing else changes.

### 6.2 Median of an even count is undefined — minor

- **Location.** §6 rule 3 "the Theil–Sen slope of the 12 minima (median of the 66 pairwise slopes)"; `othersSlope`
  "the median of s over the other players".
- **Case.** 66 is even; `clock-facts.md` §U3.1 computes with "the 33rd and 34th order statistics". Two
  implementations (lower, upper, or mean of the two) give different `slope` values near the threshold, and so
  different facts; the same for `othersSlope` at an even `others`.
- **Fix.** "median of an even count: the mean of the two middle order statistics" (or name one), once, in §6.

### 6.3 Two delay steps, one in each half, pass the split-half test — minor (derived, not simulated)

- **Location.** §6 rule 5 "One level shift lies inside one half, so the other is flat"; §10 `clockRate` "Not causes
  (simulated): … one delay step of any size".
- **Case.** Steps of +0.5 s in the one-way delay envelope at windows 3 and 9 of a fit (30 s apart, e.g. two
  uplink queue jumps). In each 6-window half, a step between windows 3 and 4 straddles 3 × 3 = 9 of 15 pairs, so
  the 8th order statistic is a straddling pair, about 0.5 s over 5–25 s, at least 0.02 s/s > 0.01. Both halves
  and the full fit count, with one sign. As the windows slide, a step between half-windows k and k + 1 straddles
  k(6 − k) pairs: 8, 9, 8 for k = 4, 3, 2, each above the 7 needed to move the 8th order statistic, and 5 for k = 1
  or 5. So the fits with the steps at k = 4, 3 and 2 in both halves (15 s of slide) count in a row: a run of 3, the
  default `reportFits`, and a fact on an unmodified client.
- **Fix.** Add "two or more delay steps spread over both halves" to the `clockRate` causes, and a staircase case to
  the §12 clock simulation; until simulated, say the split-half test is proven against one step only.

### 6.4 Memory line understates the estimator — taste

- **Location.** §6 Cost "Memory: one number per player (the first window's o, for `drift`)".
- **Fix.** "12 window minima, an index and the first window's o per player", since the line reads as the total.

## 7. Timing facts (§7)

### 7.1 The 0.5 `factor` is derived from one latency drop, and a larger drop fires it on an unmodified client — major

- **Location.** §7.1 "after a one-way latency drop from 0.10 s to 0.03 s, `roundTrip` over a ping-only minimum falls
  to 0.52–0.59 within 0.5 s (smoothing time constant assumed) … So 0.5 sits under every simulated unmodified case";
  `earlyAnswer.factor` and `reactsTo` `factor` default 0.5 "(§7.1)".
- **Case** (derived with the research's own model, `clock-facts.md` §U4: ping as an exponential average, τ 2 s or
  10 s). A phone moves from cellular to Wi-Fi: one-way 0.15 s → 0.02 s, round trip 0.30 → 0.04 s, in a game with no
  collections (so no ack round trips in b). 0.5 s later the smoothed ping is at least 0.04 + 0.26 × e^(−0.25) ≈
  0.24 s (τ 2 s), and b, a minimum over samples taken since the drop, is about that; an automatic answer takes about
  0.04 + 0.02 s. `roundTrip` / b ≈ 0.25 < 0.5: `earlyAnswer` from an unmodified client. The margin in the simulated
  case is 0.52 against 0.5, and it shrinks in proportion to new/old round trip.
- **Why it matters.** The default is called derived but bounds one scenario, not the cause; the threshold is a
  judgement about which latency changes to tolerate, which the brief gives to the developer, and the fact fires by
  default where the game can't see why.
- **Fix.** Either derive it as a bound ("`factor` ≤ the smallest new/old round-trip ratio the game's players see,
  minus the smoothing lag": not knowable by Lync) and so make `factor` required on `reactsTo` and
  `earlyAnswer.factor` default 0 (off), with the docs giving 0.5 as the simulated example; or keep 0.5 and label it
  "chosen", listing in the cause the case above with its arithmetic. The first follows the brief.

### 7.2 "One origin" holds for asks and stimuli, not for challenges — minor

- **Location.** §7 intro "They share one clock, one origin and one bound"; §7.4 "t_s is the first flush after the
  `Lync.challenge` call".
- **Case.** The game sends the token in a prompt message 2 s after calling `Lync.challenge` (after a UI
  transition). t_s is the earlier flush, so `after` and `firstAfter` include 2 s the player never had, and the
  deadline runs from a moment the token hadn't left. Nothing is false for `earlyAnswer` (elapsed only grows), but
  the result's `after` doesn't equal what the intro says, and `timeout` gains a cause.
- **Fix.** Intro: "one clock and one bound; the origin is the sending flush for asks and stimuli, and for
  challenges the first flush after the call, a lower bound on the token's departure". Add "the game sent the
  token later than the call" to `timeout`'s causes, and tell the docs recipe to call `Lync.challenge` in the
  handler that fires the prompt.

## 8. Decoys and canaries (§8–§9)

### 8.1 The interest rule admits a new decoy in the hysteresis ring, which `v5-collections.md` names as a tell — blocking

- **Location.** §8: "under `interest` …, a decoy whose filed cell is outside the viewer's block and hysteresis ring,
  or whose PVS bit … is 0, `decoyOutsideInterest`". Against it, `v5-collections.md` §8.6: a decoy fails "when it is
  new to the viewer this state tick and its filed cell is outside the viewer's block (a real record never enters at
  ring distance, so a decoy appearing there would be the only one); or it is not new and its filed cell is outside
  the block and its ring; or the viewer's `pvs` bit … is 0, or the `predicate` returns false for it", and the failing
  decoy "is removed".
- **Case.** A behaviour places a fresh decoy in a ring cell of the viewer. Under §8 it is sent; under
  `v5-collections.md` it throws. If sent, it is the only kind of record that ever appears new at ring distance: a
  viewer's one-line filter ("drop any add whose position is outside my block") removes every such decoy exactly.
  §8 also omits the `predicate` test, and says "leaves that decoy unsent" where collections says an already-sent
  decoy "is removed".
- **Why it matters.** Two files specify different behaviour, and the one this file specifies has an exact mark.
- **Fix.** Replace §8's bullet with a pointer to `v5-collections.md` §8.6's three conditions, and say what happens
  to a decoy already sent that fails later: removed in that flush (with its history entry kept, so `decoyReferenced`
  still matches it).

### 8.2 Decoys hold more slots than `MaxPlayers` × `maxPerViewer`, and churn starves real `set`s — major

- **Location.** §8 Slots: "held from its add until 2 s after its remove … Decoys hold at most `Players.MaxPlayers` ×
  `maxPerViewer` slots per collection, so `maxRecords` must cover live records, those removed in the last 2 s, and
  that product"; "A real `set` that finds none throws `recordLimit`". `v5-collections.md` §2 says the same.
- **Case.** 100 players, `maxPerViewer` 1, a behaviour that returns a decoy under a new key each state tick at
  20 Hz (keys drawn per tick, or derived from `tick`). Each tick Lync removes one decoy and adds one per viewer; each
  removed slot stays held 2 s. Each viewer then holds 1 live + 40 delayed slots: 4,100 slots, against the stated
  100. At `maxRecords` 1,024 the free slots run out within half a second, `decoysUnplaced` counts, and the game's own
  `set` throws `recordLimit`.
- **Why it matters.** The sizing rule a developer follows is wrong by the churn factor, and the failure lands on
  real records, in game code that never touched decoys.
- **Fix.** Count a viewer's delayed decoy slots against its `maxPerViewer`: "a viewer's decoys hold at most
  `maxPerViewer` slots, live or within 2 s of their remove; a decoy add beyond that is not made that tick
  (`decoysUnplaced`)". Then the product bound is exact and real `set`s can't be starved. Cost: none; a churning
  behaviour sees fewer decoys, counted. State the same in `v5-collections.md` §2 (Needs elsewhere).

### 8.3 `canary.perViewer` true by default gives two accounts, and one account, an exact mark — major

- **Location.** §9 Values: "8 such characters …, then a 4-character (4-byte) suffix per viewer carrying s = j XOR p
  … Strings write s as 4 base-62 digits … (62^4 ≥ 2^23); buffers write it as u32le"; default "**derived.** It
  reports every echo the shared form reports, plus echoes from players the value wasn't sent to"; §8 Prices: "two
  accounts comparing key sets spot a decoy only one of them holds (R15 stays refused)".
- **Case.**
  - *Two accounts* (the **share** class the option targets): every real field of a shared record is the same for
    both viewers; the canary field's last 4 characters differ. A comparator that drops "the field equal in its
    first 8 characters and different in its last 4" removes every per-viewer canary in every Lync game. With the
    shared form both viewers hold the same value, and comparison finds nothing.
  - *One account, strings:* s < 2^23 = 8,388,608, so the first suffix digit is at most ⌊8,388,607 / 62^3⌋ = 35:
    character 9 is always one of `A`–`Z`, `a`–`j` and never `k`–`z` or `0`–`9`. Over 20 records a uniform real field
    shows that pattern with probability (36/62)^20 ≈ 1.9 × 10^−5.
  - *One account, buffers:* u32le of s < 2^23 makes byte 12 always 0 and byte 11 always below 0x80.
- **Why it matters.** The derivation weighs facts gained against CPU and never against the separability it adds;
  the same reasoning that keeps R15 refused (comparison across accounts) applies to the default.
- **Fix.** Make the suffix uniform over its whole range: s = (j + p) mod M, with M = 62^4 for strings and 2^32 for
  buffers and p the keyed hash reduced to [0, M) (64-bit output mod M); the server recovers j = (s − p) mod M and
  accepts it only when j < 2^23 and the viewer's bitset holds the slot. For each j, s is then uniform in [0, M), so
  no character or byte position has a fixed range; the `canaryEchoed` chance for `sameViewer` 0 becomes
  (viewers sent the add) × 62^−12 per 12-character window (× 2^−96 per 12-byte buffer window). Then derive the default with the trade-off
  stated: per-viewer canaries let any two viewers of one record find the field; the shared form doesn't. Given the
  brief's rule, `canary.perViewer` should be required or default `false` with that line in its row.

### 8.4 A real key that meets a live decoy's key: what the viewer sees is unstated — minor

- **Location.** §8: "a key … that becomes a real key while the decoy lives, `decoyKeyLive`", which "throws in the
  behaviour's thread and leaves that decoy unsent".
- **Case.** The decoy keyed 4417 was sent to viewer V at tick 100; at tick 140 game code `set`s a real record 4417.
  The decoy was already sent, so "unsent" doesn't apply: does V get a remove then an add of the real record, two
  records of one key, or does the `set` throw? Each choice also differs in what V can observe (a decoy removed
  exactly when a real key appears is a mark).
- **Fix.** Specify: the decoy is removed from V in the same flush, before the real add, its history kept; the
  behaviour's next result throws `decoyKeyLive` if it returns the key. Say that V sees a remove followed by an add of
  one key, which also happens for real records re-added within a flush (if it does; otherwise say it is a mark).

## 11. What is good

- **One stream rule for every per-build value** (§2.2): labelled, keyed, identity at seed 0, golden set untouched.
  It is easy to audit and gives independence across values for free.
- **Mask-only variants** (§2.4): the decision is argued from what each option adds in recurring work, prices the
  layout alternative's bytecode and its clash with weaving, and keeps "a client can't choose its variant".
- **The `splitFrames` rejection** (§4) ties a client option to the frame-budget invariant it would break, which is
  the right kind of reason.
- **The clock section** (§6): signed slope, one server grid, `othersSlope` as evidence rather than a correction,
  and the decision to refuse server-wide corrections because they hide majorities; the split-half test is a small,
  derived fix for a measured false fact.
- **Challenges** (§7.4): nothing in the schema, wire or Lync's client marks them; `attempts` required; the outcome is
  a result, not a fact; the accessibility causes and the docs recipe are concrete.
- **The self-check's limits** (§5) are stated exactly and without softening ("one spoof … passes kinds 1, 2 and 4
  in every Lync game"); the same candour would fix 1.1 if applied to §1.
- **The fact table** carries evidence units and unmodified causes with figures (chance rates, simulated counts)
  throughout.

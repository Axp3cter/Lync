## §7.5 The budget bound and the defaults

Re-derivation from `probes/inbound-budgets/RESULTS.md`. Every per-frame median in claim 1's table is under
c_f + c_b × B + p(L) × E when the frame's own L is used: header-only frames 1,890 / 2,188 ns against 2,590 / 2,643;
busy input 4,698 (its highest run median 5,511) against 5,517; busy action 4,099 against 5,498; random 32-bool
columns 4,258 ns per element against p(32) = 6,256; constant 128-bool columns 7,611 against 19,024; one-message
runs 849 against 2,000; R31's arrays 27.8 and 122.7 against 2,133. The busy model fits the defaults with the stated
room: 60 of 120 unreliable frames, 170 of 8,192 and 850 of 16,384 B/s, and 70 of 411 elements at L = 6. The
allocation adds up: frames 2.53 × 60 + 2.60 × 120 = 464 µs, bytes 20.2 × 8,192 + 10.8 × 16,384 = 342 µs, elements
1,150 µs, total 1,956 µs; the bursts are 607 + 993 + 624 + 354 µs. The rekey state is covered now that §4.5 hashes
at most 5 and 3 times at any key state. The findings below are where the bound fails.

### 2. p(L) doesn't count arrays and maps (blocking)

- **Location.** §7.5, "p(L) = 2,000 + 133 × L ns per element, L the most leaves of any element … its leaves are its
  codec's leaf values outside nested arrays and maps"; §4.8, "An element is one message of a run, one array element
  or one map pair".
- **Case.** A client-sent record of 64 fields `t.array(t.bool(), 255)`, each sent empty. §4.8 charges 1 element per
  message (0 array elements). The message has no leaves outside its arrays, and an array element has 1 leaf, so
  L = 1 and p(1) = 2,133 ns. Measured (`rtreview/probe.luau`, milestone `Inbound.receive`, tag accepted, element
  count read from the reader's budget):

  | Frame | B | elements charged | F native | bound c_f,r + c_b,r·B + p(1)·E | ratio |
  |---|---|---|---|---|---|
  | 1 message, 64 empty arrays (row form) | 68 | 1 | 15,804–17,073 ns | 6,037 ns | 2.7× |
  | 256 messages, 64 empty arrays (columns) | 22 | 256 | 2.06–2.33 ms (8.1–9.1 µs per element) | 0.549 ms | 4.2× |
  | 1 message, 32 empty `t.map(t.int(0,255), t.bool(), 255)` | 36 | 1 | 9,250–9,766 ns | 5,393 ns (p(2)) | 1.8× |
  | 256 messages, 32 empty maps | 14 | 256 | 0.76–0.78 ms | 0.583 ms | 1.3× |

  Each empty array costs about 211–228 ns in row form and 116 ns in columns, and each empty map about 217 ns in
  row form: one count read and one table, with no leaf and no element. At the derived default
  ⌊1,150,000 / 2,133⌋ = 539 elements/s, the element term is 539 × 8.9 µs = 4.8 ms/s per player against the 1.15 ms/s
  allocated, so about 5.6 ms/s in all against the 2 ms/s target. One burst frame of 4,096 such messages costs about
  36.6 ms, against the 8.7 ms that 4,096 × p(1) states.
- **Why it matters.** The question this decision answers is whether a schema's own shapes can game the
  per-schema budget, and they can: any schema whose client-sent records hold several array or map fields. The
  probe's shape set has no message holding an array or map except R31's two single-array rows, where 65,536
  elements per array hide the per-array cost. The same gap covers unions (the tag read and variant dispatch aren't a
  leaf) and the codecs a client sends outside "definitions": the replies to server-asked requests and control rows.
- **Fix.** In §7.5's leaf rule, count each array and each map value (present or not) as 2 leaves, the measured row
  form cost of 211–228 ns over 133 ns, and each union as 1 more for its tag. Define L over every codec the client
  writes: event and ask `data`, the `reply` of server-asked requests, and Lync's upstream control rows. Add
  "records of empty arrays and maps, row and column form" and "a union of the widest variant" to the
  `probes/inbound-budgets/` shape set and to §9's bound test. With weight 2, the 64-array record has L = 128 and
  p = 19,024 ns, which covers 8.9 µs per element and the single-message frame (22.9 µs bound against 16.1–17.1 µs).
  §4.8's cost bullet (the wire unit's) should then quote the same rule.

### 3. c_f,u and c_b,u were measured with 2 of the 3 unreliable candidates hashed (major)

- **Location.** §7.5, "c_f,u = 2.60 µs … a 4 B unreliable frame whose tag fails at every candidate (… 3 hashes)";
  "c_b,u = 10.8 ns/B: … a 1,000 B unreliable frame failing 3 (10.8 µs)".
- **Case.** The milestone's `isTagAt` returns false without hashing when the extension is negative
  (`f1fbfd7:src/session/inbound.luau:858`, `if key == nil or seq < 0 then return false`). The probe's frames come
  from a fresh `Replay.new()` (newest −1), so `full − 4096` is always negative and every "3-hash" frame hashed
  twice. Two hashes of 1,000 B are 2 × (201 + 4.2 × 1,000) = 8.8 µs, consistent with the 10.8 µs measured; three
  would be 13.2 µs. Measured with the window's newest at 10,000, so that all three extensions are hashed
  (`rtreview/probe2.luau`, three runs): 901 B wrong-tag frames cost 14.66–14.77 µs (bound 2,600 + 10.8 × 901 =
  12,331 ns, 19% over), and header-only frames 2.76–2.92 µs (c_f,u 2.60). Any session past seq 2,048 is in this
  state.
- **Why it matters.** It is the input the defaults are derived from. Corrected to c_f,u ≈ 2.9 µs and c_b,u ≈
  (14,740 − 2,900) / 897 ≈ 13.2 ns/B, the unreliable terms are 120 × 2.9 + 16,384 × 13.2 = 564 µs against 489,
  and the total at the defaults is 2,031 µs, over the chosen 2,000 µs before findings 2 and 4. §4.5's own
  formula already prices 3 × 4.0 = 12 ns per unreliable byte, more than the 10.8 that §7.5 uses for the whole frame,
  so the two sections disagree on their face.
- **Fix.** Re-measure claim 2 part B with the replay window's newest at least 4,096 (and the reliable lane with every
  lookahead count hashed, which it already is), restate c_f,u and c_b,u, and re-split the 2,000 µs: at
  c_f,u 2.9 and c_b,u 13.2, frames take 2.53 × 60 + 2.9 × 120 = 500 µs and bytes 20.2 × 8,192 + 13.2 × 16,384 =
  381 µs, which leaves `inbound.elements` 1,119 µs, so ⌊1,100,000 / p(L)⌋ with a round share (finding 4 lowers it
  again). Note in `RESULTS.md` that the original figures hashed two candidates.

### 4. c_b,r doesn't cover byte-linear decode on frames accepted at e + 4, and the bound has no margin (major)

- **Location.** §7.5, "c_b,r = 20.2 ns/B: a 16,384 B reliable frame failing 5 hashes (330 µs)"; "every frame timed
  costs at most c_f + c_b × bytes + p(L) × elements"; §9, "fails when one costs more than §7.5's bound … on the
  reference host".
- **Case 1, a frame accepted at e + 4.** A modified client tags every reliable frame at e + 4: the server hashes
  5 times, accepts, sets e ← e + 5 and reports `frameGap` (coalesced), and the next frame does the same. Such a frame
  pays the 5 failing hashes that c_f,r and c_b,r price, plus its whole decode, but p(L) × E prices only per-element
  work. One `t.string(15900)` or `t.buffer(15900)` message is 1 element and about 13–16 µs of byte-linear decode.
  Measured: 340–381 µs for the 15,906 B frame at e + 4 (`rtreview/probe.luau`, gap rows, two runs), against
  2,530 + 20.2 × 15,906 + 2,133 = 325,964 ns. Every run is over, the fastest by 4%.
- **Case 2, the reference table itself.** `RESULTS.md` claim 2 part B: a 1,024 B reliable wrong-tag frame costs
  23,521 ns; the bound is 2,530 + 20.2 × 1,024 = 23,215 ns. c_b,r is 330,457 / 16,384, a line through the origin
  rather than through c_f, and the measured points between lie above it. On this host today the same frame costs
  24.5–25.9 µs. The busy input frame's highest run median (5,511 ns) is 6 ns under its bound.
- **Why it matters.** "Every frame timed costs at most" is false for a frame the probe timed, and §9 makes the bound
  a per-commit gate with no tolerance on a host whose spread is ±5–30%: it fails on the reference shapes at once,
  or flaps.
- **Fix.** Set c_b,r from the costliest per-byte frame at 5 hashes plus decode: (357,434 − 3,757) / 15,903 ≈
  22.3 ns/B from the e + 4 string frame; round up to 23 ns/B, and set c_f,r from the e + 4 header-only frame (3.76 µs
  here, against 2.53 at e). State a margin: the bound's prices are the measured upper fits × 1.25, and §9's test
  compares each shape's median over runs with the bound, failing above it. Name "the reference host" (the
  probe's 4-core Xeon 2.1 GHz class) or run the test as ratio checks against a header-only frame timed in the same
  run. Add the e + 4 frames and the string and buffer shapes to the shape set. The byte allocation then becomes
  23 × 8,192 + 13.2 × 16,384 = 405 µs, which comes out of the element share.

### 5. A burst frame costs max(W_max, 4,096) × p(L), not 4,096 × p(L) (major)

- **Location.** §7.5 Bursts, "A full refill costs at most 0.61 + 0.99 + 0.62 + 0.35 ms plus 4,096 × p(L) (11.5 ms
  at L = 6, 78 ms at L = 128), the last also in one frame".
- **Case.** The burst is max(W_max, 4,096) and the allowance of one frame is the bucket's whole tokens (§4.8). A
  schema with one client-sent `t.array(t.bool(), 65535)` (W_max = 65,536) and one 128-bool record (L = 128) gets
  burst 65,536 and price p(128). One frame of 65,536 constant 128-bool records is a few dozen bytes: measured
  7,611 ns per element, so 0.50 s of server CPU in one frame (bound 1.25 s), not 78 ms. L and W_max are each a
  maximum over the schema, so the widest definition and the longest one multiply even when no definition is both.
- **Why it matters.** The per-frame worst case is what decides whether one client can stall a server frame, and
  `report.md` is told to list 4,096 × p(L), which understates it by up to 16× for schemas that declare a long array.
- **Fix (smallest).** Replace "4,096 × p(L)" with "max(W_max, 4,096) × p(L)" in §7.5's Bursts and in the
  `report.md` item of "Needs elsewhere". **Fix (structural, optional).** Charge the element bucket in units of each
  element's own price, p(L_e) / p(0) tokens for an element of L_e leaves, with `perSecond` = ⌊1,150,000 / p(0)⌋. The
  bound then holds per element with no schema-wide L, a 1-leaf message doesn't pay a 128-leaf price, and W_max and L
  no longer multiply. Cost: a per-definition constant multiply at each count subtraction.

### 13. Option (a) is rejected on a scaling the chosen allocation doesn't use (minor)

- **Location.** §7.5, "(a) 1 ms/s … the frame and byte terms alone take 0.81 ms/s at budgets that admit Lync's own
  automatic flushes … at m × the busy model's use it needs m = 2.92, 29 reliable frames"; change record, "The 10%
  line was rejected because it needs reliable frame budgets below Lync's own 60 automatic flushes".
- **Case.** The 0.81 ms/s keeps the byte budgets at 8,192 and 16,384 B/s, and claim 4(c) scales every budget by one
  m. Under the non-uniform allocation (b) itself uses, 1 ms/s admits the automatic schedule: frames 60 and 120
  (464 µs), bytes 1,024 and 5,120 B/s (20.7 + 55.3 = 76 µs; 6.0× the busy model's 170 and 850 B/s), elements
  460 µs, so 164/s at L = 6 (2.3× the busy model's 70). "The smallest round target at which the defaults admit …
  its bytes and elements with 5.9× room or more" is circular: 5.9× is 411 / 70, an output of the 2 ms choice.
- **Fix.** Keep (b) if wanted, marked chosen, but state the real trade: "(a) admits the automatic schedule only with
  byte budgets of about 1 and 5 KB/s and 2.3× element room; (b) is chosen for 5.9× room on bytes and elements." Drop
  the 29-frame argument here and in the change record.

### 17. Variant lookups and `REKEY` work are outside both the bound and its exclusions (minor)

- **Location.** §7.5, "Not in the bound: game code … frames the buckets refuse … the server build"; §4.5, "plus up
  to 5 or 3 table lookups with variants (+0.24 µs native per failing 64 B frame)".
- **Case.** With variants (milestone 5), every failing frame costs 0.24 µs more than c_f: 180 × 0.24 = 43 µs/s at
  the default frame budgets. A client cycling `desync` causes up to 6.7 `REKEY` a second, each a key derivation
  (0.31 µs native, derived) and a downstream engine call, which is unpriced.
- **Fix.** Add c_v = 0.24 µs to c_f,r and c_f,u when `build.playerVariants` > 1, and list "`REKEY`: at most 6.7 a
  second, 0.31 µs each plus one engine call (unpriced, §10)" under "Not in the bound".

### 21. The minimum unreliable byte burst never admits a 1,000 B frame with instances (minor)

- **Location.** §7.5 row `inbound.unreliable.bytes`, "burst 1,000–4,194,304 … the burst's minimum fits one unreliable
  frame".
- **Case.** The charge is `buffer.len` + 8 B per instance. A 1,000 B unreliable frame of an event holding one
  `t.instance` is charged 1,008 B; at burst 1,000 the bucket never holds that, so the frame is refused forever.
- **Fix.** Minimum burst 1,000 + 8 × the most instances an unreliable frame can hold, or state that the burst must
  cover `buffer.len` + 8 × instances and derive the minimum from the codec limits.

## §6.1 Inbound pipeline

### 1. The runtime sections drop messages for `claimUnverified`, which §3.3 and `v5-checks.md` §7.3 decided never happens (blocking)

- **Location.** §6.1 step 6, "the claim requirement (`claimUnverified`)"; §7.1, "fault: `claimUnverified`,
  `validatorError`, `validatorYielded`" and the family line "`fault` (`claimUnverified`, …)"; §7.2 row "a claim with

### 6. Step 1 walks the whole instance list before any budget (major)

- **Location.** §6.1, "no frame is hashed or decoded before it is paid for: 1. Shape. One buffer, plus at most an
  array of `Instance` or `nil`"; §7.5, "frames the buckets refuse, which cost their shape check and two bucket reads
  each, … × at most 1.0 µs … ≤ 1.0 ms/s per player".
- **Case.** Checking that every entry is an `Instance` with an integer key needs one pass over the list, and the
  byte charge (8 B per instance) needs its highest index; the milestone does exactly that before `isPaid`
  (`f1fbfd7:src/session/inbound.luau:148–175`). The pass costs 5.7–6.0 ns per entry native and 35–43 interpreted
  (`rtreview/shape.luau`, the same loop over tables). A client firing frames whose second argument lists 10,000
  instances (any replicated instance, repeated) costs 57 µs per call before the byte bucket refuses it, 57× the
  1.0 µs that §7.5 states, and at the engine's ~500 calls a second per remote type about 57 ms/s per player. How many
  instance references the engine delivers per call is unmeasured.
- **Why it matters.** The one cost §7.5 bounds by the engine's call rate rests on the shape check being O(1); with
  the instance array it's O(n), with no budget.
- **Fix.** Walk the list only as far as the byte bucket can pay: at step 1 check the two argument types (O(1)); at
  step 2 take the frame token, then walk the list, refusing the frame as `overByteBudget` as soon as `buffer.len` +
  8 × (entries seen) exceeds the bucket's tokens. The walk is then at most tokens / 8 entries (6,144 at the reliable
  burst), and its cost is a per-byte term, 6 ns per 8 B = 0.75 ns/B, added to c_b. Add the pending measurement "the
  most instance references the engine delivers in one remote call" to §10.

### 7. The untagged `HELLO` path isn't in the pipeline (major)

- **Location.** §6.1 steps 2–4 (no untagged branch); §4.5, "The server treats a frame as untagged while it has seen
  no tagged frame from that client and the frame decodes canonically as untagged `HELLO`s only"; §6.1 step 2, "a
  refused reliable frame advances the expected tag count by one".
- **Case 1, decoded and then hashed, with no element charge.** Until the server accepts a tagged frame from a player,
  every paid reliable frame is first decoded as untagged `HELLO`s; if that fails it goes to the tag. In the
  milestone, `Handshake.untagged` (`f1fbfd7:src/session/handshake.luau:380–413`) reads a fresh reader with no
  element allowance and loops over every control row before checking `Bits.meets`. A client that never sends a valid
  tagged frame can send 16 KB frames of `HELLO` rows whose last bit is wrong: each is fully decoded (strings and
  tables per row, no element charge) and then hashed 5 times as a `tagMismatch`. c_b,r has no room for that decode
  (finding 4), and §4.6's "A control chunk's count is charged to the decode element budget" doesn't reach this
  path.
- **Case 2, a refused untagged frame advances e.** Untagged frames take no count on the client (§4.5). Step 2 runs
  before the server can know a frame is untagged, so an untagged `HELLO` frame refused at the budgets advances e to
  1; the client's first tagged frame (count 0) then has candidates 1–5 and fails as `tagMismatch`, so an unmodified
  client loses that reliable frame. No known cause lists it.
- **Fix.** Add the branch to §6.1 as step 3a: "Before the first accepted tagged frame from the player, a reliable
  frame is decoded as untagged `HELLO`s with the element allowance (rule 10 applies, its elements are taken from the
  bucket); if that fails, it goes to step 3 and is not decoded again before its tag." Price the attempt as
  decode in the bound (it is charged elements). For case 2, have the frame header say "untagged" in a bit the server
  reads at step 2 in O(1) (a wire change for the wire unit), and advance e only for tagged frames. If no header bit
  is wanted, list "a budget-refused untagged `HELLO` frame" as a `tagMismatch` cause.

### 18. Budget-refused old-key reliable frames after a `REKEY` advance e under the new key (minor)

- **Location.** §6.1 step 2, "a refused reliable frame advances the expected tag count by one (§4.5)".
- **Case.** The server sends `REKEY` and sets e = 0. During the next round trip the client still tags under the old
  key. Those frames fail the tag and leave e at 0, except the ones refused at the budgets, which are not hashed and
  advance e. With k such frames, the client's frames under the new key at counts 0 … k − 1 fail as `tagMismatch`
  (lost reliable data), and with k ≥ 8 they cause a second `desync`.
- **Why it matters.** Rare, since it needs a `desync` and an over-budget round trip together, but it loses an
  unmodified client's reliable frames with no cause listed.
- **Fix.** Add the cause to `tagMismatch`: "reliable frames tagged under the old key in the round trip after a
  `REKEY` and refused at the budgets, which advance e under the new key (§4.5)". The exact fix needs the client's key
  epoch in clear, a 1-bit header field: the wire unit's call.

### 20. Step 5's and step 6b's wording contradicts the order of steps (minor)

- **Location.** §6.1, "Facts of step 5 see every message that passed `limit`"; step 6b, "delivered messages only";
  §5.1, "A client or server message whose definition has no `connect` connection then is dropped and counted
  (`messagesUnhandled`)".
- **Case.** `unreachable`, `slotConflict`, `earlyAnswer` and `unresolved` come before `limit` in step 5, so they see
  messages that `limit` then drops. Step 6b runs before step 7, where a message with no connection is dropped, so a
  sampled message may never be delivered.
- **Fix.** "The report-only checks of step 5 see every message that passed `limit` …"; step 6b: "messages that pass
  step 6 and whose definition has a connection at step 7".

# Review: scope audit of draft 3.6 (what Lync does exactly, what the developer owns)

2026-10-15. Critic unit. The rule under audit: Lync does only what it can do exactly (encode, decode, verify the tag,
replay window and canonical decode, run declared checks, drop malformed input, count, report facts with exact
triggers and evidence); anything it would have to guess, approximate, name, place, weigh, score or decide is the
developer's, with Lync supplying the input, the API and an exact statement of what it still guarantees.

The design files are mid-revision (the integrity and runtime units have not ticked any section). Where two files
disagree, the finding names both and gives the split the rule requires; it does not pick a file. Names are
provisional (`reviews/v5-3.6-naming.md`); renames below are only where the name itself states a conclusion.

## A. Cross-cutting

### A1. The claim requirement is specified three ways; two of them drop canonical messages for a missing declaration — blocking

- **Where.** `v5.md` §3.3 "Decision: claims": "**Choice: (c).** … `connect` or `handle` on a definition whose `data`
  holds a claim leaf with no verifier throws the caller error `claimUnverified` at that call … No input is acted
  on". Against it: `v5-checks.md` §1.4 step 6.1 and §7.3 "**Choice: (a).** … dropped, an ask answered `rejected`,
  counted in `claimsUnverified`, and reported natively as **`claimUnverified`** (family `fault`)"; `v5.md` §6.1 step
  6 "the claim requirement (`claimUnverified`)"; `v5.md` §7.1 lists `claimUnverified` under `fault`; `v5.md` §7.2 row
  "a claim with no validator or check (`claimUnverified`) | native report …; message dropped; ask `rejected`";
  `v5.md` §7.4 counter `claimsUnverified`.
- **What Lync does.** Per `v5-checks.md`, it drops every message of a definition whose claim leaf the server hasn't
  verified yet, including messages that arrive in the window before a script's declarations run (§7.3 "Known
  causes … declares it after the definition's first messages arrive"). That drop is Lync acting on canonical input
  because of what the developer has not declared yet, which the rule excludes; `v5-checks.md` justifies it as
  "executes the developer's declaration", but the marker declares nothing about *when* verifiers exist.
- **Why it can't be exact.** Whether a verifier will be declared, and when, is the game's code; the drop window
  depends on script yield order Lync can't see.
- **Split.** Developer: declares verifiers before `connect`/`handle` (an order, enforced). Lync: throws
  `claimUnverified` (caller) at `connect`/`handle`, guarantees exactly "no message holding a claim leaf reaches a
  handler unless a validator or a declared check of the leaf existed when the handler was accepted", and, since
  nothing can be declared away, that this holds for the session. Messages before any handler are
  `messagesUnhandled`, as for every definition (`v5.md` §3.5). Remove step 6.1, the fault family entry, the
  `claimsUnverified` counter and the §7.2 row; `v5-checks.md` §7.3 becomes a pointer to `v5.md` §3.3.

### A2. "Lync varies what a counter depends on" is stated for every measure, and is false for five of them — major

- **Where.** `v5-integrity.md` §1: "'A modified client with full memory access can defeat it' and 'a universal
  counter exists' are not reasons on their own: Lync varies what a counter depends on per build (§2), per server
  (permutation), per session (the key) and per player (§2.4), so a counter written against one has to be rebuilt or
  re-run against the next." `v5.md` §6.2 repeats it.
- **The cases where nothing varies** (each from the design's or the research's own text):
  1. identity probe (§4): `setthreadidentity(2)` before calling `fire` — identical in every Lync game and build; the
     drawn member (`probe` stream) changes which read fails, not the counter;
  2. injected-frame check (§5): firing the listener from a thread of its own ("a deferred fire starts like an
     engine delivery") — one line, every game;
  3. the caller bit and every `REPORT` count: a patched Lync (§1 accepts this for client-stated measures, but §1's
     opening sentence still claims per-build variation);
  4. R18's self-checks (`refusals-rejudged-4.md` R18, adopted narrowed, landing in this file): "one spoof that
     reports the original's values passes kinds 1, 2 and 4 in every Lync game. That spoof is identical across games
     and builds";
  5. canaries (§9, D2 below): the value format is fixed across every Lync game.
- **Why it matters.** A developer deciding whether to rely on a `reported*` fact reads §1 and concludes each
  counter costs a tool per-build work; for these five it costs one change, once, for every Lync game. That is a
  guarantee Lync states and can't keep.
- **Split.** Lync: each measure's section carries one exact line, "Universal counter: yes/no — <the counter>", and
  §1's sentence is limited to the measures of §2 and §4.5 whose inputs are per build, server, session or player.
  Developer: decides whether a fact whose counter is universal informs anything, with the counter stated; where a
  measure has a cost and "no option" (§5 injected frames, R18's "Options. None"), the decision to run it is the
  developer's too, so each gets an on/off option with its cost (they are cheap; the point is that whether a
  universally defeatable report is worth any console line or observer call is the game's call, not Lync's).

## B. Traps and reachability

### B1. Generated traps: tooling removed them, four other places still build them — blocking

- **Where.** `v5-tooling.md` §1.1 "Decision: the generator emits only what the schema declares … *Choice: none
  generated.* … Its name, codec and number are the developer's." Still specifying them: `v5-integrity.md` §2.2 row
  "generated trap names and source codecs | `trap:<namespace>:<k>`"; §3 "Generated traps (`basis` 2 …). Trap k's
  name is the first output of stream `trap:<namespace>:<k>` applied to `v5-tooling.md` §1.1's candidates" (that
  candidate list no longer exists); §3 option row `build.traps`; `v5-tooling.md` §3.4 `trapsIncomplete`,
  `trapNamesShort`, §3.2's fixed-severity list naming both, §5.4 "A generated trap has no site, so it is closed",
  §5.5 `idTableHash` "the generated trap set (count, canonical positions, source codec of each)" and "`lync build`
  writes it without weaving whenever `build.traps` > 0"; `v5.md` §2 differential "with field order, code offsets and
  generated traps on", §4.6 "Generated trap definitions … take up ids among the real ones", §6.2 table row
  "traps, generated traps and reachability"; `v5-3.6-changes-tooling.md` D4 still records "Trap names (§1.1): pieces
  of the namespace's own names" as a decision.
- **What it would do.** Lync picks a trap's name (from a rule GM M15a calls "a rule the lead must fix; unverified
  that any rule yields names a reader cannot separate"), its codec (a real definition's, drawn by stream), its count
  and its place in the id space. Each choice is a judgement about plausibility to a reader. The tooling review
  (`reviews/v5-3.6-tooling.md` B4, M1) showed the names separable by key-set difference against the shipped schema
  module and by naming convention.
- **Split.** Developer: writes each trap as an ordinary definition in the shared schema (name, kind, lane, codec,
  how many) and marks it `Net.x:trap()` on the server view. Lync guarantees exactly: a declared trap passes through
  the schema module, client shard, types, manifest and id permutation by the same emitter as every definition, so
  no output Lync writes separates it (the shared schema module shows nothing; the server view isn't replicated);
  every arrival is dropped, an ask answered `rejected` (indistinguishable from a `validate` refusal), and reported
  `unreachable` with `basis` 1. Delete `basis` 2, `build.traps`, the `trap:` stream, `trapsIncomplete`,
  `trapNamesShort`, the trap set in `idTableHash`, and the four `v5.md` mentions; `basis` then takes 0, 1, 3.

### B2. Inferred reachability turns a text-scan heuristic into a default-on fact named as a conclusion — major

- **Where.** `v5-integrity.md` §3 "Inferred (`basis` 0 …, `check.reachability` true) … reachable when its name
  appears after `.` or `:` … or as a string literal, anywhere in the client scan set. A message of an unreachable
  definition is delivered and reported"; option row `check.reachability` default `true`; §10 `unreachable` known
  causes "a script outside the scanned code (§3), cloned to a client at run time". Same for `basis` 3
  (`v5-tooling.md` §5.4–§5.5: closure is the same scan), whose own `weave.dropClosed` derivation admits "code outside
  the build calling a closed definition".
- **Why it can't be exact.** The trigger is exact relative to the scan; what it *means*, "no unmodified client code
  fires this", is not. The scan set is `v5-tooling.md` §3.3's: scripts in replicating containers, every
  `LocalScript` wherever stored, `RunContext = Client` scripts, `check.clientRoots`. A `ModuleScript` stored in
  `ServerStorage` inside a `Tool` that game code clones into a `Backpack`, required by that tool's `LocalScript`, is
  outside it: the `LocalScript` is scanned, the module that fires `Net.x` isn't. So are `InsertService` assets and
  packages loaded at run time. Whether a game has such code is something only the developer knows; the fact name
  `unreachable` states the conclusion either way.
- **Split.** Lync: computes, per build, the exact list "definitions with no `.name`, `:name` or `"name"` token in
  scan set S", and writes it with S to the manifest and `report.md` (no run-time effect). Developer: chooses which
  of those are reported at run time, by namespace or definition (`check.reachability` default `false`, or a list of
  definitions), knowing their own cloning and asset patterns; or declares them `:trap()` if they are certain. Lync
  then guarantees exactly "a message of a definition the developer opted in, which the scan of S found no token
  for". The evidence name should state that observation (`basis` 0 = "no scanned reference"), not "unreachable";
  the naming pass owns the spelling.

## C. Caller probe, `REPORT` and client self-checks

### C1. One caller bit carries two triggers, and the option that separates them only removes one — major

- **Where.** `v5-integrity.md` §4 "A source not on the list fails the check; a stack with no frame outside Lync
  fails it under `callerProbe.noOuterFrame = "unlisted"` and is not checked under `"ignored"`"; "The caller bit … a
  frame holding the message of any probed call whose source check failed is tagged with u = 1"; option row
  `callerProbe.noOuterFrame` default `"unlisted"`, with the reason "ignoring it by default would leave that route
  unobserved in every game"; `v5.md` §4.5 "Decision: where the caller bit travels".
- **What Lync does.** It merges "the first non-Lync frame's source is not on the definition's list" and "there is
  no non-Lync frame at all" into one bit, then decides by default that the second counts as the first. The second
  has a known cause on every unmodified client that writes `task.spawn(view.fire, view, v)`, `coroutine.wrap`, or a
  signal connected straight to `view.fire` (`client-self-checks.md` U7, false facts). Whether a game does that is
  the game's knowledge; the developer's only lever, `"ignored"`, discards the route instead of separating it, and the
  fact's evidence can't say which trigger fired. That breaks the one-evidence-value-per-trigger rule and makes Lync
  choose coverage over false facts for every game.
- **The list itself is a scan inference** (B2's scan, plus the clone mapping, unverified on Roblox), with listed
  misses: library callbacks, renamed characters, scripts cloned outside the starter containers.
- **Split.** Lync: keeps the bit for exactly one trigger, "the first non-Lync, non-`[C]` frame's source string,
  after the clone mapping, is not among the scanned scripts whose text names the definition", and counts the
  other trigger, "no non-Lync frame on the thread", as its own `REPORT` field beside `identitySucceeded` (zero bytes
  per frame, no extra PRF; it has no definition to name, as identity has none, so a count loses nothing the bit
  gave). Each gets its own client-stated fact. `callerProbe.noOuterFrame` goes: there is nothing left to choose.
  Developer: decides what each fact means for their code, and adds sources the scan can't see (a per-definition
  `callerProbe` source list in `lync.toml`, or `check.clientRoots` widened to name modules), since only they know
  which library modules call `fire`. Lync guarantees the list is exactly the scan's plus theirs, written to the
  manifest.

## D. Decoys and canaries

### D1. "No placement tell" claims more than the mechanism gives, and §8 still describes the refused pool — minor

- **Where.** `v5-integrity.md` §8 "**No placement tell** `[review-2 M4]`"; "**Slots.** Decoys take slots from a pool
  of `maxPerViewer` slots per collection … Real allocation never uses pool slots"; `maxPerViewer` cost "the pool
  takes `maxPerViewer` slots out of `maxRecords`". Against it: `v5-collections.md` §2 "One allocator for records and
  decoys" (R16 landed: the pool marks decoys at balanced accuracy 0.65–1.00, `refusals-rejudged-4.md` R16).
- **What is exact.** Lync can guarantee only what its own mechanism controls: slot draw (one allocator, statistic
  at chance), chunk encoding (full k search, so a re-encoded chunk is as minimal as a shared one), rows riding where
  real rows ride, rewind results of the same shape, and the interest test (`decoyOutsideInterest`). It cannot
  guarantee anything about keys (a decoy keyed by a random integer among `UserId` keys), values (unless
  `decoyFrom` clones them), field distributions, add/remove timing, or position, which are the behaviour's.
- **Split.** Replace "No placement tell" with the exact list above ("Lync adds no tell through slots, encoding,
  rows, rewind or interest"); state that keys, values, timing and placement are the behaviour's; replace the pool
  text with `v5-collections.md` §2's allocator and its `maxRecords` sizing.

### D2. Canary text is generated by Lync in one format for every game — major

- **Where.** `v5-integrity.md` §9 "On each add Lync fills it with 12 random characters from `[A-Za-z0-9]` (strings)
  or 12 random bytes (buffers) … `set` or `patch` of it is `canaryWrite`"; `v5-3.6-inputs.md` §1.2 §9
  `canary.perViewer` "8 shared characters plus a 4-character per-viewer suffix" (`generation-methods.md` M15c).
- **Why it can't be exact.** Whether a canary is echoed depends on it looking like data worth sending: a
  `promoCode` field in a game whose codes are `SUMMER-2026` holds a value no real record has. And since the format
  is Lync's, one filter written once ("drop a string field that is exactly 12 characters of `[A-Za-z0-9]` on every
  record of a collection and that no UI reads", or for `perViewer`, the fixed 8 + 4 split) strips canaries in every
  Lync game: a universal counter (A2).
- **Split.** Developer: supplies the shape, `Net.c:field("promoCode"):canary({ format = fn })` with
  `fn(token: string) -> string` (or a buffer form), returning a value the game would plausibly hold; Lync calls it
  once per add. Lync: draws the token (its alphabet and length, so the chance rate stays exact: 62^−12 per window
  per canary for 12 characters, as today), checks that the formatted value contains the token once and fits
  `maxBytes` (else `valueRefused` at the add), keeps the value-to-slot map keyed by the token, matches inbound text
  by the token as §9 does, and with `perViewer` derives the suffix inside the token. Facts and evidence are
  unchanged; the guarantee reads "an inbound value containing a live token Lync drew for a record sent to that
  player". A missing `format` keeps today's bare token, stated as a format identical across games.

## E. Clock and timing facts

### E1. `clockRate` and `slope` are described as the client's clock rate; the quantity is an offset slope — minor

- **Where.** `v5-integrity.md` §6 step 4 "s = −(that slope), in seconds of client-clock gain per second of server
  `os.clock()`; positive is a fast client clock, negative a slow one"; the code name `clockRate`; §10 row.
- **Why it isn't exact.** What Lync fits is the per-window minimum of arrival − stamp, whose slope is the client's
  clock error rate **plus** the slope of the one-way-delay lower envelope (`clock-facts.md` §U3.1, verified). Its
  own known causes say a 1 s queue built over 60 s "fires for 300 of 300 simulated players". Calling the result a
  clock rate states one of its causes as the measurement.
- **Split.** Lync states the quantity exactly: "`slope`: the negated Theil–Sen slope of the 12 window minima of
  (arrival `os.clock()` − extended stamp), s/s", with "a fast client clock" as one listed cause and "a building or
  draining queue" as another, and the naming pass gives the code a name for the measurement. The threshold stays
  (below, I): `clock.reportSlope` 0.01 bounds the documented 0.6% `GetServerTimeNow()` slew, a physical quantity,
  and the per-player `clockSlope` level already lets a game apply its own threshold, as R38's counter pattern does.

## Blocking

### B1. Regenerate-and-compare doesn't pin its inputs, so `editedShard` (`regenerated` 1) fires on unedited shards

- **Location.** §3.4 `editedShard`, line 259: "with the manifest present and the running generator's `coreDigest`
  equal to the manifest's, regenerating the part at the manifest's `rotationSeed` gives another digest
  (`regenerated` 1) … error; `lync build` and `lync watch` overwrite nothing while it holds"; line 263; §4.1
  `lync build` row "runs `editedShard` before overwriting"; §5.2 "regenerates the shards and compares them with the
  place's"; §1 line 11 "For one schema, one `lync.toml`, one generator and one pair (`buildId`, `rotationSeed`),
  the compiler always produces the same files".
- **The case.** The generated files depend on more than the four inputs line 11 names. The server shard holds the
  reachability lists (line 211: "the server shard's reachability lists don't depend on the host"), traps go only
  into complete namespaces (§3.3 namespace values feed "trap placement"), and `idTableHash` covers the trap set.
  All three are functions of the scanned scripts, and the scan reads either files plus sourcemap or a place (§3.3
  Inputs). Then (reasoned):
  1. A developer builds, edits a `LocalScript` to call a new definition `Net.dash:fire()`, and runs `lync check`.
     Regenerating at the manifest's `rotationSeed` with today's scripts marks `dash` reachable, so the server part
     differs: `editedShard` (`regenerated` 1), a fixed error, though nobody touched a shard.
  2. The developer edits the schema and runs `lync check` before rebuilding: `staleShard` is right, and
     `editedShard` (`regenerated` 1) is raised beside it with a "formatter / merge" cause list. If `lync build` runs
     the same trigger (the §4.1 row says it runs `editedShard` before overwriting, and the §3.4 trigger names no
     command), every rebuild after a schema or script edit is refused: the shards regenerate differently *because*
     the inputs changed, and the build that would fix them won't write. The developer's only exit is deleting the
     shards.
  3. CI (§4.3): step 1 `lync build` has no `--place` (the place doesn't exist yet), so it scans files through the
     sourcemap; step 3 `lync weave` scans the built place. A `LocalScript` inside an `.rbxm` model has no file of
     its own (BC §1.3 lists `.rbxm` contents as instances only), and Rojo turns a `.json` module into a
     `ModuleScript` whose `Source` is generated Luau (Rojo's sync rules; not probed here). Either one changes the
     scan, so the reachability lists `lync weave` regenerates differ from the place's, and every weave of such a
     project fails with `editedShard` (`regenerated` 1) and writes nothing.
- **Fidelity.** BC §3.3: "When the manifest is present, `lync check` can also regenerate every shard at the recorded
  seed with the same generator and compare digests." BC proposed it for `lync check` in CI only, and under
  `lync build` "reported as a warning naming the file, then the shard is overwritten". The design made it
  unconditional and moved it into `lync build`'s gate.
- **Why it matters.** A fixed error with false triggers, under a rule ("no setting makes the finding right or
  wrong", line 196) that offers no way out, on the edit loop and on every woven release.
- **Fix.** (a) State every generation input on line 11: schema sources, `lync.toml`, generator, the pair, and the
  scan result (the client scan set's paths and digests, and whether they came from files or a place). (b) Record
  them in the manifest: an `inputs` object with the SHA-256 of `lync.toml`'s text, of each schema module, and of the
  scan result. Regenerate only when every recorded input equals the live one. Otherwise skip, and say which input
  differs: `staleShard` already covers the schema, and a new fixed-warning code (`regenerateSkipped`, evidence
  `input`) covers the rest. (c) State that `lync build` and `lync watch` run only `regenerated` 0 (the line-1
  digest) before overwriting. (d) `lync weave` takes the scan result recorded in the manifest, or the build must
  scan the same input: §4.3 runs `lync build --place` on a place from an earlier `rojo build`, or `lync weave`
  compares only the parts of the result it doesn't recompute.

### B2. Every woven release fails its own CI drift check

- **Location.** §4.3 step 4 "`lync check --place release.rbxl --format github`: fails on errors"; §5.2 "writes the
  output place with the woven scripts and rewritten shards (the server shard gains the site table and site decoders;
  with `weave.dropClosed`, the client shard loses closed encoders)"; §1.2 `shards` `{ part, path, digest,
  wovenDigest? }`; §3.4 `editedShard`.
- **The case** (reasoned). `release.rbxl` holds the shards `lync weave` rewrote.
  1. §5.2 never says the weaver rewrites line 1. If it doesn't, each rewritten part's line-1 digest no longer
     matches its body: `editedShard` (`regenerated` 0).
  2. If it does, `lync check` still regenerates "the part at the manifest's `rotationSeed`" (line 259), which gives
     the *unwoven* shard. That differs from the woven part: `editedShard` (`regenerated` 1).
  3. The check also rescans the place, now holding woven script text. An inline (W2) site no longer contains
     `.def`, so reachability and closure computed from `release.rbxl` differ from the build's.

  `staleManifest` alone is told about `wovenDigest` (line 261); `editedShard` isn't. Step 4 exits 1 on every woven
  project.
- **Fidelity.** BC §3.2 (table, "Not hashed" column): "If the weaver rewrites the built shard (`weave.dropClosed`),
  it is a Lync writer and rewrites line 1 with the new digest." That sentence was not carried.
- **Fix.** In §5.2: "rewrites line 1 of every part it changes, with the new digest, and records it as
  `wovenDigest`". In §3.4 `editedShard`: "for a part whose manifest entry has `wovenDigest`, `regenerated` 1
  compares the part with `wovenDigest`. `lync weave` already proved regeneration-equality before writing (§5.2)."
  In §3.3: a check over a place that `lync weave` wrote takes reachability and closure from the manifest and doesn't
  rescan woven text. Or change step 4 to check `game.rbxl` (unwoven) and leave the woven place to step 6's
  attestation.

### B3. The weave gate's differential can't pass under the default `weave.ids = "site"`

- **Location.** §5.4 gate row: "differential: for 200 value sets per site, drawn by xorshift32 seeded from the
  site's canonical index, the woven bytes equal the shard encoder's at the build's `rotationSeed` with every
  per-build method on … | `internal` (exit 3)"; §5.1 "the differential of §5.4 makes them write the same bytes";
  §5.5 "A site id's layout is its definition's layout minus the fields the site writes as constants".
- **The case** (reasoned). Under `"site"` (the default, §5.7) a woven site writes its own up-space id, and at a
  literal site it leaves the constant fields off the wire. The client shard's encoder writes the generic id and every
  field. For `Net.buy:fire({ item = "sword" })` the woven bytes are a site id and zero payload bits, and the shard's
  bytes are `buy`'s id and 1 bit. They are never equal, so every site fails and every default woven build exits 3.
  §5.1's claim that play tests (generic ids) and releases (site ids) "write the same bytes" is false for the same
  reason.

  Two more defects in the same row:
  - The site at canonical index 0 seeds xorshift32 with 0. That is its fixed point, so all 200 "value sets" are one
    draw. `v5-integrity.md` §2's zero replacement (`0x9E3779B9`) is applied at line 63 but not here.
  - "With every per-build method on" isn't the build's configuration: a build with `build.offsets = false` would be
    tested against offsets it doesn't use. The per-server permutation, which isn't per-build, is left unfixed.
- **Fidelity.** CIS §7.3: "the differential test … gains a site case: every site's bytes decode on the server to the
  same value as the generic encoding of the same call." The design kept CIS §4.3's pre-site wording ("woven bytes
  equal the shard encoder's") and dropped the site case.
- **Fix.** Gate row: "for `weave.ids = "generic"`, the woven bytes equal the shard encoder's. Otherwise, decoding
  the woven bytes with the server shard's site decoder gives the same value as decoding the shard encoder's bytes
  with the generic decoder, and the woven id is the site table's id for that site. Refused values raise the same
  message. Runs at the build's own settings and `rotationSeed`, with the identity permutation and one fixed
  nonzero permutation seed. A zero xorshift32 seed is replaced by `0x9E3779B9`." In §5.1, replace "write the same
  bytes" with "deliver the same values".

### B4. Generated traps are separable in one build: the shipped schema module lists every real definition

- **Location.** §1.1 trap decision (lines 52–65): "*Problem.* … a name a reader can tell from the real ones at a
  glance removes it"; line 49 "Generated trap definitions are in the runtime table and absent from exported Luau and
  `.d.ts` types"; change record Q#16: stripping the schema module is rejected because "the client shard's view
  already holds every definition name … while it would remove the bait `:trap()` relies on".
- **The case** (reasoned). The example layout maps `namespace.schema = "src/shared/Net/schema.luau"` into
  `ReplicatedStorage`, and the client shard requires it in Studio for `staleShard` (`v5.md` §3.2). GM M15a puts
  traps "never [in] the shared schema module". So an API driver runs
  `require(ReplicatedStorage.Net.schema)` and `require(ReplicatedStorage.Net.client)` and takes the set difference
  of their keys: that difference is exactly the generated traps, in one build, without looking at a name. The rule's
  care over names buys nothing while the schema module replicates. The Q#16 rejection reasons only about declared
  `:trap()` bait, where the schema helps; for generated traps the schema is the oracle.
- **Why it matters.** `build.traps` exists to price API drivers that browse the namespace (GM M15a). That is
  precisely the class this defeats, and an API driver already has `require`.
- **Fix.** Decide it in §1.1 as a constraint of `build.traps`. Under `build.traps` > 0, `namespace.schema` must map
  outside every replicating container (`configRange`), and the client shard's Studio `staleShard` check moves to the
  server shard, which can read `ServerStorage`. Or state in §1.1 and in `v5-integrity.md` §3 that generated traps
  price only drivers that don't read the schema module, and drop the name rule's indistinguishability goal. Revisit
  Q#16 with this case; the change record should carry the trade-off.

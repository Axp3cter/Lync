## Blocking

### B1. Regenerate-and-compare doesn't pin its inputs, so `editedShard` (`regenerated` 1) fires on unedited shards

- **Location.** §3.4 `editedShard`, line 259: "with the manifest present and the running generator's `coreDigest`
  equal to the manifest's, regenerating the part at the manifest's `rotationSeed` gives another digest
  (`regenerated` 1) … error; `lync build` and `lync watch` overwrite nothing while it holds"; line 263; §4.1
  `lync build` row "runs `editedShard` before overwriting"; §5.2 "regenerates the shards and compares them with the
  place's"; §1 line 11 "For one schema, one `lync.toml`, one generator and one pair (`buildId`, `rotationSeed`),
  the compiler always produces the same files".
- **The case.** The generated files depend on more than the four inputs line 11 names. The server shard holds the
  reachability lists (line 211: "the server shard's reachability lists don't depend on the host"), traps go only
  into complete namespaces (§3.3 namespace values feed "trap placement"), and `idTableHash` covers the trap set.
  All three are functions of the scanned scripts, and the scan reads either files plus sourcemap or a place (§3.3
  Inputs). Then (reasoned):
  1. A developer builds, edits a `LocalScript` to call a new definition `Net.dash:fire()`, and runs `lync check`.
     Regenerating at the manifest's `rotationSeed` with today's scripts marks `dash` reachable, so the server part
     differs: `editedShard` (`regenerated` 1), a fixed error, though nobody touched a shard.
  2. The developer edits the schema and runs `lync check` before rebuilding: `staleShard` is right, and
     `editedShard` (`regenerated` 1) is raised beside it with a "formatter / merge" cause list. If `lync build` runs
     the same trigger (the §4.1 row says it runs `editedShard` before overwriting, and the §3.4 trigger names no
     command), every rebuild after a schema or script edit is refused: the shards regenerate differently *because*
     the inputs changed, and the build that would fix them won't write. The developer's only exit is deleting the
     shards.
  3. CI (§4.3): step 1 `lync build` has no `--place` (the place doesn't exist yet), so it scans files through the
     sourcemap; step 3 `lync weave` scans the built place. A `LocalScript` inside an `.rbxm` model has no file of
     its own (BC §1.3 lists `.rbxm` contents as instances only), and Rojo turns a `.json` module into a
     `ModuleScript` whose `Source` is generated Luau (Rojo's sync rules; not probed here). Either one changes the
     scan, so the reachability lists `lync weave` regenerates differ from the place's, and every weave of such a
     project fails with `editedShard` (`regenerated` 1) and writes nothing.
- **Fidelity.** BC §3.3: "When the manifest is present, `lync check` can also regenerate every shard at the recorded
  seed with the same generator and compare digests." BC proposed it for `lync check` in CI only, and under
  `lync build` "reported as a warning naming the file, then the shard is overwritten". The design made it
  unconditional and moved it into `lync build`'s gate.
- **Why it matters.** A fixed error with false triggers, under a rule ("no setting makes the finding right or
  wrong", line 196) that offers no way out, on the edit loop and on every woven release.
- **Fix.** (a) State every generation input on line 11: schema sources, `lync.toml`, generator, the pair, and the
  scan result (the client scan set's paths and digests, and whether they came from files or a place). (b) Record
  them in the manifest: an `inputs` object with the SHA-256 of `lync.toml`'s text, of each schema module, and of the
  scan result. Regenerate only when every recorded input equals the live one. Otherwise skip, and say which input
  differs: `staleShard` already covers the schema, and a new fixed-warning code (`regenerateSkipped`, evidence
  `input`) covers the rest. (c) State that `lync build` and `lync watch` run only `regenerated` 0 (the line-1
  digest) before overwriting. (d) `lync weave` takes the scan result recorded in the manifest, or the build must
  scan the same input: §4.3 runs `lync build --place` on a place from an earlier `rojo build`, or `lync weave`
  compares only the parts of the result it doesn't recompute.

### B2. Every woven release fails its own CI drift check

- **Location.** §4.3 step 4 "`lync check --place release.rbxl --format github`: fails on errors"; §5.2 "writes the
  output place with the woven scripts and rewritten shards (the server shard gains the site table and site decoders;
  with `weave.dropClosed`, the client shard loses closed encoders)"; §1.2 `shards` `{ part, path, digest,
  wovenDigest? }`; §3.4 `editedShard`.
- **The case** (reasoned). `release.rbxl` holds the shards `lync weave` rewrote.
  1. §5.2 never says the weaver rewrites line 1. If it doesn't, each rewritten part's line-1 digest no longer
     matches its body: `editedShard` (`regenerated` 0).
  2. If it does, `lync check` still regenerates "the part at the manifest's `rotationSeed`" (line 259), which gives
     the *unwoven* shard. That differs from the woven part: `editedShard` (`regenerated` 1).
  3. The check also rescans the place, now holding woven script text. An inline (W2) site no longer contains
     `.def`, so reachability and closure computed from `release.rbxl` differ from the build's.

  `staleManifest` alone is told about `wovenDigest` (line 261); `editedShard` isn't. Step 4 exits 1 on every woven
  project.
- **Fidelity.** BC §3.2 (table, "Not hashed" column): "If the weaver rewrites the built shard (`weave.dropClosed`),
  it is a Lync writer and rewrites line 1 with the new digest." That sentence was not carried.
- **Fix.** In §5.2: "rewrites line 1 of every part it changes, with the new digest, and records it as
  `wovenDigest`". In §3.4 `editedShard`: "for a part whose manifest entry has `wovenDigest`, `regenerated` 1
  compares the part with `wovenDigest`. `lync weave` already proved regeneration-equality before writing (§5.2)."
  In §3.3: a check over a place that `lync weave` wrote takes reachability and closure from the manifest and doesn't
  rescan woven text. Or change step 4 to check `game.rbxl` (unwoven) and leave the woven place to step 6's
  attestation.

### B3. The weave gate's differential can't pass under the default `weave.ids = "site"`

- **Location.** §5.4 gate row: "differential: for 200 value sets per site, drawn by xorshift32 seeded from the
  site's canonical index, the woven bytes equal the shard encoder's at the build's `rotationSeed` with every
  per-build method on … | `internal` (exit 3)"; §5.1 "the differential of §5.4 makes them write the same bytes";
  §5.5 "A site id's layout is its definition's layout minus the fields the site writes as constants".
- **The case** (reasoned). Under `"site"` (the default, §5.7) a woven site writes its own up-space id, and at a
  literal site it leaves the constant fields off the wire. The client shard's encoder writes the generic id and every
  field. For `Net.buy:fire({ item = "sword" })` the woven bytes are a site id and zero payload bits, and the shard's
  bytes are `buy`'s id and 1 bit. They are never equal, so every site fails and every default woven build exits 3.
  §5.1's claim that play tests (generic ids) and releases (site ids) "write the same bytes" is false for the same
  reason.

  Two more defects in the same row:
  - The site at canonical index 0 seeds xorshift32 with 0. That is its fixed point, so all 200 "value sets" are one
    draw. `v5-integrity.md` §2's zero replacement (`0x9E3779B9`) is applied at line 63 but not here.
  - "With every per-build method on" isn't the build's configuration: a build with `build.offsets = false` would be
    tested against offsets it doesn't use. The per-server permutation, which isn't per-build, is left unfixed.
- **Fidelity.** CIS §7.3: "the differential test … gains a site case: every site's bytes decode on the server to the
  same value as the generic encoding of the same call." The design kept CIS §4.3's pre-site wording ("woven bytes
  equal the shard encoder's") and dropped the site case.
- **Fix.** Gate row: "for `weave.ids = "generic"`, the woven bytes equal the shard encoder's. Otherwise, decoding
  the woven bytes with the server shard's site decoder gives the same value as decoding the shard encoder's bytes
  with the generic decoder, and the woven id is the site table's id for that site. Refused values raise the same
  message. Runs at the build's own settings and `rotationSeed`, with the identity permutation and one fixed
  nonzero permutation seed. A zero xorshift32 seed is replaced by `0x9E3779B9`." In §5.1, replace "write the same
  bytes" with "deliver the same values".

### B4. Generated traps are separable in one build: the shipped schema module lists every real definition

- **Location.** §1.1 trap decision (lines 52–65): "*Problem.* … a name a reader can tell from the real ones at a
  glance removes it"; line 49 "Generated trap definitions are in the runtime table and absent from exported Luau and
  `.d.ts` types"; change record Q#16: stripping the schema module is rejected because "the client shard's view
  already holds every definition name … while it would remove the bait `:trap()` relies on".
- **The case** (reasoned). The example layout maps `namespace.schema = "src/shared/Net/schema.luau"` into
  `ReplicatedStorage`, and the client shard requires it in Studio for `staleShard` (`v5.md` §3.2). GM M15a puts
  traps "never [in] the shared schema module". So an API driver runs
  `require(ReplicatedStorage.Net.schema)` and `require(ReplicatedStorage.Net.client)` and takes the set difference
  of their keys: that difference is exactly the generated traps, in one build, without looking at a name. The rule's
  care over names buys nothing while the schema module replicates. The Q#16 rejection reasons only about declared
  `:trap()` bait, where the schema helps; for generated traps the schema is the oracle.
- **Why it matters.** `build.traps` exists to price API drivers that browse the namespace (GM M15a). That is
  precisely the class this defeats, and an API driver already has `require`.
- **Fix.** Decide it in §1.1 as a constraint of `build.traps`. Under `build.traps` > 0, `namespace.schema` must map
  outside every replicating container (`configRange`), and the client shard's Studio `staleShard` check moves to the
  server shard, which can read `ServerStorage`. Or state in §1.1 and in `v5-integrity.md` §3 that generated traps
  price only drivers that don't read the schema module, and drop the name rule's indistinguishability goal. Revisit
  Q#16 with this case; the change record should carry the trade-off.

## Major

### M1. The trap-name rule produces names separable at a glance for common conventions, and redraws them every release

- **Location.** §1.1 lines 57–65: "the pieces are lowercased … every ordered pair of different pieces written as the
  first followed by the second with its first letter uppercased … drawn under `rotationSeed`".
- **The case** (*checked*: the rule as written, run on Luau 0.740 in a scratch script):
  - `{ BuyItem, ChatMessage, Strike }` gives 25 candidates: `buy buyChat buyItem buyMessage buyStrike chat chatBuy
    chatItem …`. Every real name is PascalCase and every candidate is camelCase or lowercase, so the traps can be
    told apart at a glance. PascalCase is the common naming for Roblox remotes.
  - `{ buy_item, chat_message }` gives `buy_itemChat_message` and `chat_messageBuy_item`: two styles mixed in one
    name.
  - `{ buy, chat }` gives `buyChat` and `chatBuy`. With n pieces there are n singles against n(n − 1) pairs, so
    nearly every trap is a compound, while real names are often one word, and reversed pairs (`itemBuy`) read
    unlike any real name.
  - With `build.seed = "release"` the names are redrawn every run: a reader with two releases keeps the keys present
    in both and drops the traps (reasoned).
  - The candidate set excludes definition names only, not other keys the runtime namespace table holds.
- **Fidelity.** GM M15a left the rule to the lead ("unverified that any rule yields names a reader cannot
  separate"). The design marks indistinguishability unverified, but these separations need no study; they follow
  from the rule's own text.
- **Fix.** Render each candidate in the convention of the definition its first piece came from (initial case,
  separator `_` or none). Draw singles and pairs in proportion to the one-piece and multi-piece real names. Exclude
  every key of the runtime namespace table. Either draw names under a value that survives releases (a CI-held
  secret named in §2 with type, range, default and cost), or state the cross-release limit in §1.1, in
  `v5-integrity.md` §3 and in `report.md`. B4 comes first: while the schema module replicates, no name rule helps.

### M2. `idTableHash` "0 when unwoven, so G7 is unchanged" is false; and `"definition"` mode isn't hashed

- **Location.** §5.5 lines 518–519: "It is 0 with no site ids and no generated traps, so `v5.md` §4.10's G7 and every
  unwoven `HELLO` are unchanged"; change record Conflict 2.1 #11, Needs elsewhere (wire): "`idTableHash` (u32,
  protocol version 2)".
- **The case** (reasoned).
  - G7 is "untagged `HELLO` … version 1" (`v5.md` §4.10), and §4.6 fixes `HELLO`'s fields. A u32 field added at
    protocol version 2 changes every `HELLO`, whatever its value: the version byte becomes 2 and 32 bits are
    appended. G7's bytes change. If the field were sent only when nonzero, a flag bit would still change G7.
  - "0 with no site ids" leaves `weave.ids = "definition"` with `build.traps = 0` at 0. Take a definition-woven
    client against an unwoven server at one fixed seed: both send 0, the up spaces differ by D ids, and frames decode
    wrongly with no refusal. That is the failure the decision's own problem statement names.
  - A nonzero table can also hash to 0 (2^-32 per build).
- **Fidelity.** BC §4.1 (for the same shape of field): "+32 bits per `HELLO` … golden vector G7 (`HELLO`, `v5.md`
  §4.10) changes." GM M16: "It is 0 when there are no site ids and no generated traps, so G7 and every unwoven
  `HELLO` stay as they are." Conflict 2.1 #11 was settled for GM without addressing BC's G7 point.
- **Fix.** "`idTableHash` is 0 exactly when the id mode is `"generic"` and no trap is generated; otherwise the hash,
  with 0 replaced by 1." Needs elsewhere (wire): "G7 is re-cut at protocol version 2 with `idTableHash` 0; the
  version-1 vector is retired."

### M3. At a fixed `build.seed`, nothing pins the generator options, so two configurations pair silently

- **Location.** §5.5 line 515: "Not covered: values `buildId` pins (field order, tag constants, offsets)"; §3.4
  `unpairedShard` compares "one `buildId`, one generator version and one schema hash"; change record Needs
  elsewhere (integrity): "define `buildId` for a fixed `build.seed`".
- **The case** (reasoned). `build.seed = "00000000000000ff"` (the stable-diff use of BC §4.2). Developer A builds
  with `build.offsets = true` and commits the client shard; developer B builds with `build.offsets = false` and
  commits the server shard (Team Create Drafts commits per script, a known cause in line 260). Both shards carry one
  `buildId`, one generator and one schema hash, so `unpairedShard` is silent. The `idTableHash` is 0 on both sides,
  so `HELLO` matches. The server then subtracts offsets the client never added: values are delivered wrong, with
  no fact. `build.tagRounds` gives the same case: a refused tag on every frame, reported as `tagMismatch`, which
  names no build cause.
- **Fix.** In §5.5, cover only what `buildId` provably pins, and have Needs elsewhere (integrity) require: "for a
  fixed `build.seed`, `buildId` is the low 32 bits of HalfSipHash-2-4 (zero key) over the seed and the canonical
  text of every `[build]` key", so any option difference changes `buildId` and both `unpairedShard` and `HELLO` see
  it.

### M4. `--published` can't detect added scripts, matches by non-unique paths, and compares against file text, not the published `Source`

- **Location.** §4.3 lines 389–396: "The task reads the `Source` of each shard part, `wovenScripts` entry and
  `scripts` entry by path … returns `{ path, digest }`"; §1.2 `scripts`: "read from the place with `--place`, else
  from the files the sourcemap maps"; §3.4 `publishedScriptChanged` `change` 2 "added"; `publishedShardDiffers`
  evidence `foundBuild`; D1 instance paths.
- **The case** (reasoned).
  1. A collaborator publishes from Studio with a new `LocalScript`. The task reads only paths the manifest lists, so
     it never sees the new script: `change` 2 can't occur.
  2. Instance paths aren't unique. Thirty `Workspace.Zombie.AI` scripts (`Workspace` replicates, so all are in the
     client scan set), or two `StarterPack.Sword.Client`, give one path for many scripts. "By path" reads one of
     them, and `{ path, digest }` can't say which.
  3. CI step 1 has no place, so `scripts` comes from files. A script inside an `.rbxm`, or a Rojo `.json` module,
     has no file whose text equals its published `Source`. Every release then reports `publishedScriptChanged`
     (or, through case 1, misses it).
  4. `foundBuild` needs the body's `buildId`, but the task returns only `{ path, digest }`.
- **Fidelity.** R11: "The task walks the same scan set, hashes each script's `Source` … and returns `{path,
  digest}`." The design replaced the walk with reads by path.
- **Fix.** The task walks the published version's client scan set, plus the shard and `wovenScripts` paths, and
  returns `{ path, ordinal, digest, buildId? }`. `ordinal` is the instance's index among same-path siblings in
  `GetDescendants` order, and `buildId` comes only for shard parts, read from the body constant. Extend D1 to define
  `ordinal` for every manifest path list. `scripts` is always taken from a place: `lync weave` rewrites it (D13), and
  an unwoven project passes `--place game.rbxl` to `--published` as the reference for script digests.

### M5. `stagedReplicated` lists six containers; other replicating services pass, and the key table says something else

- **Location.** §3.4 `stagedReplicated`: "maps to `ReplicatedStorage`, `ReplicatedFirst`, `Workspace`, `StarterGui`,
  `StarterPack` or `StarterPlayer`"; §2 `namespace.staged` cost: "must map under `ServerStorage`"; `foreignRemote`
  `replicates`: "1 when its top-level service replicates to clients, 0 for `ServerScriptService` and
  `ServerStorage`".
- **The case** (*checked*, API dump 0.741.19). `Lighting`, `SoundService`, `Teams`, `MaterialService` and
  `TextChatService` carry no `NotReplicated` tag; `ServerStorage`, `ServerScriptService` and `Chat` do. A staged
  schema mapped to `Lighting.Unreleased.schema` replicates to every client, yet raises no `stagedReplicated`: the
  leak the code exists for. In the other direction, `replicates` gives 1 for a remote under `Chat`, which is tagged
  `NotReplicated`.
- **Fidelity.** The six-container list is IR §12.3's verbatim; the fault is inherited, but the key table's "must
  map under `ServerStorage`" already states the right rule.
- **Fix.** `stagedReplicated`: "maps anywhere other than under `ServerStorage` or `ServerScriptService`". Evidence
  `container` keeps the service name. `replicates`: "0 when the top-level service has the reflection tag
  `NotReplicated`, else 1" (rbx-dom's reflection database carries the tags). Apply the same set to §3.3's
  "replicating containers".

### M6. Any script can exempt itself from every scan by copying Lync's runtime header

- **Location.** §3.3 line 220: "Both exclude Lync's own package (the subtree of any `ModuleScript` whose first line
  is `-- Lync <version> runtime`)"; D10.
- **The case** (reasoned). A Toolbox model ships a `ModuleScript` whose line 1 is `-- Lync 5.0.0 runtime`, with
  `Instance.new("RemoteEvent")` and a `:FireServer(` below it. `remoteCreation`, `rawRemote`, `dynamicAccess`,
  reachability, `stagedReferenced` and `stagedNameLeak` all skip its subtree. The audit BC §1.1 describes ("auditing
  a package") misses exactly the hostile package. A legitimate copy of an older runtime vendored by another package
  is skipped too, though its code isn't this build's.
- **Fix.** Identify Lync's package by content: the generator carries the SHA-256 of each runtime file of its
  version. A subtree is excluded only when every module in it matches. A header-bearing module that doesn't match
  is scanned and listed (new code `lyncHeaderMismatch`, fixed warning, evidence `path`).

### M7. Per-player variant outputs are unspecified

- **Location.** §1 outputs table (client and server shard, `.d.ts`, manifest, report); §2 lines 159–163 index
  `build.playerVariants`; §5.6 restricts scope. Nothing else.
- **The case.** GM M7: "`lync build` writes N client variant `ModuleScript`s to `ServerStorage`." With
  `build.playerVariants = 16` the design doesn't say:
  - which files or instances are written, at what path, with what line 1;
  - whether each carries a digest, and whether `editedShard`, `unpairedShard`, `staleManifest` and `--published`
    cover them;
  - whether they are parts under §1.1's 200,000-byte cap (upstream scope: N × 356 B per definition, 1.1 MB at
    200 × 16, GM M7);
  - whether the scans exclude them as Lync outputs;
  - what the manifest records per variant.

  The integrity unit owns the mechanism, but the outputs are tooling's.
- **Fix.** Add an outputs row "client variant modules (`build.playerVariants` > 1)", with path rule, part rule and
  line 1; add manifest `namespaces.<name>.variants: [{ index, path, digest }]`; name them in each drift code's
  trigger and in §3.3's exclusion; list them in the `--published` task.

### M8. The Lune host's draw is unspecified, and no output records whether a build's `rotationSeed` is private

- **Location.** §4.1 Entropy (lines 337–340): "No OS entropy source in Lune is verified (§8); until one is, builds
  from the Lune host have a public-quality `rotationSeed`"; §4.2 "draws a new `buildId` and `rotationSeed` from
  `HttpService:GenerateGUID()`".
- **The case.**
  - Milestone 3 builds on Lune (line 4), so every build until milestone 6 is in this state. The design never says
    what Lune draws from: "never from a clock-seeded generator" binds only the Rust host.
  - Nothing in the manifest or report tells a developer, or `lync check`, which kind of seed a release has.
  - `GenerateGUID` returns `xxxxxxxx-xxxx-4xxx-yxxx-…`: if it is a version-4 UUID (unverified), 6 of its 128 bits
    are fixed. Taking the first 16 hex digits gives a seed with a constant `4` nibble, and deriving `buildId` from
    the same GUID bits would publish part of the secret. The design specifies neither split.
- **Fix.**
  - State Lune's draw: for example, `process.exec` of the OS's random source, verified in §8, or Luau's `math.random`
    marked public-quality.
  - Add manifest `rotation.entropy` (`"os"`, `"guid"` or `"public"`) and a report line.
  - Specify the plugin's draw: two GUIDs, one for each value; skip the version and variant nibbles; take
    `rotationSeed` from 16 hex digits of the first GUID and `buildId` from 8 of the second.

### M9. One PVS module per bake breaks the `Source` cap the design uses for shards; cell count is unbounded

- **Location.** §2 `pvs.cell` 8–256, cost "a table of N²/8 B: 128 KiB at 1,024 cells"; `pvs.output` "a server-only
  module … the table's size × 4/3 (base64) in the place"; §1.1 parts: "`Source` set the ordinary way is capped at
  200,000 characters".
- **The case** (arithmetic from the table's own formula). The default cell gives 1,024 cells on a 1,024-stud map:
  131,072 B, or 174,763 base64 characters, which fits. A 2,048-stud map at the default cell has 4,096 cells: 2 MiB,
  or 2,796,203 characters, 14 times the cap §1.1 relies on. A 4,096-stud map at cell 8 has 262,144 cells, beyond
  the runtime's `pvs` range of N ≤ 65,536 (IR §10), and an 8 GiB table. No range rejects it.
- **Fix.** Split the table into child modules of at most 200,000 bytes of `Source`, as §1.1 does for shards, with a
  line-1 digest for each. Add a `configRange` rule "N ≤ 65,536" (map side from the place's extents); state the bake
  time and table size at the derived N in the report.

### M10. Requests are never woven, so no request definition can close

- **Location.** §5.3 "It is **woven** when it is a statement"; §3.4 `weaveNotStatement` known causes: "every request
  (`invoke` yields and returns a result)".
- **The case** (reasoned). W3 is "a call into the shard's scalar entry with the fields as arguments": a function
  call, which is valid in expression context and splices line for line. Take
  `local ok = Net.buy:invoke({ item = "sword" })`: written as `local ok = Internal.buy("sword")` it keeps its line.
  Only inline W2 and the folded literal form need statement context. The rule nonetheless leaves every `invoke`
  open. Because `buy` keeps an unwoven site, it never closes, so it gets no site ids and no closed-generic fact.
  Each such site also raises a default `"warn"` that no code change can clear.
- **Fidelity.** CIS §4.1: "Requests (`invoke`) are expressions and yield; the prototype leaves them on the shard; a
  helper-call form (§5) can weave them."
- **Fix.** "Woven when … it is a statement, or, for the W3 form, any expression"; `weaveNotStatement`'s trigger
  becomes "an expression-context site whose definition would take W2 or a literal fold", and requests take W3.

### M11. A definition whose generated code alone exceeds 200,000 bytes has no rule

- **Location.** §1.1 Parts: "split, by sorted definition name, into child modules"; generator invariants (lines
  37–43).
- **The case** (reasoned). Splitting by definition can't divide one definition. `v5.md` §3.4 allows names up to
  65,535 bytes and a worst-case message up to 16,000 B, so a single-field enum of several thousand 30-byte item
  names, or a record of 2,000 one-bit fields, generates more than 200,000 bytes for one definition. Nothing in the
  invariants catches it, so a part over the reported cap is written.
- **Fix.** Add to the invariants "each part ≤ 200,000 bytes", with a declaration code
  (`definitionTooLarge`, evidence `bytes`, at the schema line). Or move a definition's lookup tables into data
  parts.

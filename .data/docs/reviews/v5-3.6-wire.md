## 2. Checked and holds

- **Hash bound, 5 / 3 per frame.** No sequence I could build exceeds it. Paths tried: a failing reliable frame (5
  candidates, one input each, since `caller` is read in clear); a failing unreliable frame (3 extensions); a pending
  `REKEY` (one key only); a client that never switches (no second key); variants (table lookups, not hashes); a
  budget-refused frame (never hashed); a frame first tried as untagged `HELLO`s (decoded, not hashed, then at most 5);
  a tag-accepted frame that is then malformed (one hash, e already moved); split frames (each part is its own frame).
- **Keyless acceptance, re-derived.** 5 × 60 + 3 × 120 = 660 candidates/s; 2^32 / 660 s = 75.3 days; at the range
  maxima 8,000/s, 6.21 days; failures 180 frames/s × 6.51 × 10^6 s = 1.17 × 10^9. 16 bits: 99.3 s, 17,900
  occurrences. Two and four inputs: 37.7 days and 3.1 days, 37.3 h at the maxima. `tagVariant` at N = 256: 7.06 h,
  4.58 × 10^6 occurrences. All as stated in §4.5 (not in `v5-integrity.md`, m3).
- **Tag CPU bound.** (5 × 8,192 + 3 × 16,384) × 4.0 ns + 660 × 196 ns = 0.49 ms/s; unrolled 0.28; accepted 0.13 and
  0.08. Correct.
- **Can a client desynchronise an unmodified client's count?** No: the server's e is per player and only that
  player's own remote calls reach it, so a modified client can only move its own e. Budget refusals of an unmodified
  client's tagged frames keep e in step, as stated. The one hole is the untagged case (m1).
- **Rekey bound.** 60/9 = 6.7 `REKEY`/s, ⌊240/9⌋ = 26 from the burst, 10 B each: correct as written (B1's fix moves
  it to 7.5/s and 30).
- **M3, first row against 0.** The forger case is right: against c the first residual is q, the block equals the
  identity's, and three messages escape every offset. Against 0, a forger can write differences without c but every
  absolute value still needs it, including mode 0 (residual 0 means w = 0, so q = −c mod n). Constant columns lose
  mode 0 under offsets (the 14.0 → 22.1 bit cost) and nothing else.
- **M8 key.** The key is a 64-bit unknown without S, with or without `WELCOME`; the derivation inputs are domain
  separated by their last byte and their lengths. The permutation is not protected as stated (M2).

## 3. Blocking

### B1. A `REKEY` that doesn't take ends the reliable lane for the session

- **Severity:** blocking.
- **Location:** §4.5 Rekey: "The `REKEY` is pending until a reliable frame is accepted under its key; a `desync`
  while one is pending sends none (`rekeySent` 0)"; §4.9 "pending `REKEY` | at most one per player".
- **Case 1, a second raise burst.** e = 0 after the `REKEY`. The unmodified client decodes it, restarts its count at
  0, and `FireServer` raises on its next 5 frames (counts 0–4), the very cause §7.3 gives for the first `desync`.
  Frame 5 arrives; candidates 0–4 fail, and so does every later frame. After 8 failures `desync` fires with a
  `REKEY` pending, so none is sent. Nothing ever clears the pending flag, since no frame can be accepted again.
- **Case 2, a refused `REKEY` frame.** The client refuses the downstream frame holding `REKEY` by any §4.8 rule (a
  Lync bug, or M1's chunk of a namespace the client refused). It keeps the old key; the server verifies only the new
  one; same end state.
- **What the unmodified client sees:** nothing. Every reliable event is dropped, every `invoke` ends `timeout`, its
  `REPORT`s and `BEACON`s never land, while unreliable traffic works (it does verify under the new key). The server
  sees `desync` with `rekeySent` 0 every 8 frames for the rest of the session. Draft 3.5's spacing retried after 60
  s; 3.6 never does, and §7.3's cause text ("every later frame fails until `REKEY`") no longer has an end.
- **Fix (exact, uses a field already in clear).** `rcv` is in the header before the tag. Record the frame index F
  of the frame that carried the pending `REKEY`. Rule: "a `desync` while a `REKEY` is pending sends a new one, which
  replaces it, when the extended `rcv` of the eighth failing frame is at least F; else none". With `rcv` < F the
  failures are old-key frames still in flight (no resend, as now); with `rcv` ≥ F the client has received the
  `REKEY`'s frame and still fails, which is cases 1 and 2. A modified client that overstates `rcv` gains one
  `REKEY` per 8 failing frames instead of per 9 frames: 7.5/s sustained and 30 from the burst at the defaults
  (restate §4.5's bound and §4.9's row). Add `rcv` ≥ F as `desync` evidence (`rekeyReceived` 0/1).

## 4. Major

### M1. A generated view refusing `layout` 1 leaves the server sending, and every frame with that namespace is lost

- **Severity:** major.
- **Location:** §4.5 Runtime-path layout: "a client shard whose `WELCOME` carries `layout` 1 reports
  `schemaMismatch` natively and drops that namespace's sends, as on `MISMATCH`; so a seed-0 shard against a
  runtime-path server never decodes a layout it doesn't hold"; §4.8 rule 7 "a chunk for a namespace not welcomed".
- **Case.** An identity-build client shard (`buildId` 0) meets a runtime-path server with `layout.vary` on. `HELLO`
  matches (both send `buildId` 0, same hash), so the server answers `WELCOME` with `layout` 1 and treats the
  namespace as welcomed. Unlike `MISMATCH`, nothing tells the server the client refused it, so it keeps writing that
  namespace's runs and state chunks into the player's reliable frames. The client decodes such a chunk for a
  namespace it did not accept: rule 7, and the whole frame is refused, including every other namespace's events,
  answers and collection writes in it, and any `REKEY` (which then triggers B1 case 2).
- **Why it matters.** §3.2 presents this as the safe outcome of mixing paths ("refuses the namespace itself");
  it in fact diverges the client on every namespace that shares a frame with it, silently on the server.
- **Fix.** Make the refusal two-sided at the handshake, where the other identity fields are checked: `HELLO` gains
  `path` u1 (0 generated view, 1 runtime path), and a server with `layout.vary` on answers a `path` 0 `HELLO` with
  `MISMATCH` (`schemaMismatch` evidence `layoutDiffers` 1). Then the client never receives `layout` 1 and §4.5's
  "a generated view can't follow it" bullet becomes the server's rule. Cost 1 bit per `HELLO`; G7 changes.

### M2. The 32-bit permutation seed falls in seconds, not 6.2 hours, and one space gives all three

- **Severity:** major (a stated security cost wrong by three orders of magnitude, on which a decision rests).
- **Location:** §4.5: "a capture holder without S can instead search it against canonical decode, 2^32 × 200 ids ×
  26 ns = 6.2 h of one core per server for 200 ids `[refusals-rejudged-3 R2]`. That is kept: Fisher–Yates under
  xorshift32 has only 2^32 permutations whatever the seed's width".
- **Case.** The figure prices each candidate as a full 200-id table build. A search needs no table: Fisher–Yates
  runs from the last index down, so after one xorshift step the wire id of canonical id n − 1 is j =
  xorshift32(seed) mod n. With one known (canonical, wire) pair for the last id, a wrong candidate is rejected after
  one step with probability (n − 1)/n. Measured: 3.64 ns per candidate native, 2^32 candidates in 15.6 s on one core
  (89 ns, 384 s interpreted), with the expected 1/200 survivors checked by a second pair
  (`perm_search.luau`, `review.out`). Where does the pair come from? §4.5 itself says "a byte tool on the client
  learns wire ids from its own sends": the up space. And the three spaces' xorshift seeds are P ⊕ h ⊕ 1, P ⊕ h ⊕ 2,
  P ⊕ h ⊕ 3 with h the public seed-0 hash, so finding the up-space seed gives P, and with it the down and
  collections tables. So M8 protects the permutation against no on-client tool, and against a capture holder with
  one known pair only for about 16 s.
- **On the stated reason.** "Only 2^32 permutations whatever the seed's width" is a property of the generator the
  design chose, not a constraint: the permutation is built once per namespace per server (21 ns per id), so a
  generator with 64-bit state seeded from the full 64-bit derivation output costs nothing per frame.
- **Fix (either).** (a) State the true figure and its consequence: "with one known (canonical, wire) pair, 2^32
  one-step candidates, about 16 s of one core native; one space's seed gives the other two; so M8 protects the
  key, not the permutation". (b) Keep the protection M8 meant: seed Fisher–Yates from the 64-bit output (for
  example j = HalfSipHash-1-3 under that output over the step index i, mod (i + 1)), so the search is 2^64; cost
  122–196 ns per id native (the tag's measured fixed cost) once per namespace per server, PERM and DERIVE re-cut.
  Either way, mix the space number into the derivation input (‖ `02` ‖ space) rather than XOR-ing it into one seed,
  so one space's table does not give the others.

### M3. Column decode accepts several residuals for one code: canonical decode has a hole

- **Severity:** major (a byte-level rule of §4.8, which claims one encoding per value up to the listed free
  choices).
- **Location:** §4.3 "Decode wraps before it adds: if r > top − previous the code is previous + (r − n), if r < lo −
  previous it is previous + (r + n), else previous + r"; §4.8 rule 2 and the free-choice list ("Column mode, k, and
  frame-of-reference base … and width").
- **Case.** The encoder's residual lies in [−⌊n/2⌋, ⌈n/2⌉ − 1], but the decoder never checks it. With n = 4 and
  previous 0, zigzags 0, 7 and 8 (r = 0, −4, 4) all decode to code 0, by the formula as written; the same holds for
  every code of every interval tried (n = 2, 4, 101; `residual_canon.luau`). A bool column (n = 2) accepts true
  after false as zigzag 1 (r = −1, the encoder's) and zigzag 2 (r = 1). Values outside the interval still fail
  rule 3, but every in-interval value has at least three accepted residuals, none listed as a free choice.
- **Why it matters.** §3.3 defines canonical decode as refusing "accepted codes the encoder never produces";
  §4.5's untagged-frame test and the M2 search filter both lean on canonical decode; and the property tests can't
  catch a second form that the text accepts.
- **Fix.** One clause in rule 2: "a column residual whose zigzag is n or more, n the column's interval size (§4.3)".
  Zigzag maps [−⌊n/2⌋, ⌈n/2⌉ − 1] onto exactly [0, n − 1], so the clause is exact, and at n = 2^53 it is §4.3's
  existing "at most 2^53 − 1". For mode 3 the check is on base + the u(width) value; for mode 2 on value + 1.

### M5. `REPORT` has four fields in §4.6 and seven in `v5-integrity.md`

- **Severity:** major (two layouts for one control message; a decoder following one misreads the other's frame).
- **Location:** §4.6 type 5: "`probes`, `identitySucceeded`, `refusedFrames`, `injectedFrames`, EG0 each"; the
  pending rule "non-zero `identitySucceeded`, `refusedFrames` or `injectedFrames`".
- **Case.** `v5-integrity.md` §4 adds `selfCheckFailures`, `selfCheckItem`, `selfCheckKind` (EG0 each, after
  `injectedFrames`) and makes `selfCheckFailures` pending; its change record asks §4.6 for exactly that row. The wire
  change record's entry 22 covers only `injectedFrames`. A server per §4.6 reading an integrity-conformant
  `REPORT`(0,1,0,0,0,0,0) stops after four codes and is left with three `1` bits: as the frame's last chunk they
  are non-zero padding (rule 4); before a game run chunk they are read as its id and count. Either way the frame,
  with its game messages, is refused or misdecoded.
- **Also affected:** §4.6's sizes and §5.1 (8–12 B alone, 11 B with `BEACON`) and integrity's "≤ 720 B/s". With
  seven fields and every count zero but one the minimum stays 8 B; the maximum depends on `selfCheckItem`'s range
  (the item index into a build-sized list), which neither file bounds.
- **Fix.** Apply integrity's row to §4.6 and its pending rule; recompute the sizes with `selfCheckItem` ≤ the
  item list's length (state that bound in integrity §5) and `selfCheckKind` 0–4.

### M6. An aliased `rcv` makes the rewind report `receivedExact` true for a wrong horizon

- **Severity:** major (a result Lync labels exact is not; the brief's "only what it can do exactly").
- **Location:** §4.1 Receipt: "The server extends it to the value in (S − 256, S] … A client 256 or more frames
  behind … extends upward, which reads a frame as received early: a fact that uses it (`earlyReaction`) can only be
  missed by that, never made"; §4.6 "the server reads which D was in force … from that frame's receipt `rcv`".
- **Case.** The claim is checked only for `earlyReaction`. `v5-collections.md` §12.3 takes the reliable horizon H as
  "f's extended `rcv` when f is a reliable frame (`receivedExact` true)" and D as "the D of the newest `RATE` among
  frames ≤ H". A client with 256 or more reliable frames outstanding (a 4.3 s downstream stall at 60 frames/s while
  its upstream flows; or a join whose catch-up splits into hundreds of 16 KB parts, each counted, §4.1) gets H read
  256 frames too new, so the rewind result is computed against state the client didn't hold, under a `RATE` it may
  not have applied, and is still marked exact.
- **Fix (exact).** Reliable upstream frames are ordered, so the previous extended receipt P is a lower bound. Extend
  to the value in [P, S] congruent to `rcv` mod 256; when S − P ≥ 256 the value is ambiguous: use the lowest
  candidate and mark it inexact (`receivedExact` false; `earlyReaction` decided by time). One integer per player.
  Then §4.1 can say "exact whenever fewer than 256 reliable frames were sent since the client's previous reliable
  frame was extended; otherwise reported inexact", and the same wording replaces integrity §7's sentence.

### M7. Sealed rows are a wire form §4 doesn't contain

- **Severity:** major (the wire section omits a row grammar and its decode rules, so §4.3 and §4.8 decide it wrongly).
- **Location:** `v5-checks.md` §9.3 "Each message of a sealed definition is one row (`v5.md` §4.3's runs): sealed row
  := kind:u2 ( seal … | reveal … | discard … )"; §4.3 "A run of `columnMinRows` or more messages … is written as
  columns … request and control runs always do [single rows]"; §4.7 hashes `sealed` but §4.1–§4.8 never mention it.
- **Case.** A flush that fires three sealed messages of one definition makes a run of three, which §4.3 writes as a
  column block, flattening a codec; a sealed row is not a codec and has no flattening rule. §4.8 has no rule for a
  `seal` id at or past `sealed.outstanding`, a reveal or discard of an unknown seal, `blocks` other than ⌈W/8⌉ under
  `hideLength`, `kind` 3, or a decrypted plaintext that breaks a rule at reveal time (the frame that carried it was
  accepted long before). §4.2's encode-once text doesn't list sealed chunks among the shared ones.
- **Fix.** In §4.1 under Run chunk: "a sealed definition's rows are `v5-checks.md` §9.3's sealed rows, always single
  rows (§4.3)". In §4.3: "request, control and sealed runs always do". In §4.8: rule 2 for `seal` ≥ `outstanding`
  and for `blocks` ≠ ⌈W/8⌉ when `hideLength`; rule 3 for `kind` 3 and for a reveal or discard of a seal not
  outstanding; and the reveal-time rule (the decrypted value is decoded by §4.8 at reveal; a refusal drops that
  message only and counts it, since the carrying frame is gone).

## 5. Minor

### m1. A budget-refused untagged frame advances e

- **Location:** §4.5 "A reliable frame refused at §6.1 step 2 advances e by 1 without a tag check. Every reliable
  frame an unmodified client sends took the next count"; "Untagged frames … don't advance the count on either end".
- **Case.** Untagged `HELLO` frames take no count, and a refused frame is never decoded, so the server can't apply
  the untagged test to it. With `inbound.reliable.frames` burst 1 (in range, §7.5), a client using two namespaces in
  consecutive flushes before its first `WELCOME` has its second `HELLO` frame refused: e becomes 1, the first tagged
  frame (count 0) fails as `tagMismatch` with no listed cause, and the lost `HELLO` is never answered.
- **Fix.** The header is in clear: "a budget-refused reliable frame advances e by 1 when its extended `rcv` counts
  the frame that carried the connection's first `WELCOME`; otherwise it was untagged and e is unchanged". The same
  test can precede the untagged decode in §4.5's untagged bullet. List "a `HELLO` frame refused at the budgets is
  not resent" where §5.3 describes the hold.

### m2. "The extended seq and its two neighbours" is undefined, and two files read it differently

- **Location:** §4.5 Verification and Replay window; §7.3 `tagMismatch` cause "6,144 or more consecutive
  unreliable frames lost"; `v5-integrity.md` §10 `tagVariant` evidence "`skipped` (… unreliable: −1, 0 or 1, the
  neighbour of the extended seq)".
- **Case.** Neighbours ±1 would hash a seq whose low 12 bits differ from the header's, which can't match an
  unmodified client; 6,144 = 2,048 + 4,096 implies neighbours ±4,096. An implementer can build either.
- **Fix.** "the extension x of the received seq and x − 4,096, x + 4,096" in §4.5 (both places) and §7.3, and
  `skipped` −1, 0, 1 defined as those three in integrity §10.

### m3. `v5-integrity.md` still uses draft 3.5's budget defaults in two figures

- **Location:** integrity §10 `tagVariant`: "one per 37.7 days at N = 2, 14.3 h at 64, 3.5 h at 256, each beside
  about 4.5 × 10^6"; integrity §7: "the receipt, 1 B per upstream reliable frame, ≤ 120 B/s at the default".
- **Case.** At 3.6's defaults (60, 120 frames/s) the rate is 660 candidates/s: 75.3 days at N = 2, 28.7 h at 64,
  7.06 h at 256 (§4.5 says 7.1 h), and the receipt is ≤ 60 B/s. The integrity figures are exactly those for 120 and
  240 frames/s (1,320/s).
- **Fix.** Replace with 75.3 days, 28.7 h, 7.1 h, "about 4.6 × 10^6" and "≤ 60 B/s".

### m4. No rule covers a frame too short for its tag, or a read past the end

- **Location:** §4.8 rules 4 and 8; §6.1 step 3; §4.8 "any raise inside it refuses the frame as `decoderRaised`
  and reports natively (a Lync bug)".
- **Case.** A client sends a 2-byte buffer after its first tagged frame. Step 3 reads `u32le` at offset −2: either
  the raise escapes the handler (a server error line per frame) or lands in the decoder's `pcall` as
  `decoderRaised`, a "Lync bug" any client can produce at will. Likewise a header or toc whose bits run past the
  buffer, and toc counts (`n`, `count − 1`), which no rule charges: a decoder that allocates by them before reading
  can be made to allocate 2^53 slots from 8 bytes.
- **Fix.** Rule 4: "a tagged frame shorter than 4 B, or a read of bits or tail past the bytes the frame has"; and
  "toc counts are not allocated by; each segment and chunk costs at least one bit, so they are bounded by the frame".

### m5. Field rules leave in-range codes undefined; "the four fields are 0 (off)" is wrong for two

- **Location:** §4.6 `WELCOME` row "the four `callerProbe` and `clock` fields are 0 (off) until milestone 5"; field
  rules "Rule 3 refuses a `WELCOME` namespace index of 0, a `stateRate` outside 10–60, a `tag.cover` over 16,384 …";
  "A `HELLO` name outside 1–64 bytes is rule 2"; §4.1 "`caller` … is 0 in untagged frames".
- **Case.** `noOuterFrame` 0 means `"unlisted"`, not off; `maxPerSecond` has no off value (range 1–63), so 0 is
  out of its range. No rule refuses `clock.beacon` 1–4 (range 0 or 5–15), `maxPerSecond` 0 at milestone 5, or
  `caller` 1 in an untagged frame, so each is accepted though no unmodified peer writes it. A name length of 0 is
  not "past its maximum" (rule 2), it is below the range (rule 3).
- **Fix.** "`oneIn` and `clock.beacon` 0 (off) and `maxPerSecond`, `noOuterFrame` ignored until milestone 5"; add
  `clock.beacon` 1–4, `maxPerSecond` 0 (when `oneIn` > 0), and `caller` 1 in an untagged frame to rule 3; name
  length 0 to rule 3, over 64 to rule 2.

### m6. `REPORT` and `BEACON` sizes are not bounded as stated

- **Location:** §4.6 "`REPORT`, 8–12 B each when alone (counts of 0–60, tag included), … `BEACON`, 9 B alone, 11 B
  with a `REPORT`".
- **Case.** Counts are "since the previous `REPORT`" and `probes` alone makes nothing pending, so `probes` grows
  between reports without bound: 60 probes/s for 10 hours is 2.16 × 10^6, an EG0 of 43 bits, so the `REPORT`
  that a later refused frame forces is 13 B alone. `BEACON` with `REPORT`(60, 60, 60, 60) is 15 B, not 11
  (`review.out`, SIZES).
- **Fix.** State the size as what it is: "alone, 19 bits of header, toc and chunk header plus 2⌊log2(c + 1)⌋ + 1
  bits per count c, rounded up to bytes, plus the 4 B tag: 8–12 B for counts up to 60; 11–15 B with a `BEACON`";
  and note that `probes` may exceed 60.

### m7. The protocol-version rule contradicts this draft and the golden set can't enforce it

- **Location:** §4.9 "any planner change that alters a frame for some (schema, `buildId`, `rotationSeed`) …
  bumps the protocol version, and the golden set enforces it, since a changed vector with an unchanged version
  fails CI"; §4.6 "Protocol version: 1 … the version counts released protocols"; §4.10 "Layouts at a nonzero seed
  are checked by the differential test … not by fixed vectors".
- **Case.** Draft 3.6 changes G4, G5, G6, G7, G8, G10 at version 1, which the CI rule as written fails. And a
  planner change that alters only nonzero-seed layouts (the field-order draw, an offset draw) changes no seed-0
  vector, while the differential test compares two paths of the same planner, so nothing fails.
- **Fix.** "After the first release, …"; and either fixed vectors at one nonzero `rotationSeed` and one `layout` 1
  seed (one frame each, field order and offsets on) or restrict the claim to "for seed 0".

### m8. Old-key reliable frames in flight after a `REKEY` are an unlisted cause

- **Location:** §4.5 "Unreliable frames the client tagged under the old key before it decoded `REKEY` are dropped
  as `tagMismatch`: at most the frames of one round trip"; §7.3 `tagMismatch` and `desync` causes.
- **Case.** The same holds on the reliable lane: frames sent between the server's `REKEY` and the client's decode
  (12 at 200 ms round trip and 60 frames/s) all fail, and 8 of them raise a second `desync` with `rekeySent` 0, on an
  unmodified client. Whether they do also depends on a rule the text lacks: whether the failure run restarts after
  a `desync`; if not, the 9th, 10th … consecutive failures each satisfy "8 consecutive failures" again.
- **Fix.** Add "reliable and unreliable frames tagged under the old key in the round trip after a `REKEY`" to the
  `tagMismatch` causes and "with `rekeySent` 0, the frames of that round trip" to `desync`; and "the run of failures
  restarts at 0 after each `desync`" to §4.5's definition.

### m9. The reliable `u16` tick has no extension rule

- **Location:** §4.1 header (down, reliable) "`'11' u16`"; Ticks bullet (the extension is given for `tick:u8` only).
- **Case.** The u16 is, by implication, T mod 2^16, which wraps every 18.2 min at 60 Hz. A client whose first
  reliable frame arrives 30 min into a server's life, or a shared frame using `'11'`, needs a rule to recover T.
- **Fix.** "`u16` is T mod 2^16, extended like `tick:u8` to the value nearest the client's estimate".

### m10. The 64-bit option's byte figure uses a different baseline

- **Location:** §4.5 tag width options: "a 64-bit output (… 8 B, 794 B/s up for the busy model …)"; §4.1 "so at
  most 594 B/s up".
- **Case.** 794 = 374 + 6 B × 70 frames, without `rcv` and `caller`; on §4.1's baseline it is 594 + 4 × 70 = 874.
- **Fix.** "874 B/s up for the busy model (§4.1's 594 + 280)".

### m11. The golden conditions need fixtures the design doesn't provide, and §4.10's milestone list is off

- **Location:** §4.10 "identity permutation … tag key `00 01 … 07` (the key nonce, since S = 0)"; "milestone 1 (G1,
  G6, G8, G9, DERIVE)"; Provenance.
- **Case.** At S = 0 the permutation seed is the per-server nonce, drawn from entropy, so a running identity-build
  server has the identity permutation only when it draws 0 (2^−32), and its key is a random nonce, not `00 … 07`.
  §9's fixtures set only `layout.vary = false`, so no test can reach G2–G5, G7, G8, G10 in a running world. G8 carries
  a 4 B tag (milestone 2) though listed for milestone 1. G2b appears in neither the "reproduced" nor the "changed"
  list.
- **Fix.** §9 fixtures: "golden-frame worlds fix the key nonce to `00 … 07` and the permutation nonce to 0"; §4.10:
  move G8 to milestone 2 or say milestone 1 reproduces its bit section; add G2b's provenance.

## 6. Taste

- **t1. PERM's label is stale.** "G6's draft 3.5 hash low `0x158b86ab`" names a hash no vector holds any more; the
  vector is a pure function test. Say "seed `0x12345678`, hash low `0x158b86ab` (an input, not G6's)".
- **t2. The derivation cost is one end of a range.** §4.5 "about 1.6 µs interpreted and 0.31 µs native … × 1.1–1.4
  for 2-4". For the 9-byte key input 2-4/64 runs 14 SipRounds against 1-3/32's 6; one straight-line implementation
  measures 1.95× interpreted and 1.74× native (`derive_rounds.luau`), at or just above the text's implied 1.4–1.9×
  and 1.2–1.6×. Give the range with the round counts: about 1.3–1.7 µs interpreted and 0.24–0.34 µs native.
- **t3. Two n's.** Rule 2's "offset code w ≥ n" uses §4.3's interval size, while §3.3's `t.number` n is one less
  (codes 0…n). Write "w outside the code interval (§4.3)".
- **t4. "Holding only a header."** §4.1's ack-only frame also holds the toc's `'1'` (G5's last byte); say "holding
  no chunks".

## 7. What is good

- Every golden vector reproduces from the prose alone: the text is precise enough to build from, bit for bit.
- Not hashing budget-refused frames, and dropping the old key at `REKEY`, close draft 3.5's 328 ms/s and doubled
  hashing cleanly; the 5 / 3 hash bound now holds on every path tried, and the CPU bound is a formula over the
  budgets with every figure re-deriving.
- The caller bit in clear and repeated in the lane byte is the right shape: one hash per candidate, covered at
  `tag.cover` 0, keyless bound unchanged.
- The M3 decision is argued from the forger's control of the block form, with the cost per pattern measured.
- The tag-width decision states its interval for the whole configured range and why 64 bits buys nothing a
  keyless tool needs.
